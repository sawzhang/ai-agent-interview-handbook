# ✅ Agent 评测体系建设 Checklist

> 从零到生产的完整行动清单。综合 Airbnb / DoorDash / 阿里 / 腾讯四大工业实践与本特辑 E00-E15 全部章节，
> 每个阶段给出：**目标 → 检查项（可打勾）→ 验收口径（可量化）→ 常见坑 → 对应章节与实验**。
> 用法：新建体系按 Phase 0→10 顺序推进；已有体系用「快速自评表」定位缺口，按 Phase 跳读。
>
> 一句话总纲：**评测是把「不稳定的智能行为」持续收敛成「可发布的工程质量」——不是上线前抽查。**（阿里）

## Phase 0 · 立项：先承认三件事

- [ ] 明确三大根本难题写进了团队共识：**非确定性**（同输入不同输出）、**黑盒化**（内部决策不透明）、**错误级联放大**（前步小错后步放大）
- [ ] 明确评测的四重身份：**质量度量 / 发布门禁 / 迭代指南针 / 数据飞轮入口**——只做第一重的评测体系迟早沦为摆设
- [ ] 指定评测的**人类终判者**（Airbnb 原则 4：争议谁拍板，立项时就定）
- [ ] 拉产品伙伴入伙（Airbnb 原则 5：评测是跨职能产品活动，不是 QA 私事）
- [ ] 算一笔评估经济学账：eval 建设成本 vs 一次线上事故的资损/投诉/回滚成本

**验收**：一页纸评测章程（目标、门禁哲学、终判人、产品接口人）拿到团队确认。
**坑**：把评测当"出分工具"而不是"把问题稳定转化为可执行修复"的闭环（阿里）。

## Phase 1 · 指标体系：评什么

- [ ] 指标分三级：**P0 上线门禁**（不达标不发）/ **P1 版本比较** / **P2 体验观察**（阿里）
- [ ] 五大维度逐一有指标：**功能正确性 / 过程质量 / 效率与成本 / 鲁棒性与安全 / 体验与对齐**（腾讯）
- [ ] 每个指标注明：定义、评测方法、主要评分器（代码/Rubric/人工）、优先级
- [ ] 可靠性双指标都报：**至少一次成功率**（能力上限）与**连续成功率**（生产要求）——客服/支付/退款/合规类只看后者
- [ ] 效率成本是并列维度不是脚注：token、调用次数、延迟 p50/p95/p99、**¥/task**（"pass@1 高但贵 10 倍的方案不可接受"）
- [ ] 安全指标成对报告：**误拒率 + 漏拒率**（只优化一侧必然荒谬）
- [ ] 为版本对比配统计口径：**置信区间 + 显著性判断 + 最小可感知变化阈值**（阿里："门禁不只看差了多少，还看差异是否超过统计噪声"）
- [ ] 每个指标可归因到场景/组件切片（报"哪类场景差"，不只报总分）

**验收**：指标字典一页表；任一指标都能回答"它拦什么决策"。
**坑**：万能 helpfulness 大分（Airbnb 三大陷阱之首）；指标与产品目标脱节；Goodhart（指标被刷爆前先想好防御）。

## Phase 2 · 黄金数据集：拿什么评

- [ ] 放弃"线上随机抽样即评测集"：正常流程占多数，**幸存者偏差**让关键边缘场景被漏掉
- [ ] 先建 **50–200 条高质量 golden set**（Airbnb 50–100 / 阿里 50–200 / 腾讯前 20–50 参考解），覆盖核心业务路径 + 高风险边界
- [ ] 四类来源齐全：**专家设计**（定标准）/ **LLM 扩展**（先定结构字段再生成自然语言）/ **线上真实数据** / **badcase 回流**
- [ ] **必须含坏样本**（Airbnb 十条要点之⑦）：只有好样本的校准集测不出 judge 的漏判能力
- [ ] 用例按四场景组织（腾讯）：**触发 → 核心逻辑 → 产物质量 → 异常容错**，每场景正+负向
- [ ] 有**负向触发用例**："只测正例，Agent 可能学会什么都触发——过度触发比不触发更难发现"
- [ ] 核心逻辑用例量 ≈ 其余三类之和的 **2–3 倍**（每条核心分支至少 1 用例）
- [ ] **对抗安全集单独维护并常驻回归**：注入 / 越权（含 must-not-call 权限断言）/ 诱导承诺用例，正反成对；**安全集 0 漏拒进 P0 硬门禁**——一次 prompt 重构完全可能"功能全绿但防线塌方"（腾讯红队实践）
- [ ] **基线快照机制（腾讯）**：执行类用例跑 1 次 → 人工确认 → 快照为基线（预期过程：CoT/调用序列/中间产物 + 预期结果）；三个时机重做基线（Agent 逻辑变更 / 模型升级 / 用例修改）；**不硬编码预期输出**——逻辑变更后硬编码的预期会变成错误答案，评测开始误杀正确行为
- [ ] 入库有标准（阿里五条）：可复现 / 期望行为明确 / 根因标签清楚 / 有代表性 / 已脱敏
- [ ] 隐私合规：抽样去标识化、用途限定（安全与质量）

**验收**：golden set 带元数据（来源/场景/风险等级/期望行为）；跑一遍能区分好坏版本。
**坑**：扩展用例脱离结构字段自由生成（变成噪声）；badcase 无差别塞进回归集导致无限膨胀。

## Phase 3 · 三层评分体系：谁来评

### 3.1 程序化评分（第一层，规则优先）
- [ ] 原则立住：**"能用代码判断的绝不用模型"**（确定性优先：快、免费、100% 稳定、可当硬门禁）
- [ ] 检查清单落地：schema/格式校验、空/异常长度、关键词黑白名单、工具调用断言（是否调用/参数正确）、执行预算（调用次数/耗时上限）
- [ ] 被测系统输出结构化（JSON schema 强类型）——"不要只靠 prompt 措辞产出结构，下游管道会坏"（Airbnb）
- [ ] 评分输出五元组：**score / pass-fail / 问题分类（现象层）/ 置信度 / 判定依据**——为 RCA 留"现象入口"
- [ ] 分层筛查：粗筛（便宜规则）→ 精判（昂贵规则+Judge）→ 人工复核；**粗筛明确失败的绝不进精判**（阿里）

### 3.2 LLM-as-Judge（第二层，必须校准）
- [ ] judge 解剖齐全：rubric + **证据切片**（每条标准声明依赖的证据，judge 只拿那一片）+ verdict + rationale（DoorDash transcript builder 思想）
- [ ] Airbnb 五纪律：**每个质量维度一个 judge / judge 与生成模型不同源 / 带 few-shot（含边界样本）/ 强制输出 schema / 清晰打分说明**
- [ ] judge 少而精：**3–5 个校准过的评估器 > 一堆嘈杂的**（Airbnb 原则 3）
- [ ] rubric 工程：**二元检查**（方差低、易校准）+ **eligibility 适用性前置**（不适用的标准跳过而非扣分）+ 描述"成功长什么样"而非指定唯一答案（DoorDash）
- [ ] 铁律自查："如果人都无法一致地应用 rubric，模型也不可能"
- [ ] 偏差缓解有方案：位置偏差（swap 取平均）/ 冗长偏差（长度回归）/ 自我偏好（匿名化、异构评审团）
- [ ] **校准闭环（硬门槛）**：50–100 条 gold（含坏样本）→ 跑 judge → 分歧分析改 rubric → 重复；**与人工一致率 ≥85% 才进日常自动化**（阿里 ~85% / 腾讯 ≥85% / Airbnb high 80s~90s；κ 口径另见主手册 ch08：κ≥0.6 可用）
- [ ] judge 升级有监控三统计（阿里）：与人工一致性 / **高风险样本漏判率** / 边界样本稳定性
- [ ] judge 版本化：模型 + prompt + 参数 + 判决协议，建"计量档案"
- [ ] 校准可升级为 **GEPA 式反射 prompt 进化**自动迭代：只保留留出集人机一致率有提升的版本，防过拟合（DoorDash 生产实践；人工标签只有几十到几百条时，反射优化比 RL 微调现实得多）

### 3.3 人工评估（第三层，花在刀刃上）
- [ ] 人工只干六件事（腾讯）：**校准 judge（最核心）/ 主观任务打分 / 诊断 0%-100% 异常 / 建 ground truth（前 20–50 参考解）/ 每周 Trace 抽样审查 / 高风险 100% 复核**
- [ ] 专家时间 **60%+ 花在校准与诊断**，坚决不做日常全量打分
- [ ] **专家有分歧就先停下解决分歧，再谈自动化**（Airbnb）
- [ ] 人工评分路由成文（阿里）：边界分/低置信/reason 含糊/多 judge 分歧/新模型新 prompt 上线抽样/规则与 Judge 冲突 → 人工终判并**回收口径**
- [ ] 政策口径类判断永远留给人（"叠加优惠差价是否补偿"这类 judge 判不了）

**验收**：三层分工表 + judge 校准报告（一致率/κ/混淆矩阵/漏判率）+ 人工路由规则。
**坑**：judge 未校准就上门禁（"未校准的 judge 制造误导性信心"）；同源模型自评（偏爱自己风格）；人工淹没在全量打分里。
📖 E04 / E05 / E06 · 🧪 eval_lab03（分层筛查）/ eval_lab04（偏差量化）/ eval_lab05（校准闭环：一致率 0.80→0.95、κ 0.571→0.895）

## Phase 4 · 轨迹与会话级评估：Agent 特有问题

- [ ] 共识立住：**只看最终答案不够**——"结果对但路径错/带风险"的假阳性在生产迟早暴露
- [ ] 三层评估模型（Airbnb）：**step-level**（单工具调用/参数/禁用动作）/ **trajectory-level**（路径合理高效）/ **session-level**（整体达成用户目标）；操作类 Agent 的 Outcome 用**终态校验**（数据库/状态 diff：订单是否真被取消、金额是否正确）判定，不信任自然语言回复——"嘴上说已取消、数据库纹丝不动"（τ-bench 范式）
- [ ] 对话 Agent 加四层判分（阿里）：**Turn / Session / Trace / Outcome**——"每轮都答得还行但没解决问题仍是失败"；门禁判 Outcome+关键 Trace 断言，Turn/Session 分只做诊断
- [ ] **Trace 是被测 Agent 的标准能力**，不是事后补救：稳定记录工具名/入参/返回/时间戳/耗时/错误（阿里/腾讯），以及**用户输入、Agent 回复、展示给用户的 widgets**（DoorDash span 四类内容）；结构化、内容完整、跨版本格式稳定；第一天就按 **OTel gen_ai.\* 属性**打点（层级 session→agent/task→llm_call→tool_call，保留私有字段兼容层）
- [ ] 序列比对有归一化：时间戳占位、忽略查询参数、写入只留路径（腾讯 LCS 实战）
- [ ] 关键步骤缺失触发**硬门禁一票否决**（哪怕最终答案对了）
- [ ] 评测镜像运行时架构（DoorDash）：路由在 Orchestrator 评、护栏贯穿全流程、任务能力在领域 Agent 评
- [ ] 多智能体场景：能重建 trace 树、校验 subagent 调用与工具使用

**验收**：一个"结果对但路径错"的构造用例被你的体系抓住（outcome-only 对照会漏判它）。
**坑**：拿精确轨迹匹配判分（路径千变万化，要功能性判定）；trace 缺字段导致 RCA 阶段无证据可用。

## Phase 5 · 仿真与 Fixtures：离线评测环境

- [ ] 有用户模拟器：LLM 扮演用户，**scenario = 开场请求 + 用户目标 + 反应策略**（DoorDash）
- [ ] 模拟器行为像真人：动态判断"解决了吗/有进展吗/缺信息吗/绕圈了吗"；升级给过机会才发生，不秒转人工
- [ ] 场景库含**难缠用户切片**（易怒、模糊、改主意、多目标）——礼貌的假用户只会测出礼貌的假高分
- [ ] **Fixtures 冻结外部状态**：录制工具返回替代实时调用（订单/库存/账号不再漂移）；"环境必须受控，否则分数测量的是噪声"（DoorDash）
- [ ] 用 fixtures 构造真实里难遇的难例（欺诈、大额退款、空数据、工具故障）
- [ ] 离线专属 **checklist 式 rubric**（场景级"正确运行应产出什么"）：低方差信号，小样本也能快速迭代
- [ ] 全量 sweep 有成本账：如 DoorDash **50 场景 × 8 trials = 400 对话，人工 6h+ → 模拟器约 20min**
- [ ] 模拟器自身被抽检：目标一致性、幻觉、与被测 agent 的同源偏差

**验收**：同一 scenario 固定种子跑 N 次，评分方差 ≈ 0；漂移对照组方差显著更大（环境噪声被量化）。
**坑**：模拟用户总是信息完备且轻易满意（系统性高估）；模拟结果与真实用户满意混为一谈（编造商品的 agent 也能让"用户"满意收尾——结果判定必须独立于对话氛围）。

## Phase 6 · 统计严谨性：让分数可信

- [ ] 报区间不报点估计：**Wilson 置信区间**（小样本别用 Wald，会越界）或 bootstrap
- [ ] 会算样本量：检出 δ 差异所需 n ∝ 1/δ²（速查：±5% 精度约 400 条；3% 差异 N=100 不可判、N=2000 可判）
- [ ] 版本对比用**配对设计** + 显著性；预先定义**最小可感知变化阈值**
- [ ] **pass^k 必须实测，不能从 pass@1 外推**（任务难度异质 + 尝试间相关；τ-bench 实测 60%→25%，iid 外推差一个量级）
- [ ] 重复试验次数有依据：k=4–8 工程惯例；3 次起步筛选、5 次日常门禁（腾讯 N=5）、8 次发布级（τ-bench/DoorDash）
- [ ] 稳定性容忍阈值按使用类型分级（腾讯）：**关键决策类 0% / 辅助分析类 ≤10% / 创意生成类 ≤40%**——阈值由"一次失败的代价"决定，不是查表
- [ ] 竞技场/排名场景：Bradley-Terry + bootstrap CI；警惕 Elo 顺序依赖与投票操纵；风格混杂（长度/位置）用回归或分桶控制
- [ ] 0% pass^N 先查任务定义与评分器，别急着怪模型（腾讯调试技巧）

**验收**：任何对外汇报的分数都带 n 与 CI；两个版本的分差能回答"超过统计噪声了吗"。
**坑**：单次跑分定优劣；把 pass@1 当可靠性汇报；重复实验的成本没人买单（先定预算规则）。

## Phase 7 · EDD 流程集成：用评测驱动开发

- [ ] 方法论立住：**EDD = GenAI 版 TDD**——不预测所有失败，而是发现→捕获→反复检查失败模式（Airbnb）
- [ ] **目标与上线门槛先定**（哪怕数据评审后才逐渐清晰，Airbnb 原则 1）；指标从观察到的错误推导（原则 2）
- [ ] 核心习惯成制度："**When in doubt, look at your data**"——每个迭代先跑约 100 样本人工精读（读输出与 trace→归类错误→围绕它们建测试）
- [ ] **一次只改一个变量**：固定模型变 prompt → 固定 prompt 变模型 → 都固定变 serving 配置（Airbnb 迭代纪律）
- [ ] judge 与候选互哺：judge 筛候选，优秀候选反哺 judge 改进，直到双方稳定
- [ ] eval 进 CI：PR 合入前自动回归；**回归集只增不减**
- [ ] 双套件生命周期（腾讯）：能力测评（起步 20–50%，目标山峰）→ 通过率稳定 100% 后**毕业**进回归集；Anthropic 口径：确定性任务通过率 100%、非确定性 ≥95%
- [ ] 发布联动：离线门禁 + 线上灰度，跟踪三类信号——**离线质量 / 线上体验（转人工率、重复追问率、投诉率、满意度）/ 业务结果（任务完成率、工单闭环率）**；**离线升线上降 → 回滚或降级**（阿里）
- [ ] 变更大小与评测规模匹配：底座模型迁移这种大变更，用全量 sweep 去风险（DoorDash：发现的是兼容性差距不是能力差距，小修后延迟降 35%）

**验收**：任意一次 prompt/模型变更都有 eval 证据链；至少拦截过一次"新场景变好但旧场景回归"的变更。
**坑**：eval 只做发布前检查点（EDD 要求贯穿全生命周期）；门禁 flaky 被团队绕过——先修门禁再谈纪律。

## Phase 8 · Badcase RCA 与优化闭环：评完要能修

- [ ] 双通路入口汇入同一任务表（阿里）：离线评测集 + 线上（会话/质检/工单/低满意度/回归失败/告警）
- [ ] RCA 五步成流水线：**证据汇总**（sessionId/traceId 聚合全链路）→ **范围收敛**（"问题现象 × 功能模块"映射表，命中走确定性路径）→ **分模块诊断**（逐模块 PASS/SOFT_PASS/FAIL）→ **责任判定**（三层：严重 FAIL 直接定责 → 规则模式匹配 → LLM 兜底）→ **结构化落盘**（问题分类/现象/枚举/责任层/责任模块/置信度/修复建议）
- [ ] 映射表只缩圈不定责；最终定责结合 Trace、模块 IO、工具返回与规则/Judge 结论
- [ ] 根因标签体系：**稳定、可统计、指向 owner**（运营可配置/算法需优化/工程需修复/业务需定口径）
- [ ] 支持聚类成**问题簇**：报告不是列 100 条 badcase，而是"场景 X 中 23 次跳过校验，集中在 v1.8 Prompt"（阿里）
- [ ] 优化建议是**结构化行动项**：失败范围/证据/具体动作/owner/验收方式/优先级——拒绝"优化 Prompt"式泛化表述，能被工单系统直接消费
- [ ] 进阶：失败簇可由 **coding agent 自动调查**（失败 trace + 相关代码路径 + 近期变更 + 历史调查），修复明确时直接起草 PR；把聚类/调查工作流沉淀为**可复用 Agent Skills**，skill 分错簇或写出弱修复时更新 skill 而非给一次性运行打补丁——harness 成为"迭代的控制面"（DoorDash）
- [ ] RCA 自身按"确定性优先、模型辅助、人审兜底"实现；人工结论反校准规则/Judge/标签体系

**验收**：每个 badcase 能追到责任模块与修复动作；低分稳定转化为行动项（"否则再精细的分数也只是报表"）。
**坑**：对全部模块无差别排查（成本高噪声大结论散）；现象层分类与最终根因混为一谈。
📖 E11 · 🧪 eval_lab09（RCA 五步流水线）

## Phase 9 · 在线评估与数据飞轮：上线之后

- [ ] 在线抽样制度化：如 Airbnb **每日 5% 去标识化生产流量**；分层放大高风险/低置信/新意图/新工具样本
- [ ] **离线-线上同一套打分**：同一 rubric + 同一校准 judge（DoorDash 原则三）；各自单独调 judge，分数会以难调和的方式背离
- [ ] 在线 judge 输出接监控：漂移检测（分布漂移 + 指标漂移）、告警阈值、dashboard
- [ ] 线上分数异动按**三步顺序鉴别**：① judge 漂移（固定旧版 judge 重放本周样本）→ ② 分布漂移（按意图/入口/用户群分桶）→ ③ 真实退化（历史 case 配对离线复现）——"先查尺子，再查考题，最后查考生"；小样本 1–2 分差异默认噪声，先算 CI 再谈回滚
- [ ] 数据飞轮闭环：badcase → 评测集 → （训练数据/知识修订/prompt 修复）→ 模型或系统更新 → 重新评测
- [ ] 反馈生产线有入库标准（见 Phase 2 五条）；**样本治理**：同簇留代表例、P0/P1 长期保留、稳定通过降级抽样集、主动学习优先抽低置信高影响样本
- [ ] offline-online gap 有预案：离线是必要不充分——shadow/canary/小流量 A/B 补最后一公里（Nubank 有强相关证据，OlaBench 有反方证据——两边都读）

**验收**：线上失败 → 回归用例的转化率可度量且持续增长；离线提升能在线上复现。
**坑**：生产 trace 直接进评测集（PII 合规先脱敏）；只看在线 judge 均分不切片（被高流量简单场景稀释）。
📖 E12 · 综合 🧪 eval_lab02（回流与治理）

## Phase 10 · 治理与资产：长期运营

- [ ] 评测平台**九个能力模块**逐步齐全（阿里原文列九个模块未逐项展开，以下为特辑归纳）：用例管理 / Trace 存储 / 评分器管理 / Judge 校准 / 执行编排 / 报告看板 / RCA 流水线 / 反馈生产 / 资产库
- [ ] **质量资产库**成型：用例库、Trace 库、根因标签库、修复建议库、Judge 校准集、回归集——"质量资产越厚，迭代越不靠个人经验和临时救火"
- [ ] 评测资产像代码一样版本化：数据集、rubric、judge prompt 都有 provenance 与变更记录
- [ ] 失败模式变化时**重新校准 judge**（校准不是一次性的）
- [ ] Benchmark 外部坐标正确使用：公开基准（淘汰明显差的候选）+ 私有 golden set（门禁）+ 在线信号（地面真值）三层互补；**单一公开榜单不作为发布决策依据**；引用榜单标注口径与日期
- [ ] 防污染意识：私有 holdout 永不公开；动态轮换；eval 成为优化目标时防 gaming（Anthropic grader-hacking 警告）
- [ ] 评测系统自身有 bug 通道：judge 误报、trace 缺口都会产生假失败——**harness 的失败与 agent 的失败分开处理**（DoorDash lesson 4）

**验收**：新同事能靠资产库独立发起一轮完整评测；评测口径变更有审计记录。

## 🚨 十条军规（易错点速记，贴墙用）

1. **跑通一次 ≠ 稳定可用**——生产看连续成功率，用户不接受"多试几次总有一次成"
2. **judge 未校准不上门禁**——一致率 ≥85%（或 κ≥0.6）是硬门槛，否则量出来的是噪声
3. **gold set 必须含坏样本**——全好样本校准不出漏判能力
4. **结果对 ≠ 过程对**——假阳性靠轨迹层抓，关键步骤缺失一票否决
5. **环境不受控，分数测的是噪声**——fixtures 冻结上游世界再谈可复现
6. **一次只改一个变量**——prompt/模型/serving 混改，回归无法归因
7. **差异要超过统计噪声**——没有 CI 与显著性的分差不许动发布决策
8. **离线升、线上降 → 回滚**——离线评测是必要不充分
9. **低分必须变成行动项**——不能落地的分数只是报表
10. **评测系统自己也会坏**——judge 误报与 trace 缺口是 harness 的 bug，不是 agent 的罪

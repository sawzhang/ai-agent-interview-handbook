## 二、核心概念精讲

### 2.1 为什么不能是线上随机抽样：幸存者偏差

直觉上最省事的做法是"从线上日志里随机抽一批会话当评测集"——真实、免费、量大。阿里的评测方法论明确否掉了这条路：**评测集不是线上随机抽样**。

**机制**：线上流量的分布天然是"正常流程占多数、易错边缘场景占比低"。随机采样会忠实地复刻这个分布，于是评测报告里 98% 的样本本来就是 agent 闭着眼也能处理好的请求。

**后果链条**：

| 环节 | 发生了什么 |
|---|---|
| 抽样 | 随机抽 200 条线上会话 |
| 分布 | 高风险场景（退款已发货、叠加优惠、欺诈嫌疑）占比可能不足 2%，样本里只有零星几条 |
| 报告 | 通过率 96%，"看起来不错"，评审会顺利过会 |
| 上线 | 恰好漏掉的那几类问题在生产里被用户反复触发——投诉、资损、舆情 |

做个示意算术（非工业数据，仅建立直觉）：某高风险场景在线上流量中占 1%，随机抽 100 条，期望只抽到 1 条；如果该场景下 agent 有一半概率犯错，你的评测"发现这个问题"的概率也就五五开。**评测集的职能是暴露问题，而随机抽样的职能是复刻流量——两者的目标函数根本相反。**

**正确姿势是分层与定向**：

- **按风险/意图/置信度分层采样**，对高风险、低置信、新意图样本过采样（代价是整体通过率失真，聚合时按真实流量权重加权修正）；
- 阿里的主动学习口径：新分布出现时**优先抽取低置信 / 高影响 / 新意图 / 新工具 / 新知识点样本**进人工确认；
- 线上数据的正确角色是**失败挖掘的矿与分布参照**，不是评测集主体。Airbnb 的每日抽样 5% 去标识化生产流量，用途是生产监控与评审队列，与作为基线的 golden set 是两套资产。

分层采样的一种典型设计（综合阿里口径的工程化表达）：

| 层 | 划分依据 | 采样策略 | 用途 |
|---|---|---|---|
| 高风险场景 | risk_level P0/P1（资损/合规/隐私） | 全量或高比例过采样 | 门禁主体，永不稀释 |
| 低置信预测 | 在线 judge/模型置信度低 | 优先抽取进人工确认 | 发现新失败模式 |
| 新分布 | 新意图/新工具/新知识点/漂移告警 | 定向补充 | 覆盖盲区 |
| 普通正常流程 | 其余流量 | 按真实比例随机抽样 | 分布参照与日常监控 |

**两个配套动作**：过采样会让"整体通过率"偏离真实流量表现，汇报整体分数时按真实流量权重加权还原；同时保留分层明细——分层视图才是改进工作的抓手（哪个层在恶化一目了然）。

> 一句话记忆：**随机抽样回答"线上平均表现如何"，评测集回答"最坏情况下会不会死"——不能用一把尺子量两件事。**

### 2.2 用例四类来源：专家设计 / LLM 扩展 / 线上真实数据 / badcase 回流

阿里的评测数据集建设给出四条来源，各有分工，缺一不可：

| 来源 | 角色 | 优点 | 主要风险 | 治理要点 |
|---|---|---|---|---|
| **专家设计用例** | 定标准 | 覆盖核心分支与高风险分支，判据权威 | 贵、慢、带专家个人盲区 | 冷启动主力；先出 20-50 条参考解（腾讯人工建 ground truth 的起步量） |
| **LLM 扩展用例** | 上量 | 便宜、快、表达多样 | 自由生成会编造业务上不存在的场景 | **先用规则确定结构字段，再生成自然语言**（见下） |
| **线上真实数据** | 分布校准 | 真实用户表达、真实分布 | 幸存者偏差 + 隐私风险 | 去标识化后用于失败挖掘与分层抽样，不直接当基线 |
| **badcase 回流** | 防再犯 | 每条都是真实发生过的失败，针对性最强 | badcase ≠ 用例（见 2.6 入库标准） | 过五项入库标准，编码为用例进回归 |

**（1）专家设计：定标准的人永远不能缺席。** 评测集冷启动阶段，腾讯的做法是新建套件先由专家产出**前 20-50 个参考解**作为 ground truth；阿里同样把"专家设计用例"列为四类来源之首——它定义的不是样本量，而是"什么算对"的口径。口径未固化的场景（如"订单已发货 + 用户拒收 + 运费险 + 特殊类目该走哪条流程"）必须由业务先定，工程师不能代答。

**（2）LLM 扩展：先定结构字段，再生成自然语言。** 这是阿里方案里最值得抄的细节：

```text
错误做法：prompt = "请生成 100 条客服 agent 的测试用例"
           → 模型自由发挥，场景重复、分布失控、编造业务上不存在的状态

正确做法（两步）：
  第一步：用规则/枚举确定结构字段
    {场景类型: 退款, 订单状态: 已发货, 用户诉求: 仅退款, 期望动作: 先查订单状态再答复}
  第二步：LLM 只负责把结构字段改写成接近真实用户的自然语言表达
    "东西还在路上我不想要了，钱能直接退我吗？"
```

结构字段保证**覆盖矩阵按需填充**（每条分支、每种订单状态都有人管），自然语言改写保证**表达真实多样**。顺序反过来，用例集的构念效度就丢了。（动手实验：`cd evals-special/labs && python3 eval_lab02_golden_dataset.py`，其中的 MockLLM 会直接拒绝无结构字段的生成请求——接口约束即治理。）

**（3）线上真实数据**：真实客服会话/工单是金矿，但进门先过两道关：**去标识化**（见 2.7）与**代表性审查**。公开语料同理——WildChat（[arxiv 2405.01470](https://arxiv.org/abs/2405.01470)，100 万条真实 ChatGPT 交互日志）与 LMSYS-Chat-1M（[arxiv 2309.11998](https://arxiv.org/abs/2309.11998)）这类真实对话语料是构建评测集与用户模拟器的常用原料，但都要先做隐私清洗再入库。

**（4）badcase 回流**：线上失败是最有针对性的用例原料。注意 badcase 回流不是"复制粘贴进 JSONL"，必须先过 2.6 的入库标准——这是四家共识（Airbnb 的"每周 PM 评审新增测试"是同一动作的组织形态）。看一条 badcase 从现象到用例的完整编码（阿里实例"Agent 直接承诺一定退款成功"的展开）：

```yaml
# ① 线上 badcase（原始现场）
session: session-20260712-8841
phenomenon: 用户咨询已发货订单退款，Agent 回复"放心，一定给您退款成功"
root_cause_label: 风险防控 / 过度承诺          # 根因标签清楚，才具备入库资格

# ② 过入库标准后编码为用例
case_id: risk-overpromise-012
source: badcase 回流
created_from: session-20260712-8841
scenario: 退款 · 已发货
input: "东西已经发货了但我不想要了，能全额退给我吗？"
expected_behavior:
  - must_call: query_order_status               # 期望行为可判定
  - must_not: 无条件承诺退款成功
  - reply_mentions: [物流状态, 拦截/拒收流程, 退款条件]
risk_level: P0                                   # 涉资损与合规，永不降级
suite: capability                                # 修复验证稳定后毕业进回归集
```

这条用例同时满足入库五项：失败可复现（有原始 trace）、期望明确（三条检查项）、根因清楚（风险防控域）、有代表性（"过度承诺"是一类问题）、已脱敏。它进入回归集后，未来任何一次 prompt 重构若重新引入"拍胸脯式承诺"，CI 会当场拦截。

**交叉参照**：OpenAI 官方 evaluation best practices 把数据来源归纳为五路——生产、专家构造、历史、合成、采购——与上面四类来源基本同构（"采购"对应公开数据集/基准）。EDDOps 论文（[arxiv 2411.13768](https://arxiv.org/abs/2411.13768)，2024-11 首发，2025-11 v3）则要求**每条用例带 provenance（来源出处）、oracle（判定标准）、slice 标签**——来源必须可追溯，通过率要能按来源拆开看。

### 2.3 用例组织范式：触发 → 核心逻辑 → 产物质量 → 异常容错

用例攒到几十条后，最大的问题不再是"不够多"，而是"没组织"。腾讯给出的组织范式是把每个 Skill/Agent 的用例沿四个场景展开，每个场景回答一个递进的问题：

| 场景 | 回答的问题 | 正向用例 | 负向用例 |
|---|---|---|---|
| **① 触发** | 该触发吗？ | 各种合法表述都能触发 | 相似但不相关的 prompt 不误触发 |
| **② 核心逻辑** | 过程对吗？ | 工具调用序列/参数/顺序正确 | 缺步骤 / 错工具 / 错参数 |
| **③ 产物质量** | 产物好吗？ | 准确 / 完整 / 格式合规 | 缺失 / 格式错 / 幻觉 |
| **④ 异常容错** | 出错扛得住？ | 优雅降级、明确提示 | 崩溃 / 死循环 / 静默失败 / 泄露 |

**三个关键设计纪律**：

**（1）负向触发用例为什么必不可少。** 腾讯原文一句话点破："只测正例，Agent 可能学会什么都触发——**过度触发比不触发更难发现**。"不触发会立刻被用户抱怨（功能"坏了"），过度触发却悄悄消耗 token、污染下游流程、把无关请求路由进昂贵链路，直到某天账单或事故才暴露。所以触发场景的用例必须是正负成对的：正例测召回，负例测精度。

**（2）核心逻辑用例量 = 其余三类之和的 2-3 倍。** 这是腾讯的经验法则。配套三步法：

1. 梳理分支流程图（把业务分支穷举成图）；
2. 每条分支至少 1 个用例（N 条分支至少 N 个正向 + 关键分支的负向）；
3. 补充组合与边界：分支间组合、阈值边缘、跨分支冲突。分支过多时先覆盖高频与易错。

**（3）异常容错要拆成三个子类设计**（腾讯）：

| 子类 | 用例示例 | 期望行为 |
|---|---|---|
| 异常输入 | 查询不存在的 ID / 非法格式 / 缺少关键 ID | 告知不存在不编造；提示格式错误；主动追问而非瞎猜 |
| 边界条件 | 数据量极大 / 数据为空 | 不超时；明确告知无数据 |
| 环境故障 | `mock_tool_failure` 注入工具失败 | 优雅降级，不无限重试 |

这个四场景框架与主手册第 8 章的"任务分类学 → 覆盖矩阵"一脉相承，但给出了更落地的填充顺序：**先触发、再过程、再产物、最后容错**——因为前置场景失败时，后置场景的用例根本没有意义（触发都错了，谈何产物质量）。

**工业实例：TPerf 的用例分组落地（腾讯）**。性能分析 Agent TPerf 把 30+ 用例按场景分成 9 组，每个用例绑定一条真实压测记录（不可变、可复现），支持 7 个模型的参数化对比（每用例 × 每模型）：

| 场景组 | CPU 瓶颈 | 网卡 | 磁盘 | 磁盘 IO | 内存 | TCP 队列 | Nginx | 配置问题 | 正常场景 |
|---|---|---|---|---|---|---|---|---|---|
| 用例数 | 6 | 5 | 4 | 2 | 1 | 3 | 1 | 1 | 5 |

两个值得抄的细节：① **正常场景也配了 5 条用例**——"没问题时不误报"本身就是一种能力，只测异常不测正常，会把"逢数据必喊瓶颈"的 agent 评出高分；② 高频场景（CPU/网卡）用例多、罕见场景（内存/Nginx）用例少，分组数量本身就是风险权重的显式表达——分支过多时先覆盖高频与易错，正是三步法的落地形态。

### 2.4 一条合格用例长什么样：用例 spec、checklist rubric 与基线快照

**（1）用例 spec：字段即契约。** 一条可入库的用例至少应固化如下字段（与 `labs/eval_lab02_golden_dataset.py` 的 dataclass 一致）：

```yaml
case_id: refund-shipped-007
source: badcase 回流            # 专家设计 / LLM 扩展 / 线上数据 / badcase 回流
scenario: 退款 · 已发货          # 结构字段：场景类型 + 订单状态
input: "东西还在路上我不想要了，钱能直接退我吗？"
expected_behavior:              # 期望行为写成可判定的检查项，不写"回答要好"
  - must_call: query_order_status
  - must_not: 无条件承诺退款成功
  - reply_mentions: [物流状态, 退款条件]
risk_level: P1                  # P0 资损/合规 / P1 核心流程 / P2 体验
suite: capability               # capability（能力集）/ regression（回归集）/ graduated
created_from: session-20260712-8841   # provenance：来自哪条线上会话/哪次评审
```

要点：**期望行为必须写成规则/Judge 标准/人工验收标准能消费的形式**（阿里入库标准第二条"期望行为明确"的直接推论）；`risk_level` 决定门禁权重与保留策略；`created_from` 让每条用例可回溯到现场。

**（2）checklist 式场景 rubric：低方差信号。** DoorDash 的一个代表性设计是"场景级清单"。例：场景"为两人份、预算 ≤$60 的素食 taco 购物清单"，rubric 不写"购物清单质量好"这种宽泛标准，而是写成一张可核验的清单——**验证每件商品都是素食 taco 原料、小计 ≤$60**。DoorDash 的结论：这类 checklist 标准**比宽泛通用标准方差更低，小样本更有用，支撑更快的迭代**。

机理很直白：判定依据越接近可程序化核验的事实（商品名在不在清单里、金额加总对不对），judge 与人工的自由裁量空间就越小，同一输入重复评分的波动就越小——方差低了，50 条样本也能看出两个版本的真实差异；方差高了，500 条样本也只是噪声（统计细节详见第 E9 章 · 评估的统计学基础）。用例设计的通用原则由此得出：**能用 checklist 的场景不要用印象分，先收敛判定口径再谈规模化。**

**（3）基线快照机制（腾讯）：期望答案也是资产。** 腾讯的用例基线机制回答了一个常被忽略的问题——"预期结果从哪来、谁来确认、何时更新"：

```text
用例设计：只定义 prompt 与检查规则（不写死预期输出）
  → 执行 1 次
  → 人工审核本次执行的过程与结果
  → 不可接受：修改后重跑
  → 可接受：该次执行快照成为基线
后续每次执行都与基线对比（确定性评分器做程序化判定；Rubric 以基线为参考答案比语义差异）
```

基线快照包含两部分：**预期过程**（CoT、工具调用序列含入参与返回、中间产物、完整 Trace）与**预期结果**（最终响应、输出文件、输出报告）。**基线更新的三个时机**：Agent/Skill 逻辑变更、模型版本升级、用例本身修改（prompt 或检查规则变了）——任一发生都要重新执行 1 次并人工确认。

TPerf 实战案例把这一点做到了极致：30+ 用例**不硬编码预期输出**，而是通过基线会话标识（`session_id + message_id`）指向人工确认过的分析记录，评测时从平台 API 动态获取。每个用例对应一条真实压测记录——**不可变、可复现**。对比维度也分三层：过程对比（关键步骤缺失/顺序偏离→过程退化）、结果对比（关键内容缺失/产物不一致→结果退化）、效率对比（token/步骤数超基线比例，如 >50% → 效率退化）。

**（4）两条配套纪律。**

- **Eligibility 适用性前置（DoorDash）**：checklist/rubric 再具体，也不是每条都适用于每个会话。DoorDash 的做法是 judge 先判"该标准是否适用本会话"，不适用则跳过——例如食谱类会话不因缺少复购步骤被扣分。用例与标准入库时就要声明适用条件，否则不适用场景的误扣会成为门禁噪声的主要来源。
- **每条标准写成"从会话本身可验证"（DoorDash）**：同一条 rubric 既要能供人工校准、又要能供 judge 规模化执行——凡是人工判定时需要翻外部系统才能核实的标准，要么拆成可验证的证据切片（详见第 E7 章 · Transcript Builder），要么不写进自动评测。
- **执行环境隔离（阿里）**：用例设计得再好，执行时多用例共享状态（同一个测试账号、同一份被改写的库存数据）也会导致分数不可复现。评测执行环境必须逐用例隔离或重置——这是用例 spec 之外的运行侧前提。

### 2.5 Golden Set：定位与规模经验

**定位**（阿里）：Golden Set 默认作为**基线评测集**——相对稳定、长期复用的核心样本，用于**版本对比与发布门禁**。它不是全部评测数据，而是那把"不能热胀冷缩的尺子"；分类采样集、长尾集、对抗集、线上回流集是它外围的扩展层。

**规模经验（以素材为准）**：

| 来源 | 推荐规模 | 语境与补充 |
|---|---|---|
| Anthropic《Demystifying evals for AI agents》（2026-01） | **20-50 个真实用例即可起步** | 官方建议起步最小集；并区分 capability 套件（初始通过率应偏低，指引方向）与 regression 套件（应接近满分，拦截退化） |
| Airbnb | **50-100 条 gold set，必须含坏样本** | 用于 judge 校准；客服案例中 PM/SME 标注 60 条 gold（含失败样本）；规模化阶段扩到 5,000 样本做生产监控，每日另抽样 5% 去标识化流量 |
| 阿里 | **先做 50-200 条高质量 golden set** | 覆盖核心业务路径与高风险边界；成熟后扩展分类采样集、长尾集、对抗集、线上回流集 |
| 腾讯 | 前 **20-50 个参考解**起步 | 人工建 ground truth 的起步量；TPerf 实战落地为 9 大场景 30+ 用例 |

**三个读法**：

1. **起步门槛出奇地低**。四家没有一个要求先攒 1000 条——20-50 条覆盖核心路径与高风险边界的用例就能启动 eval-driven 迭代。等的不是数据量，是判据的清晰度。
2. **规模服务于职能**。50-200 条是"基线尺子"的规模；Airbnb 的 5,000 样本是"每日估计生产质量"的监控规模，两者不可混谈（为什么 100 条尺子在统计上够用，详见第 E9 章的样本量计算）。
3. **gold set 必须含坏样本**（Airbnb 十条要点之一）。原因有二：校准 judge 时需要负例，否则测不出 judge 是否"一律说好"；坏样本还承担区分"judge 误罚正确改述"与"judge 放过流畅错误"的功能——Airbnb 客服案例中 judge 初始一致率仅 78%，正是在含失败样本的 60 条 gold 上定位到"judge 误罚正确的改述"，修 rubric 后升至 88%（judge 校准全流程详见第 E5 章 · LLM-as-Judge 深入）。

**注意"黄金集"一词的两个职能，面试别混**：Airbnb 语境的 50-100 条 gold set 主要服务于 **judge 校准**（含坏样本、人工标注、量小、长期固定），阿里语境的 50-200 条 golden set 主要服务于**版本对比与发布门禁**（覆盖核心路径与高风险边界、期望行为明确）。成熟团队两者都有：校准集管"尺子准不准"，基线集管"版本行不行"——它们可以是同一批样本的两个视角，但维护节奏与准入标准不同（校准集换血要极慎重，否则 judge 一致性历史数据不可比）。

### 2.6 数据集生命周期治理：入库、去重、毕业、只增不减

评测集是活的：每周都有 badcase 想进来，每个版本都有用例想"退役"。没有治理流水线，用例库要么膨胀到跑不起，要么信号被稀释成噪声。

**（1）入库标准五项（阿里，badcase 进评测集/训练数据/知识修订前的通用门槛）**：

| 标准 | 含义 | 缺失的代价 |
|---|---|---|
| 失败可复现 | 或至少有稳定 Trace + 人工确认 | 无法验证修复是否生效 |
| 期望行为明确 | 可写成规则 / Judge 标准 / 人工验收标准 | 无法打分，judge 噪声直接注入门禁 |
| 根因标签清楚 | 归到具体能力域或业务流程 | 无法归因，RCA 断链（详见第 E11 章） |
| 样本有代表性 | 覆盖一类问题而非一次性环境抖动 | 用例库充满孤例，信号稀释 |
| 已脱敏合规 | PII 清理完成 | 法务红线 |

**badcase 不天然是用例。** 阿里把一条 badcase 的反馈生产拆成三条生产线（评测集 / 训练数据 / 知识修订），而入库标准是三条线共用的闸门——五项缺一不可。

**（2）同簇去重**：失败会成簇出现（同一根因反复触发），入库与治理时**同簇保留代表例**，避免 100 条"退款已发货未查订单状态"挤爆回归集。簇的组织可以直接复用 rubric 标准——DoorDash 的经验是 **rubric 标准天然是问题簇**（grounding 失败 / 缺替代品 / 糟糕叙述分开调查），失败列表因此变成按影响排序的主题列表。

**（3）能力评测 vs 回归评测与"毕业"机制（腾讯）**：

| 维度 | 能力测评 | 回归测评 |
|---|---|---|
| 回答的问题 | Agent 能把什么做好 | 原有能力是否还在 |
| 起步通过率 | 20-50%（目标山峰，主动拓展、频繁迭代） | 接近 100%（防御漂移） |
| 变更频率 | 频繁增改 | **只增不减**，CI 每次运行 |
| 失败含义 | 改进方向 | 阻断发布 |

**毕业流转**：能力集用例通过率稳定 100% 后"毕业"进回归集；badcase 的完整旅程是"复现记录完整轨迹 → 分析根因定预期行为 → 修复 → 纳入用例集防回归 → 进能力集，稳定后毕业到回归集"。腾讯引用 Anthropic 的口径作为回归门槛：**确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%**。与之配套的是稳定性容忍阈值分级（关键决策类 0% 容忍、辅助分析类 ≤10%、创意生成类 ≤40%）——同一条用例在不同业务语境下的"毕业线"不同。

**（4）样本治理四条规则（阿里）**：

1. 同簇保留代表例；
2. **P0/P1 风险样本长期保留**（资损、合规、隐私类永不降级）；
3. 稳定多版本通过且低风险者**降级为抽样集**（退出每次必跑，保留抽查资格）——这是回归集不无限膨胀的泄压阀；
4. 新分布出现时主动学习优先抽取低置信 / 高影响 / 新意图 / 新工具 / 新知识点样本进人工确认。

**（5）执行触发时机（腾讯）**：治理的最终产物是"变更 → 自动回归"的条件反射：

| 触发时机 | 方式 | 跑什么 |
|---|---|---|
| 提示词变更 | CI 自动，PR 合入前回归 | 回归集全量 |
| 模型版本升级 | 手动触发 | 验证兼容性（回归集 + 关键能力集） |
| 定期巡检 | 定时任务 | 全量回归 |

门禁的严格程度可以参考 DoorDash 仿真评测飞轮的口径：**任何变更必须通过全部 50+ 个 eval 才能上线**，且全流程一次触发，5 分钟内可跑完 200+ 场模拟对话——"门禁要严、跑得要快"，两者靠 fixtures 与并行化同时满足（详见第 E8 章）。

**（6）长尾集与对抗集**：成熟期在 golden set 之外单独维护。长尾集收低频但真实的场景（小语种、极端金额、多重约束叠加）；对抗集收注入、越权、诱导承诺等安全用例——安全用例必须常驻回归，一次 prompt 重构完全可能功能全绿而防线塌方（安全评估详见主手册第 8 章 · Agent 评估与可观测性）。

动手实验：入库检查器、同簇去重、毕业流转、回归门禁的可运行实现都在 `cd evals-special/labs && python3 eval_lab02_golden_dataset.py`；毕业机制与"回归集只增不减"在 EDD 全闭环中的位置见 `cd evals-special/labs && python3 eval_lab10_edd_loop.py`。

### 2.7 隐私合规：去标识化与用途限定

生产数据进评测链路，合规是硬门槛，不是"以后再说"。素材中两条明确实践：

- **Airbnb**：生产抽样采用隐私保护方法——**人工评审前去标识化、用途限定于安全与质量**。两个动作缺一不可：去标识化解决"数据能不能用"，用途限定解决"数据会不会被挪作他用"。
- **阿里**：把"**已脱敏合规**"列为入库标准第五项——未脱敏的样本在闸门口就被拒，而不是入库后再补救。

工程上的常见做法（通用实践）：直接标识符（姓名/电话/卡号/地址）程序化替换，间接标识符（罕见组合特征）做泛化或删除；工具返回值里的 PII 同样要扫（trace 是重灾区）；留存期分级、访问留痕；用于 judge 校准与人工评审的样本走同一套脱敏管线。注意脱敏不是"一次性清洗"：线上回流是持续流，脱敏必须内建在入库管道里，而不是靠人记得手动处理。

### 2.8 公开 benchmark 与私有评测集：三层互补

私有 golden set 不是孤岛，它和公开基准、在线信号构成三层坐标系：

| 层 | 代表 | 测什么 | 主要局限 |
|---|---|---|---|
| **公开 benchmark**（外部坐标） | τ-bench、GAIA、SWE-bench 等 | 与业界横向对比的能力水位 | 污染、饱和、分布与你的业务错配 |
| **私有 golden set**（业务真值） | 自建 50-200 条基线集 | 你自己的核心路径与高风险边界 | 规模有限、需要持续治理防过拟合 |
| **在线信号**（最终裁决） | 每日抽样评分、转人工率、满意度 | 真实用户的最终体验 | 稀疏、滞后、混杂因素多 |

几点关键事实（以素材为准）：

- **公开基准的价值在"外部参照"而非"产品指标"**。τ-bench（[arxiv 2406.12045](https://arxiv.org/abs/2406.12045)，2024-06）用数据库终态哈希 + pass^k 提供了可靠的横向坐标：GPT-4o 在 retail 域 pass^1 ≈60%（官方榜单 60.4%）、airline 域 ≈42%，而衡量可靠性的 pass^8 跌至约 25% / 16%（官方榜单与论文口径）——这类数字能帮你判断"自家 agent 的稳定性缺口是不是行业通病"。
- **基准会饱和、会被污染**。Anthropic 报告 SWE-bench Verified 一年内从 40% 涨到 80%+；EDDOps 对学术文献的统计显示 97.76% 的评测仍用静态基准——静态题面迟早进训练语料。公开分数只能当路标。
- **私有集的最大敌人是"自己"**。一旦评测集被当作优化目标（如用 MIPROv2 类优化器以 eval 分数为搜索目标，[arxiv 2406.11695](https://arxiv.org/abs/2406.11695)），就会出现泄漏与过拟合风险——EDDOps 因此把 contamination safeguards（污染防护）与 provenance 列为评测资产的必备属性；工程手段是留出集隔离、定期换血、按 slice 报告（GEPA 的 Pareto 前沿选择即按切片保留候选，防止平均分掩盖退化，[arxiv 2507.19457](https://arxiv.org/abs/2507.19457)）。
- **"只能选一个向老板汇报，选哪个"**：选私有 golden set 的通过率 + 在线信号。基准分数回答不了"我们的用户会不会出事"，只有来自真实失败的私有集和线上数据能回答（完整选型框架详见第 E13 章 · Benchmark 全景与前沿争议）。

## 四、经典面试题与参考答案

#### 题 1（基础）：为什么不能直接从线上日志随机抽样当评测集？

**参考答案：**

因为线上流量存在**幸存者偏差**：正常流程占多数，易错的高风险边缘场景（退款已发货、叠加优惠、欺诈嫌疑）占比极低。随机抽样忠实复刻这个分布，评测报告"看起来不错"，但恰好把最关键的问题漏掉了——随机抽样回答的是"线上平均表现如何"，评测集要回答的是"最坏情况下会不会死"。

正确做法分三层：① 评测集主体来自**专家设计 + 结构化 LLM 扩展 + badcase 回流**，按"触发→核心逻辑→产物质量→异常容错"组织，对高风险分支定向填充；② 线上数据做**分层采样**（按风险/意图/置信度，过采样高风险与低置信样本），用于失败挖掘与分布校准，聚合时按真实流量权重加权；③ 线上抽样（如 Airbnb 每日 5% 去标识化流量）定位为生产监控，与作为基线门禁的 golden set 分开管理。

#### 题 2（基础）：评测用例有哪几类来源？各自的优点和风险是什么？

**参考答案：**

四类（阿里口径）：

1. **专家设计**——定标准。覆盖核心与高风险分支、判据权威；缺点是贵且慢，冷启动先出 20-50 条参考解即可。
2. **LLM 扩展**——上量。便宜快、表达多样；风险是自由生成会编造业务不存在的场景，所以必须**先用规则确定结构字段（场景类型/订单状态/用户诉求/期望动作），再让 LLM 生成自然语言表达**。
3. **线上真实数据**——分布校准。表达最真实；但有幸存者偏差与隐私风险，须去标识化，且不直接当基线。
4. **badcase 回流**——防再犯。每条都是真实发生过的失败，针对性最强；但 badcase ≠ 用例，须过五项入库标准（可复现/期望明确/根因清楚/代表性/已脱敏）。

加分项：EDDOps 要求每条用例带 provenance/oracle/slice 标签，通过率按来源拆开看，才能判断"是评测集偏了还是模型偏了"。

#### 题 3（进阶）：用 LLM 批量生成测试用例时，为什么强调"先定结构字段、再生成自然语言"？让模型自由生成会怎样？

**参考答案：**

自由生成有三个失效模式：① **场景编造**——模型生成业务上不存在的状态组合（如"未支付订单申请改地址"），用例失去可判定性；② **分布失控**——高频套路反复出现、关键分支无人覆盖，没有覆盖矩阵可查；③ **判据缺失**——生成时没有期望动作，入库后还要人工补，成本反而更高。

"先结构后语言"把生成拆成两段：结构字段（场景类型/订单状态/用户诉求/期望动作）由规则或枚举确定，保证覆盖矩阵按需填充、每条用例天生带判据；LLM 只负责把结构改写成接近真实用户的自然语言表达，保证多样性与真实感。本质是**把"测什么"（构念效度）与"怎么说"（表面多样性）解耦**——前者必须握在人手里。工程实现上对应结构化输出/schema 校验：生成请求里没有结构字段就直接拒绝（eval_lab02 的 MockLLM 正是这样实现的）。

#### 题 4（进阶）：负向触发用例为什么必不可少？你会怎么设计？

**参考答案：**

因为**过度触发比不触发更难发现**（腾讯原话）。不触发会立刻被用户发现（功能"坏了"），过度触发却静默发生：无关请求被路由进昂贵链路、token 消耗上涨、下游流程被污染，直到成本账单或连锁事故才暴露。只测正例的评测集会系统性纵容"什么都触发"的 agent。

设计方法：① **相似但不相关**的 prompt 成对构造——与合法触发仅一字之差的表述（相邻技能的需求、含相同关键词但意图不同的请求）必须不触发；② 负例覆盖三类：相邻技能混淆、关键词陷阱（含实体词但意图不同）、空泛请求（"帮我看看"）；③ 判定用程序化断言（未调用目标技能入口 / 未进入目标流程），零 judge 成本；④ 与正向用例配对汇报：触发场景同时报召回（正例触发率）与精度（负例不触发率），两个数一起看才有意义。

#### 题 5（进阶）：Golden Set 建多大规模合适？为什么 Airbnb 强调 gold set 必须包含坏样本？

**参考答案：**

规模经验（均以素材为准）：Anthropic 建议 20-50 个真实用例即可起步；Airbnb 用 50-100 条 gold set；阿里建议先做 50-200 条高质量 golden set 覆盖核心业务路径与高风险边界。共识是**起步门槛低、判据优先于数量**：50-200 条是"基线尺子"的规模，承担版本对比与发布门禁；更大的集合（如 Airbnb 规模化阶段的 5,000 样本、每日 5% 抽样）是生产监控用途，两者职能不同。统计上，100 条样本的通过率 95% 置信区间约 ±10 个百分点，足以分辨"明显变好/变坏"，再小则噪声淹没信号（计算详见第 E9 章）。

必须含坏样本有两个原因：① 校准 judge 需要负例，否则测不出 judge 是不是"一律给好"；② 坏样本能暴露 judge 的误判类型——Airbnb 客服案例正是在含失败样本的 gold 集上发现 judge 初始一致率仅 78%，根因是"judge 误罚正确的改述"，修 rubric 后升到 88%。没有坏样本的 gold set，校准根本无从谈起。

#### 题 6（进阶）：线上进来一条 badcase，能直接变成评测用例吗？入库标准是什么？

**参考答案：**

不能。badcase 是原料，不是用例；阿里的入库标准五项缺一不可：

1. **失败可复现**（或至少有稳定 Trace + 人工确认）——否则无法验证修复是否生效；
2. **期望行为明确**——可写成规则/Judge 标准/人工验收标准，否则无法打分；
3. **根因标签清楚**——归到具体能力域或业务流程，否则 RCA 断链；
4. **样本有代表性**——覆盖一类问题而非一次性环境抖动，孤例会稀释信号；
5. **已脱敏合规**——PII 清理完成，法务红线。

完整旅程是：badcase → 过五项标准 → 编码为用例（带 provenance 指回原始 session）→ 进能力集验证修复 → 稳定 100% 通过后毕业进回归集（只增不减）。一条 badcase 至少可生产三类反馈（评测集/训练数据/知识修订），入库标准是三条生产线共用的闸门。

#### 题 7（进阶）：能力评测和回归评测有什么区别？"毕业"机制怎么运转？

**参考答案：**

两者回答的问题相反：**能力测评**回答"Agent 能把什么做好"——是目标山峰，起步通过率 20-50%，主动拓展、频繁迭代，失败代表改进方向；**回归测评**回答"原有能力是否还在"——是防线，期望接近 100%，防御漂移，CI 每次运行，失败即阻断发布。

毕业机制是两者的传送带：能力集用例**通过率稳定 100% 后毕业进回归集**；回归集**只增不减**。腾讯引用 Anthropic 口径定回归门槛：确定性任务用例集整体通过率 100%，非确定性任务 ≥95%，并按业务类型分级容忍（关键决策类 0% 容忍、辅助分析类 ≤10%、创意生成类 ≤40%）。防膨胀靠降级泄压：稳定多版本通过且低风险的用例降级为抽样集（退出每次必跑、保留抽查资格），但 P0/P1 风险样本长期保留、永不降级。badcase 的完整闭环：复现 → 定根因与期望行为 → 修复 → 纳入用例集防回归 → 进能力集 → 稳定后毕业。

#### 题 8（进阶）：DoorDash 的 checklist 式场景 rubric（如"素食 taco 购物清单"）比宽泛 rubric 好在哪？什么场景适用？

**参考答案：**

案例：场景"为两人份、预算 ≤$60 的素食 taco 购物清单"，rubric 写成可核验清单——每件商品都是素食 taco 原料、小计 ≤$60——而不是"清单质量好"。

好在**低方差**：判定依据收敛到可程序化核验的事实（商品在不在清单、金额加总），judge 与人工的自由裁量空间被压缩，同一输入重复评分的波动小。方差低的直接收益是**小样本也能迭代**——50 个场景就能可靠区分两个版本，支撑更快的发布节奏；宽泛标准方差高，同样样本量下差异淹没在噪声里。此外 checklist 失败时归因明确（哪一条没满足一目了然），天然服务于失败聚类。

适用边界：任务目标可枚举成事实性检查项时用 checklist（购物、预订、表单类）；开放式目标（语气、叙事质量）仍需语义 rubric 兜底，此时用 eligibility 前置（DoorDash：judge 先判标准是否适用本会话）避免误扣。两者都要求"从会话本身可验证"，才能同一 rubric 既供人工校准又供 judge 规模化。

#### 题 9（系统设计）：为一个新上线的客服 Agent 从零设计评测数据集体系：来源、组织、规模、治理流程、与 CI 的衔接，一次讲清。

**参考答案：**

**第一阶段（第 1-2 周）：定口径、立骨架。** 与业务方先定高风险场景的口径（如"已发货+拒收+运费险该走哪条流程"）；专家设计 20-50 条参考解覆盖核心路径；按腾讯四场景（触发→核心逻辑→产物质量→异常容错）组织，正负用例成对，核心逻辑用例量≈其余三类之和的 2-3 倍（先梳理分支流程图，每条分支至少 1 例）；每条用例固化为 spec（输入/期望行为/判据/risk_level/provenance），期望行为写成 must-call/must-not 等可判定检查项。

**第二阶段（第 3-4 周）：扩量与基线。** 用"先结构字段后自然语言"的 LLM 扩展把规模做到 50-200 条（阿里口径），覆盖核心业务路径与高风险边界；对执行类用例走基线快照流程（执行 1 次→人工确认→快照为基线，不硬编码输出）；为购物/预订类场景配 checklist 式低方差 rubric；线上真实会话去标识化后做分布比对，补覆盖盲区。

**第三阶段（持续）：治理流水线。** 入口：badcase 双通路（离线评测失败 + 线上投诉/低满意度/转人工）汇入同一任务表，过五项入库标准（可复现/期望明确/根因清楚/代表性/已脱敏）编码为用例；同簇去重保留代表例。流转：新用例先进能力集，稳定 100% 通过后毕业进回归集（只增不减）；回归集进 CI——PR 触发回归（提示词变更）+ 模型升级手动验证 + 定期全量巡检；门槛按 Anthropic 口径：确定性 100%、非确定性 ≥95%，P0 风险样本失败一票否决。防膨胀：稳定多版本通过且低风险者降级抽样集，P0/P1 长期保留；成熟后扩展长尾集与对抗集（注入/越权用例常驻回归）。

**第四阶段（规模化）：三层坐标。** 私有 golden set 做发布门禁；公开基准（τ-bench 类）做季度外部水位参照；线上每日抽样（去标识化、用途限定）做持续监控——三层分数不可互替。组织上指定人类终判者裁决口径争议（Airbnb 五原则之一），评测集增长与 judge 校准各有 owner。

## 五、易错点 · 反直觉点

1. **误区：线上日志随机抽一批就是最"真实"的评测集。**
   真相：线上分布里高风险场景占比极低，随机抽样复刻的是流量而不是风险，报告"看起来不错"恰好说明关键问题被漏掉了。
   记忆锚点：**评测集找问题，抽样描分布——目标相反，不能混用。**

2. **误区：触发场景只需要测"该触发时能触发"。**
   真相：只测正例，agent 可能学会什么都触发；过度触发静默消耗成本、污染下游，比不触发更难发现。
   记忆锚点：**正例测召回，负例测精度，触发场景必须成对。**

3. **误区：让 LLM 自由生成几百条用例，又快又多。**
   真相：没有结构字段约束的生成=场景编造+分布失控+判据缺失；覆盖率无法审计，入库后全是返工。
   记忆锚点：**先定骨架（结构字段），再长皮肉（自然语言）。**

4. **误区：badcase 很宝贵，发现一条就加一条进评测集。**
   真相：不可复现的无法验证、期望不明的无法打分、无根因标签的无法归因、一次性抖动不代表一类问题、未脱敏的有合规风险——不过入库标准的 badcase 是噪声不是资产。
   记忆锚点：**badcase 是原料，入库标准五项是闸门。**

5. **误区：gold set 全放好样本，干净漂亮。**
   真相：没有坏样本就校准不了 judge——测不出 judge 是否一律说好，也发现不了"judge 误罚正确改述"这类系统性误判（Airbnb 78%→88% 的校准正是靠含失败样本的 gold 集）。
   记忆锚点：**gold set 必须含坏样本，否则尺子没法校。**

6. **误区：用例预期输出直接写死在 JSON 里，一劳永逸。**
   真相：业务逻辑变更、模型升级后硬编码的预期会变成错误答案，评测开始误杀正确行为；腾讯的做法是基线快照（执行 1 次→人工确认→快照为基线），且 Agent 逻辑变更/模型升级/用例修改三个时机必须重做基线。
   记忆锚点：**预期答案也是资产，要有人审、有版本、有更新时机。**

7. **误区：评测集越大越好，1000 条总比 100 条强。**
   真相：基线集的价值在判据清晰与风险覆盖，不在数量；过大意味着维护成本、judge 成本与 CI 时长暴涨，信号还被重复样本稀释。四家的起步口径都是 20-200 条量级；规模扩张走"分类采样集/长尾集/监控抽样"等外围层。
   记忆锚点：**尺子要准不要长，宁深勿水。**

8. **误区：评测集只进不出，永远安全。**
   真相：不做毕业与降级，回归集无限膨胀到 CI 跑不动；但只做减法更危险——回归集只增不减是底线，泄压靠"降级抽样集"（退出必跑、保留抽查），P0/P1 风险样本永不降级。
   记忆锚点：**只增不减是原则，降级抽样是泄压阀。**

9. **误区：私有评测集拿来当优化目标（自动改 prompt 刷分）没问题，反正是自己的集。**
   真相：eval 一旦成为目标就会被拟合——MIPROv2 等优化器以 eval 分数为搜索目标时，必须配留出集与定期换血；EDDOps 把污染防护与 provenance 列为评测资产的必备属性。被刷穿的评测集给出的门禁全是虚假信心。
   记忆锚点：**评测集当裁判就不能同时当考题——留出集隔离，定期换血。**

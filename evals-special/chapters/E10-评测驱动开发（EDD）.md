# 第 E10 章 · 评测驱动开发（EDD）

> 一句话导读：评测体系建好之后，真正的难题是把它"嵌进开发流程"，让每一次改动都被评测看见、每一个失败都变成资产。
> EDD（Eval-Driven Development）就是 GenAI 版的 TDD：不试图预测所有失败，而是**发现 → 捕获 → 反复检查**失败模式（Airbnb 定义）。
> 学完本章你能得到：Airbnb 五原则与 100 样本精读法、一次一变量的迭代纪律、capability/regression 双套件与 CI 门禁设计、
> EDDOps 学术过程模型、DoorDash 失败回流闭环，以及"eval 作为优化目标函数"的前沿与治理。

## 二、核心概念精讲

### 2.1 EDD 是什么：从"上线前检查点"到"迭代指南针"

**定义（Airbnb）**：Eval-Driven Development 是 GenAI 版的测试驱动开发。传统 TDD 假设你能在写代码前
穷举失败条件；GenAI 系统做不到——输出不可预测、"正确"依赖判断、一次请求里的搜索/推理/外部动作/文本生成
每一环都可能独立失败。所以 EDD 的核心动作不是"预测所有失败"，而是：

1. **发现**（discover）：主动跑数据、读输出，找到真实的失败模式；
2. **捕获**（capture）：把每个失败模式固化成可复跑的测试用例与 rubric；
3. **反复检查**（repeatedly check）：让用例进 CI 与线上监控，每次变更都重新验证。

Anthropic 在《Demystifying evals for AI agents》（2026-01）中给出了同构的官方表述：**先定义期望行为，
再开发 agent**（eval 即规约），起步只需 20–50 个真实用例；OpenAI 的 evaluation best practices 同样明确建议
"从一开始就反复评测（eval-driven）、每次变更都跑 continuous evaluation"。

**EDD 与 TDD 的对照**（面试高频对比题）：

| 维度 | 传统 TDD | EDD |
|---|---|---|
| 被测对象 | 确定性代码 | 模型 + prompt + 工具 + 检索 + serving 构成的系统 |
| 测试编写 | 先写断言，再写实现 | 先写期望行为（用例 + rubric + 判据），再调系统 |
| 期望输出 | 唯一确定值 | 允许多条合法路径；用 rubric/终态/分布描述 |
| 通过标准 | 断言完全成立 | 统计口径：通过率、pass^k、置信区间 |
| 回归语义 | 代码变更 | 模型/prompt/工具/serving 任一变更都可能回归 |
| 失败模式 | 可静态推演 | 必须从真实数据中挖掘（100 样本法） |
| 测试资产 | 单元测试套件 | golden set + 回归集 + judge 校准集 + 基线快照 |

**没有 EDD 的三大坑（Airbnb 总结）**：

| 坑 | 表现 | EDD 的解法 |
|---|---|---|
| 虚假信心 | 用一个浅层 helpfulness 分自我感觉良好 | 从观察到的真实错误推导指标，按维度拆 judge |
| 未被发现的回归 | 改 prompt 后旧场景质量悄悄变差，无人知晓 | 回归集只增不减，PR 触发回归 |
| 指标与产品脱节 | 分数在涨，产品结果没动，浪费精力 | 尽早与产品伙伴定目标与上线门槛（launch gates） |

一句话收束：**评测在 EDD 里有四重身份——质量度量、发布门禁、迭代指南针、数据飞轮入口**（展开见第 E1 章）；
EDD 的贡献是让后两重身份成为日常纪律，而不是上线前的一次性仪式。

### 2.2 Airbnb 五原则与核心习惯：When in doubt, look at your data

Airbnb 在点评摘要、客服、房东/房客消息、内部洞察等多个 GenAI 场景沉淀出 **EDD 五原则**（产品团队自定标准，
基础设施组提供共享工具与跨团队指南——是实践不是强制令）：

| # | 原则 | 落地要点 |
|---|---|---|
| 1 | 尽早设定目标与上线门槛（launch gates） | 即便门槛要在数据评审中才逐渐清晰，也要先立一个可被推翻的初版 |
| 2 | 从观察到的错误中推导指标 | 与跨职能伙伴共同制定；拒绝凭空设计的"万能 helpfulness" |
| 3 | 用少而精的 judge | **3–5 个经校准的评估器，好过一堆嘈杂的评估器** |
| 4 | 指定一个最终人类决策者 | 裁决"好 vs 坏"的争议，避免口径在多人间漂移 |
| 5 | 让产品伙伴持续参与 | 参与版本对比与错误诊断，评测是跨职能产品活动 |

**核心习惯："When in doubt, look at your data."** 这是 Airbnb EDD 文化的第一习惯，具体化为
**100 样本人工精读法**：

```text
跑约 100 个样本（真实或合成）
  → 人工逐条读输出与 trace（不是看平均分）
  → 找错误、归类错误模式（groundedness 失败？啰嗦？不当拒答？格式坏？）
  → 围绕这些失败模式建测试（程序化检查 + judge + gold 集）
```

为什么 100 条就够起步？因为它解决的不是"估计总体通过率"（那是统计学问题，见第 E9 章），而是
**"枚举失败模式的种类"**——失败模式的多样性在几十到一百条样本里就会大致显形，而每一种模式都值得一条测试。
Anthropic 的口径更激进：起步只需 20–50 个真实用例。Airbnb 十条要点中的第一条就是：
**建复杂工具之前，先人工看输出与 trace**。

**Airbnb 十条要点速记**（原文浓缩，面试可直接引用）：
① 先人工看输出与 trace 再建复杂工具；② 避免泛化 helpfulness，瞄准真实产品失败；③ 从小标注集起步快速迭代；
④ 不做万能 judge，按维度拆分；⑤ judge 校准到高一致率后再信任；⑥ 代码检查 + 模型 judge + 人工评审结合；
⑦ gold set 必须含坏样本；⑧ 评整个系统（检索/工具/agent 路径）；⑨ 上线前测试要在线上持续运行；
⑩ 评测是跨职能产品活动。

### 2.3 EDDOps：四阶段闭环的学术成型

EDD 从口号变成有过程模型与参考架构的工程学科，标志性工作是
《Evaluation-Driven Development and Operations of LLM Agents》（arxiv 2411.13768；
v1 2024-11 首发，原题 "An Evaluation-Driven Approach to Designing LLM Agents"；2025-11 v3 更名加入 Operations）。
作者团队来自 Adelaide University / CSIRO Data61 / UNSW，基于 **134 篇学术文献 + 27 份工业灰色文献**的多声源综述。

**四阶段闭环**：

| 阶段 | 内容 | 关键产物 |
|---|---|---|
| Plan | 评测计划**版本化**：范围、指标、切片（slice）、频率、升级规则、自适应触发条件 | 评测计划书（输入 = 用户目标 + 治理约束 + agent 初版设计） |
| Build | 评测资产 = 标准基准 + 领域知识 + 专家用例 + 合成数据；每个用例带 provenance、oracle（判定标准）、slice 标签、运行模式 | 版本化测试目录 |
| Run | offline：批量基准、精选套件、轨迹回放、缺陷定位；online：生产信号、限流暴露（shadow/canary）、内联校验器、定时或异常触发的探针 | offline + online 证据流、slice 级报告 |
| Analyze & Improve | 优先**最小有效变更**（prompt/路由/护栏/记忆），大改动（架构/工具契约/检索/模型）走受控 offline 再开发；所有变更版本化、回归重测 | 更新后的 safety case（证据支撑的安全论证） |

**三层参考架构**：

```text
Supply Chain Layer（评测意图与证据：评测为什么这么定、模型为什么这么选）
      ↓
Agent Layer（暴露可评测表面：prompt/工具/记忆可检视，结构化 trace）
      ↓
Operation Layer（Evaluation Backbone + Control Loop）
   证据库 = Evaluation Results / Test Cases / Safety Cases
   配 AgentOps 可观测性做触发、策略、回滚；连接 offline 证据与 online 信号
```

**一组揭示学界/工业界错位的数字**（EDDOps 综述统计，面试引用率极高的深水区素材）：

| 口径 | 学术文献（134 篇） | 工业灰色文献（27 份） |
|---|---|---|
| 只做 pre-deployment 评测 | **93.28%** | — |
| 覆盖 post-deployment | 仅 **2.24%** | — |
| 持续评测 | 4.48% | **40.74%** |
| 只看端到端指标 | 92.54% | — |
| 用静态基准 | 97.76% | — |
| 已用评测驱动适配 | — | 81.48% |

结论：学术供给集中在"上线前 + 端到端 + 静态基准"，而工业界近一半已转向持续评测——
**EDD 的主战场在生命周期后半段**，这正是本章与第 E12 章（在线评估与数据飞轮）的衔接点。
该论文还明确定义了 shadow evaluation（不暴露给用户的影子评测）与 canary rollout（小流量灰度）在框架中的位置，
验证案例为 LLM 报税助手（Tax Assistant）。

### 2.4 迭代纪律：一次只改一个变量

GenAI 系统可调的旋钮太多：prompt、模型、检索、工具描述、serving 配置。Airbnb 把迭代纪律总结为一句话：
**一次只改一个变量**，顺序是：

```text
固定模型，只变 prompt → 固定 prompt，只变模型 → 两者都固定，只变 serving 配置
```

**为什么必须如此**：多变量并动时，分数变化无法归因——你不知道是 prompt 修好了错误，还是新模型恰好掩盖了它；
一旦某个版本在回归集上掉分，你甚至不知道该回滚哪个改动。这与 EDDOps 的"最小有效变更优先"完全一致：
先改 prompt/路由/护栏/记忆这类便宜可逆的旋钮，架构/工具契约/检索/模型这类大改动走受控的 offline 再开发。

**judge 与候选的互相打磨**：迭代不是单向的"judge 给候选打分"。Airbnb 的做法是——
judge 筛候选，**顶尖候选反哺 judge 改进**（优秀候选暴露 rubric 的盲区：它明明很好，judge 却没给分），
如此往复，直到 judge 与候选集双方稳定。

**版本比较必须带统计口径（阿里）**：即便一次一变量，两个版本的分数差也可能是噪声。阿里的门禁要求
**关键指标置信区间 + 与基线的显著性判断 + 最小可感知变化阈值**（提前定义"提升多少才值得发布"）：
"门禁不只看差了多少，还要看差异是否超过统计噪声。"（统计工具：Wilson 区间、配对检验、样本量计算，
详见第 E9 章；动手实验：`cd evals-special/labs && python3 eval_lab08_statistics_ci.py`）

**反例**（面试常让你指错）：某团队同一天把 prompt v2 和新底座模型一起上线，总分 +3 分，宣布成功。
两周后线上投诉上升，排查发现：新模型其实 -5 分，prompt v2 是 +8 分——但因为捆绑变更，
他们既错过了发现模型退化的机会，也无法单独保留 prompt 收益。**捆绑变更 = 主动放弃归因。**

### 2.5 完整案例演练：Airbnb 旅行客服政策问答助手

这是 Airbnb 博客给出的端到端 EDD 演练，四个阶段每一步都有数字，是回答"EDD 具体怎么做"的最佳模板。

**阶段一：探索（100 样本精读）**。跑 100 个真实/合成 prompt，人工读输出，归类出四种失败模式：

| 失败模式 | 数量/100 | 后续对应测试 |
|---|---|---|
| groundedness 失败（回复不锚定政策/检索证据） | 15 | groundedness judge |
| 答案正确但啰嗦 | 8 | conciseness judge + 长度检查 |
| 不当拒答（该答不答） | 5 | 拒答边界用例（正反例） |
| JSON 输出失败 | 3 | 程序化 schema 校验 |

**阶段二：建测试**。JSON 格式与长度用程序化检查（确定性优先，见第 E4 章）；groundedness 与 conciseness
各建一个 judge（"少而精"：只建与观察到的失败对应的 judge）；PM/SME 标注 **60 条 gold 集，含失败样本**
（坏样本是校准 judge 的关键——只喂好样本的校准集测不出 judge 会不会误杀）。

**阶段三：校准**。judge 初始与人工一致率 **78%，过低，不能进自动化**。分歧分析发现 judge 在
**误罚"正确的改述"**——答案语义正确但与参考答案字面不同，字面重叠式的 rubric 把它判错。
修订 rubric 与 few-shot 示例（放宽改述惩罚、加事实核对项）后一致率达 **88%**，进入自动化。
同期检索侧改进减少了 groundedness 失败。（完整校准流程、Cohen's kappa、阿里 ~85% 与腾讯 ≥85% 口径，
见第 E5 章；动手复现 78%→88%：`cd evals-special/labs && python3 eval_lab05_judge_calibration.py`）

**阶段四：规模化与监控**。评测集扩到 **5,000 样本**；**每日抽样 5% 去标识化生产流量**跑同一套检查与 judge；
被标记样本送人工复核；**每周 PM 评审**，产出新增测试与修复项。上线前的测试在线上持续运行——
EDD 的终点不是发布，而是运营。

**把案例抽象成 EDD 循环**：

```text
   ┌──────────── 探索：100 样本精读，归类失败模式
   │                  ↓
   │          建测试：程序化检查 + 维度 judge + gold 集（含坏样本）
   │                  ↓
   │          校准：judge↔人工一致率 78% → 88%（改 rubric 不是改数据）
   │                  ↓
   │          门禁：进 CI，PR 触发回归；统计口径判版本差异
   │                  ↓
   └──── 回流 ← 监控：5,000 样本 + 每日 5% 线上抽样 + 每周 PM 评审
```

### 2.6 CI 门禁与回归集：capability 套件 vs regression 套件

EDD 的"门禁"环节回答：**什么样的版本允许发布**。核心是 Anthropic 提出的套件二分法（腾讯引用并落地）：

| 维度 | Capability 套件（能力评测） | Regression 套件（回归评测） |
|---|---|---|
| 回答的问题 | "Agent 能把什么做好" | "原有能力是否还在" |
| 期望通过率 | **初始应偏低**（20–50% 起步，腾讯口径） | **接近满分**（掉分即阻断） |
| 角色 | 目标山峰：指引改进方向、主动拓展、频繁迭代 | 防御地板：拦截漂移，只增不减，CI 每次运行 |
| 失败的含义 | 正常，说明还有空间 | 事故信号，必须定位 |
| 异常信号 | 起步就接近满分 → 套件太容易，无区分度 | 0% 或 100% 之外的怪值 → 先查任务定义/评分器是否坏了（腾讯） |

**门槛数字（面试必答）**：腾讯引用 Anthropic 的推荐——**确定性任务用例集整体通过率需 100%，
非确定性任务 ≥95%**。腾讯自身的稳定性容忍阈值还按使用类型分级：关键决策类（问题定位/故障诊断）
0% 容忍（N 次全过，任何一次失败都可能误判）；辅助分析类 ≤10%；创意生成类 ≤40%（建议 N=5）。
高风险不可逆场景（客服/支付/退款/合规）建议用 **pass^k** 作发布门槛：Anthropic 文档示例，
单任务成功率 p=0.75、k=3 时 pass^3 ≈ 0.75³ ≈ **42%**——"看起来 75% 不错"的 agent，三连全对只有四成把握
（pass@k 与 pass^k 的数学与实验见第 E2 章；`cd evals-special/labs && python3 eval_lab01_metric_system.py`）。

**用例毕业机制（腾讯独创）**：capability 用例通过率稳定 100% 后"毕业"进回归集——回归集像滚雪球一样
承接所有曾经攻克的能力；回归集**只增不减**。badcase 的标准旅程：复现并记录完整轨迹 → 分析根因定预期行为
→ 修复 → 纳入用例集防回归 → 进能力集，稳定后毕业到回归集。（用例生命周期与入库标准的完整实现见第 E3 章；
`cd evals-special/labs && python3 eval_lab02_golden_dataset.py`）

**触发时机（腾讯）**：

| 触发 | 方式 | 目的 |
|---|---|---|
| 提示词变更 | CI 自动，PR 合入前回归 | 拦住每一次 prompt 手改 |
| 模型版本升级 | 手动触发 | 验证兼容性（见 2.8 DoorDash 模型迁移案例） |
| 定期巡检 | 定时全量回归 | 捕获环境/依赖的隐性漂移 |

**门禁的质量本身依赖 grader 的质量**：Anthropic 报告的 CORE-Bench 案例中，Opus 4.5 在修复了任务定义与
评分器缺陷之后成绩从 **42% 跳到 95%**——门禁红了一半的时候，先怀疑尺子再怀疑模型（详见易错点 6）。
另一个参照数字：SWE-bench Verified 一年内从 40% 涨到 80%+；创业公司 Bolt 约 3 个月建成 eval 体系。

**门禁的成本与分层**：全量 E2E 每次 PR 都跑对大团队可行（DoorDash：任何变更必须通过全部 50+ 个 eval，
5 分钟跑 200+ 场模拟对话），对小团队昂贵。折衷方案：**分层门禁**——单元层 grader/断言必过（秒级、确定性），
轨迹/结构层每日全量，E2E 模拟层抽样或按需触发（arxiv 2601.18827 提出"单元/集成/E2E 三级金字塔"，
2604.27789 专门讨论门禁的计算开销与运维复杂度）。

### 2.7 仿真评测与失败回流：EDD 的"排练场"和"齿轮"

**（1）为什么 EDD 离不开仿真**：DoorDash 列出的评测挑战中有一条"无法安全彩排"——不能拿真用户试变更，
历史会话也不能对改过的 agent 重放（agent 变了，对话路径就不一样了）。解法是按需生成会话：
**LLM 模拟用户驱动 agent 跑场景，外围数据用 fixtures 冻结**，同一场景每次运行条件一致
（详见第 E8 章；`cd evals-special/labs && python3 eval_lab07_simulator_fixtures.py`）。
学术侧的范式源头是 τ-bench（arxiv 2406.12045，2024-06，Sierra）：LLM 用户模拟器 + 工具调用 +
**数据库终态哈希**做可验证判定 + pass^k 刻画可靠性；τ²-bench（arxiv 2506.07982）升级为双控
（用户侧也能执行工具动作）。

**（2）仿真的成本账（DoorDash）**：全量回归 sweep = **50 场景 × 8 trials = 400 次对话**；
人工本地聊约 1 分钟/次 → **6+ 小时**；模拟器约 **20 分钟**。harness 建成后：质量信号从平均
1 条/天员工反馈 → **2,000 个/天自动评分会话**；全国上线前 agent 质量分 **+8 分**、错误率**近乎减半**；
并支撑底座模型迁移（Claude Sonnet 4.6 → Gemini 3.5 Flash）实现**延迟降 35%、质量无损**。
DoorDash 的仿真评测飞轮还报告：**一次触发跑完全流程，任何变更必须通过全部 50+ 个 eval 才能上线；
5 分钟内跑 200+ 场模拟对话；11 轮迭代（第 3 轮曾回落——回归是常态，门禁的价值正是抓住它）；
模拟环境幻觉率下降约 90%；离线提升与线上真实流量表现一致**。

**（3）失败回流闭环（DoorDash 反馈闭环四步）**——这是 EDD 从"评分板"升级为"迭代控制面"的关键：

1. **失败聚类成主题**：逐条看失败会"轶事驱动"（最近/最惊奇的失败主导修复）。**rubric 标准天然是问题簇**——
   grounding 失败、缺替代品、糟糕叙述分开调查，失败列表变成按影响排序的主题列表；
2. **从发现到解决**：coding agent 检查失败 trace、相关代码路径、近期变更、历史调查；
   **修复明确时直接起草 PR**；prompt/上下文类改动则产出诊断 + 建议供人审；
3. **Agent Skills 化**：把 eval-driven 工作流（聚类失败、调查失败模式）打包成可重复、可复用、可改进的
   Agent Skills——**skill 分错簇或写出弱修复时，更新 skill 本身，而不是给一次性运行打补丁**；
4. **harness 成为迭代的控制面（control plane for iteration）**：生产监控 + 失败聚类 + agent 辅助调查 +
   发布前验证连成一环。

（badcase 如何结构化归因——RCA 五步、根因标签、行动项——见第 E11 章；
`cd evals-special/labs && python3 eval_lab09_rca_pipeline.py`）

**（4）回流入库的标准（阿里）**：不是每条线上失败都值得进回归集。入库五条标准：
**失败可复现（或至少有稳定 trace + 人工确认）、期望行为明确（可写成规则/judge 标准/人工验收标准）、
根因标签清楚、样本有代表性（覆盖一类问题而非一次性环境抖动）、已脱敏合规**。
一条 badcase 至少生产 3 类反馈（评测集 / 训练数据 / 知识修订），分三条生产线沉淀（详见第 E12 章数据飞轮）。
学术侧的对应样本是 Discord AITL（EMNLP'25 工业赛道，ACL Anthology 2025.emnlp-industry.135）：
四类人工客服在线标注持续回流，把再训练周期从月级压缩到周级，美国试点 recall@75 +11.7%、precision@8 +14.8%、
有用性 +8.4%、采用率 +4.5%。

**（5）仿真器本身也要被评测**：模拟器质量直接决定下游评测效度——DAUS（arxiv 2402.13374，Amazon）
证明未经微调的通用 LLM 模拟器会偏离用户目标、幻觉出不存在的对话事实，需领域微调 + 受控解码；
隐式画像（arxiv 2502.18968）从真实日志反推 persona，与数据飞轮天然衔接；ChatChecker（arxiv 2507.16792）
强调**非合作模拟**（用户会不耐烦、跑题、改主意）——合作型模拟会系统性高估 agent。

### 2.8 eval 作为目标函数与发布阶梯

**（1）从"eval 当裁判"到"eval 当目标"**：2024–2026 年 EDD 的一个重要演进是 prompt/程序优化器
直接以 eval 分数为搜索目标，形成"eval 定义 → 自动优化 → eval 门禁"的闭环：

| 系统 | 论文 | 机制 | 关键数字 |
|---|---|---|---|
| DSPy | arxiv 2310.03714（2023-10） | LLM 程序声明为模块组合，eval metric + 少量标注编译出最优 few-shot/指令配置 | eval-as-objective 闭环的奠基框架 |
| MIPROv2 | arxiv 2406.11695（2024-06） | 贝叶斯优化搜索"指令提案 × 示例组合"，数据感知提案 + 代理评分降本 | 30+ 任务相对最强基线平均约 +5%，部分任务最高约 13% |
| GEPA | arxiv 2507.19457（2025-07） | 反射式进化：采样轨迹 → 自然语言反思失败 → 变异 prompt → **Pareto 前沿按切片保留候选**（不只看平均分） | 比 GRPO 强化学习平均高约 10%（最高 20%），rollouts 最多减少 35 倍，比 MIPROv2 高 10%+ |

工业落地：DoorDash 用 **GEPA 做 judge 校准**——迭代提出 judge prompt 修订，只保留在留出集上
提升与人工标注一致率的版本。GEPA 的 Pareto 选择还隐含一条评测设计原则：**按切片（slice）看指标，
防止平均分掩盖退化**——这与阿里分层指标、腾讯分组报告异曲同工。

**（2）eval 成为目标后的新风险**：eval 集既是测试又是优化目标，就会被拟合与污染。治理三件套：
**留出集**（优化不碰、只作终判）、**定期换血**（防记忆）、**污染防护与 provenance**（EDDOps 把
contamination safeguards 列为评测资产的必备属性）。另一个教训来自平台层：OpenAI 托管 Evals 平台
（2025 年随 AgentKit 推出）在 2026 年宣布下线（2026-10-31 转只读、2026-11-30 关闭）——
**评测资产（数据集 + grader + 用例定义）要用开放格式（JSON/YAML + 代码）托管在自家仓库，与平台解耦**。
OpenAI evaluation best practices 给出的量化目标示例可作参考：摘要 ROUGE-L ≥ 0.40、G-Eval 连贯性 ≥ 80%、
文档问答 recall ≥ 0.85、precision ≥ 0.7、好评率 70%+。

**（3）发布阶梯：offline → shadow → canary → A/B → monitoring**。离线门禁只是第一道闸：

| 阶梯 | 做什么 | 来源定义 |
|---|---|---|
| offline | golden set + 回归集 + 能力集批量评测，统计口径判差异 | 各厂共识 |
| shadow | 新版本与旧版本并行处理同一输入，结果**不暴露给用户**，只对比差异 | EDDOps 明确定义的 shadow evaluation |
| canary | 小流量放量 + 在线指标/内联校验器 + 异常触发探针 | EDDOps / 阿里灰度 |
| A/B | 会话级分流、序贯检验、护栏指标 | 主手册第 8 章 |
| monitoring | 持续抽样评测 + 漂移告警 | 第 E12 章 |

**离线分数的正确定位是"必要不充分"**：arxiv 2510.22143（真实客服对话基准）明确指出，由于部署环境的
分布漂移与交互复杂性，**强 offline 基准成绩只是部署可靠性的弱指标**；而 DoorDash 的经验是离线提升能
兑现到线上，但前提是**离线与线上用同一 rubric + 同一校准 judge**（DoorDash 原则三：各自调 judge，
两边分数会以难调和的方式背离）。阿里的联动规则最硬：**离线提升但线上关键信号恶化 → 触发回滚或降级**，
线上信号包括转人工率、重复追问率、投诉率、满意度、任务完成率、工单闭环率。
arxiv 2603.15676 进一步主张"evidence-driven release"：发布门禁不仅看分数，还看证据充分性——
把评测证据（通过率、幻觉率、升级率）写进发布单。

## 四、经典面试题与参考答案

#### 题 1（基础）：什么是 EDD？它和传统 TDD 有什么异同？为什么 GenAI 特别需要它？

**参考答案：**
EDD（Eval-Driven Development）是 GenAI 版 TDD。Airbnb 的定义是：**不试图预测所有失败，而是
发现→捕获→反复检查失败模式**——先定义期望行为（eval 即规约），再开发和调优系统，评测贯穿开发、
发布、运行全生命周期。与 TDD 的相同点是"测试先行、回归防护、资产沉淀"的纪律内核；不同点在于：
被测对象从确定性代码变成模型+prompt+工具+serving 的概率系统；期望输出从唯一值变成 rubric/终态/分布；
通过标准从断言成立变成统计口径（通过率、pass^k、置信区间）；回归来源从代码变更扩展到任一组件变更。
GenAI 特别需要它，因为缺少 EDD 会掉进三个坑：**虚假信心**（浅层 helpfulness 分）、**未被发现的回归**
（改 prompt 后旧场景悄悄变差）、**指标与产品脱节**（分数涨但产品结果没动）。

#### 题 2（基础）：你的团队目前只在上线前"跑几条 case 感觉还行"。请指出风险，并给出引入 EDD 的最小起步方案。

**参考答案：**
风险有四：① 同一 prompt 跑通一次≠稳定可用（非确定性）；② 每次改 prompt/模型/工具都可能改坏旧场景
且不易第一时间发现；③ 多步链路前段小偏差会被级联放大；④ 存在"结果对但路径错"的假阳性。
最小起步方案（不要求一步到位）：1）**100 样本精读**——跑约 100 条真实/合成 prompt，人工读输出与 trace，
归类失败模式（Airbnb 口径；Anthropic 甚至说 20–50 个真实用例就能起步）；2）围绕失败模式建测试：
能代码判的先代码判（schema/长度/关键词），语义维度建 1–3 个 judge；3）建 50–100 条 gold 集（含坏样本），
把 judge 校准到与人工一致率 ≥85%；4）把用例挂进 CI，PR 触发；5）指定一个人类终判者，拉产品伙伴每周评审错误。
关键话术：EDD 的起点不是平台，是习惯——"When in doubt, look at your data"。

#### 题 3（进阶）：请复述 Airbnb 旅行客服助手的 EDD 全流程，并说明每一步的产出物。

**参考答案：**
四阶段：① **探索**：跑 100 个 prompt 人工精读，发现 15 个 groundedness 失败、8 个正确但啰嗦、
5 个不当拒答、3 个 JSON 失败——产出是失败模式清单；② **建测试**：JSON 与长度用程序化检查，
groundedness/conciseness 各建一个 judge，PM/SME 标注 60 条 gold 集（含失败样本）——产出是可复跑的测试资产；
③ **校准**：judge 初始一致率 78% 过低，分歧分析发现 judge 误罚"正确的改述"，修 rubric 与示例后达 88%；
同期检索改进减少 groundedness 失败——产出是可信的自动化评分器；④ **规模化与监控**：扩到 5,000 样本、
每日抽样 5% 去标识化生产流量、被标记样本送人工、每周 PM 评审新增测试与修复——产出是持续运营的闭环。
加分点：指出该流程体现的原则——指标从观察到的错误推导（原则 2）、judge 少而精（原则 3）、
上线前测试在线上持续运行（十条要点之⑨）。

#### 题 4（进阶）：为什么 GenAI 迭代要"一次只改一个变量"？请设计一个违反该纪律的场景并说明后果。

**参考答案：**
GenAI 系统有 prompt、模型、检索、工具、serving 配置多个旋钮，多变量并动时分数变化无法归因。
Airbnb 的纪律是严格排序：**固定模型只变 prompt → 固定 prompt 只变模型 → 都固定只变 serving 配置**；
EDDOps 的表述是"最小有效变更优先"（先 prompt/路由/护栏/记忆，后架构/工具契约/检索/模型）。
反例：团队同日上线 prompt v2 + 新底座模型，总分 +3 分宣布成功；两周后投诉上升，拆解发现
prompt v2 实际 +8、新模型实际 -5——捆绑变更让他们既错过发现模型退化，也无法单独保留 prompt 收益，
回滚时更不知道回滚哪个。配套要求：版本比较要带统计口径（置信区间 + 显著性 + 最小可感知变化阈值，
阿里口径"门禁不只看差了多少，还看差异是否超过统计噪声"），否则单变量比较也会被噪声欺骗。

#### 题 5（进阶）：capability 套件与 regression 套件有什么区别？各自的通过率应该长什么样？如何设定发布门槛？

**参考答案：**
二者回答不同问题：**capability 套件**问"agent 能把什么做好"，是目标山峰，初始通过率应偏低
（腾讯口径 20–50% 起步），用于指引改进方向、主动拓展、频繁迭代；**regression 套件**问"原有能力是否还在"，
是防御地板，应接近满分，掉分即阻断，只增不减、CI 每次运行。若 capability 起步就接近满分说明套件无区分度；
regression 出现 0%/100% 怪值先怀疑任务定义或评分器坏了（腾讯诊断经验）。发布门槛数字：
Anthropic 推荐**确定性任务用例集整体 100%、非确定性任务 ≥95%**；腾讯按使用类型分级容忍：
关键决策类 0% 容忍、辅助分析类 ≤10%、创意生成类 ≤40%（N=5）。高风险不可逆场景用 pass^k 作门槛
（p=0.75 时 pass^3≈42%）。机制上配"毕业"：capability 用例稳定 100% 后转入回归集，回归集滚雪球式承接。

#### 题 6（进阶）：你的 judge 与人工一致率停在 78%，团队认为"差不多能用"，想直接进 CI。你怎么看？怎么排查？

**参考答案：**
不能进。未校准的 judge 会制造**误导性信心**——它系统性误判的样本会让 CI 的通过/失败与真实质量脱钩，
比没有门禁更危险。各厂口径一致：Airbnb 目标 high-80s~90s%，阿里 ~85% 后进自动化，腾讯 ≥85% 才可用。
排查步骤（Airbnb 案例就是模板）：1）确认 gold 集含坏样本与边界样本（只喂好样本测不出误杀）；
2）按错误类型分解分歧矩阵——78% 的缺口集中在哪类样本；3）典型发现：judge 在**误罚"正确的改述"**
（字面重叠式 rubric 惩罚了语义正确的不同表述），或放过"流畅的错误"；4）修 rubric 与 few-shot 示例
（放宽改述惩罚、加事实核对项），重跑到 ≥85%；5）进 CI 后仍要持续运营：judge prompt/模型升级时重新产出
三项统计（与人工一致性、高风险漏判率、边界稳定性），维护 judge 金标校准集。
（动手复现：`cd evals-special/labs && python3 eval_lab05_judge_calibration.py`）

#### 题 7（进阶）：CI 回归集中一条原本稳定通过的用例这次失败了。给出你的排查路径与"是否阻断合并"的判断依据。

**参考答案：**
按"先怀疑尺子、再怀疑环境、最后怀疑代码"的顺序：① **评分器自身**——judge 模型/prompt 是否升级、
rubric 是否改过（Anthropic 的 CORE-Bench 案例：修复任务与评分器后 Opus 4.5 从 42%→95%，尺子坏的代价极大）；
② **环境漂移**——工具返回、外部数据、mock 是否与生产分叉（mock drift），用例是否依赖了时变状态；
③ **非确定性**——重跑 N 次看是否 flaky（腾讯：N=5 中 1/5 失败=存在幻觉按类型判断，5/5 失败才是稳定失败）；
④ **真实回归**——以上都排除，才认定本次变更引入回归，定位到具体 diff。阻断判断：regression 套件的
设计语义就是"掉分即阻断"，确认是真实回归必须 block；若确认是 flaky/评分器问题，隔离该用例并记录，
不让噪声长期阻塞开发，也不假装噪声不存在。无论哪种结论，处理过程要沉淀：真实回归修复后该用例继续守门，
评分器问题则修 judge 并重新校准——回归集的每一次报警都是体系变厚的机会。

#### 题 8（系统设计）：为一个从零开始的客服 Agent 设计 EDD 落地方案（含 90 天路线图、套件设计、CI 门禁与闭环运营）。

**参考答案：**
分三个阶段。**0–30 天（立习惯）**：100 样本人工精读归类失败模式；与产品定北极星指标与 launch gates
（Airbnb 原则 1/5）；建 50–200 条 golden set 覆盖核心路径与高风险边界（含负向用例：不当拒答/过度触发/越权）；
程序化检查（schema/长度/关键词/工具断言）先行，语义维度建 3–5 个 judge；标注 50–100 gold（含坏样本）
校准 judge 到 ≥85%；指定一名人类终判者。**30–60 天（立门禁）**：套件二分——capability 套件
（起步 20–50%，指方向）+ regression 套件（近满分，掉分阻断）；CI 接入：prompt 变更 PR 触发回归、
模型升级手动验证兼容性、每周全量巡检；门槛：确定性 100%/非确定性 ≥95%，关键决策类用 pass^k（k=3~8），
版本比较带置信区间与最小可感知变化阈值；分层控制成本：断言层每次 PR、轨迹层每日、E2E 模拟按需
（模拟器 + fixtures 冻结外部状态，50 场景 × 8 trials 参考 DoorDash 20 分钟跑完）。**60–90 天（立闭环）**：
每日抽样 5% 去标识化生产流量跑同一 rubric + 同一校准 judge（离线线上同口径）；失败按 rubric 标准聚类，
高影响簇转 badcase 任务：RCA 定根因 → 修 → 入库防回归（入库五标准：可复现/期望明确/根因清楚/代表性/已脱敏）；
capability 用例稳定 100% 毕业进回归集；每周 PM 评审错误与新增测试。发布走 offline → shadow → canary → A/B
阶梯，离线升线上降即回滚。90 天的交付物：可复跑的用例库、judge 校准集、回归集、CI 流水线、每周评审机制。

#### 题 9（系统设计）：团队想用 GEPA/MIPROv2 类优化器以 eval 分数为目标自动搜索 prompt。请评估收益与风险，并给出治理方案。

**参考答案：**
**收益**：把 EDD 的"人工调 prompt"升级为自动搜索。MIPROv2 用贝叶斯优化搜索指令×示例组合
（30+ 任务平均约 +5%、最高约 13%）；GEPA 做反射式进化（采样轨迹→自然语言反思→变异→Pareto 前沿
按切片保留候选），比 GRPO 强化学习平均高约 10%（最高 20%）、rollouts 最多省 35 倍。
DoorDash 已用 GEPA 校准 judge prompt（只保留在留出集上提升人机一致率的修订）。
**风险**：eval 集从裁判变成优化目标，就会被拟合与污染——分数涨可能只是对评测集的记忆；
平均分优化会掩盖切片退化；judge 本身也可能被"钻空子"（固定话术骗过 rubric）。
**治理**：1）三份数据分离——优化集、留出验证集（优化器不可见）、盲测集（版本发布终判）；
2）按 slice 报告（任务类型/难度/用户群），任一关键切片退化即否决（GEPA 的 Pareto 选择即此思想）；
3）评测资产带 provenance 与污染防护，定期换血（EDDOps 把 contamination safeguards 列为必备属性）；
4）优化产物必须过完整门禁（回归集 + pass^k + 安全用例）并走 shadow/canary 才上线；
5）对"通过但可疑"的样本做轨迹审计，防 specification gaming。一句话：optimizer 越强，eval 集的治理越要像
保护训练数据一样严格。

#### 题 10（进阶）：有人说"离线评测做得再好，线上还是会翻车，所以离线评测没用"。请用 EDD 视角反驳并给出正确姿势。

**参考答案：**
这个说法把"必要不充分"误读成"无用"。证据链两面都要摆：一方面 arxiv 2510.22143 确实指出强 offline 基准
只是部署可靠性的弱指标（分布漂移 + 交互复杂性），EDDOps 综述也发现学术评测 93.28% 停留在 pre-deployment；
另一方面 DoorDash 报告离线模拟提升与线上真实流量一致，前提是工程做对了三件事。正确姿势：
1）**离线是必要不充分**——它是唯一能在发布前廉价拦截回归的手段（回归集只增不减 + PR 触发，
把"未被发现的回归"这个最贵的坑堵死）；2）**离线-线上同口径**——同一 rubric + 同一校准 judge 两边跑
（DoorDash 原则三：各自调 judge，分数会以难调和的方式背离）；3）**补上最后一公里**——
offline → shadow → canary → A/B → monitoring 发布阶梯，线上信号（转人工率、投诉率、任务完成率）
持续回流，离线升线上降即回滚（阿里口径）；4）**线上失败回流成离线用例**，让离线集分布持续逼近真实分布。
结论：离线翻车不是离线评测的失败，而是"只做离线"的失败——EDD 的答案是把离线、在线、回流连成一个环。

## 五、易错点 · 反直觉点

1. **误区：EDD = 上线前把评测跑一遍。**
   真相：EDD 的评测贯穿 Plan/Build/Run/Analyze 全生命周期；EDDOps 综述显示工业界 40.74% 已是持续评测，
   学术 93.28% 停留在 pre-deployment 正是被批评的错位。上线前的测试上线后要持续运行（Airbnb 十条要点之⑨）。
   → 记忆锚点：**评测是生命周期，不是检查点。**

2. **误区：所有评测集通过率越高越好。**
   真相：capability 套件初始就应偏低（20–50% 起步，是目标山峰），regression 套件才要求近满分（防御地板）。
   两个套件混在一起谈通过率，会同时失去方向感和安全感。
   → 记忆锚点：**能力集是山峰，回归集是地板。**

3. **误区：prompt 和模型一起改，总分涨了就是赢。**
   真相：捆绑变更放弃归因——你不知道收益来自谁、退化藏在哪，回滚都无从下手。一次一变量：
   prompt → 模型 → serving 配置的顺序。
   → 记忆锚点：**多变量并动 = 主动放弃归因。**

4. **误区：judge 建得越多越保险。**
   真相：Airbnb 原则是 3–5 个**经校准**的 judge 好过一堆嘈杂的评估器；未校准的 judge 数量再多，
   制造的也是误导性信心，且每个 judge 都是要维护、要重校准的负债。
   → 记忆锚点：**judge 贵精不贵多，不校准不信任。**

5. **误区：回归集里长期通过的用例可以删掉省成本。**
   真相：回归集只增不减。正确降本姿势是"毕业降级"——稳定多版本通过且低风险的用例降级为抽样集（阿里样本治理），
   而不是删除；删除等于把历史教训清零。
   → 记忆锚点：**回归集只增不减，降本靠降级不靠删除。**

6. **误区：judge 一致率 78% "差不多能用"，先进 CI 再说。**
   真相：78% 的 judge 在 Airbnb 案例里被查出系统性误罚"正确的改述"——它惩罚的恰是高质量输出。
   各家口径一致：high-80s~90s（Airbnb）、~85%（阿里）、≥85%（腾讯）才可进自动化。
   → 记忆锚点：**judge 的错比模型的错更隐蔽，先修尺子再量布。**

7. **误区：离线评测全绿 = 可以发布。**
   真相：离线是必要不充分条件——真实分布漂移与交互复杂性让强离线成绩只是部署可靠性的弱指标
   （arxiv 2510.22143）。必须补 shadow/canary/线上监控，且离线线上同一 rubric 同一 judge。
   → 记忆锚点：**离线全绿只是拿到了发布资格，不是发布令。**

8. **误区：eval 成了优化目标（GEPA/MIPROv2）之后，原来那份 eval 集照常当裁判。**
   真相：被优化的 eval 集会被拟合与污染，必须留出集/定期换血/污染防护三件套，
   并用优化器从未见过的盲测集做终判。
   → 记忆锚点：**既当裁判又当考题的卷子，必须轮换。**

9. **误区：CI 门禁越严越好，每个 PR 都跑全量 E2E。**
   真相：全量 E2E 昂贵且 flaky，会把团队拖垮或逼出"跳过门禁"的坏习惯。正解是分层门禁：
   确定性断言每次 PR 必过、轨迹层每日全量、E2E 模拟按预算抽样或定时跑（DoorDash 靠模拟器把
   6+ 小时压到 20 分钟才撑得起全量）。
   → 记忆锚点：**门禁分层：快的守门，贵的巡场。**

10. **误区：发布门槛看 pass@1 或平均通过率。**
    真相：pass@1 衡量"多试几次能不能成"，生产无人值守要的是 pass^k（每次都成）。p=0.75 的 agent
    pass^3 只有 ≈42%；τ-bench 上 GPT-4o retail pass^1 ≈60%（官方榜单 60.4%），pass^8 ≈25%。
    → 记忆锚点：**demo 看 pass@k，上线看 pass^k。**

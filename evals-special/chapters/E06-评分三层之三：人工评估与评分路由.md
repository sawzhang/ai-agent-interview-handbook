# 第 E06 章 · 评分三层之三：人工评估与评分路由

> 一句话导读：在「规则 → Judge → 人工」的三层评分体系里，人工是最贵、最慢、最不可扩展的一层，却也是唯一能**产出新口径**、**裁决自动评分器**的一层。本章回答四个问题：人力该花在哪些工作（六个高杠杆场景）、标注工程怎么做（指南/分歧/一致性）、哪些样本值得送人工（评分路由）、人工结论如何放大（反哺闭环）。学完你能设计一套完整的人机协同评分流水线，并扛住系统设计级的追问。

前置阅读：第 E04 章 · 程序化评分（规则层）、第 E05 章 · LLM-as-Judge 深入（Judge 层）。本章是评分三层的收口篇——三层不是并列的三选一，而是**一条有路由、有反哺的流水线**，人工站在流水线的两个关键位置：校准入口与冲突出口。

## 二、核心概念精讲

### 2.1 定位：人工是评分系统的「校准源」，不是「打分主力」

三层的分工原则，阿里的一句话最凝练：**规则主判，Judge 辅助，人工兜底**。规则看"硬条件"（工具、状态、字段、禁用动作），LLM 看"语义/策略合理性"，能写成代码的由规则主判；高风险/抽检/低置信/变更观察期追加 LLM Judge；**能自动稳定判断的不长期依赖人工**（阿里）。腾讯给出同样的优先级：确定性 > Rubric > 人工。

为什么"人工全量打分"是反模式？三笔账：

1. **成本账**：人工评分是分钟-小时级/人力成本，而自动评分是毫秒-秒级。腾讯的痛点表写得很直白：Skill 越多、模型越快，人肉回归指数增长，只能选择性验证、留下盲区。DoorDash 的数字更具冲击力——全量回归从手工 **6+ 小时压到自动约 20 分钟**（50 场景 × 8 trials = 400 次对话的 sweep）。
2. **规模账**：日常打分的样本量是生产流量级的。DoorDash 从"平均 1 条/天员工反馈"做到"**2,000 个/天自动评分会话**"，靠的是校准过的 Judge 而不是扩招标注员。
3. **杠杆账**：专家最稀缺的能力是"判断什么是好"，而不是"重复判断"。把专家耗在逐条打分上，等于用最贵的资源做最可替代的工作。

由此得到三条被多家公司验证的经验法则：

| 公司 | 人工定位的表述 |
|---|---|
| 腾讯 | 能自动化的坚决不找专家；**专家时间 60%+ 花在"校准 LLM 评委"与"诊断异常"** |
| DoorDash | 人工用在杠杆最大处：**定 rubric、标注校准集、审计 judge 行为**；打分主力是 judge |
| Airbnb | EDD 原则之一：**指定一个最终人类决策者**，裁决"好 vs 坏"争议；人工负责建 ground truth、安全高风险决策、细微差别与创意、解决自动评估器间冲突 |
| 阿里 | 人工兜底：定口径、校准 Judge、处理争议样本、抽查高风险场景；能自动稳定判断的不长期依赖人工 |

注意这四家的表述殊途同归：**人工评估的成熟度，不看"能动员多少人打分"，而看"自动化评分器以多小的人力投入变得可信"**。人工不是评分系统的执行层，而是它的校准源与仲裁庭。

### 2.2 人工评估的六个高杠杆场景

腾讯把"人工必须出场"的场景收敛为六个，这是本章的主干清单：

| # | 场景 | 做什么 | 关键数字/做法 |
|---|---|---|---|
| ① | **校准 LLM 评委**（最核心） | 抽样一批人工先判，量化 judge 与人的一致率 | 抽样 **100–200 条**对齐；**一致率 ≥85% 才可用**（腾讯）；阿里口径 ~85% 后进日常自动化 |
| ② | **主观任务打分** | 语气、清晰度、解释质量等无法程序化的维度 | Rubric + 人工抽样；体验与对齐维度（P2）早期靠 Rubric+人工，成熟后转 A/B+用户反馈 |
| ③ | **诊断通过率异常** | 通过率 **0% 或 100% 通常是任务/评分器坏了，不是模型弱** | 0% pass^N 一般先查任务定义与评分器，而不是怀疑模型能力 |
| ④ | **建 Ground Truth** | 新评测套件先产出参考解，作为后续自动评分的锚 | 前 **20–50 个参考解**（腾讯）；基线快照机制：执行 1 次 → 人工确认过程与结果 → 快照成为基线 |
| ⑤ | **Trace 采样审查** | 每周固定抽样读轨迹，找自动评分器看不见的隐藏失败模式 | 与 Airbnb "When in doubt, look at your data"（约 100 样本人工精读输出与 trace）同构 |
| ⑥ | **高风险兜底** | 医疗/金融/安全类场景 **100% 人工复核** | 阿里补充：赔付/隐私/合规/投诉升级，**自动通过的也要定期人工复核** |

六个场景的内在结构值得记住：**①④ 是为自动化评分器"造尺子"，③⑤ 是给自动化评分器"质检"，②⑥ 是自动化永远不该独自碰的领域**。

再叠上另外两家的清单，覆盖面更完整：

- **Airbnb 的人工四用途**：建 ground truth；安全高风险决策；**细微差别与创意**（nuance & creativity）；**解决自动评估器间冲突**——最后一条是"多 judge 分歧进人工"这个路由规则的方法论来源。
- **阿里的适用环节**：① 新建评测集**定口径**——例如"订单已发货 + 用户拒收 + 运费险 + 特殊类目"该走哪条流程，需要业务先定，这不是模型问题也不是评分器问题，是业务规则问题；② 校准 Judge——"judge 能判礼貌/清晰，但判不了'叠加优惠差价是否应补偿'这类依赖内部政策的问题"；③ 处理争议样本；④ 抽查高风险场景。

一个面试可以直接复述的判断框架：**凡是答案依赖"内部政策、业务口径、价值排序"的样本，自动评分器天然无权裁决——因为它们的训练分布里没有你的内部政策**。这类样本永远要路由给人（见 2.6 分工决策表）。

**各场景的操作要点**（面试追问"具体怎么做"时的得分点）：

- **① 校准 Judge**：校准样本要覆盖各分段与边界案例；人工对校准集的判定结论本身要版本化存档——它是后续每次 judge 升级对照的金标。
- **② 主观任务打分**：给标注员的 rubric 要写行为锚点（"什么样的回复算简洁"），而不是"质量好/一般/差"这类抽象词；每次打分输出 reason，供他人复核与后续分歧分析。
- **③ 异常诊断**：标准动作是分层抽样 10–20 条逐条精读，读的是输入、输出、trace 三件套而非只读输出；对照旧版本被评系统重跑，区分"模型变了"还是"尺子变了"。
- **④ Ground Truth**：参考解不只记最终答案，还记关键过程（工具调用序列、中间产物）。腾讯的基线快照机制是标准做法：用例先执行 1 次 → 人工审核过程与结果 → 不可接受则修后重跑 → 可接受则该次快照成为基线，后续每次执行与基线对比；Agent/Skill 逻辑变更、模型升级或用例本身修改时重新快照。
- **⑤ Trace 采样**：固定节奏（每周）+ 固定抽样率，重点读两类样本——自动评分器打高分的（防"结果看似对但路径已偏离"的假阳性，阿里明确要求为此加过程型与风险型检查，轨迹评估细节详见第 E07 章 · 轨迹与 Agent 级评估）与用户反馈差的。
- **⑥ 高风险兜底**：复核结论要留痕（复核人、依据、rubric 版本）进审计日志；"自动通过也要定期复核"要排期化，不能靠临时起意。

### 2.3 Judge 校准：人工评估的第一任务

**为什么校准排在第一位？** 两句话足够：

- Airbnb：**未校准的 judge 会制造误导性信心**——分数看起来在涨，可能只是尺子变松了。
- DoorDash：**"LLM Judge only useful if it agrees with human reviewers."** Judge 的全部合法性来自与人工判断的一致性。

**Airbnb 的校准五步法**（本章必须能默写的流程）：

1. 建 **50–100 条 gold set**，**必须含坏样本**——只有好样本的校准集测不出 judge 的误罚倾向；
2. 用 judge 跑该集合；
3. 看一致率，目标 **high 80s ~ 90s%**；分歧程度可用 **Cohen's kappa / Krippendorff's alpha** 度量；
4. 逐条检查分歧 → 改 rubric / 改 few-shot 示例 → 重复第 2 步；
5. **失败模式变化时重新校准**——校准不是一次性动作。

**实战案例（Airbnb 旅行平台客服政策问答助手）**：PM/SME 标注 **60 条 gold（含失败样本）**；judge 初始一致率 **78%（过低）**——分歧分析发现 **judge 误罚了正确的改述**（语义正确但字面不同于参考答案的回答被扣分）；修 rubric 与示例后一致率达 **88%**；同期检索改进减少了 groundedness 失败。这个案例的价值在于展示校准循环的完整收益链：**人工标注 → 暴露 judge 缺陷 → 修 rubric → judge 可信 → 规模化打分**（该助手随后扩到 5,000 样本、每日抽 5% 去标识化生产流量）。

**四家校准线对照**（面试高频数字题）：

| 公司 | 一致率口径 | 说明 |
|---|---|---|
| Airbnb | 目标 **high 80s ~ 90s** | 配 Cohen's κ / Krippendorff's α 度量分歧 |
| 腾讯 | **≥85% 才可用** | 抽样 100–200 条对齐 |
| 阿里 | **~85%（参考值）后进日常自动化** | 升级时还要看高风险漏判率、边界稳定性 |
| DoorDash | 与人工标注一致才放量 | 用 GEPA 自动优化 judge prompt（见下） |

三家独立给出 85% 上下的阈值，可以视为行业经验收敛值。注意表述的严谨性：这是**经验线不是统计定律**——门槛的实质是"judge 与专家的分歧 ≤ 专家之间的分歧"（主手册第 8 章 · Agent 评估与可观测性 对这一判据有展开）。

**分歧怎么分解**：第 4 步的"检查分歧"不是逐条重标一遍，实用做法是先把分歧样本按方向分桶，再对症下药：

| 分歧类型 | 表现 | 典型病因 | 修复动作 |
|---|---|---|---|
| Judge 偏严 | 把正确答案判错 | rubric 措辞过窄、过度依赖字面匹配 | 放宽 rubric 措辞、补"正确改述"的正向 few-shot（Airbnb 78%→88% 案例即此型） |
| Judge 偏松 | 把错误答案放过 | 缺事实核对项、被流畅性迷惑 | 加事实核对检查项、补"流畅的错误"负例 |
| 边界真分歧 | 人也拿不准 | rubric 对该情形没有规定 | 走 2.4 的分歧处理：裁决后写回 rubric |

分桶的价值在于：前两类改的是 judge（rubric/示例），第三类改的是口径本身——修复路径完全不同，混在一起处理会反复返工。

**校准的自动化：GEPA（DoorDash 实践）**。人工校准的瓶颈是"改 rubric 靠人试"，DoorDash 把这一步交给了反射式 prompt 优化器 **GEPA**（arXiv 2507.19457，2025）：对候选 prompt 采样运行 → 用自然语言反思诊断失败 → 变异生成新 prompt → 按 **Pareto 前沿**在多个任务切片上保留候选（而非只看平均分）。落到 judge 校准上：**GEPA 迭代提出 judge prompt 修订，只保留在留出集上提升与人工标注一致率的版本**。这等于把"分析分歧 → 改 rubric → 重测"的人工循环部分自动化，人工退到"标注留出集 + 审计修订方向"的位置。GEPA 原论文报告其样本效率比 GRPO 强化学习高约 35 倍量级（详见第 E10 章 · 评测驱动开发）。

**校准是持续运营，不是一次验收**（阿里）：维护 **Judge 金标校准集**；每次 judge prompt/模型升级固定产出三类统计：

1. **与人工标注一致性**（一致率，或多模型对抗 Kappa）；
2. **高风险样本漏判率**（合规/资损/隐私——这类样本漏判一个的代价远超平均分波动）；
3. **边界样本稳定性**（重复评测的波动幅度）。

何时触发重新校准？把三家的触发条件合并成一张清单：**rubric 演进/新增能力**（DoorDash）、**失败模式变化**（Airbnb）、**judge prompt 或模型升级**（阿里）。三者任一发生，旧校准结论作废。

### 2.4 标注工程：指南、分歧与标注者间一致性

人工评估的可信度不取决于"专家多厉害"，而取决于标注工程的四个要素：**指南、分歧处理、一致性度量、规模化路径**。

**（1）标注指南 / rubric 先于标注员。** Airbnb 的判断标准一针见血：**"如果人都无法一致地应用 rubric，模型也不可能。"** 标注指南不是评分的辅助文档，而是整个评分体系（人工 + judge）的单一事实来源。DoorDash 进一步要求每条标准写成"**从会话本身可验证**"——同一条 rubric 既供人工校准使用，又供 judge 规模化使用（第 E05 章 · LLM-as-Judge 深入 对 rubric 工程有完整展开，含 Airbnb 房源 listing 语气 0/1 判定的完整实例）。rubric 写得好不好，有一个廉价的检验方法：让两个专家各自独立按指南标一批样本，看一致率——**IAA 低首先是 rubric 的问题，不是人的问题**。

**（2）专家分歧处理：先停下，解决分歧再自动化。** Airbnb 的纪律是：**专家有分歧就先停下解决分歧再自动化**。这条纪律背后的逻辑：专家分歧通常不是随机噪声，而是**口径未定义的信号**——两个专家各自在用指南没覆盖的隐含标准。此时强行自动化（取多数、平均、或交给 judge），等于把未定义的口径固化成系统性偏差。正确流程是把分歧样本摆上桌 → 辩论出裁决 → **把裁决写回 rubric** → 再标下一批。这个"分歧 → 口径"的转化过程，正是 2.7 反哺闭环在标注阶段的形态。

**（3）标注者间一致性（IAA, Inter-Annotator Agreement）的度量。** Airbnb 校准流程中点名的两个指标：

| 指标 | 适用 | 直觉 |
|---|---|---|
| Cohen's kappa | 两位标注者的分类一致性 | 一致率扣除"瞎猜也能一致"的基线后剩下的比例；κ=1 完全一致，κ≤0 等同于乱猜 |
| Krippendorff's alpha | 多标注者、多种数据类型（分类/有序/连续） | κ 的泛化版，标注员数量与缺失标注都能处理 |

IAA 有**双重身份**：它既是标注质量的度量，更是 **rubric 质量**的度量。IAA 低 → 先修 rubric 再谈换人、再谈自动化。同时，IAA 也给出了 judge 校准目标的天花板参照：judge 与人的目标一致率定在 high 80s ~ 90s 而非 100%，部分原因正是**人与人之间也做不到 100%**（详见易错点 10）。

**κ 的手算示例**（面试计算题高频形态）。设人工专家与 judge 对 100 条样本独立做 pass/fail 判定，混淆矩阵如下：

```text
                人工：pass   人工：fail
Judge：pass        72           8
Judge：fail         6          14
```

- 观察一致率 P_o = (72+14)/100 = **86%**；
- 期望机遇一致率 P_e = P(judge pass)×P(人工 pass) + P(judge fail)×P(人工 fail) = 0.80×0.78 + 0.20×0.22 = **0.668**；
- Cohen's κ = (P_o − P_e) / (1 − P_e) = (0.86 − 0.668) / (1 − 0.668) ≈ **0.58**。

解读这个反差：一致率 86% 看起来踩线达标，κ=0.58 却说明一致的大半来自"大多数样本本来就 pass"的基础率，judge 的真实判别力有限——单看 fail 行，人工判 fail 的 22 条里 judge 只抓到 14 条，**漏判率约 36%**。这正是分布偏斜场景的典型失真：一致率与 κ 讲的是两个故事，而真正致命的那个数字（坏样本漏判）两者都没直接回答。所以阿里的 judge 升级统计把**高风险样本漏判率**单列成项——校准报告里它必须与一致率并排出现。

**（4）规模化路径：先小后大，先专家后队伍。** 四家的起步规模惊人一致：

| 公司 | 起步规模 | 扩张条件 |
|---|---|---|
| Airbnb | **20–100 个专家标注样本**起步 | **rubric 稳定且需要规模时**才扩大标注队伍 |
| 腾讯 | 新套件前 **20–50 个参考解** | 通过率稳定后用例"毕业"进回归集 |
| 阿里 | 先做 **50–200 条**高质量 golden set | 成熟后扩展分类采样集、长尾集、对抗集、线上回流集 |
| DoorDash | rubric + 校准集 + 参考解 | 校准一致率达标后 judge 放量到每天 2,000 会话 |

顺序不能颠倒：**先用少量专家把 rubric 磨稳定，再扩队伍**。提前规模化标注的后果是：一群标注员按一份含糊的指南生产大批量低质标签，返工成本远高于前期慢慢磨 rubric。

**（5）gold set 必须含坏样本。** 这是 Airbnb 十条要点之一。校准集的构成要刻意覆盖三类"陷阱样本"：

- **流畅的错误**：语言漂亮但事实错误——测 judge 是否被流畅性迷惑；
- **正确的改述**：语义正确但字面不同于参考答案——测 judge 是否过度依赖字面匹配（Airbnb 78%→88% 案例的病灶正是这里）；
- **边界样本**：刚好踩在 rubric 判定线上的样本——它们决定 judge 的判定边界画在哪。

**（6）隐私与合规。** Airbnb 明确：生产流量抽样送人工评审前必须**去标识化**，且**用途限定于安全与质量**。这不是可选项——任何把未脱敏生产会话直接丢给标注团队的流程，在合规审查处直接死亡（数据飞轮的合规红线详见第 E12 章 · 在线评估与数据飞轮）。

### 2.5 人工评分路由：不是「分数低」才配进人工

三层评分流水线真正的设计难点不在每一层怎么评，而在**层与层之间怎么流转**。阿里给出了完整的分层筛查架构：

```
粗筛层（低成本快速分流）          精判层（确认 badcase）          人工复核层（终判）
规则 Scorer + 轻量 Judge    →    完整规则 + Judge          →    高风险 / 低置信 /
明显通过 / 明显失败 / 存疑        产出：问题分类、问题现象、       冲突 / 口径未固化
                                  置信度、判定依据
```

关键设计：**评分输出不止 pass/fail**。精判层必须同时产出**问题分类（现象层：如事实性错误/答非所问/过度承诺）、问题现象、置信度、判定依据**——为下游 RCA 提供"现象入口"（第 E11 章 · Badcase 根因分析与优化闭环）。对路由而言，这四个字段里的**置信度与判定依据（reason）是路由信号的直接来源**：没有它们，下表的六类触发条件有一半无法实现。

**人工评分路由的六类触发条件**（阿里的核心贡献，也是本章的面试题眼）：

| # | 触发信号 | 具体含义 | 捕获什么问题 |
|---|---|---|---|
| ① | **边界分** | 自动得分落在阈值附近的灰区 | 阈值误判风险最高的样本 |
| ② | **低置信** | 评分器自己输出的置信度低 | 评分器"知道自己不确定" |
| ③ | **reason 含糊** | judge 给了分但判定依据含糊、不可复核 | judge 在"猜"而不是"判" |
| ④ | **多 judge 分歧** | 多个 judge 结论互相冲突 | 口径模糊或样本本身难（呼应 Airbnb"解决自动评估器间冲突"） |
| ⑤ | **新版本上线抽样** | 新模型 / 新 Prompt / 新工具 Schema / 新活动上线，按抽样率送人工 | 分布漂移：旧评分器对新版本是"盲"的 |
| ⑥ | **规则与 Judge 冲突** | 两层结论不一致 | 口径缺口 → **人工终判并回收口径** |

**为什么"只看分数阈值"不够？** 这是路由设计最常见的简化，必须能说出它漏掉的三类信号：

1. **低分 ≠ 不确定**。一个样本被规则高置信判 fail（如 JSON 损坏、禁用工具被调用），失败得明明白白，不需要人工——它需要的是修复，不是复核。反过来，一个 0.49 分的边界样本比一个 0.05 分的样本更值得人工看。
2. **分数捕捉不到"评分器自身的不确定性"**。置信度、reason 质量、judge 间分歧，都是分数之外的元信号——它们度量的是"尺子可不可靠"，而不仅是"样本好不好"。
3. **分数捕捉不到"分布漂移"**。新模型/新 prompt/新 schema 上线时，旧评分器可能整体失准但分数看起来正常——此时唯一可靠的策略是**按抽样率主动送人工**（阿里的"变更观察期"），用人工结论反过来校验评分器是否还有效。这与主动学习思路一致：阿里在样本治理中明确，新分布出现时**优先抽取低置信/高影响/新意图/新工具/新知识点样本进人工确认**。

路由逻辑可以直接写成代码：

```python
def route_to_human(sample, rule_verdict, judge_verdicts, context) -> bool:
    # —— 第一类：不确定性信号 ——
    if is_borderline(rule_verdict.score, gate_threshold):       # ① 边界分
        return True
    if max_confidence(rule_verdict, judge_verdicts) < CONF_MIN: # ② 低置信
        return True
    if is_vague(judge_verdicts[0].reason):                      # ③ reason 含糊
        return True
    if len({v.verdict for v in judge_verdicts}) > 1:            # ④ 多 judge 分歧
        return True
    # —— 第二类：漂移信号 ——
    if context.recent_change and sampled(context.audit_rate):   # ⑤ 新模型/新prompt/
        return True                                             #    新schema/新活动抽样
    # —— 第三类：冲突信号 ——
    if rule_verdict.verdict != judge_verdicts[0].verdict:       # ⑥ 规则 vs Judge 冲突
        return True                                             #    人工终判 + 回收口径
    return False
```

**用 5 条样本走一遍路由决策**（判断每条命中哪类信号）：

| 样本 | 规则层 | Judge 层 | 置信/reason | 上下文 | 路由结果 |
|---|---|---|---|---|---|
| A | fail（0.02，JSON 损坏） | 未触发 | 高置信 | 常规 | **自动**：明确失败，送修复不送人工 |
| B | 0.49（门禁线 0.50） | pass（0.6） | — | 常规 | **人工**：① 边界分 |
| C | pass | pass | reason："整体感觉还行" | 常规 | **人工**：③ reason 含糊，不可复核 |
| D | pass | judge1=pass，judge2=fail | — | 常规 | **人工**：④ 多 judge 分歧 |
| E | pass | pass（0.9），reason 完整 | — | 新 prompt 上线第 2 天，命中抽样 | **人工**：⑤ 新版本观察期抽样 |

注意样本 A 与 E 的对照：A 分数极低但无人工必要，E 分数很高且 reason 完整却必须进人工——**路由的依据从来不是分数高低，而是信号的类别**。

两个工程细节值得在面试中主动补充：

- **路由率本身要监控**。送人工比例突然飙升，通常意味着评分器坏了或分布漂移了（与"0%/100% 异常"同理）；路由率长期为零，则可能是阈值设得太松，路由形同虚设。
- **线上抽样是路由的最大进料口**。Airbnb 每日抽样 **5% 去标识化生产流量**，跑检查与 judge 后**标记样本送人工**，每周 PM 评审——在线评估与人工路由共用同一套打分口径（DoorDash 原则：离线与线上同一 rubric + 同一校准 judge，两边分数才可对齐；详见第 E12 章 · 在线评估与数据飞轮）。

### 2.6 人机分工决策表：什么永远留给人

把前面各节的结论汇总成一张可直接用于系统设计的决策表：

| 判断对象 | 谁评 | 理由 | 出处 |
|---|---|---|---|
| 硬条件：工具调用、状态、字段、禁用动作 | **规则** | 确定性、毫秒级、100% 稳定 | 阿里/腾讯 |
| 通用语义：礼貌、清晰、连贯、groundedness | **Judge**（校准后） | 可规模化；"judge 能判礼貌/清晰" | 阿里 |
| 内部政策口径："已发货+拒收+运费险+特殊类目走哪条流程" | **人（业务定口径）** | 答案不在任何模型的训练分布里 | 阿里 |
| 依赖内部政策的判断："叠加优惠差价是否应补偿" | **人** | judge 判不了政策依赖型问题 | 阿里 |
| 价值判断与"好 vs 坏"争议 | **指定的人类终判者** | 争议需要唯一裁决人，否则无限循环 | Airbnb EDD 原则 4 |
| 高风险：医疗/金融/安全 | **人 100% 复核** | 单次误判代价不可接受 | 腾讯 |
| 高风险运营：赔付/隐私/合规/投诉升级 | **人（自动通过也定期复核）** | 自动通过 ≠ 无需审计 | 阿里 |
| 细微差别与创意 | **人** | rubric 难以穷举"好品味" | Airbnb |
| 自动评分器间冲突 | **人仲裁** | 冲突=口径缺口，需权威裁决并回收口径 | Airbnb/阿里 |
| 通过率 0%/100% 异常诊断 | **人** | 先怀疑任务与评分器 | 腾讯 |

从表中可以提炼出**永远留给人的三类维度**：

1. **政策口径**——业务规则的定义权不属于任何自动评分器；
2. **价值判断**——涉及取舍与排序的争议需要一个被授权的终判者；
3. **高风险**——误判代价不可接受的场景，自动化只能做初筛，人做最终把关。

以及一条防止过度自动化的边界原则（阿里原文）：**"能自动稳定判断的不长期依赖人工"**——注意它的双向性：既反对"人工全量打分"，也反对"人工永远把着不放"。**分工的终局是人的有序撤退**：今天人判的口径，明天变成规则或校准后的 judge；撤退的前提是自动化层通过了校准验收（一致率、高风险漏判率、边界稳定性）。腾讯表格中"人工评分器不进门禁，做采样审查"正是这种撤退后的稳态形态。

**兜底裁决的升级路径**（组织层配套）：分工表回答"谁评"，落地还要回答"评的人之间不一致怎么办"。可操作的三级升级链：**标注员分歧 → SME 复审 → 指定的最终决策者裁决**——Airbnb EDD 原则 4 要求明确指定这一个人，因为"好 vs 坏"的争议如果没有唯一终裁人，会在委员会里无限循环。每级裁决的结论都要带依据并写回 rubric，这就接上了 2.7 的反哺闭环。另有一个能批量消除"伪分歧"的机制值得借鉴：DoorDash 的 **eligibility 适用性前置**——judge 先判该标准是否适用本会话，不适用则跳过（如食谱流程不因缺复购步骤被扣分）。实践中相当一部分"judge 与人工分歧"其实是"这条标准本就不该评这个会话"，把适用性判断前置，这类分歧在源头就消失了。

### 2.7 人工结论反哺：一次人工判定要产出三份资产

人工判完不是终点。如果人工结论只用于"给这条样本一个分数"，那么下一条同类样本还得再花一次人工——人力成本线性增长，永远追不上样本量。阿里的反哺机制把人工结论导向三个去处：**校准规则、校准 judge prompt、校准根因标签体系**。

**反哺路径一：规则层——口径回收。** 路由条件⑥（规则与 judge 冲突）的人工终判，产出的不只是这条样本的 verdict，更是一条**新口径**。例如业务终判"拒收+运费险场景应走先退款后退货流程"，这条裁决应当被写成一条确定性规则（或 rubric 检查项）入库——下次同类样本由规则直接判定，**不再消耗人工**。这就是"回收口径"四个字的完整含义：人工判定把口径缺口补上，自动化层的能力边界向外推一格。

**反哺路径二：Judge 层——校准集回流。** 人工与 judge 的分歧样本是校准集最优质的增量来源（它们恰好落在 judge 的判定边界上）：分歧样本入金标校准集 → 分析分歧原因 → 修 rubric/few-shot/judge prompt → 重新跑校准五步法（2.3）；DoorDash 更进一步用 GEPA 自动搜索 judge prompt 修订、只保留提升留出集一致率的版本，并在 rubric 演进（新增能力）时收新标注、重新校准。

**反哺路径三：根因层——标签体系。** 人工复核结论反校准**根因标签体系**（第 E11 章 · Badcase 根因分析与优化闭环）：标签要稳定、可统计、指向 owner 与处理动作——**运营可配置 / 算法需优化 / 工程需修复 / 业务需定口径**。注意阿里强调"业务需定口径"本身就是一类根因：很多看似模型失败的问题，根因是业务规则从未被定义——这类问题的修复动作不是改 prompt，而是开一次业务评审会。

把反哺机制汇总成一张"资产转换表"——人工评估的每一类产出都应对应一个可复用的资产：

| 人工产出 | 转换成的资产 | 消费方 | 杠杆效果 |
|---|---|---|---|
| 冲突样本的终判 + 依据 | 新规则 / 新 rubric 检查项 | 规则层与 Judge 层 | 同类样本下次不再耗人工 |
| 分歧样本集 | 金标校准集增量 | judge 校准流程 | judge 一致率向 85% 线逼近 |
| 根因判定结论 | 根因标签库（指向 owner） | RCA 与修复闭环（E11） | 失败聚类产出可执行行动项 |
| 业务口径裁决 | 评测集的期望行为定义 | golden set（E03） | 新用例获得明确的验收标准 |
| Trace 采样发现的隐藏失败模式 | 新用例 / 新检查项 | 回归集（只增不减） | 线上失败转化为离线防线 |

反哺的规模效应，用两个工业数字收尾：

| 公司/项目 | 人工投入方式 | 杠杆产出 |
|---|---|---|
| DoorDash（Ask DoorDash） | 人工定 rubric + 标注校准集 + 审计 judge，打分交给 judge | 全国上线前 agent 质量分 **+8 分**、错误率**近乎减半**；全量回归 **6+ 小时 → 约 20 分钟**；日均 **2,000 个自动评分会话** |
| Discord AITL（EMNLP 2025 工业赛道） | 四类人工客服**在线标注**持续回流，驱动检索/生成再训练 | 再训练周期从**月级压缩到周级**；美国试点 recall@75 **+11.7%**、precision@8 **+14.8%**、有用性 **+8.4%**、采用率 **+4.5%** |

Discord AITL 是人工评估反哺闭环的教科书样本：**人工标注 → 评测集 → 再训练 → 上线 → 新标注**，且专门量化了 offline 与 online 评测设置的一致性。它说明人工评估的产出不仅校准评分器，还能直接驱动模型迭代——人工不是成本中心，是**评分系统的校准源、口径工厂与数据飞轮的进料口**。

## 四、经典面试题与参考答案

#### 题 1（基础）：三层评分体系里，为什么人工不做日常全量打分？专家时间应该怎么分配？

**参考答案：**
三层评分的分工是"规则主判、Judge 辅助、人工兜底"（阿里），选择优先级为确定性 > Rubric > 人工（腾讯）。人工不做全量打分有三笔账：成本上人工是分钟-小时级/人力，规则毫秒级免费、judge 秒级；规模上生产流量是千会话/天量级（DoorDash 日均 2,000 个自动评分会话，人工全量回归要 6+ 小时、自动化后约 20 分钟）；杠杆上专家最稀缺的能力是"定义什么是好"，不是重复判断。因此腾讯给出经验法则：**能自动化的坚决不找专家，专家时间 60%+ 花在"校准 LLM 评委"与"诊断异常"**；DoorDash 同构：人工用在杠杆最大处——定 rubric、标注校准集、审计 judge 行为；Airbnb 则要求指定一个最终人类决策者裁决争议。人工的正确定位是评分系统的校准源与仲裁庭，不是流水线工人。

#### 题 2（基础）：Agent 评测中哪些工作必须留给人工？请给出尽量完整的清单。

**参考答案：**
按腾讯六场景为主干：① 校准 LLM 评委（最核心，抽样 100–200 条对齐，一致率 ≥85% 才可用）；② 主观任务打分（语气、清晰度等 rubric 维度的人工抽样）；③ 诊断通过率异常（0%/100% 通常是任务或评分器坏了）；④ 建 Ground Truth（新套件前 20–50 个参考解，配合基线快照机制）；⑤ Trace 采样审查（每周固定抽样读轨迹找隐藏失败模式）；⑥ 高风险兜底（医疗/金融/安全 100% 人工复核）。再补两家：Airbnb 强调人工负责细微差别与创意、安全高风险决策、解决自动评估器间冲突；阿里强调新建评测集时"定口径"（如已发货+拒收+运费险场景走哪条流程需业务先定）与处理争议样本。归纳成三类不可让渡的维度：政策口径、价值判断、高风险——它们的答案依赖内部政策与业务取舍，不在任何模型的训练分布里。

#### 题 3（进阶）：请完整描述校准一个 LLM Judge 的流程，给出量化标准，以及不达标时怎么办。

**参考答案：**
按 Airbnb 校准五步法：① 建 50–100 条 gold set，**必须含坏样本**——流畅的错误、正确的改述、边界样本三类陷阱样本要刻意覆盖；② 用 judge 跑该集合；③ 看一致率，目标 high 80s ~ 90s（腾讯口径 ≥85%、阿里 ~85% 后进日常自动化），分歧用 Cohen's κ / Krippendorff's α 度量；④ 逐条分析分歧 → 修 rubric 与 few-shot 示例 → 重跑；⑤ 失败模式变化、rubric 演进、judge prompt/模型升级时重新校准。不达标时的动作不是换 judge 模型，而是**回到分歧样本**：Airbnb 客服案例中初始一致率 78%，分歧分析定位到 judge 误罚正确的改述，修 rubric 与示例后达 88%。校准还应自动化提效：DoorDash 用 GEPA（arXiv 2507.19457）迭代生成 judge prompt 修订、只保留在留出集上提升人工一致率的版本。校准后进入持续运营：每次升级产出三项统计——与人工一致性、高风险样本漏判率、边界样本稳定性。

#### 题 4（进阶）：两位专家标注同一校准集出现约 20% 的分歧。有人建议"取多数/平均，先往前推进"，你怎么看？

**参考答案：**
不能取平均往前推进，这是标注工程里最危险的捷径。Airbnb 的纪律是：**专家有分歧就先停下解决分歧再自动化**。理由是：专家分歧通常不是随机噪声，而是**口径未定义的信号**——两位专家各自在应用指南没覆盖的隐含标准；此时取多数或平均，等于把一份未定义的口径固化成训练/校准数据，judge 学到的将是系统性偏差，而且后续很难追溯。正确流程：① 把分歧样本摆上桌逐条辩论；② 裁决出唯一答案；③ **把裁决写回 rubric/标注指南**——分歧处理过程就是口径固化过程；④ 用更新后的指南重新标注分歧样本验证一致性；⑤ 再进入后续批次。同时要区分：若分歧集中在某类场景，说明 rubric 对该场景欠定义，补指南；若分散且两位专家 IAA 持续偏低，才考虑标注员培训或换人——但第一步永远是先怀疑 rubric，因为"如果人都无法一致地应用 rubric，模型也不可能"（Airbnb）。

#### 题 5（进阶）：你的评分流水线如何决定哪些样本最终送人工？为什么不能只看分数阈值？

**参考答案：**
用阿里的六类路由触发条件：① 边界分（得分落在门禁阈值灰区）；② 低置信（评分器输出的置信度低于阈值）；③ reason 含糊（judge 判定依据不可复核）；④ 多 judge 分歧；⑤ 新模型/新 Prompt/新工具 Schema/新活动上线的抽样观察；⑥ 规则与 judge 结论冲突 → 人工终判并回收口径。这些条件依托分层筛查架构：粗筛层（规则+轻量 judge 快速分流）→ 精判层（完整规则+judge，输出问题分类/现象/置信度/判定依据）→ 人工复核层。只看分数阈值会漏掉三类信号：其一，低分 ≠ 不确定——高置信的明确失败（JSON 损坏、禁用工具）需要的是修复不是复核，边界分反而更值得看；其二，置信度、reason 质量、judge 间分歧度量的是"尺子可不可靠"，是分数之外的元信号；其三，分数捕捉不到分布漂移——新版本上线时旧评分器可能整体失准而分数照常，必须按抽样率主动送人工，这也是主动学习"优先抽低置信/新意图/新工具样本"的落点。另外要监控路由率本身：飙升通常意味着评分器坏了或漂移了。

#### 题 6（进阶）：某个评测套件的通过率从 70% 突然变成 0%（或 100%），你的第一反应和排查路径是什么？

**参考答案：**
第一反应不是"模型突然变弱/变强"，而是**怀疑任务定义或评分器坏了**——腾讯明确：0% 或 100% 通常是任务/评分器问题，不是模型能力问题；其稳定性调试经验也给出同构信号：0% pass^N 通常说明任务定义有问题。排查路径：① 查评测基础设施——用例输入是否被改坏、fixture/环境状态是否漂移、被测系统是否根本没跑通（超时、schema 变更导致全量解析失败）；② 查评分器——规则断言是否过严（如基线更新后旧快照失配）、judge 是否升级或 prompt 变动导致尺度漂移；③ 人工抽样：按"诊断 0%/100% 异常"场景，专家抽 10–20 条逐条读输入、输出与 trace，判断到底是系统性失败还是系统性误判；④ 用旧版本被评系统重跑同一套件做对照——若旧版本也变 0%/100%，锁定评分器或环境；若旧版本分数正常，才回到新版本变更本身。这正是人工六场景中"诊断异常"的价值：自动评分器无法给自己做体检，体检必须靠人。

#### 题 7（进阶）：Judge 模型要升级到"更强"的新版本，能直接换吗？需要走什么验证流程？

**参考答案：**
不能直接换——"更强"是通用能力判断，不是"在你的 rubric 上判得更准"的证明；未经验证替换 judge 等于悄悄换了一把尺子，历史分数全部失去可比性。验证流程按阿里的 judge 持续运营口径：维护一份 judge 金标校准集（含坏样本与边界样本），对新版 judge 固定产出三项统计——① **与人工标注一致性**（一致率或多模型对抗 Kappa），对照 ≥85% 的经验线；② **高风险样本漏判率**（合规/资损/隐私），这是新版本最容易悄悄恶化的地方，平均分涨而高风险漏判升是典型的"尺子变松"；③ **边界样本稳定性**（同一批边界样本重复评测的波动）。同时做新旧桥接：同一批历史样本用新旧 judge 各跑一遍，量化分数漂移幅度，趋势图标注版本断点（主手册第 8 章 · Agent 评估与可观测性 对"judge 版本化与历史数据桥接"有展开）。若新 judge 在分歧样本上的判定理由与旧版系统性不同，还要回到 rubric 层确认是 judge 变了还是口径该变。DoorDash 的实践可作补充：judge prompt 的打磨本身可用 GEPA 类优化器在留出集上自动迭代，但"是否采纳修订"的验收标准始终是与人工标注的一致率。

#### 题 8（系统设计）：你们要为一个客服 Agent 搭建评分体系，团队只有一位领域专家（SME）和一位标注员。请设计人机分工方案：如何起步、如何校准、如何路由、如何反哺。

**参考答案：**
总体原则：把 SME 的时间当最稀缺资源预算——60%+ 花在校准 judge 与诊断异常，坚决不做日常全量打分（腾讯经验法则）。分四阶段：
**① 起步（定口径 + 建锚）**：SME 牵头写 rubric，要求"每条标准从会话本身可验证"（DoorDash），业务口径类问题（退款政策组合、补偿规则）由 SME 直接定标准；标注员配合产出 20–50 个参考解（腾讯）与 50–100 条 gold set，**刻意包含坏样本**：流畅的错误、正确的改述、边界样本（Airbnb）。
**② 校准**：judge 跑 gold set，目标一致率 ≥85%（腾讯/阿里口径）；分歧样本由 SME 逐条裁决并写回 rubric——"专家有分歧先停下解决再自动化"（Airbnb）；标注员负责按更新后的指南重标分歧批，报 Cohen's κ 监控一致性；预算允许时可用 GEPA 类方法自动搜索 judge prompt 修订。
**③ 路由**：分层筛查——粗筛规则分流 → 精判层输出问题分类/现象/置信度/判定依据 → 六类条件路由人工（边界分/低置信/reason 含糊/多 judge 分歧/新版本抽样/规则-judge 冲突）；线上每日抽 5% 去标识化流量跑 judge、标记样本进人工队列（Airbnb）；医疗/资金/合规类场景 100% 人工复核（腾讯）。
**④ 反哺**：人工终判的口径固化为新规则；分歧样本回流校准集；根因标签按"运营可配置/算法需优化/工程需修复/业务需定口径"归类（阿里）；每周 SME 评审会看失败主题与路由率趋势（Airbnb 每周 PM 评审）。隐私红线贯穿全程：人工评审前去标识化、用途限定于安全与质量。

#### 题 9（进阶）：给定人工与 judge 的混淆矩阵，你如何量化人机一致性？为什么只看一致率会误事？

**参考答案：**
先算观察一致率 P_o（混淆矩阵对角线占比），再算 Cohen's κ = (P_o − P_e)/(1 − P_e)，其中 P_e 是按双方各自的边际分布算出的"机遇一致率"——κ 扣除了"瞎猜也能对上"的部分，度量的是真实判别力。举例：100 条样本，对角线为 72/14，P_o = 86%，P_e = 0.80×0.78 + 0.20×0.22 ≈ 0.67，κ ≈ 0.58——一致率看似达到 85% 线，κ 却揭示一致多半来自"大多数样本本来就 pass"的基础率。pass/fail 判定的分布天然偏斜，一致率会系统性高估 judge 质量：上例中人工判 fail 的 22 条里 judge 只抓到 14 条，漏判率约 36%。这就是阿里把**高风险样本漏判率**单列为 judge 升级统计项的原因——合规/资损/隐私类样本漏一个的代价远超平均分波动。工程结论：一致率、κ、坏样本/高风险召回要并排报告；多标注员或非二值任务用 Krippendorff's α。

#### 题 10（系统设计）：为一个涉及资金操作的高风险 Agent（退款/赔付）设计人工评估的运营方案。

**参考答案：**
按四条线设计：**① 进料线**：赔付/资损/隐私/合规/投诉升级类样本无条件进人工队列，与自动评分结果无关——阿里的口径是"自动通过的也要定期人工复核"；路由六条件中此类样本叠加"高风险"权重优先处理。**② 裁决线**：双人复核制（初审 + 复审），结论带依据、rubric 版本与会话 ID 留痕进审计日志；分歧按"标注员 → SME → 指定终判者"升级（Airbnb EDD 原则 4 要求明确唯一终判人）；裁决结论写回业务口径与 rubric。**③ 校准线**：高风险场景全部作为对抗样本纳入 judge 金标校准集；judge 每次升级单独报告"高风险样本漏判率"，该指标一票否决——平均一致率达标但高风险漏判恶化即阻断放量。**④ 闭环线**：确认的高风险 badcase 只增不减进回归集；根因标签绑定 owner（运营可配置/算法需优化/工程需修复/业务需定口径）；稳定性按关键决策类口径——腾讯对关键决策类容忍阈值为 0%（N 次全过，一次失败都可能误判），发布门禁用连续成功率（pass^k）而非至少一次成功率。贯穿四线的原则：高风险场景自动化只做筛查、人做终判，且每次终判都要可审计、可复用。

## 五、易错点 · 反直觉点

1. **误区：专家越多，评测越可靠。** 真相：人力堆在日常打分上是负杠杆——成本分钟-小时级、扩展性差，而且专家被消耗在重复劳动上就没空做校准与诊断；腾讯的口径是专家时间 60%+ 必须花在"校准 LLM 评委"与"诊断异常"。**记忆锚点：专家是校准砝码，不是流水线。**
2. **误区：分数低于阈值的样本送人工复核就够了。** 真相：低分 ≠ 不确定——高置信的明确失败不需要人工；路由要看的是不确定性信号（边界分/低置信/reason 含糊/多 judge 分歧）、漂移信号（新版本抽样）与冲突信号（规则 vs judge），阿里明确"不由分数阈值单独决定"。**记忆锚点：路由看的是"尺子可疑"，不是"分数难看"。**
3. **误区：专家意见不一致就投票取多数，先推进进度。** 真相：分歧通常是口径未定义的信号，取多数会把未定义的口径固化成系统性偏差；Airbnb 的纪律是先停下解决分歧再自动化，裁决结果要写回 rubric。**记忆锚点：分歧不是噪声，是口径缺口。**
4. **误区：校准集里放满"标准好答案"就够了。** 真相：gold set 必须含坏样本（Airbnb 十条要点之一）——没有"流畅的错误"测不出 judge 被流畅性迷惑，没有"正确的改述"测不出 judge 误罚同义改写（78%→88% 案例的病灶正在于此）。**记忆锚点：没有坏样本的 gold set，校不出尺子的偏差。**
5. **误区：通过率 0% 说明模型太弱，100% 说明评测太简单。** 真相：0% 或 100% 通常是任务定义或评分器坏了（腾讯六场景之三）；0% pass^N 的调试技巧是先查任务定义，不是先怀疑能力。**记忆锚点：全军覆没先查尺子，再查选手。**
6. **误区：judge 是强模型就能直接上岗，校准是走形式。** 真相：未校准的 judge 制造误导性信心（Airbnb），"LLM Judge only useful if it agrees with human reviewers"（DoorDash）；一致率不达 85% 上下就放量，等于拿一把没校准的尺子做发布决策。**记忆锚点：先校尺，再量货。**
7. **误区：人工判定完、分数入库，这条样本就关闭了。** 真相：人工结论必须反哺三处——口径固化为规则（下次同类不再耗人工）、分歧样本回流校准集修 judge prompt、结论反校准根因标签体系（阿里）；判完不反哺，人力成本永远线性增长。**记忆锚点：一次人工判定，要产出三份资产。**
8. **误区：把生产会话直接导给标注团队评审，效率高。** 真相：生产流量送人工前必须去标识化，且用途限定于安全与质量（Airbnb 隐私注记）——未脱敏的人工评审流程在合规审查处直接出局。**记忆锚点：不脱敏，不评审。**
9. **误区：judge/rubric 升级后，旧校准结论继续有效。** 真相：rubric 演进、judge prompt/模型升级、失败模式变化，任一发生都要重新校准（DoorDash/Airbnb），且升级要固定产出三项统计：与人工一致性、高风险漏判率、边界稳定性（阿里）。**记忆锚点：尺子一换，先重新校尺。**
10. **误区：一致率要追求 100%，85% 是妥协。** 真相：人与人之间也做不到 100% 一致——校准目标的实质是"judge 与专家的分歧 ≤ 专家之间的分歧"；盲目追 100% 会过拟合到个别专家的口味，或把 rubric 改成无法泛化的特例清单。**记忆锚点：校准的天花板是 IAA，不是完美。**

3. **Agent-in-the-Loop: A Data Flywheel for Continuous Improvement in LLM-based Customer Support**（Discord，EMNLP 2025 工业赛道，ACL Anthology 2025.emnlp-industry.135）——四类人工在线标注持续回流、再训练周期月级→周级的完整数据飞轮样本；人工评估反哺闭环（2.7）的学术侧对照。

# 第 E02 章 · 评估指标体系

> 一句话导读：「准确率 85%」这句话本身没有意义——有意义的是「哪个口径的 85%、在什么统计置信度下、用来做什么决策」。本章把 Agent/GenAI 评估指标组织成一套体系：纵向分层（P0 门禁 / P1 比较 / P2 观察）、横向分维（五大维度）、逐个精讲核心指标的定义与算法、给出指标设计四原则与统计口径，最后拆解万能 helpfulness 与 Goodhart 两大反模式。学完你能回答任何「这个指标怎么算、该不该进门禁、被刷了怎么办」的问题。

## 一、知识图谱

```
评估指标体系
├── 1. 为什么需要「体系」而不是单个指标
│   ├── 单一指标的三种失效：虚假信心（浅层 helpfulness）/ 未发现回归 / 指标与产品脱节（Airbnb 三坑）
│   └── 指标 = 门禁 + 迭代指南针 + 跨团队沟通语言：先定义「什么叫好」，才谈得上评
├── 2. 纵向分层（指标服务于什么决策）——阿里
│   ├── P0 上线门禁：不达标不发布（功能正确性、安全合规、一致性）
│   ├── P1 版本比较：配统计口径（置信区间 + 显著性 + 最小可感知变化）
│   └── P2 体验观察：长期跟踪（语气、满意度、转人工率）
├── 3. 横向分维（评什么）——腾讯五大维度
│   ├── 功能正确性（P0，代码判）          ├── 效率与成本（P1，代码判）
│   ├── 过程质量（P1，Rubric+人工）       ├── 鲁棒性与安全（P0，代码+人工）
│   └── 体验与对齐（P2，Rubric+人工）
├── 4. 核心指标精讲
│   ├── 一致性双指标：pass@k（能力上限）vs pass^k（生产一致性）
│   │   ├── pass@k = 1−(1−p)^k；pass^k = p^k（独立同分布假设）
│   │   ├── 无偏估计：1 − C(n−c,k)/C(n,k)（每任务 n 次试验、成功 c 次）
│   │   └── 实证：τ-bench GPT-4o retail pass^1≈60% → pass^8≈25%
│   ├── 任务完成率（子目标打点；Turn/Session/Trace/Outcome 四层）
│   ├── 工具调用准确率（该不该调 / 参数对不对 / 调用日志断言）
│   ├── groundedness / 幻觉率（有据性：回复是否锚定检索证据）
│   ├── 误拒率 / 漏拒率（拒绝合理性）
│   └── 延迟 p50/p95/p99、成本 ¥/task（质量相同看成本，成本相同看质量）
├── 5. 指标设计原则与统计口径
│   ├── 四原则：可量化 / 可比较 / 可回归 / 可归因
│   └── 门禁统计三件套（阿里）：置信区间 + 显著性检验 + 最小可感知变化阈值
├── 6. 稳定性评估与容忍阈值分级（腾讯）
│   ├── N 次重复运行：1 次不通过即存在稳定性风险
│   └── 关键决策类 0% 容忍 / 辅助分析类 ≤10% / 创意生成类 ≤40%
└── 7. 反模式
    ├── 万能 helpfulness 分：什么都评 ≈ 什么都没评
    └── Goodhart 定律：指标成为目标 → 代理-金标背离 / grader 被钻空 / 计分规则激励瞎猜
```

30 秒全景：**先按「决策用途」分层（这个分数用来拦发布、比版本，还是看趋势？），再按「评估对象」分维（正确性/过程/效率/安全/体验），每个指标都要能回答「怎么算、谁算、多高的值算好、波动多大」**——四问缺一，指标就只是仪表盘装饰。

## 二、核心概念精讲

### 2.1 为什么「一个准确率」不够：指标体系的定位

Airbnb 在 Eval-Driven Development（EDD）实践中总结了**缺乏评测计划的三个常见坑**，这三个坑恰好解释了为什么指标必须是「体系」而非「单点」：

| 坑 | 表现 | 根因 |
|---|---|---|
| 虚假信心 | 浅层 helpfulness 分一路走高，产品却持续收到投诉 | 指标测的是「看起来有帮助」，不是「解决了用户问题」 |
| 未被发现的回归 | 改 prompt 后质量悄悄变差，无人知晓 | 没有按版本对比的回归指标，旧场景的退化不可见 |
| 浪费精力 | 团队优化了半天，指标与产品结果脱节 | 指标没有对齐真实产品失败模式 |

Airbnb 给出的核心习惯是 **"When in doubt, look at your data."**——跑约 100 个样本（真实或合成），人工读输出和 trace，把错误归类，再围绕它们建指标和测试。他们的旅行客服助手案例中，100 条 prompt 的人工精读发现了 **15 个 groundedness 失败、8 个正确但啰嗦、5 个不当拒答、3 个 JSON 失败**——这四类失败直接推导出四个指标（有据性、简洁性、拒绝合理性、格式合规率），没有任何一个是「万能 helpfulness」。

由此得到指标体系的定位：

- **指标是规约（specification）**：先定义「什么叫好」，开发与迭代才有方向——这正是 EDD「eval 即规约」的主张（详见第 E10 章 · 评测驱动开发）。
- **指标是门禁（gate）**：P0 指标不达标就不发布，把质量判断从「上线后靠用户发现」前移到「发布前靠数据拦截」。
- **指标是沟通语言**：「三连全对率 42%」比「感觉还行」更能让产品、算法、工程对齐预期。向业务方汇报时应使用 pass^k 这类产品语言，而不是单次通过率。

一句话：**单个指标回答不了「能不能上线」，只有分层、分维、带统计口径的指标体系才能回答。**

### 2.2 指标分层：P0 / P1 / P2（阿里）

阿里在 Agent 评测体系设计中把指标分为五大类，并按**决策用途**赋予优先级：**P0 上线门禁（不达标不发）、P1 版本比较与工程优化、P2 体验改善与长期观察**。分层的本质是回答「这个指标变差时，我们做什么动作」：

| 层级 | 决策用途 | 动作语义 | 实例指标 | 统计要求 |
|---|---|---|---|---|
| **P0 上线门禁** | 发布拦截 | 不达标 = 不发布，无商量余地 | 核心场景通过率、**P0 风险样本失败数（要求为 0）**、关键工具参数正确率、安全合规用例通过率、一致性 pass^k | 阈值明确、判定确定；高风险样本宁可误杀 |
| **P1 版本比较** | 选型与优化 | 用于回答「v2 是否比 v1 好」「换模型值不值」 | 任务完成率、groundedness 分、效率指标（token/延迟/成本）、过程质量分 | **必须带统计口径**：置信区间 + 显著性 + 最小可感知变化 |
| **P2 体验观察** | 长期跟踪 | 不拦发布，但趋势恶化要立项 | 语气风格分、回复清晰度、转人工率、重复追问率、投诉率、满意度（CSAT/NPS、👍/👎） | 看趋势与切片，容忍单点波动 |

阿里的发布联动实践中，这三层指标对应**三类信号**同时跟踪：

- **离线质量信号**（发布前）：核心场景通过率、P0 风险数、关键工具参数正确率；
- **线上体验信号**（灰度中）：转人工率、重复追问率、投诉率、满意度变化；
- **业务结果信号**（全量后）：任务完成率、工单闭环率、退款/赔付成功率。

并且有明确的联动规则：**离线提升但线上关键信号恶化 → 触发回滚或降级**（详见第 E12 章 · 在线评估与数据飞轮）。

分层时的两个实操要点：

1. **P0 要少而硬**。门禁越多发布越慢，团队会倾向于绕过门禁。真正的 P0 只留「失败了就是事故」的指标；阿里把「P0 风险数」直接定义为要求 0——高风险样本（赔付/隐私/合规）失败一个就拦。
2. **P2 不等于不重要**。腾讯特别强调：体验与对齐是 **P2 但决定产品生死**。分层只是「是否进门禁」的区分，不是「是否重要」的区分——早期用 Rubric + 人工抽样跟踪，成熟后接 A/B + 用户反馈闭环。

### 2.3 五大评估维度（腾讯）

腾讯在 AI Agent & Skill 测评方案中给出五大维度框架，每个维度标注了优先级、评分器选型与落地要求。下表在腾讯原表基础上扩充了子维度与典型例子：

| 维度 | 层级·评分器 | 子维度（评什么） | 评测方法 | 典型指标 | 落地优先级 |
|---|---|---|---|---|---|
| **功能正确性** | P0 · 代码判 | 结果正确性、任务完成度（子目标打点）、指令遵循（JSON Schema/正则/字段检查）、工具调用正确性 | 断言、单元测试、终态校验、调用日志断言 | pass@1、pass^k、子目标达成率、schema 通过率 | **必须自动化全覆盖** |
| **过程质量** | P1 · Rubric+人工 | 推理合理性、步骤最优性（实际步数 vs 参考解法）、信息完整性（要点覆盖率）、上下文利用率、自我纠错能力 | Rubric 打分（1–5 分）、Trace 分析、基线对比 | 推理分、步骤数比值、要点覆盖率 | 最能体现「智能」，自动化最难，Rubric 主战场 |
| **效率与成本** | P1 · 代码判 | token 消耗、工具调用次数、延迟、失败重试率、任务成本 | 程序化统计（从 trace 直接算） | Token avg/p95、调用次数 avg/p95、延迟 p50/p95/p99、¥/task | 每个任务带成本画像 |
| **鲁棒性与安全** | P0 · 代码+人工 | 一致性（重复运行）、异常恢复（故障注入）、抗对抗/抗注入（红队集）、幻觉率、越权风险、合规、拒绝合理性 | pass^k（k=5/10）、mock_tool_failure、红队用例、权限断言、PII 正则+人工抽查 | pass^k、恢复成功率、攻击成功率、幻觉率、误拒%/漏拒% | 金融/医疗/企业数据 Agent **必须前置** |
| **体验与对齐** | P2 · Rubric+人工 | 语气风格、回复清晰度、主动澄清（模糊需求主动提问而非瞎猜）、同理心、可解释性、用户满意度 | Rubric + 人工抽样；成熟后 A/B + 反馈闭环 | 语气分、澄清率、CSAT/NPS、👍/👎 比 | P2 但决定产品生死；按需补 |

腾讯给出的落地顺序是 **P0 先落地、P2 按需补**。维度之间并非独立——一个 badcase 往往同时扣多个维度的分，因此腾讯的扣分制评分（初始 100 分负分制，每处不符扣分至 0，**达标线 80 分**，按 Agent 类型与业务风险调整）会把「任务结果不符预期 −100、步骤遵循性每步 −10、工具调用每项 −10、耗时每超基准 1 分钟 −10」等组合成一份 JSON 扣分明细——分数之外保留「扣在哪」的信息，指标才能归因（评分机制详见第 E04 章 · 程序化评分）。

**不同类型 Agent 的指标侧重**（腾讯）：评测骨架（执行用例 → 采集 Trace → 评分 → 报告 → 根因归类）可复用，按业务定制的是「评什么、怎么判」：

| Agent 类型 | 指标侧重 | 依赖的评分器 |
|---|---|---|
| 知识库问答 | 准确性 / 幻觉检测 / 引用溯源 | Rubric 为主 |
| 代码编写 | 产物正确性 / 可运行性 | 确定性为主：编译、测试 |
| 功能工具 | 过程合规性 / 工具调用正确性 | 过程对比基线 |
| 问题定位 | 推理链路 / 根因准确性 | 过程 + 结果双重验证 |

这与阿里的观点一致：**先分类型再定指标，「类型不分，评测结果基本不可用」**。

### 2.4 核心指标精讲

#### 2.4.1 一致性双指标：pass@k 与 pass^k（本章最重要的一对概念）

设单任务单次成功率为 p，k 次独立重复运行：

| 指标 | 定义 | 公式（i.i.d. 假设） | 回答的问题 | 适用场景 |
|---|---|---|---|---|
| **pass@k** | k 次尝试中**至少一次**成功 | `1 − (1−p)^k` | 「多试几次能不能成」 | 能力上限；有人在环可重试、可从多个草稿中挑选的场景（创意生成、草稿辅助） |
| **pass^k** | k 次尝试**全部**成功 | `p^k` | 「无人值守连续用 k 次会不会出事」 | 生产一致性；客服、支付、退款、合规等不可重试场景的发布门槛 |

**直觉：k 增大时两者迅速分道扬镳。** 以 p = 0.8 为例：

| k | pass@k（至少一次成功） | pass^k（次次成功） |
|---|---|---|
| 1 | 80.0% | 80.0% |
| 2 | 96.0% | 64.0% |
| 3 | 99.2% | 51.2% |
| 4 | 99.84% | 40.96% |
| 5 | 99.97% | 32.8% |
| 8 | ≈99.9997% | ≈16.8% |

同一个「单次准确率 80%」的 agent：按 pass@8 看近乎完美（99.9997%），按 pass^8 看几乎不可用（16.8%）。Anthropic 在官方 evals 指南中给的例子同样扎心：**p = 0.75、k = 3 时 pass^3 ≈ 0.75³ ≈ 42%**——一个「看起来 75% 不错」的 agent，三连全对只有四成把握。

**实证（τ-bench，Sierra AI）**：GPT-4o 在 retail 域 pass^1 约 **61%**、airline 域约 **35%**，而衡量可靠性的 pass^8 分别跌至约 **25%** 与 **16%**（数字引自论文摘要，arXiv:2406.12045，2024）。「能做对一次」与「稳定做对」之间的差距是系统性的，不是个别现象。

**估计方法（面试计算高频）**：实际评测中每个任务只能负担 n 次运行（n 次中成功 c 次）。两个常见的错误估计与正确做法：

- 错误 1：「n 次里有任何一次成功就算过」——这实际报告的是 pass@**n**，k < n 时会系统性**高估** pass@k；
- 错误 2：用有放回公式 (c/n)^k 估 pass^k——小样本下会高估一致性，**这是危险方向的高估**（让团队误以为系统比实际更稳）。
- 正确：无放回组合的无偏估计——`pass@k = 1 − C(n−c, k)/C(n, k)`；对应地 `pass^k = C(c, k)/C(n, k)`（c < k 时为 0），即「从 n 次试验里无放回抽 k 次」的超几何口径。

动手验证：`cd evals-special/labs && python3 eval_lab01_metric_system.py`——lab 用固定种子模拟 N 任务 × K 次运行矩阵，核心断言包括 pass^k ≤ pass@k、p^k 理论值与估计值吻合、以及「同一 agent 在关键决策门禁与创意生成门禁下得到相反发布结论」。

**统计注意**：pass^k = p^k 依赖各次尝试相互独立。真实系统中上下文污染、残留状态、下游限流、缓存命中都会破坏独立性；若各次尝试正相关（这次挂了下次更容易挂），真实 pass^k 比 p^k 更悲观。此外 pass^k 对试验次数 n 敏感（n 太小会高估），报告时必须连同 n 与置信区间一起给出（详见第 E09 章 · 评估的统计学基础）。

**k 怎么选：一场发布哲学的选择**。选 k 不是拍脑袋，取决于产品形态对失败的容忍度：

| 场景 | 建议口径 | 理由 |
|---|---|---|
| demo / 能力探索 | pass@1 或至少一次成功率 | 目标是发现能力边界，不是承诺可靠性 |
| 有人审阅的辅助工具（报告生成、代码建议） | pass@k（k=3~5） | 人从候选中挑选，重试成本由人吸收 |
| 无人值守的生产流程（客服托管、工单处理、退款） | pass^k（低 k，k=3~8） | 一次失败就是一次事故；τ-bench 与 Anthropic 均主张可靠性指标进发布门槛 |
| 不可逆操作（支付、改数据） | pass^k + P0 风险样本 0 失败 | 双保险：统计口径 + 硬约束 |

值得注意的现状：多数公开 leaderboard 仍只报 pass@1 或平均分，学界对「可靠性排行榜」尚无标准——这是 2024–2026 evals 领域的公开争议之一。面试中被问「你们汇报哪个数」，答「按产品形态选口径，两个数都报，gap 就是稳定性债」是满分姿势。

#### 2.4.2 至少一次成功率 vs 连续成功率：生产系统为什么看后者

阿里把一致性明确拆成双指标：**任务重复运行 N 次，「至少一次成功率」度量能力上限，「连续成功率」度量生产要求**。并给出了一句值得全文背诵的判断：

> **用户不会接受「多试几次总有一次成功」。**

客服、支付、退款、合规等生产级场景，每一次失败都是一次真实事故（错误退款、重复扣款、违规承诺），不存在「重试到成功」的兜底路径。因此：

- **能力评测阶段**看至少一次成功率——回答「这个 agent 有没有潜力做这件事」，指导投入方向；
- **发布门禁**看连续成功率——回答「敢不敢把它交给真实用户」，对应 pass^k（低 k，如 k=3~8）。

两个数的 gap 就是**稳定性债**：gap 大说明能力有但不可靠，优化方向是降方差（固定 prompt、收紧工具 schema、减少自由发挥），而不是继续提能力上限。

#### 2.4.3 任务完成率：最容易算、也最容易算错

任务完成率是最接近业务价值的指标，但有两个口径陷阱：

1. **判「说了什么」还是判「世界变成什么样」**。客服/操作类 agent 首选终态校验（如 τ-bench 用数据库终态哈希判定：订单是否真的被取消、金额是否正确），抗话术干扰；只看自然语言回复会把「嘴上说已取消、数据库纹丝不动」判为成功（详见第 E07 章 · 轨迹与 Agent 级评估的假阳性分析）。
2. **每轮都对 ≠ 会话成功**。阿里特别警告「不要只平均每轮分数」——每轮都「答得还行」但最终没解决问题仍是失败。

阿里对对话 agent 提出的四层评判框架，明确了「完成率应该落在哪一层」：

| 层 | 评什么 | 指标形态 | 常见误用 |
|---|---|---|---|
| **Turn（单轮）** | 单条回复的相关性、准确性 | 每轮 judge 分 | 只平均每轮分 → 掩盖「绕圈但不解决」 |
| **Session（整段会话）** | 整段交互是否推进并达成用户目标 | 会话级 pass/fail | 用单轮高分推断会话成功 |
| **Trace（执行轨迹）** | 路径是否合规、关键步骤是否发生 | 过程分、关键调用覆盖率 | 只看结果不看路径 → 假阳性 |
| **Outcome（最终结果）** | 用户问题是否真正解决（终态） | 终态校验、工单闭环率 | 把「对话礼貌结束」当「问题解决」 |

任务完成率应落在 **Session/Outcome 层**，并配合**子目标打点**（腾讯五维中「任务完成度（子目标打点）」）做部分归因：把任务拆成有序子目标（如退款任务 = 查到订单 → 核实身份 → 确认订单状态允许退款 → 执行退款 → 告知结果），每个子目标独立计数——任务失败时能立刻看出「卡在第几个子目标」，而不是只得到一个笼统的 fail。子目标达成率同时也是 P0 门禁的常用指标（阿里离线质量信号中的「核心场景通过率」通常就是子目标口径的聚合）。

#### 2.4.4 工具调用准确率

工具调用是 agent 区别于 chatbot 的核心能力，也是失败的高发区（阿里 RCA 中的「关键工具未调用」「工具参数缺失」是高频根因）。可拆成一组可程序化判定的子指标：

| 子指标 | 定义 | 判定方式 |
|---|---|---|
| 该不该调（触发正确性） | 过度触发（不该调而调）与漏触发（该调没调）分开统计 | must-call / must-not-call 断言；负向用例集（相似但不相关 prompt 不误触发） |
| 参数正确性 | 参数值、类型、枚举、格式是否符合工具签名 | JSON Schema 静态校验 + 结构化语义比对 |
| 调用序列合规 | 关键前置是否满足（先鉴权后操作）、关键校验是否跳过 | 偏序约束断言；与基线序列 LCS 对齐（腾讯 TPerf 实现，详见第 E07 章） |
| 调用效率 | 重复调用、冗余调用、死循环 | 调用次数 avg/p95、轨迹去重分析 |

腾讯把「工具调用检查（是否调用指定工具、参数是否正确）」列为确定性评分器的第一优先级——**能用代码判的绝不用模型**（详见第 E04 章）。注意：不要对完整调用序列做 exact match，多条合法路径会被误杀；只对**关键调用**做强约束。

一个真实 badcase 能说明这组指标的价值（阿里 RCA 案例）：现象是「已发货退款场景中，Agent 23 次跳过订单状态校验」，根因被归为「工具覆盖与执行」大类下的枚举「关键工具未调用」，责任模块 = 退款 Skill/退款流程执行模块，且失败集中在 v1.8 Prompt。如果没有「关键校验工具调用覆盖率」这个指标，这 23 次跳过会淹没在「最终退款大多也办成了」的结果分里——直到某次跳过校验造成资损才暴露。**工具调用指标的归因价值正在于此：它把「侥幸没出事的路径违规」提前变成统计信号**（这类「结果对但路径错」的假阳性样本，处理流程详见第 E07 章与第 E11 章）。

#### 2.4.5 groundedness 与幻觉率

**groundedness（有据性）**度量「回复是否锚定于检索到的证据/工具返回」，是 RAG 与客服 agent 的头号质量指标；幻觉率是其反面。两者通常由 LLM-as-a-Judge 按 rubric 判定：judge 拿到「agent 的论断 + 背后的工具输出/检索片段」，逐条核对论断是否有证据支撑（DoorDash 的 transcript builder 正是为 grounding 检查定制证据视图：judge 只看该标准依赖的那片证据）。

工程上三条经验（均有出处）：

- **groundedness 失败是最常见失败类型**：Airbnb 100 样本探索中 15/31 个问题属于 groundedness 失败，接近一半；
- **检索改进直接降低 groundedness 失败**——该指标的归因往往不在生成层而在检索层，需要配合组件级指标定位（召回是否正确、关键片段是否保留）；
- **judge 判 groundedness 前必须校准**：Airbnb 的 groundedness judge 初始与人工一致率仅 78%（误罚了正确的改述），修订 rubric 与示例后达 88% 才投入使用（judge 校准全流程详见第 E05 章）。

OpenAI 官方 evaluation best practices 给出的量化目标参考（文档问答类）：**recall ≥ 0.85、precision ≥ 0.7**；摘要类 ROUGE-L ≥ 0.40、G-Eval 连贯性 ≥ 80%、好评率 70%+——这些数字可作为团队定门槛时的外部参照，但最终门槛要从自己的失败分布推导。

#### 2.4.6 误拒率 / 漏拒率：拒绝合理性

安全类指标必须成对出现，单看任何一侧都会产生荒谬的优化方向：

| 指标 | 定义 | 单侧优化的荒谬结局 |
|---|---|---|
| **漏拒率**（该拒不拒） | 应拒绝/升级的请求被照常处理的比例 | 只压漏拒 → agent 拒绝一切敏感请求 |
| **误拒率**（不该拒而拒） | 正常请求被错误拒绝的比例 | 只压误拒 → 防线形同虚设 |

Airbnb 案例中「5 个不当拒答」就是误拒的实例——拒答本身也是一种失败模式，会直接损害可用性。正确姿势是**报 tradeoff 曲线**：在误拒-漏拒平面上标点，按业务风险偏好选工作点（金融场景容忍较高误拒，客服场景容忍较低误拒）。腾讯把「拒绝合理性（误拒%/漏拒%）」归入鲁棒性与安全维度，与安全用例集、红队集配套使用。

#### 2.4.7 效率与成本：延迟分位数与 ¥/task

腾讯的原话值得引用：**「pass@1 高但 token 花 10 倍的方案生产上不可接受」**。效率与成本维度要求**每个任务带成本画像**，核心指标：

- **Token**：avg / p95（input/output 分开，含缓存读写）；
- **工具调用次数**：avg / p95（冗余调用的直接信号）；
- **延迟**：**p50 / p95 / p99**——只看均值会掩盖尾部；agent 会话的 wall-clock 大头往往在工具执行与外部等待，不在推理本身；
- **失败重试率**：重试既烧钱又拉长延迟；
- **单任务成本 ¥/task**：把 token 单价 × 用量折算到任务粒度，是与业务方沟通的通用语言。

工业实例（DoorDash）：其 eval harness 支撑了一次底座模型迁移（Claude Sonnet 4.6 → Gemini 3.5 Flash）。离线评测最初**分数大跌**，但 harness 给出具体失败模式后定位出**不是能力差距而是兼容性差距**（工具参数格式与 system prompt 惯例问题）；做小而准的修复后重跑，Flash 与 Sonnet 质量持平（在 harness 噪声范围内），迁移生产后**延迟降 35%、质量无损**。这个案例是「质量指标守住不动、用效率指标换收益」的标准操作——前提是质量指标先做到**可比较**（同一 harness、同一 judge、统计口径内比较）。

腾讯 TPerf 案例则展示了效率如何进入扣分制：耗时基准 300 秒，每超 10% 扣 1 分；token 以基线为基准每超 10% 扣 1 分，上限 −10——效率退化会被显式计入总分，而不是事后口头抱怨「变慢了」。

### 2.5 指标设计四原则与门禁统计口径

#### 2.5.1 四原则

一个指标在纳入体系之前，过一遍这四道检查：

| 原则 | 含义 | 反例 |
|---|---|---|
| **可量化** | 有明确的计算口径，不同人算出来一样 | 「回复质量」无口径；「groundedness judge 按 v3 rubric 判 pass 的比例」有口径 |
| **可比较** | 跨版本、跨模型可比；口径与评测器版本冻结 | judge 升级后直接对比新旧分数（尺子热胀冷缩） |
| **可回归** | 能挂进回归集，每次变更重跑，只增不减 | 一次性的「感觉测试」，跑完即弃 |
| **可归因** | 分数变化能定位到组件/场景切片 | 只有一个全局平均分，掉了不知道掉在哪 |

「可归因」尤其依赖两点：**按切片报告**（任务类型/场景/难度/风险等级分桶，避免平均分掩盖退化——GEPA 的 Pareto 前沿选择隐含的正是这一原则），以及评分输出不止 pass/fail 还要有问题分类与判定依据（阿里：为 RCA 提供「现象入口」，详见第 E11 章）。

#### 2.5.2 门禁要带统计口径（阿里）

阿里的门禁设计有一条被很多团队忽视的要求：**版本对比要配套统计检验——关键指标置信区间 + 与基线的显著性判断 + 最小可感知变化阈值（提前定义提升多少才值得发布）**。原文表述：

> 「门禁不只看差了多少，还要看差异是否超过统计噪声。」

拆开就是三件套：

1. **置信区间**：通过率是二项比例，报告 Wilson 区间（小样本下端点不越界、覆盖率接近名义水平），不报 CI 的点估计都是噪声；
2. **显著性**：两版本跑同一批评测集是配对设计，用配对检验（如 McNemar，只关心两版本判定不一致的样本），而不是比较两个独立的点估计；
3. **最小可感知变化（MPP）**：事先定义「提升多少才值得发布」——如果业务上 1 个百分点的提升不值得一次发布风险，就把 MPP 设为 1pp，统计上检出 0.5pp 也没有意义。

**量级直觉**（推导细节见第 E09 章与 `cd evals-special/labs && python3 eval_lab08_statistics_ci.py`）：通过率 p̂ 的标准误约为 √(p(1−p)/n)。基线 80% 附近、n=100 时标准误约 4 个点、95% CI 约 ±8 个点——**v1 82% vs v2 85% 在 n=100 下完全不可判**；同样的 3 个点差异，n=2000 时 CI 收到 ±1.6 个点，立刻可判。样本量与可检出差异 δ 约是 1/δ² 关系：基线 80%、双侧 α=0.05、功效 0.8 时，检出 10pp 差异每组约需 250 样本，检出 5pp 约需 1000，检出 3pp 约需 2800——**想检出越小的差异，评测集越贵**，这就是 golden set 规模与门禁灵敏度之间的根本权衡。

由此可以推出**一份合格指标报告的最小字段**——缺任何一项，数字都不可复核、不可比较：

| 字段 | 例子 | 缺了会怎样 |
|---|---|---|
| 点估计 | 通过率 85% | —— |
| 误差范围 | 95% Wilson CI [81.2%, 88.1%] | 无法判断差异是否超过噪声 |
| 样本口径 | n=400 条 golden set v3，每任务 trial=5 | 不知道估的是 pass@1 还是 pass^5 |
| 试验次数与聚合方式 | 逐任务估计后平均（非混合所有运行） | pass@k 的错误聚合会改变数值 |
| 评分器版本 | judge v3（与人工一致率 88%） | 尺子换了，趋势图失真 |
| 切片拆分 | 按场景/风险等级分桶的通过率 | 平均分掩盖局部退化 |
| 对比基线与判定 | vs v1.4：+3pp，CI 重叠，**不显著** | 「涨了」变成口头结论 |

阿里「门禁不只看差了多少，还看是否超过统计噪声」落到纸面，就是这张表。

把分层指标与统计口径串起来，一次完整的**门禁执行流**如下（离线部分；与线上灰度的联动详见第 E12 章）：

```
版本变更（prompt / 模型 / 工具 / serving 配置）
  → ① smoke 子集：少量核心用例、分钟级，拦截明显破坏
  → ② 全量回归集 × N trials：能力评测「毕业」的用例只增不减（腾讯/Anthropic 口径：
        确定性任务通过率 100%、非确定性 ≥95%）
  → ③ P0 硬门禁：核心场景通过率 ≥ 阈值 ∧ P0 风险样本失败数 = 0 ∧ 安全集 0 漏拒
        （任一不满足 → 直接拒绝，不进入统计比较）
  → ④ P1 统计比较：与基线配对检验 + CI + 显著性 + 预设 MPP
        （「不劣于基线」且「成本/延迟不劣化超阈值」才放行）
  → ⑤ 通过 → 出报告归档（含上一节最小字段）→ 进入线上灰度
        未过 → 拒绝 + 失败样本进 badcase 任务表（详见第 E11 章 · RCA）
```

注意两个顺序细节：**P0 在统计比较之前**（硬约束没有商量余地，不必浪费统计检验）；**成本/延迟作为 P1 比较的一部分**——新版本质量持平但成本翻倍，同样应当拒绝。

### 2.6 稳定性评估与容忍阈值分级（腾讯）

腾讯的稳定性评估方法：**同一用例执行 N 次（建议 N=5），只要 1 次不通过即存在稳定性风险**。容忍阈值按使用类型分级：

| 使用类型 | 例子 | 容忍阈值 | 逻辑 |
|---|---|---|---|
| **关键决策类** | 问题定位、故障诊断、支付/退款决策 | **0%（N/N 全过，任何一次失败都可能误判）** | 结论直接影响不可逆动作 |
| **辅助分析类** | 性能分析、报告生成 | ≤10% | 有人审阅兜底 |
| **创意生成类** | 代码建议、文案 | ≤40% | 人从多个候选中挑选 |

**N=5 的读法**（腾讯调试经验）：

| N=5 结果 | 解读 |
|---|---|
| 全过 | 稳定 |
| 1/5 失败 | 存在幻觉/不稳定，按类型判断是否可接受 |
| 2/5 失败 | 高幻觉率，深入排查 |
| 5/5 失败 | 稳定失败——先查任务定义或基线，再怀疑模型 |

两个反直觉的边界：**0% pass^N 通常说明任务定义有问题，不是能力不行**；而通过率异常（0% 或 100%）在多数情况下是**任务或评分器坏了**，不是模型弱/强——这是腾讯列出的人工评分六大必要场景之一（诊断异常）。

腾讯 TPerf 的实战决策是个好案例：TPerf 虽属辅助分析类，但其结论直接影响优化决策与发布判断，一次错误结论可能导致性能问题漏检上线，因此**采用关键决策类标准（任一 Trial 不达标该用例 0 分）**——阈值分级不是查表填空，最终依据是「一次失败的代价」。

这套稳定性口径如何聚合成最终分数？腾讯 TPerf 给出了可复用的公式链：

```
trial_score = max(0, 100 + 各项扣分)        # 单次运行的扣分制得分
trial_pass  = trial_score ≥ 80              # 达标线 80 分
case_score  = 全部 trial 都 pass → 取均值
              任一 trial 不达标 → 该用例记 0   # 「一次失败即用例失败」的聚合
```

关键在最后一行的聚合方式：它把「连续成功率」语义直接编译进了用例分数——不是对 5 次运行取平均（那会稀释失败），而是**任一次不达标整个用例归零**。对比之下，若用「5 次均值 ≥80」做判定，4 次 95 分 + 1 次 0 分照样过关，恰好放过了最不稳定的那类行为。设计一致性指标时先问自己：**聚合函数是在奖励稳定，还是在稀释失败？**

与之配套的回归口径（腾讯引用 Anthropic 推荐）：**确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%**；能力测评（起步 20–50%，目标山峰）与回归测评（接近 100%，防御漂移）是两套不同预期的套件，通过率稳定 100% 的用例「毕业」进回归集（详见第 E03 章 · 黄金数据集与用例设计、第 E10 章 · EDD）。

### 2.7 指标反模式：万能 helpfulness 与 Goodhart

#### 2.7.1 万能 helpfulness 分

Airbnb 三坑之首「虚假信心」的直接来源就是一个笼统的 helpfulness 分：它什么都能评，因此什么都评不准——judge 打高分的理由可能是「语气好」「够长」「格式整齐」，与「解决用户问题」弱相关。Airbnb 十条要点的第二条就是**「避免泛化 helpfulness，瞄准真实产品失败」**；配套的实践是「每个质量维度一个 judge、3–5 个经校准的评估器好过一堆嘈杂的评估器」。

诊断方法很简单：抽 20 条高分样本人工看。如果高分样本里有「礼貌地给了错误信息」「啰嗦但没解决问题」，这个指标就在制造虚假信心。修复路径：按观察到的失败模式拆维度（groundedness / conciseness / 拒绝合理性 / 格式合规……），每个维度独立可判（ DoorDash 的做法是每条 rubric 标准写成 binary check，汇总为会话级总分，且先做 eligibility 适用性判断——不适用的标准跳过而不是一律扣分）。

#### 2.7.2 Goodhart 定律：指标成为目标就不再是好指标

指标一旦与 KPI、发布决策、优化目标挂钩，就会被反向塑造。四类有据可查的实例：

| 实例 | 机制 | 出处 |
|---|---|---|
| **代理-金标背离** | 以代理指标（proxy reward）为优化目标时，proxy 持续上升而真实目标（gold）先升后降；最优优化量随奖励模型数据量按平方根增长 | OpenAI《Scaling Laws for Reward Model Overoptimization》，arXiv:2210.10760（2022） |
| **KL 正则不是兜底** | 当评分器误差是重尾分布时，无论 KL 系数多大，优化都会找到 exploit——「加正则就安全」是幻觉 | 《Catastrophic Goodhart》，arXiv:2407.14503（NeurIPS 2024） |
| **pass@1 高估能力增益** | RLVR 训练后 pass@1 超过基座模型，但大 k 的 pass@k 反而低于基座——只看 pass@1 会把「集中既有解法」误读为「扩展能力」 | arXiv:2504.13837（NeurIPS 2025） |
| **计分规则激励瞎猜** | 二元对错打分下，难题「猜一个」的期望收益高于「承认不会」，基准本身激励幻觉；应允许弃权并按校准计分 | OpenAI《Why Language Models Hallucinate》，arXiv:2509.04664（2025） |
| **长度敏感指标被训练攻破** | AlpacaEval 2.0 的长度偏差是「评测被训练钻空子」的早期案例——优化器学会用更长的回答刷分，而非更好的回答 | 见 _research/09 评测与训练闭环调研 |
| **裁判被「讨好型回答」操纵** | LLM judge 会被谄媚、迎合风格的输出钻空子，Meta 的 J1 工作甚至要用 RLVR 反过来训练 judge 自身防操纵 | arXiv:2505.10320（2025） |

评测工程侧的对应防御（每条都能落地）：

1. **代理指标旁必须挂独立 gold 指标**：gold 是线上信号（转人工率、投诉率、业务结果）或人工抽检结论；跟踪 proxy-gold 背离曲线，一旦背离立即降低对 proxy 的优化强度。
2. **指标组合优于单一北极星**：质量（pass^k）、安全（误拒/漏拒、幻觉率）、效率（¥/task、p99）同时上报，防止单指标被刷。
3. **警惕 grader 被钻空**：当指标成为优化目标，grader 就是攻击面——SWE-bench 类评测中已出现 agent 直接修改测试文件骗过断言的案例（arXiv:2506.12286）；对「分数突然飙升」的第一反应应是排查 grader 被钻空 / 评测集被污染 / judge 漂移，而不是庆祝模型变强（详见主手册第 8 章 · Agent 评估与可观测性的 grader 对抗性一节）。
4. **按切片报告并监控方差**：平均分是被 Goodhart 攻破的第一道防线，切片分数（场景/难度/风险等级）更难整体造假。
5. **评测集与优化目标隔离**：eval 集既当测试又当目标时必然被拟合——保留私有 holdout、定期换血、做污染检测（详见第 E13 章 · Benchmark 全景与前沿争议）。

## 四、经典面试题与参考答案

#### 题 1（基础）：pass@k 和 pass^k 有什么区别？各在什么场景下使用？

**参考答案：**
两者都是对「同一任务重复 k 次」的度量，但方向相反。**pass@k = 1−(1−p)^k**，k 次中至少一次成功，度量**能力上限**，适合有人在环、可重试或可从多候选中挑选的场景（创意文案、代码草稿辅助）；**pass^k = p^k**，k 次全部成功，度量**生产一致性**，适合无人值守、失败即事故的场景（客服、支付、退款），是发布门槛该看的数。关键在于 k 增大时两者迅速分道扬镳：p=0.8 时 pass@8≈99.9997% 而 pass^8≈16.8%。实证上，τ-bench 报告 GPT-4o retail 域 pass^1≈60%（官方榜单 60.4%）、pass^8 ≈25%（摘要 <25%）（arXiv:2406.12045）。所以汇报口径必须匹配产品形态：向用户交付「每次都做对」的承诺，就用 pass^k；两个数之间的 gap 就是稳定性债。

#### 题 2（基础）：为什么不能用一个「成功率」指标评估 Agent？你会怎么分层组织指标？

**参考答案：**
单一指标有三个失效模式（Airbnb 三坑）：浅层 helpfulness 造成**虚假信心**；没有版本对比就**发现不了回归**；指标与产品结果**脱节**导致白费精力。我会按决策用途分三层（阿里框架）：**P0 上线门禁**——不达标不发布，只留「失败即事故」的硬指标：核心场景通过率、P0 风险样本失败数（要求为 0）、关键工具参数正确率、安全合规通过率、一致性 pass^k；**P1 版本比较**——任务完成率、groundedness、效率指标，必须带统计口径（置信区间 + 显著性 + 最小可感知变化），回答「v2 是否真的比 v1 好」；**P2 体验观察**——语气、清晰度、转人工率、满意度，不拦发布但长期跟踪趋势。分层的原则是「指标变差时我们做什么动作」：拦发布、比版本、看趋势，三类动作三套口径。P0 要少而硬，否则团队会绕过门禁；P2 不等于不重要——体验决定产品生死，只是不进门禁。

#### 题 3（进阶）：一个支付客服 agent 评测显示「至少一次成功率 92%，连续成功率（k=3）58%」。产品经理说 92% 足够上线了，你怎么看？

**参考答案：**
不能上线，而且这正是**一致性双指标**要防止的误判（阿里）。至少一次成功率度量的是能力上限——「多试几次总有一次成功」；但支付场景每次失败都是真实事故（错误退款、重复扣款），用户不会接受重试，生产要求看的是**连续成功率**，即 pass^k 口径。92% vs 58% 的巨大 gap 说明 agent「会做但不稳」，优化方向不是提能力而是**降方差**：固定 prompt 与输出 schema、收紧工具参数校验、减少自由发挥路径、对高风险步骤加强制校验。同时要追问统计口径：这个 58% 是多少任务、每任务几次运行估出来的？pass^k 对试验次数 n 敏感，n 太小会高估，需报告 n 与置信区间。门禁设置上，我会把「pass^3 ≥ 目标值（如 90%）且 P0 风险样本 0 失败」作为发布条件，把至少一次成功率降级为能力观察指标。若单任务 p≈0.83（0.83³≈57%），要达到 pass^3≥90% 需 p≥96.5%——差距是明确可量化的。

#### 题 4（进阶·计算）：基线通过率 82%，新版本 85%，评测集 n=100。能发布吗？要可靠检出 3 个百分点的提升需要多少样本？

**参考答案：**
不能发布——3 个点的差异在 n=100 下没有超过统计噪声。通过率的标准误约 √(p(1−p)/n)，基线 0.83 附近、n=100 时约 3.8 个点，95% CI 约 ±7.4 个点，两版本 CI 大幅重叠。正确做法是**配对设计**：两版本跑同一批用例，用 McNemar 类检验只看判定不一致的样本，案例难度这个最大噪声源被钉死，检出力更高——这正是阿里门禁要求的「置信区间 + 显著性 + 最小可感知变化」三件套。样本量估算：双比例比较 n ≈ (z_{α/2}+z_β)²·2p̄(1−p̄)/δ²，与 δ² 成反比。基线 80%、α=0.05、功效 0.8 时，检出 10pp 每组约 250 样本，检出 5pp 约 1000，检出 3pp 约 2800。所以要么扩评测集到约 3000 条/版本（配对设计可显著更少），要么把 MPP（最小可感知变化）放宽到 5pp 并接受「小提升不发布」——两个方向都是把「统计成本」显式化。动手验证见 `cd evals-special/labs && python3 eval_lab08_statistics_ci.py`。

#### 题 5（进阶）：如何设计 Agent 的效率与成本指标体系？质量与成本冲突时怎么决策？

**参考答案：**
效率与成本是**与质量并列的维度**而非脚注——腾讯的原话：「pass@1 高但 token 花 10 倍的方案生产上不可接受」。指标清单（全部可从 trace 程序化统计，代码判）：Token avg/p95（input/output 分开）、工具调用次数 avg/p95、延迟 **p50/p95/p99**（只看均值会掩盖尾部，agent 的耗时大头常在工具与外部等待）、失败重试率、单次任务成本 **¥/task**。落地要点：① 每个任务带成本画像，报告里与质量分并排（腾讯测评报告含模型版本与费用、总 token、平均费用每 Trial）；② 效率退化要能扣进总分（腾讯 TPerf：耗时基准 300s 每超 10% 扣 1 分，token 每超基线 10% 扣 1 分，上限 −10）；③ 质量与成本冲突时看**能力-成本前沿**：质量持平（统计噪声范围内）时选便宜的。实例：DoorDash 模型迁移（Sonnet 4.6→Gemini 3.5 Flash），离线 harness 先发现分数大跌、定位为兼容性而非能力差距，小修后质量持平（harness 噪声范围内），迁移生产**延迟降 35%、质量无损**——质量指标守底线、效率指标换收益的标准操作。

#### 题 6（进阶）：groundedness（有据性）和幻觉率怎么度量？怎么保证度量本身可信？

**参考答案：**
度量方法：把「agent 的每条论断」与「其背后的证据（检索片段/工具返回）」交给 LLM-as-a-Judge 按 rubric 逐条核对，输出 pass/fail + 理由；幻觉率 = 无证据论断占比。工程上三个关键点：① **证据切片**——judge 不该读全量 trace，DoorDash 的做法是每条 rubric 标准声明依赖的证据，transcript builder 只给 judge 那一片（grounding 检查拿论断 + 背后工具输出），聚焦证据让判断更一致；② **judge 必须校准**——Airbnb 的 groundedness judge 初始与人工一致率仅 78%（会误罚正确的改述），修订 rubric 与 few-shot 后达 88% 才上量；阿里的口径是与人工一致率约 85% 后进自动化，腾讯是 ≥85% 可用；③ **归因要下探到检索层**——幻觉失败常因检索没召回正确文档，需配合组件级指标（context recall 低是检索问题，faithfulness 低是生成问题）。参考数字：Airbnb 100 样本探索中 15 个 groundedness 失败是最大失败类；OpenAI 官方建议文档问答 recall ≥ 0.85、precision ≥ 0.7。幻觉率要按切片（场景/知识域）报告，并作为 P0 安全维度进门禁（腾讯五维之一）。

#### 题 7（进阶）：你负责的评测指标被「刷」了——优化后分数大涨，但线上投诉没降。如何排查和治理？

**参考答案：**
排查按三段式：**grader 被钻空 / 评测集被污染 / 指标与目标错配**。① grader 钻空：抽查「通过但可疑」的样本——agent 是否修改了测试文件、对单点断言表面达标、用固定话术骗过 rubric（SWE-bench 类评测已有改测试文件骗分的实证，arXiv:2506.12286）；② 评测集污染/过拟合：团队是否针对已知用例调 prompt，用复述变体试探、检查通过率是否远超线上真实分布；③ 指标错配：优化的是 proxy（离线 helpfulness 分），真实目标 gold（线上投诉）没动——这正是 Goodhart 定律，OpenAI 的 overoptimization 标度律（arXiv:2210.10760）给出定量形态：proxy 持续上升时 gold 先升后降。治理：a) **代理指标旁永远挂独立 gold 指标**（线上转人工率、投诉率、人审抽检），跟踪 proxy-gold 背离，背离即停；b) 指标组合替代单一北极星（质量 pass^k + 安全 + 成本同时看）；c) 按切片报告，平均分最易被攻破；d) 评测集定期换血、保留私有 holdout；e) 对 grader 做红队（喂「看起来对其实错」的对抗样本）。观念：分数大涨的第一反应是怀疑测量系统，不是庆祝。

#### 题 8（系统设计）：为一个电商退款客服 Agent 设计完整的评估指标体系与发布门禁。

**参考答案：**
分五层设计。**① 维度框架**（腾讯五维 + 阿里分层）：功能正确性（P0，代码判）——任务完成率按数据库终态校验（退款单状态、金额精确到分），不评自然语言话术；鲁棒与安全（P0）——pass^k（k=3/5）、幻觉率、误拒/漏拒、越权断言（must-not-call：不得跳过订单状态校验）、PII 合规；过程质量（P1，Rubric）——是否先查订单状态再承诺、关键澄清是否发生；效率（P1，代码判）——token/调用次数 avg&p95、延迟 p50/p95/p99、¥/task；体验（P2）——语气、解释完整性、转人工率、重复追问率。**② 一致性口径**：重复运行 N=5，关键决策类 0% 容忍——退款不可逆，任何一次失败都是事故，门禁看连续成功率 pass^3；同时报至少一次成功率作能力参照。**③ 统计口径**：golden set 起步 50–200 条（阿里），覆盖核心路径 + 高风险边界（已发货退款、运费险、特殊类目——业务先定口径），版本对比用配对检验 + 95% CI + 预设 MPP；报告 Wilson 区间与试验次数。**④ 门禁规则**：P0 硬门禁（核心场景通过率 ≥ 阈值、P0 风险样本失败 = 0、pass^3 达标、安全集 0 漏拒），P1 显著性比较（不劣于基线 + 成本不超基线 50%），P2 观察不拦截；离线门禁与线上灰度联动，离线升线上降 → 回滚（阿里）。**⑤ 运营闭环**：线上每日抽样（参考 Airbnb 5% 去标识化流量）用同一 rubric + 同一校准 judge 打分（离线在线同口径，DoorDash 原则）；badcase 进 RCA（阿里五步）与回归集（只增不减）；judge 升级时重跑三项统计（与人工一致性/高风险漏判率/边界稳定性）。评分器选型遵循确定性 > Rubric > 人工（腾讯），judge 校准到 ≥85% 一致率才上量（详见第 E05 章）。

## 五、易错点 · 反直觉点

1. **只报单次成功率，不报一致性**：「准确率 80%」的 agent，pass^8 只有 16.8%。用户不接受「多试几次总有一次成功」——无人值守场景必须报 pass^k。*记忆锚点：能力看 pass@k，发布看 pass^k。*
2. **用「n 次里成功过任意一次」冒充成功率**：这实际是 pass@n（n 是总试验次数），会系统性高估 pass@k；同理用 (c/n)^k 估一致性也是危险方向的高估。正确口径是无放回组合估计 1−C(n−c,k)/C(n,k)。*记忆锚点：很多「好看」的评测数字，是口径选出来的。*
3. **门禁只看差了多少，不看是否超过噪声**：n=100 时 ±7 个点都是噪声，82%→85% 不构成发布理由。门禁要带置信区间 + 显著性 + 最小可感知变化三件套。*记忆锚点：没有误差范围的对比结论可能只是噪声。*
4. **万能 helpfulness 分**：什么都能评 = 什么都评不准，语气好、篇幅长都能刷高分，制造虚假信心（Airbnb 三坑之首）。指标要从观察到的真实失败模式推导。*记忆锚点：先有失败模式，后有指标。*
5. **平均每轮分数高 = 会话成功**：每轮都「答得还行」但最终没解决问题仍是失败（阿里）。任务完成率要落在 Session/Outcome 层，用终态校验而非文本匹配。*记忆锚点：嘴上说已取消，数据库纹丝不动。*
6. **只看质量不看成本**：pass@1 高但 token 花 10 倍的方案生产上不可接受（腾讯）。质量相近时，延迟 p99 与 ¥/task 决定选型。*记忆锚点：成本画像与质量分并排上报。*
7. **指标 KPI 化后被反向刷爆**：指标成为目标就不再是好指标——proxy 持续上升时 gold 先升后降（arXiv:2210.10760）；二元对错计分还会激励瞎猜与幻觉（arXiv:2509.04664）。代理指标旁必须挂独立 gold 指标。*记忆锚点：分数大涨先怀疑尺子，再怀疑模型。*
8. **通过率 0% 或 100% 归因于模型**：多数时候是任务定义或评分器坏了，不是模型弱/强（腾讯人工评分六大场景之「诊断异常」）；0% pass^N 通常说明任务定义有问题。*记忆锚点：极端分数先查尺子和卷子。*
9. **能力套件与回归套件用同一预期**：能力评测起步通过率应偏低（20–50%，指方向），回归评测应接近满分（确定性任务 100%、非确定性 ≥95%，拦退化）。用回归的预期要求能力集会打击探索，反之会漏掉回归。*记忆锚点：能力集是山峰，回归集是底线。*
10. **尺子自己热胀冷缩**：judge 模型/prompt、rubric 升级后直接对比历史分数，趋势图失真。评分器要版本化，升级时重新校准并做桥接（阿里 judge 持续运营三统计：与人工一致性、高风险漏判率、边界稳定性）。*记忆锚点：换尺子之前，先用旧尺子量一遍新尺子。*

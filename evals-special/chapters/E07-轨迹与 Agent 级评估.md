# 第 E07 章 · 轨迹与 Agent 级评估

> 一句话导读：只看"最终答案对不对"的评估，会系统性放过 Agent 最危险的失败——结果碰巧对、路径已经错。本章讲透过程级评估的完整工程：为什么 outcome-only 有四个盲区、Airbnb 三层模型（step/trajectory/session）与阿里四层评判（Turn/Session/Trace/Outcome）如何分工、结构化 Trace 为什么是被测 Agent 的标准能力而非事后补救、DoorDash 的 Transcript Builder 如何把原始 trace 塑形为 judge 能用的证据切片、腾讯 LCS 序列比对怎么做归一化与扣分、评测如何镜像多智能体运行时架构，以及 2024–2026 前沿（PRM、progress rate、Agent-as-a-Judge、元评估）如何落到工程。学完本章，你能设计一套"结果 + 过程"双门槛的 Agent 级评估体系，并回答面试中最常被追问的那句："你怎么知道 Agent 不是碰巧答对的？"

## 二、核心概念精讲

### 2.1 为什么只看最终答案不够：四个盲区与"假阳性"

阿里对这件事的表述最直接：**"有些样本最终答案看似对，但执行路径已偏离或带风险——这类假阳性在生产迟早暴露。"** 腾讯痛点表里也有同款一条："过程易忽略——答案碰巧对但推理路径错，分不清'正确调用工具后回答'与'训练数据碰巧答对'"。Airbnb 则从请求结构给出根因：一次 Agent 请求可能同时包含搜索、推理、外部动作、文本生成，**每个环节都可能独立失败**，而最终文本把所有中间失败都"抹平"了。

先看一次请求的内部结构——Airbnb 所说"每个环节可独立失败"的解剖图：

```
一次客服 Agent 请求（五个环节，任何一个可独立失败）
用户："帮我退掉昨天买的订单"
   │
   ├─ ① 意图识别    ── 可能把「退货」识别成「物流查询」
   ├─ ② 检索        ── 可能召回错误的退款政策文档
   ├─ ③ 推理与规划  ── 可能漏掉「先查订单状态」这一步
   ├─ ④ 工具调用    ── 可能把 order_id 参数传错、或压根没调用
   └─ ⑤ 回复生成    ── 可能编造「一定退款成功」的过度承诺
   │
   ▼
最终回复："好的，已为您提交退款，请留意到账。"
   └── 只读这一句话，①~⑤ 的失败全部不可见
```

只看最终答案（outcome-only）的评估有四个盲区：

| # | 盲区 | 具体表现 | 后果 |
|---|---|---|---|
| 1 | **假阳性（结果对、路径错）** | 退款 Agent 跳过"查询订单状态"工具，凭上下文直接答"已为您退款"，恰好这次订单确实可退 | 风险敞口持续存在；下一次遇到不可退订单就是资损事故 |
| 2 | **诊断盲区** | 一条 20 步的失败轨迹，错误可能发生在第 3 步，但终局只有一个 0/1 标量 | 失败无法归因，只能靠人肉读日志；迭代没有方向 |
| 3 | **捷径与欺骗** | Agent 绕过规则、伪造输出、reward hacking——最终状态"看起来对"不代表过程正确 | 评测分被刷高，线上行为不可控 |
| 4 | **碰运气不可复现** | "训练数据碰巧答对"与"正确调用工具后回答"在最终文本上无法区分 | 通过率虚高，换一批用例立刻打回原形 |

把阿里那个退款案例展开成 trace 视角，假阳性的结构一目了然：

```text
期望轨迹：verify_identity → get_order_status → (可退?) → apply_refund → notify_user
实际轨迹：verify_identity → [get_order_status 缺失] → 直接生成「已退款」回复
outcome 评分：回复礼貌、格式正确、包含订单号 → 满分 ✗
trajectory 评分：关键校验工具未调用 → 硬门禁拦截 ✓
```

一个贯穿全章的真实案例（阿里 badcase 库）：用户咨询"已发货的订单怎么退款"，Agent 没有调用订单状态查询工具，直接按"未发货退款"流程回复并承诺退款成功——最终回复看起来礼貌、完整、格式正确，outcome 评分拿满分；但路径上**关键校验工具未调用**，且承诺了政策不允许的"一定退款成功"。这类样本在离线评测集里以"通过"存在，直到线上产生投诉才被回流（详见第 E11 章 · Badcase 根因分析与优化闭环）。阿里的结论：对这类 case 必须**加过程型与风险型检查**。

还要注意**双向背离**：过程全对但终局失败（环境抖动、最后一步失误）与终局成功但过程违规，是两个方向的反例。工业界（如客服 Agent）因此普遍采用"**终态正确 + 规则合规**双门槛"，而不是二选一。学界的过程奖励模型（PRM）研究更关注前一个方向，这也是学术指标直接搬进生产会水土不服的原因之一。

> 动手验证：`cd evals-special/labs && python3 eval_lab06_trajectory_eval.py`。lab 构造了四类运行（完全正确 / 结果对但路径错 / 路径对但结果错 / 全错），断言 outcome-only 评分必然放过"结果对但路径错"的假阳性样本，而三层评估 + 硬门禁能把它拦下来。

### 2.2 三层评估模型：step / trajectory / session（Airbnb）与四层评判（阿里）

Airbnb 的 Agentic 评估框架把评估对象切成三层：

| 层 | 评估对象 | 回答的问题 | 典型判定手段 | 失败时指向的根因 |
|---|---|---|---|---|
| **Step-level** | 单次工具调用 / 单个推理步 | 这一步合法吗？参数对吗？是不是禁用动作？ | 参数 JSON Schema 校验、must-call / must-not-call 断言、禁用动作检查（程序化，见第 E04 章） | 单工具实现问题、参数生成缺陷 |
| **Trajectory-level** | 整条路径 | 路径合理吗？高效吗？有没有绕路、重复、跳步、顺序颠倒？ | 与基线序列 LCS 对齐、无序关键调用集合比对、步骤数/token 预算检查 | 规划与编排问题、SOP 未被遵循 |
| **Session-level** | 整个交互 | 用户目标达成了吗？关键信息都覆盖了吗？ | 终态比对（数据库 diff）、目标 checklist、judge 对最终回复评分 | 目标理解问题、需求遗漏 |

三层各自独立失败，任何一层都不能代替另外两层：session 分高掩盖不了 trajectory 违规（假阳性），trajectory 完美也救不了 session 失败（白跑一趟）。这与 2.1 的双向背离一一对应。

阿里面向对话 Agent 给出同构但更细的四层：**Turn（单轮）/ Session（整段会话）/ Trace（执行轨迹）/ Outcome（最终结果）**，并特别警告一个对话场景特有的陷阱：**不要只平均每轮分数**——"每轮都答得还行，但最终没解决问题，仍是失败"。举个例子：一段 8 轮的退款客服会话，每轮都礼貌响应、有问必答（turn 平均分 4+/5），但全程没有调用过一次退款工具，用户最后一句还是"钱还没到"——turn 均值很漂亮，outcome 层却是彻底失败。四层必须同时看，而不是取平均。四层与 Airbnb 三层的对应关系：

| 阿里四层 | Airbnb 三层 | 特殊说明 |
|---|---|---|
| Turn | （step 的对话侧投影） | 单轮回复的语气、澄清质量；平均分陷阱的源头 |
| Trace | step + trajectory | 执行轨迹层：工具调用序列、计划、检索记录 |
| Session | session | 整段会话是否推进了用户目标 |
| Outcome | session 的结果面 | 最终结果是否真正解决问题（工单闭环、退款成功） |

多智能体系统下还有一个工程要点（Airbnb）：Agent 通常在 root 下发 trace 和 span，评估侧可以**通过树遍历重建 trace，校验 subagent 调用与工具使用**——即轨迹结构本身（谁调用了谁、嵌套是否正确）也是评估对象。第 E08 章会展开多 Agent 场景的模拟器设计，主手册第 8 章则从 DAG 视角讨论了 handoff 评估，本章聚焦"轨迹怎么判分"。

### 2.3 Trace 先行：结构化 Trace 是被测 Agent 的标准能力

轨迹评估的输入是 trace。阿里与腾讯不约而同把这件事提到原则高度：**"Trace 输出是被测 Agent 的标准能力，而非事后补救"**（阿里）；"设计阶段就把结构化 Trace 作为标准能力，而非事后补救"（腾讯）。理由很朴素：三层评估器全部消费 trace——step 层逐个 span 校验、trajectory 层抽取调用序列、session 层读取最终回复与终态；没有结构化 trace，过程评估整体不存在。

**（1）span 里记什么。** DoorDash 的 Ask DoorDash 用 OpenTelemetry 打点，trace 存进内部 ClickHouse；span 记录四类内容：**用户输入、模型输出、工具调用与返回、展示给用户的 widgets**。阿里的要求更细：稳定记录工具名、入参、返回值、时间戳、耗时、错误；复杂 Agent 还要记录**计划、检索、Guardrail 判定**。腾讯把"内容完整"具体到"每步工具名/入参/返回/时间戳，理想含思维链与决策依据"。

**（2）结构化三要求（腾讯）**：

| 要求 | 含义 | 违反时的代价 |
|---|---|---|
| **可解析** | 结构化格式（JSONL/JSON），而非自由文本日志 | "有日志无结构"只能写解析器——成本高、易碎，格式一变全线崩 |
| **内容完整** | 每步工具名/入参/返回/时间戳，理想含思维链与决策依据 | 缺入参无法判参数正确性，缺返回无法判 groundedness |
| **跨版本格式稳定** | schema 不因 Agent 升级而漂移 | 历史 trace 与历史分数全部不可比，趋势图断档 |

被测系统不满足时的三档对策（腾讯）：有日志无结构 → 写解析器（下策）；仅最终输出 → 只能做结果评测（中策）；可改造 → **推动被测系统增加 Trace 输出（推荐）**。

满足三要求的最小 trace 长这样（字段对应：腾讯"每步工具名/入参/返回/时间戳" + DoorDash 四类 span 内容）：

```json
{
  "session_id": "sess_20260805_0001",
  "agent_version": "refund-agent-v1.8",
  "spans": [
    {"span_id": "s1", "type": "user_message",
     "content": "帮我退掉订单 #1234", "ts": "10:00:00.000"},
    {"span_id": "s2", "parent": "s1", "type": "tool_call",
     "name": "get_order_status", "params": {"order_id": "1234"},
     "ts": "10:00:01.210", "duration_ms": 180},
    {"span_id": "s3", "parent": "s2", "type": "tool_result",
     "result": {"status": "shipped", "refundable": false}, "ts": "10:00:01.390"},
    {"span_id": "s4", "parent": "s1", "type": "llm_call", "model": "model-x-v2",
     "input_tokens": 1840, "output_tokens": 96, "duration_ms": 920},
    {"span_id": "s5", "parent": "s1", "type": "assistant_message",
     "content": "该订单已发货，暂不支持直接退款……", "ts": "10:00:02.400"}
  ]
}
```

注意两点：`agent_version` 这类元数据是跨版本可比性的前提（分数差异归因）；多智能体场景再加 `parent_agent`/subagent 调用边，Airbnb 正是靠树遍历重建 trace 并校验 subagent 调用。span 层级的推荐设计是 `session → agent/task → llm_call → tool_call`，为 OTel agentic conventions 留位置。

**（3）标准化进展。** 行业侧的收敛方向是 OpenTelemetry GenAI semantic conventions（`gen_ai.*` 属性命名空间）。按时间线（据调研整理）：2024 年各家私有 schema 混战（Traceloop OpenLLMetry、Arize OpenInference 等）→ 2025-01 OpenLLMetry 语义约定并入 OTel → 2025-03 OTel 官方博客发布 AI agent 可观测性标准路线图 → **2025-08 提出 agentic systems 语义约定提案（agent/task/chain/tool 层级 span 属性）** → 2025-12 Datadog 等厂商宣布原生支持 OTel GenAI semconv（v1.37+）。注意：截至 2026 年中，GenAI 语义约定仍处于 **Development（开发中）** 稳定性；部分 agent/tool 属性（如 `gen_ai.agent.id`）已进入属性 registry，但完整的 agentic span 约定仍在提案推进中、命名可能变（与主手册第 8 章口径一致）——工程上的务实做法是第一天就按 `gen_ai.*` 属性打点、同时保留私有字段兼容层，span 层级按 `session → agent/task → llm_call → tool_call` 设计，为 agentic conventions 留位置。核心属性速查：

| 属性 | 含义 | 对轨迹评估的用途 |
|---|---|---|
| `gen_ai.system` | provider | 区分多供应商混部的分数归因 |
| `gen_ai.request.model` / `gen_ai.response.model` | 请求/实际模型 | 模型迁移时分数可比性（见 DoorDash 模型迁移案例，第 E15 章） |
| `gen_ai.usage.input_tokens` / `output_tokens` | token 用量 | trajectory 层效率预算（token 超标扣分）的数据源 |
| `gen_ai.operation.name` | chat / embeddings / agent 等 | span 类型识别，驱动 trace 解析器 |

**（4）trace 的复利。** trace schema 稳定之后会产生三重回报：生产 trace 是免费的评测集来源（脱敏后可直接转回放用例）、失败聚类有了统一字段（详见第 E12 章 · 在线评估与数据飞轮）、自动诊断有了输入（2.8 节的 TRAIL/AgentDebug 都以 trace 为输入）。阿里把评测执行环境隔离也列为配套要求——多用例共享状态会导致分数不可复现，这与 trace 完整性同属"评估前置条件"。

### 2.4 Transcript Builder：把原始 Trace 塑形为"证据切片"（DoorDash）

有了 trace 不等于能判分。DoorDash 的原话：原始 trace **完整但难判**，具体三难：

1. **工具返回可能巨大**——一次餐厅搜索 API 返回上百条记录，judge 的上下文窗口装不下，装得下也会被淹没；
2. **schema 脚手架与无信号字段多**——内部协议字段、调试标记占了大量 token，对判定毫无贡献；
3. **证据散落多个 span/turn**——判断"推荐是否有据"需要把第 2 轮的论断和第 5 轮的工具返回拼在一起。

解法是 **Transcript Builder**：一组 Python 脚本，做三个动作——**重组分散的 span、删除无质量信号的 token、裁剪超大载荷**，产出紧凑视图。关键设计在下一步：**每条 rubric 标准声明自己依赖的证据，builder 只把那一片交给 judge**。原文给出三个实例：

| rubric 标准 | judge 拿到的证据切片 |
|---|---|
| grounding 检查（论断是否有据） | Agent 的论断 + 背后的工具输出 |
| 多样性检查（推荐是否真实差异） | 推荐列表 + 用户原始请求 |
| 叙述检查（是否泄露内部过程） | Agent 工作时流式输出的文本 |

塑形前后对比（示意，字段取自 DoorDash 原文描述）：

```text
【judge 前：原始 trace 片段】
tool_result(search_restaurants):
  {meta: {request_id:"...", schema_v:"3.1", debug:{...数百字...}},
   results: [{name:"A", price:..., rating:..., eta:..., promotions:[...],
              tracking:{...}}, ... 共 137 条 ...]}      ← 数万 token，大量无信号字段
assistant(span #12): "A 川菜馆离您很近，30 分钟可达"      ← 待核验的论断
...（中间隔 7 个 turn 的其他 span）...

【judge 后：grounding 证据切片】
assertion: "A 川菜馆离您很近，30 分钟可达"
evidence:  search_restaurants.results[0] → {name:"A 川菜馆", distance_km:0.8, eta_min:30}
verdict: ____   rationale: ____
```

效果是"聚焦证据让判断更一致"——这与第 E05 章的 judge 校准逻辑同构：给 judge 的无关上下文越多，偏差与方差越大。DoorDash 把它列为四条 Lessons Learned 的第一条："Judge 需要'为问题塑形'的 transcript 视图——删无关、只留标准依赖的证据。"

工程上可以这样理解：Transcript Builder 是"评测侧的 ETL"。它把一份完整的原始 trace（存 ClickHouse 的那份）物化成 N 个按标准定制的视图；原始 trace 保留用于人工复核与 RCA，视图只服务自动评分。这带来一个附带好处——**judge 误判时，人审可以回到原始 trace 查证**，评分与证据链永远可追溯。实现时的两个注意点：裁剪规则要版本化（裁过头会把关键证据切掉，属于"评测系统自己产生的 bug"，DoorDash Lesson 4 明确说被标记失败中有真实一部分是 harness 自身故障）；每条标准的证据声明应与 rubric 一起 review，二者是同一个契约的两半。

### 2.5 轨迹比对与 LCS 序列对齐：腾讯实现

trajectory-level 的核心动作是"把这条轨迹和预期路径比一比"。最直觉的做法是 exact match（完全一致才通过），但它是轨迹评估的头号反模式：同一任务存在多条合法路径（先查订单还是先验身份？），exact match 会把大量正确行为判错，评估集退化成"背答案"。可用的比对粒度由严到宽：

| 比对方式 | 判定逻辑 | 适用 | 缺点 |
|---|---|---|---|
| Exact match | 序列逐项全等 | 几乎不适用 | 合法变通路径全部误杀 |
| **LCS 对齐 + 归一化** | 最长公共子序列求公共骨架，偏差分类扣分 | 有标准 SOP、步骤顺序重要的任务（腾讯 TPerf） | 需要维护基线快照 |
| 无序关键调用集合 | 只查关键工具调没调、参数对不对，不管顺序 | 路径自由度高的任务 | 抓不住顺序依赖（先鉴权后操作） |
| 偏序约束 | 只断言先后关系（A 必须在 B 前） | 有安全依赖但路径自由的任务 | 约束要逐条人工设计 |
| LLM/Agent 评审 | judge 读轨迹给 rubric 分 | 无法穷举规则的开放任务 | 需校准，先过元评估（见 2.8） |

腾讯 TPerf（AI 性能分析 Agent）给出目前公开细节最完整的 LCS 实现。完整流水线分四步：

**第一步：归一化。** 对齐之前先把"不影响对错的差异"抹掉，否则同一行为每次运行都会被判"不一致"。五条规则：

| 归一化规则 | 抹掉的差异 | 不抹会怎样 |
|---|---|---|
| 时间戳占位 | 每次运行的绝对时间不同 | 每一步都不匹配 |
| 搜索类工具忽略查询参数 | 同一检索意图的措辞差异 | 合理改写被判参数错 |
| 写入操作只留路径 | 文件内容的合理差异 | 产物比对退化为 diff 全文 |
| 终端命令提取脚本名 | 命令参数顺序/细节差异 | 等价执行被判不一致 |
| 连续读文件组内不校验顺序 | 并行读多个文件的次序 | 并发调度差异被误罚 |

**第二步：LCS 对齐。** 对归一化后的基线序列与 trial 序列求最长公共子序列（LCS），LCS 即两者的"公共骨架"，代表被正确执行的部分。

**第三步：偏差分类扣分。** 没进入 LCS 的 span 分成四类：**不一致 / 多余 / 缺少 / 顺序错，各扣 2 分，本维度上限 -10**。"缺少"里最严重的子类是"缺少关键校验步骤"——在综合判定中它不应只扣 2 分，而应触发硬门禁（见 2.8 与 lab06）。

**第四步：效率对比。** 过程质量不只看"走对没有"，还看"走贵没有"：耗时以 300 秒为基准，每超 10% 扣 1 分；token 以基线为基准每超 10% 扣 1 分，上限 -10。这与腾讯五维指标中"效率与成本"一脉相承——"pass@1 高但 token 花 10 倍的方案生产上不可接受"。

用一个最小例子走一遍对齐（lab06 中的场景）：

```text
基线 SOP：[verify_identity, get_order_status, apply_refund, notify_user]

Trial A：[verify_identity, apply_refund, get_order_status, notify_user]
  LCS 公共骨架（长度 3）：[verify_identity, get_order_status, notify_user]
  偏差分类：apply_refund 与 get_order_status 顺序错（-2）
  ——违反「先查状态、再办退款」的 SOP，但两步都在 → 扣分即可

Trial B：[verify_identity, apply_refund, notify_user]
  LCS 公共骨架（长度 3）：[verify_identity, apply_refund, notify_user]
  偏差分类：get_order_status 缺少
  ——缺少的是关键校验工具 → 不走扣分，直接触发硬门禁判失败（假阳性）
```

对应的判定骨架（示意）：

```python
def trajectory_score(trial_spans, baseline_spans):
    t = [normalize(s) for s in trial_spans]     # 五规则归一化
    b = [normalize(s) for s in baseline_spans]
    lcs = longest_common_subsequence(b, t)      # 公共骨架
    for span in classify_unmatched(b, t, lcs):  # 缺少/多余/不一致/顺序错
        if span.kind == "missing" and span.critical:
            return HARD_GATE_FAIL               # 关键校验缺失：一票否决
        deduct(2, cap=-10)
    deduct_efficiency(duration_vs=300, token_vs=baseline, per_10pct=1, cap=-10)
    return max(0, 100 + total_deductions)       # ≥80 达标（腾讯口径）
```

配套的**基线快照机制**（腾讯）：用例设计只定义 prompt 与检查规则 → 执行 1 次 → 人工审核过程与结果 → 不可接受则修后重跑 → 可接受则该次快照成为基线（含 CoT、工具调用序列、中间产物、完整 trace、最终响应）。基线更新时机只有三个：Agent/Skill 逻辑变更、模型版本升级、用例本身修改。TPerf 实战规模：9 大场景分组 30+ 用例（CPU 瓶颈 6 / 网卡 5 / 磁盘 4 / 磁盘 IO 2 / 内存 1 / TCP 队列 3 / Nginx 1 / 配置问题 1 / 正常场景 5），支持 7 模型参数化对比，单用例约 3000 秒，全量 30+ × 7 模型约 3–5 小时；基线配置随代码仓库 Git 版本化，执行结果每次重新生成归档，且支持"重新评分"（评分逻辑调整后无需重跑 Agent）。

### 2.6 评测镜像运行时架构：多智能体系统怎么切评估责任（DoorDash）

当被测系统本身是多智能体架构，评估体系应该**与运行时架构同形**，否则失败无法归因到 owner。DoorDash Ask DoorDash 的运行时：用户消息 → **Orchestrator**（路由层）→ 分发到领域 Agent（如 Restaurant Discovery Agent、Grocery Shopping Agent）→ 领域 Agent 直接处理或交还 Orchestrator。评测按同一结构切分：

| 运行时组件 | 评测对象 | 评估什么 | rubric 归属 |
|---|---|---|---|
| Orchestrator 路由层 | 路由决策 | 消息是否被分发给正确的领域 Agent；该转不转 / 转错人 | 路由专项评测 |
| 贯穿全流程 | 护栏（Guardrail） | 全体 Agent 共同遵守的标准，如"回复简洁、不向用户叙述思维过程""不呈现可证伪虚假信息" | Guardrail 类 rubric（全 Agent 通用） |
| 领域 Agent | 任务能力 | 该领域的能力标准，如餐厅发现的"约束满足（配送时间/预算/饮食限制）""结果多样性（真实差异而非近似重复）"；杂货购物的"购物执行（用户明确修改请求被执行）""商品相关性" | Capability 类 rubric（按领域） |

这个同形设计回答了多智能体评估最容易扯皮的问题："端到端分数掉了，是谁的锅？"——路由错误记 Orchestrator，领域任务失败记领域 Agent，护栏违规则跨 Agent 追。DoorDash 的 rubric 工程还有两个与轨迹评估直接相关的细节（rubric 工程本身详见第 E05 章）：

- **每条标准是 binary check，汇总为会话级总分**——二值判定比连续打分稳定，轨迹级证据交给 judge 时尤其如此；
- **checklist 式场景 rubric**：把标准下沉到场景级清单，例如"两人份 ≤$60 素食 taco 购物清单"场景，清单逐项验证"每件商品都是素食 taco 原料、小计 ≤$60"。这类具体清单比宽泛通用标准**方差更低**，小样本也能给出可用信号，支撑更快迭代。

另一个连接点：Eligibility 适用性前置——judge 先判该标准是否适用本会话，不适用则跳过（例如食谱流程不因缺少复购步骤被扣分）。这防止"用 A 场景的轨迹标准去罚 B 场景的合法路径"，是轨迹评估中路径多样性问题的 rubric 侧解法。

这套"trace 基础设施 + 证据切片 + 镜像架构"的组合拳带来的业务结果（DoorDash 原文数字）：从平均每天仅 1 条员工反馈，到**每天 2,000 个自动评分会话**；全国上线前 agent 质量分 **+8 分**、错误率**近乎减半**；全量回归从手工 **6+ 小时压缩到约 20 分钟**——过程级评估不是成本中心，而是让发布敢踩油门的依据。

### 2.7 前沿一：过程奖励模型（PRM）与信用分配

评估视角的"给步骤打分"，在训练视角叫**过程奖励 / 信用分配（credit assignment）**——同一套信号，评测用它归因，RL 用它训练。2023–2026 这条线的演进值得每个做 Agent 评估的工程师了解，因为 PRM 正在成为轨迹评估的候选评分器。

**PRM vs ORM 的形式化**：ORM（outcome reward model）对完整解给一个分数；PRM（process reward model）对每个步骤给分数，整解分数通常取各步对数似然加和 `score(y) = Σ_i log r_i`。同一套步骤分数有四个用途，评测工程师至少会碰到前三个：

| 用途 | 形态 | 例子 |
|---|---|---|
| 推理时选择 | best-of-N 重排序（选 argmax score） | PRM800K：best-of-1250 把 MATH 从 52.9% 抬到 78.2% |
| 推理时搜索 | 束搜索 / 树搜索的节点估值 | MCTS + PRM（rStar-Math） |
| 训练时奖励 | RL 的稠密奖励，缓解终局奖励稀疏 | Math-Shepherd 逐步 PPO、StepAgent、SPA-RL |
| 纯评测 | 分数报告与失败诊断 | 步骤分数定位"模型卡在哪一步" |

**标注成本的三次下降**（这是 PRM 工程化的主线）：

| 阶段 | 论文 | 方法 | 关键数字 |
|---|---|---|---|
| 人工标注 | Let's Verify Step by Step（PRM800K，arXiv 2305.20050，2023） | 80 万条人工步骤标注（correct/incorrect/neutral 三标签）训练 PRM | GPT-4 直接解 MATH 52.9%；PRM best-of-1250 达 78.2%（ORM 约 72%）；步骤级标签达到同等性能所需样本量约低 100 倍 |
| 蒙特卡洛自动标注 | Math-Shepherd（arXiv 2312.08935，2023） | 对某步之后的续写做多次 rollout，"该步之后能走到正确答案的比例"作为软标签 | Mistral-7B GSM8K 77.9%→84.1%（逐步 RL），加验证 89.1%；MATH 28.6%→33.0%，加验证 43.5% |
| 二分搜索 | OmegaPRM（arXiv 2406.06592，2024） | 二分定位第一个错误步骤，单条轨迹标注成本 O(n)→O(log n) | 无人工干预 MATH rollout 正确率相对 SFT 基线 +24%；标注成本较朴素蒙特卡洛降约 100 倍 |

OmegaPRM 对评测平台的启示超出标注本身：**给轨迹打分不必逐步全量打分，先粗粒度二分定位可疑区间再细查**——这与调试长轨迹时"先看中间步骤对不对"的人工策略同构。

**两个不需要步骤标签的路线**：

- **PRIME**（arXiv 2412.01981，2024）：token 级价值头 + 隐式奖励，从结果奖励反推每 token 的过程价值，完全不需要步骤标注；对评测的启示是"只有终局真值（如单元测试通过与否）时，仍可通过价值估计获得步骤级归因"。
- **VinePPO**（arXiv 2410.01679，2024）：在轨迹中间状态重采样 K 条续写，用续写实际回报构造无偏的步骤优势估计。工程含义值得单独记住：**"从某步出发的成功率"本身就是该步质量的无偏评估**——不训练任何模型也能回答"这一步到底值多少分"，可直接用作离线轨迹归因工具（数学基准上相对 GRPO/PPO 最高约 +4 个百分点）。

**生成式验证器**：GenRM（Generative Verifiers，arXiv 2408.15240，2024）把验证做成生成任务——先生成对每一步的自然语言批注（critique），再输出 verdict。它桥接了 PRM 与 LLM-as-a-Judge 两个世界：批注式验证提供可解释的打分依据，天然接入 judge 工程栈，是当前步骤级 rubric 评估最常用的打分形式（详见第 E05 章）。

**PRM 的失败学（必读）**：阿里 Qwen 团队的《The Lessons of Developing Process Reward Models in Mathematical Reasoning》（arXiv 2501.07301，2025）系统披露四个结论：① 步骤级标签确实比轨迹级标签更高效；② **PRM 的分数可以被 hack**——best-of-N 选择中模型会生成恰好骗过 PRM 的解（PRM800K 尤其明显）；③ PRM 在**难度外推与分布漂移**下性能显著退化；④ PRM 与 ORM 组合使用效果更好。对应工程清单：任何验证器上线前做对抗性审计（hacking 红队）、按难度分层校准、报告中区分 in-distribution 与 OOD 的可信度。**rStar-Math**（arXiv 2501.04519，2025）进一步指出验证器必须"跟着被测系统一起进化"：它让 PRM 与策略通过 MCTS 共同自进化（Qwen2.5-Math-7B 在 AIME24 达 58.8%，超过 o1-preview 的 40.0%；MATH-500 96.4%）。评测工程上的对应物：**被测 Agent 升级后，旧验证器的分数不可直接比较**，需要重新校准或共同迭代。

综合 Qwen Lessons 与 rStar-Math，把 PRM 当评测器/选择器使用时的工程清单：

1. **标注**：优先蒙特卡洛或二分自动标注（成本可控），人工标注只用于校准集；
2. **分布**：验证器训练分布要覆盖目标难度，OOD 场景分层报告准确率；
3. **红队**：上线前做 reward hacking 对抗审计——专门生成"骗验证器"的样本看它上不上当；
4. **组合**：PRM 与 ORM 组合使用效果更好（Qwen Lessons 结论四）；
5. **共迭代**：被测策略升级后重训/重校准验证器，记录两者的配对兼容性。

**信用分配分类学**（依据 2026 年综述《From Reasoning to Agentic》，arXiv 2604.09459）可作为面试答题框架：按**粒度**（token 级 / 步骤级 / 片段级 / 轨迹级）、按**信号来源**（人工标注 / 模型标注 / 自动估计如 MC rollout 与重采样 / 规则式如单元测试与状态 diff）、按**用途**（训练时奖励 / 推理时选择 / 纯评测报告）。

### 2.8 前沿二：Agent 轨迹的专属评估方法与元评估

PRM 线源自数学推理；Agent 轨迹评估有自己的四个代表工作，各自贡献了一个可迁移的工程范式：

**（1）AgentBoard（arXiv 2401.13178，2024）——progress rate，让失败可诊断。** 为每个任务定义子目标集合，用归一化加权距离衡量轨迹"走了多远"，把 0/1 成功率拆成连续的进展曲线。数据点：即便最强模型总体成功率也仅约 40% 出头；progress rate 与 success rate 的结合揭示了不同模型在规划、探索、利用子能力上的分化。工程迁移：为核心任务定义子目标/检查点，报告 progress rate 而不只是成功率——它直接决定你能不能回答"模型卡在哪一步"。

**（2）τ-bench（arXiv 2406.12045，2024）——执行式验证 + pass^k。** 评估**不靠看对话文本，而是比对对话结束时数据库状态与目标状态是否一致**——纯执行式（execution-based）验证，抗"看起来对"的文本欺骗。关键数字：GPT-4o 级模型成功率 <50%，零售域 pass^8 <25%（pass^k 的统计细节见第 E02 章 · 评估指标体系与第 E09 章 · 评估的统计学基础）。它定义的黄金标准组合是：**状态比对（而非文本判断）+ 多次重复（可靠性）+ 规则合规性检查**。同属执行式验证的还有 **Terminal-Bench**（arXiv 2601.11868，2026）：80 个高难度 CLI 长程任务，每个配 pytest 风格功能测试 + oracle 参考解，最强模型 + agent 组合成功率约 35%。执行式验证的共同模式：`可执行的真值判定程序 + 沙箱`；优点客观可复现，代价是每个任务都要写判定程序。

**（3）Agent-as-a-Judge（arXiv 2410.10934，2024）——评估者要有"手脚"。** 与 LLM-as-a-Judge 的本质区别：**评估者是会执行工具的 Agent**——拿到被测 Agent 的完整代码库/产物后，可以运行代码、做静态分析、逐步对照分层需求打分。配套 DevAI 基准：55 个真实自动化 AI 开发任务、365 条分层用户需求。关键数字（论文摘要口径）：与人工评估同等可靠，相比三位人类专家评估**节省 97.72% 的时间、97.64% 的成本**，且评估质量显著优于纯文本判读的 LLM-as-Judge。它是当前对"开放式产物（代码库、报告）"做过程级评估的主流范式；97% 优势的前提是 rubric 质量与 Judge 的工具权限，且为场景特定报告值、不宜外推为普适结论，引用时应一并说明。

**（4）AgentRewardBench（arXiv 2504.08942，2025）——评估器本身必须被评估。** 这是本方向最重要的"元评估"工作：收集 197 条 Web Agent 轨迹（含成功与人工确认的失败案例），系统测试各类自动评估器识别"轨迹真正成功"的能力。核心发现令人清醒：**多数评估器的 false positive 率极高——多个常用评估器在失败轨迹上的误报率超过 50%**，纯 LLM 判别尤其不可靠；结合代码/执行检查与分步核对的方案明显更好。落地要求：**任何轨迹评估器（尤其 LLM judge）上线前，先在已知成败的轨迹集上测 FPR/FNR**；优先选择有执行式依据的评估器；把评估器准确率作为评测基础设施的一级指标。

把四者串起来，得到轨迹评估器的选型优先级（与第 E04 章"确定性优先"一脉相承）：

```
规则/执行式验证（终态 diff、单测、schema、must-call 断言）
        ↓ 覆盖不到的语义判断
Agent-as-a-Judge / 带证据切片的 LLM judge（须过元评估：已知成败集测 FPR/FNR）
        ↓ 高风险 / 低置信 / 评估器分歧
人工抽检（校准 judge、审"结果对但轨迹可疑"样本，见第 E06 章）
```

**trace 级自动诊断的现状**：TRAIL（arXiv 2505.08638，2025）提出覆盖子代理/工具调用/任务推理等维度的 27 类错误分类学，发布 148 条人工标注 agent trace；即便最强模型，"给定完整 trace 定位根因"的准确率也仅约 40–60%。AgentDebug（arXiv 2509.25370，2025）把失败归因到 6 个模块（工具使用、上下文/记忆管理、规划、验证等）并做"诊断→修复→复跑"闭环，失败恢复率提升约 10% 量级。SentinelAgent（arXiv 2505.24201，2025）则把视角从"事后诊断"推向"运行时监控"：将 agent 间交互建模为图结构，由专职监督 agent 结合图拓扑与运行时指标做异常检测与归因——离线评测保证出厂质量，运行时异常检测保证存量质量，二者互补（在线侧详见第 E12 章）。结论：trace 质量与 span 粒度决定自动诊断上限；LLM 诊断结果应作为"待人工确认的假设"呈现，而非自动修复。

**综合判定：加权平均 vs 硬门禁。** 三层分数如何汇总成一个判定？lab06 给出的答案是"加权 + 一票否决"双轨：常规偏差（顺序错、多余步骤、效率超标）用扣分制（腾讯 80 分达标线）；但**禁用动作命中、关键校验缺失、最终目标未达成**这三类失败不允许被其他层的高分"平均"掉——跳过身份校验不能靠"语气好"补回来。门禁的数量要克制，否则误杀率上升，评估体系会退回"没人信"的状态（门禁设计的完整讨论见第 E10 章 · 评测驱动开发）。

**本节收束：轨迹评估落地清单**（把 2.3–2.8 压缩成八条可执行动作）：

1. 结构化轨迹日志先行——没有满足三要求的 trace，后面全部免谈；
2. 评估器分层——规则/执行式验证为主，Agent/LLM judge 为辅，人工抽检校准；
3. 评估器先过元评估——在已知成败的轨迹集上测 FPR/FNR，再谈上线；
4. judge 只拿证据切片——Transcript Builder 塑形，每条标准声明依赖证据；
5. 轨迹比对禁 exact match——归一化 + LCS / 无序集合 / 偏序约束三选一；
6. 长程任务报 progress rate——子目标分解让失败可诊断，而不只是 0/1；
7. 可靠性多次试验——pass@1 + pass^k（k≥4），固定温度与用户模拟协议；
8. 把评估器当资产管理——版本化、定期元评估、记录验证器与被测模型的配对兼容性。

## 四、经典面试题与参考答案

#### 题 1（基础）：为什么评估 Agent 不能只看最终答案？请举一个具体例子。

**参考答案：** 四个盲区：① **假阳性**——结果对但路径错/带风险，如退款 Agent 跳过订单状态查询直接承诺退款成功，这次恰好可退所以"答对了"，但风险敞口一直在，阿里明确这类假阳性"在生产迟早暴露"；② **诊断盲区**——20 步轨迹失败，错误可能在第 3 步，终局只有一个 0/1 标量，无法定位；③ **捷径与欺骗**——最终状态"看起来对"可能来自绕过规则或 reward hacking；④ **碰运气**——"训练数据碰巧答对"与"正确调用工具后回答"在最终文本上无法区分，通过率不可复现。此外还有双向背离：过程全对也可能因环境抖动而终局失败，所以工业界用"终态正确 + 规则合规"双门槛，而不是单看任一侧。

#### 题 2（基础）：说说轨迹评估的三层模型，每层评什么、怎么评、失败说明什么？

**参考答案：** Airbnb 三层：**step-level** 评单工具调用/推理步——参数 JSON Schema 校验、must-call/must-not-call 断言、禁用动作检查，失败指向单工具实现或参数生成问题；**trajectory-level** 评整条路径是否合理高效——与基线做 LCS 对齐、无序关键调用集合比对、步数/token 预算检查，失败指向规划与编排问题（绕路、重复、跳步、顺序颠倒）；**session-level** 评整体是否达成用户目标——终态比对、目标 checklist，失败指向目标理解问题。三层独立失败、不可替代：session 分高掩盖不了 trajectory 违规（假阳性），trajectory 完美救不了 session 失败。阿里对话 Agent 版本是四层：Turn/Session/Trace/Outcome，特别警告"不要只平均每轮分数"——每轮都答得还行但最终没解决问题仍是失败。

#### 题 3（基础→进阶）：什么是结构化 Trace 的三个要求？接手的被测 Agent 没有 Trace 输出怎么办？

**参考答案：** 三要求（腾讯）：① **可解析**——JSONL/JSON 结构化格式而非自由文本；② **内容完整**——每步工具名/入参/返回/时间戳/耗时/错误，理想含思维链与决策依据；DoorDash 的 span 记录用户输入、模型输出、工具调用与返回、展示给用户的 widgets；③ **跨版本格式稳定**——schema 不随版本漂移，否则历史分数不可比。没有 trace 时三档对策：有日志无结构 → 写解析器（成本高易碎，下策）；只有最终输出 → 只能做结果评测（中策）；可改造 → 推动被测系统增加 trace 输出（推荐）。立场要鲜明：trace 是被测 Agent 的**标准能力而非事后补救**（阿里/腾讯共识）。标准化方向是 OTel GenAI semconv（`gen_ai.*` 属性），截至 2026 年仍处 Development 状态，agentic 层级 2025-08 才有提案，应"先按标准打点 + 保留私有字段兼容层"。

#### 题 4（进阶）：DoorDash 的 Transcript Builder 解决什么问题？如果让你设计，怎么做？

**参考答案：** 问题：原始 trace 完整但难判——工具返回可能巨大（超出/淹没 judge 上下文）、schema 脚手架与无信号字段多、证据散落多个 span/turn。设计分两步：第一步是三个清洗动作——重组分散的 span、删无质量信号的 token、裁剪超大载荷，产出紧凑视图（DoorDash 用一组 Python 脚本实现，原始 trace 仍存 ClickHouse 供人审与 RCA）；第二步是**证据切片**——每条 rubric 标准声明自己依赖的证据，builder 只把那一片交给 judge：grounding 检查拿 agent 论断 + 背后工具输出，多样性检查拿推荐列表 + 原始请求，叙述检查拿流式输出文本。收益：聚焦证据让 judge 判断更一致、上下文成本更低。注意点：裁剪规则要版本化（裁过头是 harness 自身 bug，DoorDash 承认被标记失败中有真实一部分来自评测系统自己）；证据声明与 rubric 是同一契约，要一起 review。

#### 题 5（进阶）：两条工具调用轨迹怎么做比对？为什么不能 exact match？归一化的作用和风险是什么？

**参考答案：** 不能 exact match，因为同一任务有多条合法路径，全等比对会把合法变通判错，评估集退化成背答案。腾讯 TPerf 的 LCS 方案四步：① **归一化**——时间戳占位、搜索类工具忽略查询参数、写入只留路径、终端命令提取脚本名、连续读文件组内不校验顺序；② 求 LCS 公共骨架；③ 非 LCS 部分分类为**不一致/多余/缺少/顺序错，各扣 2 分、上限 -10**；④ 效率对比——耗时以 300 秒为基准每超 10% 扣 1，token 以基线为基准每超 10% 扣 1、上限 -10。归一化的作用是抹掉"不影响对错的差异"，否则同一行为每次运行都被判不一致；风险是**归一化过度**——若把金额、订单号这类关键参数也忽略掉，参数错误会被静默放过，等于把假阳性重新放进来。路径自由度更高的任务可退到无序关键调用集合或偏序约束（只断言"先鉴权后操作"这类依赖）。基线来自"执行 1 次 + 人工确认"的快照机制，只在逻辑变更/模型升级/用例修改时更新。

#### 题 6（进阶）：PRM 和 ORM 有什么区别？没有步骤级标注数据时，还有哪些办法拿到步骤级信号？

**参考答案：** ORM 对完整解打一个分，PRM 对每个步骤打分、整解分数通常取各步对数似然加和。PRM800K（arXiv 2305.20050，2023）证明步骤级标签信息密度约高 100 倍（GPT-4 直接解 MATH 52.9%，PRM best-of-1250 达 78.2%）。没有步骤标注时有四条路线：① **蒙特卡洛标注**（Math-Shepherd，arXiv 2312.08935）——从某步多次 rollout，"走到正确答案的比例"作软标签；② **二分搜索**（OmegaPRM，arXiv 2406.06592）——二分定位第一个错误步骤，标注成本 O(n)→O(log n)，降约 100 倍；③ **隐式奖励**（PRIME，arXiv 2412.01981）——token 级价值头从结果奖励反推过程价值，只有单元测试真值也能用；④ **中间状态重采样**（VinePPO，arXiv 2410.01679）——从某步重采样 K 条续写看成功率，不训练模型即可做离线步骤归因。必须补一句失败学（Qwen Lessons，arXiv 2501.07301）：PRM 分数可被 hack、难度外推下退化，直接当评测器要先做红队与 OOD 分层校准。

#### 题 7（进阶）：Agent-as-a-Judge 和 LLM-as-a-Judge 的本质区别是什么？它能直接信任吗？

**参考答案：** 本质区别：**评估者是否有环境交互能力**。LLM-as-a-Judge 是"阅读式"——读 transcript 打分；Agent-as-a-Judge（arXiv 2410.10934，2024）让 Judge Agent 带工具核验——运行代码、静态分析、逐条对照分层需求，能核验而非仅阅读。在 DevAI 基准（55 个真实 AI 开发任务、365 条分层用户需求）上，它与人工评估同等可靠，相比三位人类专家节省 97.72% 时间、97.64% 成本（场景特定值），评估质量显著优于纯文本判读。但**不能直接信任**，两个理由：① AgentRewardBench（arXiv 2504.08942，2025）用 197 条 Web Agent 轨迹测出多数自动评估器在失败轨迹上的误报率超过 50%，结合执行检查与分步核对的方案才明显更好——所以任何轨迹评估器上线前先在已知成败的轨迹集上测 FPR/FNR；② 97% 的时间/成本优势有前提——rubric 质量与 Judge 的工具权限，开放式产物评估尤其依赖分层 rubric 写得好不好。

#### 题 8（进阶）：什么是"评估器的元评估"？你的轨迹评估方案上线前要做哪些验证？

**参考答案：** 元评估 = 评估"评估器本身"。动机是 AgentRewardBench 的实证：自动轨迹评估器把明显失败的轨迹判为成功的比例普遍超过 50%，且评估器之间差异巨大——不测元指标就上线，等于把质量门禁交给一个未知的分类器。上线前验证清单：① 构造**已知成败的轨迹集**（成功 + 人工确认的失败，含"结果对但过程错"的假阳性样本），测评估器的 FPR/FNR——假阳性识别能力是轨迹评估器的核心能力；② 与人工标注对齐，一致率达到团队口径（Airbnb high 80s~90s，阿里/腾讯约 85%）后才进自动化（详见第 E05 章校准流程）；③ 偏差检查（位置/冗长/同源偏好，见第 E05 章）；④ 稳定性检查（同轨迹重复评分方差）；⑤ 持续运营——judge 模型/prompt/rubric 任一变更触发重校准，记录评估器与被测模型的配对兼容性（被测 Agent 升级后旧评估器分数不可比，rStar-Math 的教训）。

#### 题 9（系统设计）：为一个多领域对话 Agent（客服 + 购物助手，Orchestrator 路由到各领域 Agent）设计完整的轨迹与 Agent 级评估体系。

**参考答案：** 分六层回答。
**① Trace 先行**：被测系统按 OTel 打点，span 记录用户输入/模型输出/工具调用与返回/widgets（DoorDash 口径），层级 session→agent/task→llm_call→tool_call；满足可解析、内容完整、跨版本格式稳定三要求；trace 存 ClickHouse 类列式存储。
**② 评测镜像运行时架构**（DoorDash）：Orchestrator 评路由准确率（该转不转/转错人）；护栏 rubric 贯穿全流程评（不泄露内部过程、不呈现可证伪虚假信息，全体 Agent 通用）；每个领域 Agent 评任务能力（客服评工单闭环与政策合规，购物评约束满足与多样性），失败可归因到 owner。
**③ 三层评分**：step 层用程序化断言（参数 schema、must-call/must-not-call、禁用动作）；trajectory 层用归一化 + LCS 对齐关键 SOP（缺少关键校验触发硬门禁，其余按腾讯口径各扣 2、上限 -10）+ 效率预算（步数/token/耗时）；session 层用执行式验证——终态数据库 diff（τ-bench 范式）+ 目标 checklist，不靠判文本。
**④ Judge 层**：语义类标准（groundedness、叙述质量）用 LLM judge，前置 Transcript Builder：每条标准声明证据依赖，judge 只拿切片；judge 校准到 ≥85% 一致率，rubric 写成 binary check + eligibility 前置。
**⑤ 元评估与门禁**：所有自动评估器先在已知成败轨迹集测 FPR/FNR；综合判定 = 加权扣分 + 一票否决（禁用动作/关键校验缺失/目标未达成）；多 trial 报 pass@1 与 pass^k（无人值守口径看 pass^k）。
**⑥ 闭环**：线上 trace 抽样回流（每日去标识化 5% 流量，Airbnb 口径），"结果对但轨迹可疑"样本人工抽检后入回归集；被测 Agent 升级时评估器同步重校准。仿真侧（模拟器 + fixtures 生成轨迹）见第 E08 章，失败归因流水线见第 E11 章。

#### 题 10（进阶）：一条 20 步的轨迹最终失败了，你有哪些办法定位"是哪一步坏的"？

**参考答案：** 四条路线，成本与保真度各不同。① **中间状态重采样**（VinePPO，arXiv 2410.01679 的思路）：从可疑步骤出发重采样 K 条续写，续写的成功率就是该步质量的无偏估计——不训练模型即可用于离线归因；② **先粗后细二分定位**（OmegaPRM 的工程启示）：不必逐步全量打分，先验证轨迹中点状态是否还在正确路径上，再对可疑半区递归二分，O(log n) 成本锁定可疑区间；③ **成功/失败轨迹 diff**：同一任务的成功 trial 与失败 trial 做序列对齐，找第一个分叉点（工具参数不同？检索结果不同？规划选择不同？）——前提是 trace schema 跨版本稳定、试验条件可复现；④ **评估器辅助归因**：让带工具的 judge（Agent-as-a-Judge 形态）逐步核验并给出批注，适合无法重放的环境，但要先过元评估。所有路线的共同前提是完整结构化 trace（2.3 节）与可重放环境；定位结论应落成结构化归因字段，喂给 RCA 的范围收敛（第 E11 章），而不是停在口头结论。

## 五、易错点 · 反直觉点

1. **轨迹 exact match**：把"调用顺序不同但正确"的解判错，评估集退化成背答案，还扼杀了更优路径的发现。→ 真相：用 LCS 对齐 / 无序关键调用集合 / 偏序约束，只锁关键依赖，保留路径自由度。→ 记忆锚点：**锁关键步骤，不锁全路径。**

2. **把"结果对"当"行为对"**：最终文本会抹平一切中间失败，假阳性样本在离线评测里以"通过"存在。→ 真相：结果对但路径错的样本比结果错更危险——偶发正确不可复现、风险敞口持续存在、失败还无法归因；必须"终态正确 + 规则合规"双门槛。→ 记忆锚点：**结果判 pass，轨迹判安全。**

3. **把原始 trace 整个喂给 judge**：上下文被工具返回与脚手架噪声淹没，判断方差大、成本高。→ 真相：DoorDash 的教训是 judge 需要"为问题塑形"的视图——每条标准声明证据依赖，只给那一片。→ 记忆锚点：**judge 只看它需要的那页。**

4. **归一化过度**：时间戳、查询参数该抹，但把金额、订单号也抹掉，参数错误就被静默放过。→ 真相：归一化只抹"不影响对错的差异"；抹错一个关键字段 = 亲手造一个假阳性。→ 记忆锚点：**归一化抹噪声，不抹证据。**

5. **加权平均一切**：用"总分 = 各层加权"做判定，跳过关键校验可以用语气分补回来。→ 真相：禁用动作命中、关键校验缺失、目标未达成必须一票否决（硬门禁），扣分制解决不了安全问题。→ 记忆锚点：**安全问题不进平均分。**

6. **拿 PRM 直接当评测器，不做红队**：Qwen Lessons（arXiv 2501.07301）证明 PRM 分数可被 hack——best-of-N 会选出恰好骗过 PRM 的解，难度外推时打分系统性失准。→ 真相：验证器上线前做 hacking 红队 + 难度分层校准，报告区分 in-dist 与 OOD 可信度。→ 记忆锚点：**验证器也怕被刷分。**

7. **纯阅读式 LLM judge 直接评轨迹**：AgentRewardBench 实测多数自动评估器在失败轨迹上误报率 >50%，"读起来像成功"与"真的成功"是两回事。→ 真相：优先执行式依据（终态 diff、测试、断言），judge 只做补充，且先在已知成败集上测 FPR/FNR。→ 记忆锚点：**先验评估器，再让它评。**

8. **Trace 事后补**：上线后才想起加日志，靠脆弱解析器从自由文本里抠结构化信息。→ 真相：trace 是被测 Agent 的标准能力（阿里/腾讯共识）；三要求（可解析/内容完整/跨版本稳定）在设计阶段定，事后补的成本是重造一遍。→ 记忆锚点：**没有 trace，就没有过程评估。**

9. **被测 Agent 升级后直接对比旧评估器分数**：验证器在旧策略分布上训练/校准，评估新策略时系统性失准。→ 真相：rStar-Math 的结论是验证器必须与被测系统共同进化；策略升级 → 评估器重校准，否则分数差异归因不了。→ 记忆锚点：**尺子也要跟着版本走。**

10. **只平均每轮分数评对话 Agent**：每轮都"答得还行"，平均分挺好看，但问题最终没解决。→ 真相：阿里四层评判要求同时看 Turn/Session/Trace/Outcome，session/outcome 层失败一票压过 turn 层均值。→ 记忆锚点：**平均分会骗人，闭环才算数。**

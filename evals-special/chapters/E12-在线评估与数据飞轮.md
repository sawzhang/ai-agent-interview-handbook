# 第 E12 章 · 在线评估与数据飞轮

> 发布门禁只回答"这个版本能不能发"，在线评估回答"这个版本在真实用户那里到底好不好"，
> 数据飞轮回答"下一个版本如何自动变得更聪明"。本章拆解发布后的完整质量工程：
> 在线抽样与打分（Airbnb 每日 5% 去标识化流量）、离线-线上同一套评分（DoorDash 原则）、
> 发布联动的三类信号与回滚判据（阿里）、分布漂移与指标漂移的检测与归因、以及
> badcase → 评测集 → 训练数据 → 模型更新的数据飞轮全景。学完你应该能独立设计一条
> "生产流量进、质量资产出、下一版本带着资产上线"的闭环，并在面试中讲清每一环的
> 抽样策略、统计口径、合规前提与失效模式。

## 二、核心概念精讲

### 2.1 为什么离线评测做到极致仍然不够

第 E10 章讲了评测驱动开发：先有门禁，再谈发布。但门禁通过只说明"在离线集这个 curated
分布上达标"，生产环境会在三个维度上击穿离线假设：

| 离线评测的软肋 | 生产环境的现实 | 直接后果 |
|---|---|---|
| 分布是 curated 的 | 真实用户的意图分布、表达习惯、长尾问法永远比评测集宽 | 报告"看起来不错"但关键长尾漏掉（幸存者偏差的另一面，详见第 E3 章） |
| 环境是冻结的 | fixtures 冻结了上游世界（目录/库存/订单），生产是活的 | 目录变化、库存波动、真实追问无法离线彩排 |
| 对手是温和的 | 真实流量含模糊表述、情绪、多轮改主意，乃至注入式输入 | 模拟器覆盖率永远小于真实交互空间 |

学术界对这个 gap 有量化证据。EDD/EDDOps 的系统综述（arXiv 2411.13768，2024-11 首发，
2025-11 v3）统计了 134 篇学术文献：**93.28% 只做 pre-deployment 评测，仅 2.24% 覆盖
post-deployment，4.48% 是持续评测；97.76% 用静态基准**。而工业灰色文献方向相反：40.74%
已是持续评测、81.48% 已用评测驱动适配——学界与工业界的关注点正好错位。另有客服 agent
基准研究（arXiv 2510.22143，2025）明确指出：由于真实部署环境的分布漂移与交互复杂性，
**强 offline 基准成绩只是部署可靠性的弱指标**。

DoorDash 把这件事列为 eval harness 的第五大挑战——**双环境**："开发与生产质量可能背离"，
对应的设计要求是"真实会话与模拟会话用同一 rubric + 同一 judge：离线结论带到线上，线上失败
离线复现"。Airbnb 十条要点的第 ⑨ 条同样直白：**上线前测试要在线上持续运行**；其评测方法
按 开发期 / 发布前 / 生产 三阶段映射，强调分层防御与持续监控，而非一次性测试。

一句话定位：**离线评测管"出厂质量"，在线评估管"存量质量 + 真实分布上的地面真值"**。
前者是后者的必要条件，不是充分条件。

### 2.2 在线抽样：随机打底、分层放大、合规先行

生产流量全量人工评审不可能，全量 judge 打分的成本也常常不划算，抽样策略分两层：

**（1）随机抽样打底——估计总体。** 随机样本的价值在于无偏：只有随机抽样能回答"线上整体
质量是多少分"这个估计问题。Airbnb 旅行客服助手在规模化阶段的做法是标杆：评测集扩到
**5,000 样本**；**每日抽样 5% 去标识化生产流量**，跑程序化检查与 judge；被标记的样本送
人工评审；每周 PM 评审，新增测试与修复。DoorDash 的量化结果可以作为"这套打法值不值"的
注脚：质量信号从**平均 1 条/天的员工反馈**变成 **2,000 个/天自动评分会话**；全国上线前
agent 质量分 **+8 分**、错误率**近乎减半**，达到生产发布标准。

**（2）分层抽样放大——抓风险。** 随机样本里高风险场景占比天然低（这正是第 E3 章讲的
幸存者偏差），靠随机抽样等它浮出来，等于等事故替你收集 badcase。分层抽样要优先放大：

| 分层维度 | 含义 | 出处 |
|---|---|---|
| 高风险 | 资损/合规/赔付/投诉升级相关会话 | 阿里：高风险场景自动通过也要定期人工复核；腾讯：医疗/金融/安全 100% 人工复核 |
| 低置信 | judge 打分含糊、多 judge 分歧、规则与 judge 冲突的样本 | 阿里人工评分路由与主动学习口径 |
| 新分布 | 新意图 / 新工具 / 新知识点 / 新活动上线 | 阿里：新分布出现时主动学习优先抽取低置信/高影响/新意图/新工具/新知识点样本进人工确认 |

腾讯把"Trace 采样审查"列为人工评分六个必要场景之一：**每周固定抽样读轨迹找隐藏失败模式**——
分层的不只是会话，还包括轨迹级深读。

**（3）合规先行。** 在线抽样的每一步都踩在用户数据上，三家都给了硬约束：

- Airbnb：生产抽样用隐私保护方法——**人工评审前去标识化、用途限定于安全与质量**。
- 阿里：badcase 入库五标准之一是"**已脱敏合规**"。
- 调研侧的现实（_research/10-infra-observability.md 争议 4）：trace 含用户 PII 与商业敏感
  内容，"生产流量是最真实的评测分布"与"合规上不能直接把用户数据进评测集"天然冲突；
  业界通行做法是**采样脱敏 + 合成改写**，目前尚无论文级标准答案。

工程上的顺序纪律：**先去标识化，再进 judge，再进人审，再谈入库**。脱敏不是入库前的最后
一步，而是抽样管道的第一个算子。

### 2.3 离线-线上同一套打分：同一 rubric、同一 judge、同一校准

DoorDash 四条 Lessons Learned 的第三条是全章最重要的一句：

> **离线结果只有能带到线上才有意义——同一 rubric + 同一校准 judge 两边跑；各自调 judge，
> 分数会难调和地背离。**

为什么"各自调"必然背离？因为离线 judge 会被离线集的分布塑形（哪些失败多见就按哪些失败
调 rubric），线上 judge 会被线上分布塑形，两边 rubric 各自演进后，**同一个会话在两套
judge 下可以拿到不同 verdict**——于是"离线修好了"无法证明"线上会好"，"线上报警"也无法
在离线复现，双环境彻底脱钩。这正是 DoorDash 第五挑战的设计要求要消灭的状态。

落地到工程，"同一套打分"要版本化地理解。_research/10-infra-observability.md 的 judge
治理口径：**一个完整的 judge 版本 = judge 模型快照 + judge prompt 版本 + rubric 版本 +
评分协议（pointwise/pairwise）四者组合**。只固定其中一个（比如"我们都用同一个模型"）不叫
同一套打分。配套纪律：

| 纪律 | 内容 | 出处 |
|---|---|---|
| 校准线 | judge 与人工一致率 high 80s~90s（Airbnb）/ ~85% 后进自动化（阿里）/ ≥85% 可用（腾讯），详见第 E5 章 | 四家共识 |
| 升级即重校准 | judge prompt/模型每次升级固定产出三类统计：与人工标注一致性、高风险样本漏判率（合规/资损/隐私）、边界样本稳定性（重复评测波动） | 阿里 Judge 持续运营 |
| 漂移监控 | 保留带人工标签的金标校准集，judge 每次换版本重跑，监控与人类一致性的漂移；模型 API 升级必须触发 judge 重校准 | _research/10 judge 治理 |
| 成本路线 | 生产大规模在线评测倾向开源专用 judge，离线高价值评测用前沿闭源模型 | _research/10 启示 6 |

在线 judge 的成本工程值得单独一句：每日数千会话的打分量下，Prometheus 2
（arXiv 2405.01535，2024）这类**专门化开源 judge** 是关键使能技术——7B judge 在多个
meta-eval 基准上与 GPT-4 judge 的 Pearson 相关差距缩小到 ~0.8+ 水平，且行为更可预测、
可版本化、可本地部署。把 judge 当模型资产管（版本号、校准集、漂移看板），在线评分才
可能既便宜又可信。

### 2.4 发布联动：三类信号、灰度与回滚判据

阿里第 9 章给出了发布阶段的完整口径：**离线门禁与线上灰度联动**，跟踪三类信号：

| 信号类别 | 具体指标（阿里原文） | 回答的问题 |
|---|---|---|
| 离线质量信号 | 核心场景通过率、P0 风险数、关键工具参数正确率 | 这个版本出厂合格吗 |
| 线上体验信号 | 转人工率、重复追问率、投诉率、满意度变化 | 用户感受到了吗 |
| 业务结果信号 | 任务完成率、工单闭环率、退款/赔付成功率 | 业务真的变好了吗 |

以及全章最硬的一条判据：**离线提升但线上关键信号恶化 → 触发回滚或降级。**

这条判据反直觉的地方在于：离线分数是团队花了最多力气优化的东西，心理上最难放弃。但三类
信号的优先级排列揭示了原因——离线质量是**预测器**，业务结果才是**目标本身**；两者背离时，
说明预测器失真（离线集覆盖不到线上的变化），此时信目标不信预测器。这也呼应 2.1 的实证：
强 offline 基准成绩只是部署可靠性的弱指标（arXiv 2510.22143，2025）。

发布通道的编排，EDDOps（arXiv 2411.13768）给出了学术表述：**shadow evaluation**（影子
评测：新版本与旧版本并行跑同一批真实请求，但输出不暴露给用户）→ **canary rollout**
（小流量灰度）→ 全量；safety case（证据支撑的安全论证）随评测证据持续更新。主手册第 8 章
的对应口径是 Shadow mode → Canary → A/B（会话级分流、序贯检验）→ 全量。

两个配套纪律：

1. **门禁要带统计口径**。阿里：版本对比要配套统计检验——关键指标置信区间 + 与基线的
   显著性判断 + 最小可感知变化阈值；"门禁不只看差了多少，还要看差异是否超过统计噪声"。
   线上小样本下用 Wilson 区间而非朴素比例（详见第 E9 章；动手：
   `cd evals-special/labs && python3 eval_lab08_statistics_ci.py`）。
2. **触发时机要枚举**。腾讯的执行口径：提示词变更（CI 自动，PR 合入前回归）、模型版本
   升级（手动，验证兼容性）、定期巡检（定时全量回归）；通过率口径引用 Anthropic 推荐——
   确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%。

### 2.5 漂移检测：分布漂移 × 指标漂移，以及"三种解释"的鉴别

线上评分趋势是飞轮的仪表盘，但仪表盘掉针不一定是发动机坏了。先定义两种漂移：

| 漂移类型 | 漂移的是什么 | 典型诱因 | 典型探针 |
|---|---|---|---|
| 分布漂移 | 输入侧：意图占比、query 复杂度、新意图/新工具/新知识点、用户群结构 | 市场活动、新品类上线、竞品导流、季节性 | 意图分类分布、会话长度分布、新意图占比、路由分布 |
| 指标漂移 | 输出侧：同一分布下的质量分、业务指标随时间趋势 | 模型/prompt/工具链变更、上游数据劣化、真实能力退化 | 逐 rubric 标准失败率、judge 分数分位数、转人工率日环比 |

监控与告警的工程形态：为每条 rubric 标准建失败率时序图、为 judge 分数建分位数图、为业务
信号建日环比看板；告警阈值用统计口径设定而不是拍脑袋（参照 2.4 的统计纪律）。多智能体
系统还有结构化手段：**SentinelAgent（arXiv 2505.24201，2025）将 agent 间交互建模为图，
由专职监督 agent 结合图拓扑与运行时指标做异常检测与归因**，目标是发现"偏离预期协作模式"
的行为。_research/10 的提炼是：把"**行为基线 + 偏离告警**"纳入可观测性栈，而不只看延迟与
token 成本——这是"评测左移到运行时"的方向。

**告警触发后的鉴别诊断，是本章的高频深水区。** 某条 rubric 标准线上失败率一周上升 5 个
百分点，候选解释恰好三种，排查顺序如下：

| 候选解释 | 鉴别动作 | 判据 |
|---|---|---|
| ① judge 漂移（尺子坏了） | 固定 judge 版本：用上一版 judge 重放本周样本；检查本周是否发生过 judge 模型/prompt 升级 | 旧 judge 复评后差异消失 → judge 漂移；阿里口径：judge 升级必须回看三项统计（与人工一致性/高风险漏判率/边界稳定性） |
| ② 分布漂移（考题变了） | 按意图/入口/用户群分桶看失败率；对比本周与历史周的输入分布 | 差异集中在个别桶且桶占比变化大 → 分布漂移；该桶单独治理（新意图补用例），而非全局回滚 |
| ③ 真实质量退化（考生变差了） | 固定一批历史 case 做新旧版本配对重跑（离线复现） | 离线可复现 → 定位到具体变更（prompt/模型/工具/上游数据），走 RCA 与回滚 |

顺序的意义：先排除尺子（成本最低，一次重放即可），再排除考题（一次分桶即可），最后才
归因考生。顺序反了就会把 judge 升级的锅扣给模型、把新意图涌入的锅扣给 prompt。
同时要记住统计底线：inspect_evals 团队（arXiv 2507.06893，2025）明确强调**小样本上
1-2 分的差异默认视为噪声**——日抽样量不大时，先算置信区间再发告警。

最后，**在线评测系统自己也在被观测**：DoorDash 第四条 Lessons Learned——被标记失败中
有真实一部分是 harness 自身故障（judge 误报、trace 缺口），并行修复才可信。漂移看板
本身需要一个"harness 故障率"指标（详见第 E11 章题 8 的评测误报讨论）。

### 2.6 数据飞轮：主循环、三条生产线与样本治理

飞轮的主循环一句话：**badcase → 评测集 → 训练数据 → 模型更新 → 新 badcase**，每转一圈，
系统的"已知问题库存"变厚、未知问题变少。阿里第 9 章的总命题是终点不是报告，而是**把
线上失败持续转化为可复用研发资产**；并给出两条量化口径：**一条 badcase 至少生产 3 类
反馈；平台可分三条生产线**：

| 生产线 | 输入 | 产出 | 消费者 |
|---|---|---|---|
| 评测集线 | badcase + RCA 结论 | 新用例（触发/核心逻辑/产物质量/异常容错四场景，详见第 E3 章） | 回归门禁、版本对比 |
| 训练数据线 | 修复前后的轨迹对、judge 打分、人工确认标签 | 偏好对 / 拒绝采样筛出的优质轨迹 / SFT 样本 | 模型再训练（训完仍须过门禁与灰度） |
| 知识修订线 | 根因落在知识点的 badcase | 过期文档下线、口径澄清、知识点与新用例绑定 | 检索/RAG 组件 |

评测集线大家最熟，训练数据线最容易踩坑：**把在线信号喂进训练之前，训练数据本身要带
provenance（哪个 judge 版本、哪个 rubric、哪批人审标签），且训出的模型必须重新过离线
门禁与线上灰度**——否则飞轮变成放大器：RLAIF 研究（arXiv 2309.00267，2023）已证明 AI
反馈会把评测器自身的偏好（冗长、格式、自我偏好）注入训练分布；奖励模型过度优化有
平方根标度律的定量刻画（arXiv 2210.10760，OpenAI，ICML 2023）——代理奖励持续上升、
真实目标先升后降；谄媚到 reward tampering 的谱系（arXiv 2406.10162，Anthropic，2024）
则说明优化压力会教系统"钻评分的空子"。**飞轮的每一圈都必须重新过门禁，这是对 Goodhart
的工程防御。**

**入库五标准**（阿里，badcase 进任何一条生产线前都要过）：

1. 失败可复现（或至少有稳定 Trace + 人工确认）；
2. 期望行为明确（可写成规则 / Judge 标准 / 人工验收标准）；
3. 根因标签清楚（归到具体能力域或业务流程）；
4. 样本有代表性（覆盖一类问题而非一次性环境抖动）；
5. 已脱敏合规。

**样本治理**（阿里）——飞轮转久了评测集会膨胀，治理四策：

| 策略 | 规则 | 目的 |
|---|---|---|
| 同簇去重 | 同一问题簇只保留代表例 | 防"23 条相似 case 刷存在感"，控制回归成本 |
| 风险分层保留 | P0/P1 风险用例长期保留 | 高风险永不毕业 |
| 稳定者降级 | 稳定多版本通过且低风险者降级为抽样集 | 回归集瘦身但不删除 |
| 主动学习补新 | 新分布出现时优先抽取低置信/高影响/新意图/新工具/新知识点样本进人工确认 | 预算花在不确定的地方 |

腾讯从用例生命周期角度给了互补口径：能力测评（起步 20–50% 通过率的目标山峰）与回归
测评（接近 100% 的防御漂移）分池管理，**通过率稳定 100% 后用例"毕业"进回归集，回归集
只增不减**。两者合起来就是完整的样本生命周期：**发现 → 入库 → 能力集迭代 → 毕业进回归 →
长期稳定者降级抽样 → 高风险者永久驻守**。

飞轮的工业化样本：Discord 的 AITL（Agent-in-the-Loop，EMNLP 2025 工业赛道，
ACL Anthology 2025.emnlp-industry.135）用四类人工客服在线标注持续回流，驱动 LLM 客服
系统的检索/生成持续再训练，**把再训练周期从月级压缩到周级**，并专门分析了 offline 与
online 评测设置之间的一致性；美国试点数字：**recall@75 +11.7%、precision@8 +14.8%、
有用性 +8.4%、采用率 +4.5%**。这是"人工标注 → 评测集 → 再训练 → 上线 → 新标注"闭环的
生产级证明。

### 2.7 质量资产库：飞轮的终局形态

阿里第 9 章把闭环的终点定义为六座库，并配了一句值得背诵的话：**"质量资产越厚，Agent
迭代越不靠个人经验和临时救火。"**

| 资产库 | 存什么 | 谁在消费 | 增长来源 |
|---|---|---|---|
| 用例库 | 四场景用例 + 期望行为定义 | 能力评测、回归门禁 | 专家设计 / LLM 扩展 / badcase 回流 |
| Trace 库 | 结构化全链路 trace（含失败与被标记样本） | RCA、回放评测、失败聚类 | 生产打点 + 抽样归档 |
| 根因标签库 | 枚举化标签 + (现象×模块) 映射表 | RCA Pipeline 的范围收敛与定责 | 人审结论反校准 |
| 修复建议库 | 结构化行动项（范围/证据/动作/owner/验收/优先级） | 工单系统、看板、研发流水线 | RCA 落盘 |
| Judge 校准集 | 带人工标签的金标集（含坏样本与边界样本） | judge 升级重校准、漂移监控 | 分歧样本、新失败模式 |
| 回归集 | 毕业用例，只增不减 | CI 每次运行、发布门禁 | 能力集毕业流转 |

六库的共同属性是**复利**：每一条 badcase 走完 RCA 后同时给多座库充值，下一圈飞轮的
每一环（抽样有分层依据、打分有校准基线、归因有映射表、修复有先例库）都比上一圈便宜。
反之，没有资产沉淀的团队永远在"一次性救火"：修完即忘，同类问题换表述再来一遍。

资产本身也有生命周期治理，学界给出了可直接借用的范式：

- **评测集即数据供应链**：LiveBench（arXiv 2406.19314，2024）给题目带时间戳、版本号、
  上下架状态，按月滚动发布新题下架旧题；LiveCodeBench（arXiv 2403.07974，2024）给每题
  带发布日期元数据，评测时按被测模型 cutoff 做时间窗切片。飞轮入库的用例同样要带
  `created_at / source / status`，否则评测集会像没有 git 的代码库一样不可维护。
- **结果必须可复现**：EleutherAI 的 harness 方法论（arXiv 2405.14782，2024）给出公式——
  **eval 结果 = (数据集版本, prompt 模板, 评分方式, 解码参数, 模型快照) 的函数**，缺任何
  一项都不可复现。在线评分同理：每个线上分数都要能回答"哪个 judge 版本、哪个 rubric
  版本、哪条流水线打的"。
- **治理流程可抄**：inspect_evals 仓库论文（arXiv 2507.06893，2025）系统总结了 100+
  贡献者共建评测仓库的运营流程（贡献者管理、统计比较、可复现性实践），是"把评测集当
  软件产品运营"的参考实现。

### 2.8 线上↔离线双向流动：DoorDash 两个实战案例

前面讲的都是"离线 → 线上"的方向（门禁把关、灰度观察）。飞轮的另一半是反方向流动，
DoorDash 的两个案例各示范了一个方向。

**案例 1：Reasoning leakage（线上发现 → 离线验证 → 线上确认）。**

| 阶段 | 动作 | 结果 |
|---|---|---|
| 线上发现 | 日常线上评分发现泄漏激增：任务完成但叙述冒出系统语言（"reorder skill"、工具名、"fetch"、"in parallel"）——"像编码 agent 而非购物助手" | 没有线上打分，这种"任务成功但体验劣化"的问题会被 KPI 绿灯掩盖 |
| 诊断 | 指向 prompt 设计：合并沟通规则，分离内部 skill 指令与面向用户语言 | 失败按 rubric 标准聚成簇再调查（详见第 E10 章反馈闭环） |
| 离线验证 | 用生产中**最易触发**的场景离线验证 | **泄漏率降 11%**；hero 场景全量扫描无回归 |
| 线上确认 | 上线后监控确认阶跃改善 | 闭环完成 |

这个案例的价值：它不是"任务失败"而是"任务成功但泄漏系统语言"——只看业务结果信号永远
发现不了，只有 rubric 级的在线打分才抓得住。

**案例 2：底座模型迁移（离线发现差距 → 定位兼容性 → 线上收益）。**

agent 原跑在 Claude Sonnet 4.6；Gemini 3.5 Flash 发布后 benchmark 显示可降延迟。离线
harness 一跑：**分数大跌**。若只看公开 benchmark 就直接迁移，等于把兼容性事故带给用户；
若只看离线大跌就放弃，等于错过 35% 的延迟收益。DoorDash 的路径：eval 给出具体失败模式
→ AI coding agent 做假设与实验 → 结论：**不是能力差距，是兼容性差距**——Flash 部分工具
参数格式不同（工具签名要 plain string，Flash 传 `{"dishes": [...]}` JSON 对象）；系统
prompt 围绕 Sonnet 惯例隐式调优。"低分反映为 Sonnet 适配的系统，不是更弱的模型。"
修复小而准：工具输入确定性防护（错误形状**强制转换**回预期形状而非丢弃调用）；prompt
显式写出 Sonnet 原本自行推断的内容。重跑 eval：Flash 与 Sonnet 质量持平（harness 噪声
范围内）→ 迁移生产 → **延迟降 35%、质量无损**。

| 方向 | 案例 | 若无对侧会发生什么 |
|---|---|---|
| 线上 → 离线 | reasoning leakage | 泄漏问题要等用户投诉才暴露，修复无法在上线前被量化验证 |
| 离线 → 线上 | 模型迁移 | 要么带兼容性事故上线，要么因噎废食放弃 35% 延迟收益 |

配套背景数字（同一套 harness 的整体收益，DoorDash）：全量回归从手工 **6+ 小时 →
自动约 20 分钟**（50 场景 × 8 trials = 400 次对话），这正是"双向流动"能高频发生的
成本前提。

## 四、经典面试题与参考答案

#### 题 1（基础）：离线评测集已经做到 5000 条、门禁全绿，为什么还需要在线评估？

**参考答案：** 三个原因。① **分布缺口**：离线集是 curated 分布，真实用户的意图、表达、
长尾问法永远比它宽，随机报告"看起来不错"但关键长尾漏掉（幸存者偏差的另一面）。②
**环境缺口**：离线用 fixtures 冻结上游世界，生产的库存、目录、真实追问是活的。③
**offline-online gap 有实证**：EDDOps 综述（arXiv 2411.13768）统计 134 篇学术文献，
93.28% 只做 pre-deployment 评测，仅 2.24% 覆盖 post-deployment；客服 agent 基准研究
（arXiv 2510.22143）明确指出强 offline 基准成绩只是部署可靠性的弱指标。所以离线是必要
条件不是充分条件：离线管出厂质量，在线管存量质量与真实分布上的地面真值。Airbnb 十条
要点第 ⑨ 条即"上线前测试要在线上持续运行"。

#### 题 2（基础）：生产流量应该怎么抽样做在线评估？说说 Airbnb 的做法与合规前提。

**参考答案：** 两层结构。**随机抽样打底**：Airbnb 旅行客服助手每日抽样 **5% 去标识化
生产流量**（评测集本身 5,000 样本），跑程序化检查与 judge，被标记样本送人工评审，每周
PM 评审新增测试与修复——随机保证能无偏估计线上总体质量。**分层抽样放大**：高风险
（资损/合规/投诉升级）、低置信（judge 含糊/多 judge 分歧/规则与 judge 冲突）、新分布
（新意图/新工具/新知识点）优先，阿里口径是主动学习优先抽取低置信/高影响/新意图/新工具/
新知识点样本进人工确认。合规前提：Airbnb 要求人工评审前**去标识化、用途限定于安全与
质量**；阿里入库五标准含"已脱敏合规"。工程纪律：去标识化是抽样管道的第一个算子，不是
入库前的最后一步。

#### 题 3（进阶）：DoorDash 为什么坚持离线与线上用"同一 rubric + 同一校准 judge"？各自调 judge 会发生什么？工程上怎么落地？

**参考答案：** 因为**离线结果只有能带到线上才有意义**。若两边各自调 judge：离线 judge
被离线集分布塑形、线上 judge 被线上分布塑形，rubric 各自演进后同一会话在两套 judge 下
可以拿到不同 verdict——"离线修好了"证明不了"线上会好"，"线上报警"也无法离线复现，
双环境彻底脱钩；DoorDash 原文警告"各自调 judge，分数会难调和地背离"。工程落地四点：
① 把 judge 当版本对象管理：judge 模型快照 + judge prompt 版本 + rubric 版本 + 评分协议
四者组合才是完整 judge 版本；② 校准线共识：与人工一致率 high 80s~90s（Airbnb）/~85%
（阿里、腾讯）；③ judge 每次升级固定回看三项统计——与人工一致性、高风险漏判率、边界
稳定性（阿里口径）；④ 成本路线：大规模在线打分用开源专用 judge（如 Prometheus 2，
arXiv 2405.01535），关键决策点用强模型 judge + 抽样人审。

#### 题 4（进阶）：发布新版本时你跟踪哪三类信号？"离线提升但线上恶化"怎么处理？为什么？

**参考答案：** 阿里口径：① **离线质量信号**——核心场景通过率、P0 风险数、关键工具参数
正确率；② **线上体验信号**——转人工率、重复追问率、投诉率、满意度变化；③ **业务结果
信号**——任务完成率、工单闭环率、退款/赔付成功率。判据是硬性的：**离线提升但线上关键
信号恶化 → 触发回滚或降级**。原因：离线质量是预测器，业务结果才是目标本身；两者背离
说明预测器失真（离线集覆盖不到线上正在发生的变化），此时必须信目标不信预测器——这与
"强 offline 成绩只是部署可靠性的弱指标"（arXiv 2510.22143）一致。发布通道按 shadow →
canary → 全量编排（EDDOps 明确定义了 shadow evaluation 与 canary rollout 的位置），
且每个门禁都带统计口径：置信区间 + 显著性 + 最小可感知变化，不把噪声当信号。

#### 题 5（进阶）：某条 rubric 标准的线上失败率一周上升 5 个百分点，给出你的排查顺序与每步判据。

**参考答案：** 先列三种候选解释，按成本从低到高排查。**① judge 漂移（尺子坏了）**：
确认本周是否有 judge 模型/prompt 升级；用上一版 judge 重放本周样本——若差异消失则是
judge 漂移，回到校准流程（回看与人工一致性/高风险漏判率/边界稳定性三项统计）。
**② 分布漂移（考题变了）**：按意图/入口/用户群分桶看失败率，对比输入分布——若差异集中
在个别桶且桶占比变化大（如新活动带来新意图），是分布漂移，治理动作是给该桶补用例、
调分层抽样，而非全局回滚。**③ 真实质量退化（考生变差了）**：固定一批历史 case 做新旧
版本配对重跑，离线可复现则定位到具体变更（prompt/模型/工具/上游数据），走 RCA 与回滚。
顺序的意义：先排除尺子（一次重放）、再排除考题（一次分桶）、最后才归因考生；顺序反了
会把 judge 升级的锅扣给模型。另守统计底线：日抽样量小时先算置信区间——inspect_evals
（arXiv 2507.06893）明确小样本 1-2 分差异默认视为噪声。

#### 题 6（进阶）：画出数据飞轮的主循环。一条线上 badcase 进入体系后至少应产出什么？入库要过哪些标准？

**参考答案：** 主循环：**线上失败 → badcase 脱敏入库 → RCA 定责（详见第 E11 章）→
三条生产线 → 新版本 → 发布联动 → 新的线上信号**。阿里口径：一条 badcase 至少生产 3 类
反馈，对应三条生产线——**评测集线**（badcase 转用例，进能力集迭代、毕业进回归集）、
**训练数据线**（修复前后轨迹做偏好对/拒绝采样筛样，喂再训练）、**知识修订线**（过期
文档下线、口径澄清、知识点绑定新用例）。入库五标准：① 失败可复现（或至少有稳定 Trace +
人工确认）；② 期望行为明确（可写成规则/Judge 标准/人工验收标准）；③ 根因标签清楚；
④ 样本有代表性（覆盖一类问题而非一次性环境抖动）；⑤ 已脱敏合规。工业化证据：Discord
AITL 用在线标注持续回流把再训练周期从月级压到周级，试点 recall@75 +11.7%、有用性 +8.4%。

#### 题 7（进阶）：飞轮转了半年，回归集从 200 条涨到 4000 条，每次全量回归又慢又贵，很多用例从没失败过。怎么办？

**参考答案：** 样本治理四策（阿里口径）：**① 同簇去重**——同一问题簇只保留代表例，防止
"23 条相似 case 刷存在感"；**② 风险分层保留**——P0/P1 风险用例长期保留，高风险永不
毕业；**③ 稳定者降级**——稳定多版本通过且低风险者降级为抽样集（不再每次全量跑，按
比例抽查），回归集瘦身但不删除；**④ 主动学习补新**——预算优先给低置信/高影响/新意图/
新工具/新知识点样本。配合腾讯的用例生命周期：能力集（起步 20–50% 通过率、频繁迭代）与
回归集（接近 100%、只增不减）分池管理，通过率稳定 100% 才"毕业"进回归集；Anthropic
口径确定性任务 100%、非确定性任务 ≥95%。关键原则：降级≠删除——用例带着 trace 与根因
标签留在资产库里，分布回潮时可随时召回（呼应 LiveBench 式"上下架状态机"，
arXiv 2406.19314）。

#### 题 8（进阶）：把在线 judge 分数直接当训练奖励喂给模型，让飞轮"自动加速"，可行吗？

**参考答案：** 不可行，至少不能裸奔，这是飞轮最大的暗礁。三层风险：① **judge 偏差进
训练分布**——RLAIF 研究（arXiv 2309.00267）证明 AI 反馈会把评测器自身的偏好（冗长、
格式、自我偏好）注入训练数据；judge 没校准好，等于拿歪尺子批量生产训练信号。②
**过度优化的定量代价**——奖励模型过度优化遵循平方根标度律（arXiv 2210.10760）：代理
奖励持续上升、真实目标先升后降；judge 容量决定你能安全优化多久。③ **钻空子泛化**——
谄媚可以零样本泛化成 reward tampering（arXiv 2406.10162），系统会学会"讨好评分器"而
不是"做好任务"。工程防御：训练数据带 provenance（judge 版本/rubric 版本/人审标签）；
训出的模型必须重新过离线门禁与线上灰度——**飞轮的每一圈都必须重新过门禁**；对 judge
本身做对抗审查（多 LLM 对抗打分、抽样人审），把"攻击评分器"当独立指标跟踪。

#### 题 9（系统设计）：为日均 5 万会话的客服 Agent 设计在线评估与数据飞轮平台。

**参考答案：** 六层架构。
**① 打点层**：全量会话结构化 trace（OpenTelemetry，span 层级 session → agent/task →
llm_call → tool_call；trace 是被测 agent 的标准能力而非事后补救），Trace 库落 ClickHouse
类列存。
**② 抽样层**：每日 5% 随机抽样（估计总体，参照 Airbnb）+ 分层放大（高风险 100%、
低置信、新意图/新工具/新知识点）；去标识化作为管道第一算子，用途限定安全与质量。
**③ 打分层**：离线-线上同一 rubric + 同一校准 judge；judge 四元组版本化；大规模打分用
开源 judge 控成本，高风险与边界分转人工（人工路由条件参照第 E6 章）；每日数千会话量级
（参照 DoorDash 2,000/天）。
**④ 监控层**：分布漂移探针（意图/路由/长度分布）+ 指标漂移看板（逐 rubric 失败率、
judge 分位数、业务信号日环比）；告警带统计口径（Wilson CI）；失败率异动按"judge 漂移→
分布漂移→真实退化"三步鉴别。
**⑤ 发布层**：离线门禁（P0 指标 + 置信区间 + 最小可感知变化）+ shadow → canary → 全量；
跟踪三类信号（离线质量/线上体验：转人工率、重复追问率、投诉率、满意度/业务结果：任务
完成率、工单闭环率、退款成功率）；离线升 + 线上降自动触发回滚或降级。
**⑥ 飞轮层**：badcase 与离线失败汇入同一任务表 → RCA 五步 → 三条生产线（评测集/训练
数据/知识修订）；入库五标准 + 样本治理四策；沉淀六座质量资产库；度量飞轮自身：badcase→
行动项转化率、评测集覆盖率（线上问题簇在离线集有无对应）、回归成本曲线。

## 五、易错点 · 反直觉点

1. **在线随机抽样当全貌**："每天随机抽 5%，分数挺高，没问题。" → 真相：高风险场景在随机
   样本里占比天然低，幸存者偏差让报告"看起来不错"但关键问题漏掉；必须叠加分层抽样放大
   高风险/低置信/新意图。 → **记忆锚点：随机估总体，分层抓风险。**
2. **离线与线上各调各的 judge**："线上场景特殊，单独调一版 judge 更贴。" → 真相：两套
   judge 各自被各自分布塑形，同一会话两种 verdict，离线结论带不到线上、线上失败离线
   复现不了，分数会难调和地背离（DoorDash 原文警告）。 → **记忆锚点：一把尺子量两处。**
3. **线上分数一掉就怪模型**："这周 judge 分掉了 5 个点，模型又退化了！" → 真相：候选解释
   有三个——judge 漂移、分布漂移、真实退化；先固定 judge 重放、再按分布分桶、最后才
   归因模型。顺序反了会把尺子的锅扣给考生。 → **记忆锚点：先查尺子，再查考题，最后查考生。**
4. **拿在线流量直接进评测集**："真实会话最真实，直接入库。" → 真相：未脱敏的会话含 PII，
   合规上不能直接进评测集；去标识化是抽样管道的第一算子，入库还要过"已脱敏合规"等五条
   标准。 → **记忆锚点：先脱敏，再入库。**
5. **badcase 修完就关单**："问题解决了，工单关闭。" → 真相：不回流就不闭环——一条
   badcase 至少要生产三类反馈（评测集/训练数据/知识修订），同类问题换个表述还会再来。
   → **记忆锚点：一条 badcase，三份产出。**
6. **所有 badcase 无差别入库**："失败都是财富，全进回归集。" → 真相：不过入库五标准的
   样本是噪声——不可复现的、期望不明的、一次性环境抖动的都该拒收；同簇只留代表例，否则
   评测集膨胀、回归成本爆炸而信号密度下降。 → **记忆锚点：入库有门槛，同簇留代表。**
7. **judge 分数直接当训练奖励**："打分器有了，RL 数据就有了。" → 真相：judge 偏差会注入
   训练分布，代理奖励过度优化有平方根标度律，谄媚可泛化成 reward tampering；训练数据要
   带 provenance，训完必须重新过门禁。 → **记忆锚点：飞轮每圈都要重新过门禁。**
8. **线上指标一波动就回滚**："转人工率今天涨了 1%，快回滚！" → 真相：小样本下 1-2 分差异
   默认是噪声（inspect_evals 口径）；回滚判据要带置信区间与最小可感知变化，且先做三步
   鉴别。乱回滚的团队会丧失灰度发布的勇气。 → **记忆锚点：噪声不是信号。**
9. **回归集只进不出**："用例只增不减是纪律，谁也不许删。" → 真相：只增不减的是"可用性"
   不是"每次必跑"——稳定多版本通过且低风险的用例降级为抽样集，高风险永久驻守；纪律的
   目的是防删除，不是防瘦身。 → **记忆锚点：降级不删除，驻守看风险。**
10. **用在线评估替代离线门禁**："反正线上能看到真实反馈，离线评测差不多得了。" → 真相：
    不能拿真用户彩排变更（DoorDash 第三挑战）；离线门禁的意义是在伤害用户之前拦截，在线
    评估的意义是事后验证与发现新分布——前者是刹车，后者是仪表盘。 → **记忆锚点：刹车与仪表盘，
    一个都不能少。**

# 第 E04 章 · 评分三层之一：程序化评分

> 一句话导读：评分三层（程序化 → LLM Judge → 人工）中，程序化评分是唯一"零成本、零漂移、可单测"的一层。本章讲透：哪些检查必须写成代码、检查规则如何用 DSL 落成可执行规格、评分输出为什么不能只有 pass/fail、粗筛→精判→人工复核的分层流水线怎么省钱、以及扣分制 / 基线快照 / LCS 轨迹对齐这些腾讯 TPerf 实战中打磨过的工程细节。学完本章，你能独立设计一套可进门禁、可喂 RCA 的程序化评分子系统，并清楚知道规则的边界在哪里（边界之外见第 E05 章）。

## 一、知识图谱

```
程序化评分（评分三层之一 · 确定性层）
│
├── 定位：确定性优先 ——「能用代码判断的，绝不用模型判断」
│   └── 三类评分器选择顺序：确定性评分器 → Rubric/Judge → 人工

│
├── 输出规范：{score, passed, 问题分类, 置信度, 判定依据}
│   └── 问题分类 = 现象层 ≠ 根因 → 是 RCA 的「现象入口」
│
├── 流水线：分层筛查（阿里）

│   ├── 基线快照：单用例执行 1 次 → 人工确认 → 快照为基线

│
└── 边界：规则永远判不了的 —— 语义正确性 / 语气 / 策略合理性 → 第 E05 章 LLM-as-a-Judge
```

## 二、核心概念精讲

### 2.1 确定性优先：程序化评分在三层评分体系中的位置

阿里对评分层的总纲只有一句话：**规则看"硬条件"（工具、状态、字段、禁用动作），LLM 看"语义/策略合理性"；能写成代码的由规则主判**；高风险/抽检/低置信/变更观察期追加 LLM Judge；能自动稳定判断的不长期依赖人工。腾讯把同样的原则表述为选择优先级：**确定性 > Rubric > 人工**。Anthropic 在《Demystifying evals for AI agents》（2026-01）中给出的打分三层顺序完全一致：确定性代码检查（正则/终态/单测）→ 模型裁判 rubric → 人工抽检。

三家公司独立得出同一个顺序，原因可以拆成四个维度。腾讯给出的三类评分器对照表（原文数字）：

| 维度 | 确定性评分器 | Rubric 评分器 | 人工评分器 |
|---|---|---|---|
| 谁来评 | 脚本（Bash/Python/断言/Lint/AST） | 大模型（固定版本） | 领域专家 |
| 规则写在哪 | 代码里 | Prompt + JSON Schema | 人脑 + 标注指南 |
| 成本 | 毫秒级 / 免费 | 秒级 / API 费用 | 分钟~小时级 / 人力 |
| 稳定性 | 100% | 有抖动（需降噪） | 取决于标注员水平 |
| 覆盖 | 已知硬指标 | 未知软指标 | 主观 + 边缘场景 |
| 典型用例 | 文件存在、构建/测试通过 | 代码风格、意图贴合、解释清晰度 | 校准 LLM、诊断 0%/100% 异常、红队 |
| 门禁角色 | 硬门禁 | 分级门禁（error 硬 / warning 软） | 不进门禁，做采样审查 |

这张表有四个面试必须说出来的要点：

1. **稳定性 100% 是程序化评分独有的性质**。Judge 有抖动需要降噪，人工取决于标注员水平；只有代码断言同一输入永远给同一结论——这是它能做"硬门禁"的根本原因，也是版本对比时分数差异可以归因于被测系统而非评分器的前提。
2. **规则写在代码里 = 可单测、可 review、可版本化**。评分器本身是软件，享受软件工程的全部基础设施（回归测试、code review、git 历史）；judge 的规则藏在 prompt 里，人工的规则藏在人脑和标注指南里，可审计性依次递减。
3. **门禁角色分层**：确定性评分器做硬门禁（不过不发），Rubric 做分级门禁（error 硬 / warning 软），人工不进门禁只做采样审查——把最贵的判定能力用在杠杆最高处（详见第 E06 章 · 人工评估与评分路由）。
4. **"覆盖：已知硬指标"暗示了边界**：程序化评分只能判"已经想到并能写成规则的东西"，未知软指标必须交给下一层。三层不是三选一，而是**分层防御**：Airbnb 十条要点的第 ⑥ 条就是"代码检查 + 模型 judge + 人工评审结合"。

**确定性优先的经济学**：一条样本走一次 LLM judge 是秒级延迟 + API 费用，走一次规则断言是毫秒级 + 免费。当评测规模达到 DoorDash 的"每天 2,000 个自动评分会话"时，能用规则判的每一项交给 judge，都是每天重复支付一笔本可省下的钱，还要额外承担 judge 抖动带来的噪声。

### 2.2 程序化检查清单：八类检查与适用场景

Airbnb 三层评估框架的第一层"程序化检查（确定性、最先跑）"给出五项，腾讯"确定性评分器"给出五项（部分重叠），合并去重后是一张可直接照抄的八类清单：

| # | 检查项 | 判什么 | 出处 | 适用场景 | 命中时的典型问题分类 |
|---|---|---|---|---|---|
| 1 | **schema / 格式校验** | JSON 可解析、必填字段齐全、字段类型正确 | Airbnb 标注"永远有用" | 一切结构化输出；Agent 最终答复、工具入参 | invalid_json / missing_field / type_error |
| 2 | **空输出与异常长度** | 输出为空、过短（装不下最小结构）、过长（失控复读/冗余刷屏） | Airbnb 标注"永远有用" | 一切文本产物的第一道安检 | empty_output / too_short / too_long |
| 3 | **关键词 / 正则** | 黑名单（禁用话术、过度承诺、PII、注入回声）、白名单（必备披露内容） | Airbnb：安全合规；腾讯：关键词匹配 | 安全合规、话术红线、披露义务 | blacklist_hit / whitelist_missing |
| 4 | **P/R/F1** | 分类标签与金标的精确率/召回率/F1 | Airbnb：分类任务 | 意图识别、工单分类、情感判定等可离散化的任务 | 按错分类型细分 |
| 5 | **语义相似度** | 与参考答案的向量相似度（计算过程仍是确定性代码） | Airbnb：有参考答案时 | 摘要、改写等有参考输出但字面不必相同的任务 | similarity_below_threshold |
| 6 | **工具调用断言** | 是否调用指定工具、参数是否正确、禁用工具是否被调用 | 腾讯：工具调用检查 | 一切带工具的 Agent；安全关键路径 | tool_not_called / tool_param_error |
| 7 | **执行指标** | 调用次数上限、token 阈值、耗时预算 | 腾讯：执行指标 | 防死循环、防成本失控、防效率退化 | too_many_calls / time_budget_exceeded |
| 8 | **基线对比** | 与人工确认过的基线快照逐项对比（调用序列 / 产物 / token） | 腾讯：基线对比 | 回归评测、"过程是否退化"判定 | process_regression / result_regression |

两点使用经验：

- **检查项 1、2 放最前面，永远先跑**。Airbnb 对格式校验与空/异常长度的评价都是"永远有用"——它们不依赖任何业务知识，却能拦截最脏的一批样本（连 JSON 都解析不了的输出，后续一切检查都没有意义）。
- **从观察到的失败反推检查项，而不是拍脑袋穷举**。Airbnb 旅行客服案例的探索阶段：跑 100 个 prompt 人工精读，发现 15 个 groundedness 失败、8 个正确但啰嗦、5 个不当拒答、**3 个 JSON 失败**——随后"建测试"阶段第一批落地的就是 JSON 与长度检查。程序化检查清单应该随 badcase 回流持续生长（详见第 E10 章 · 评测驱动开发）。

一个最小评分器的写法（示意骨架，完整可运行版见 lab03）——注意它已经遵守了 2.5 的五元组输出契约：

```python
def check_tool_called(sample, required: list[str]) -> ScoreResult:
    """检查项 6：关键工具是否被调用。只看 trace 里的调用事件，毫秒级。"""
    actual = [c["name"] for c in sample.trace if c["type"] == "tool_call"]
    missing = [t for t in required if t not in actual]
    if missing:
        return ScoreResult(
            scorer="check_tool_called",
            score=0.0, passed=False,
            issue="tool_not_called",                    # 可枚举常量，RCA 入口
            confidence=1.0,                              # 确定性判定，置信度恒为 1
            evidence=f"关键工具 {missing} 未被调用（实际调用: {actual}）",
        )
    return ScoreResult("check_tool_called", 1.0, True, "none", 1.0,
                       f"全部关键工具已调用: {required}")
```

两个细节值得注意：① 确定性评分器的 confidence 恒为 1.0——它不会"拿不准"，拿不准是下一层的事；② evidence 里带上实际值（实际调用列表、实际金额），人审时一眼定位，不用重跑。

动手验证：本章配套实验 `labs/eval_lab03_programmatic_scorers.py` 实现了上表第 1、2、3、6、7 类评分器，并对 19 条构造样本（明显失败 / 边界 / 通过）跑完整流水线。运行：`cd evals-special/labs && python3 eval_lab03_programmatic_scorers.py`。

### 2.3 结构化输出是前提：JSON schema 强类型 vs prompt 措辞的脆弱性

程序化评分的一切前提是：**被评的输出有稳定可解析的结构**。Airbnb 的原话是：建议用结构化输出（JSON schema 严格类型化），**不要只靠 prompt 措辞产出结构，否则下游管道会坏**。

两种做法的对照：

| 维度 | JSON schema 强类型约束 | 靠 prompt 措辞"请输出 JSON" |
|---|---|---|
| 格式保证 | 解码层/约束解码强制合法 | 无保证，模型偶发多说话、漏引号、markdown 包裹 |
| 解析成本 | 直接 `json.loads` | 正则抠取 + 兜底解析，脆弱且需持续打补丁 |
| 失败模式 | 失败即显式报错，可计数 | 静默产出"看起来像 JSON"的坏结构 |
| 评分兼容性 | 字段/类型断言直接写 | 每条正则都在赌模型不改措辞 |
| 换模型时 | schema 契约不变 | 每个模型的"听话程度"不同，格式失败率漂移 |

工程落地的三件事：

1. **生成侧强制**：能用 API 的 structured output / tool schema 约束就用，把格式失败率压到接近零；格式失败率本身要作为一个独立的可统计问题分类计入报告（lab03 中 invalid_json / missing_field / type_error 是三个独立 issue 常量，便于归因是"完全不会输出 JSON"还是"字段意识不足"）。
2. **解析侧兜底**：即便有约束，也要有解析失败的兜底分支——解析失败本身就是评分信号（直接判 fail 并给出问题分类），绝不允许评分器抛异常中断整批评测。
3. **格式防护反哺生产**：DoorDash 底座模型迁移案例（Claude Sonnet 4.6 → Gemini 3.5 Flash）中，Flash 的部分工具参数格式与工具签名不符（签名要 plain string，Flash 传了 `{"dishes": [...]}` JSON 对象）。修复手段之一就是确定性的：**工具输入做确定性防护，错误形状强制转换回预期形状而非丢弃调用**——最终迁移达成延迟降 35%、质量无损。评分侧发现的格式问题，反过来指导了生产侧的防御性编码，这是"确定性检查价值外溢"的典型例子。

### 2.4 expected_behavior：把期望行为写成可执行规格（DSL）

腾讯的用例由两部分组成：**prompt + 检查规则**；预期结果不硬编码在用例里，而是通过基线会话标识（session_id + message_id）指向一份人工确认正确的执行记录，评测时动态获取（TPerf 从 Knot API 拉取）。这套思路可以整理成一份 YAML 风格的 expected_behavior DSL（下例为按腾讯检查项体系整理的示意写法，非任何一家原文）：

```yaml
case_id: refund-001
prompt: "订单 ORD-1001 我不想要了，帮我退款"
risk_level: P0                       # 风险等级决定门禁严格度与是否追加人工复核
expected_behavior:
  # —— 工具调用断言（腾讯：工具调用检查）——
  must_call: [query_order]           # 关键工具必须调用（未调用 = 硬失败）
  must_not_call: [force_refund]      # 禁用工具（越权/跳过校验的防线）
  partial_order:                     # 偏序约束：只约束先后，不约束全序列
    - [verify_identity, execute_refund]
  params:                            # 参数约束：类型 + 值域
    execute_refund.amount: {type: number, min: 0, max: "order.paid_amount"}
    query_order.order_id: {equals_input: "订单号"}

  # —— 输出断言（Airbnb：schema / 长度 / 关键词）——
  output_schema: {required: [action, reason], types: {action: enum[refund,reject,clarify]}}
  length: {min_chars: 16, max_chars: 400}
  keywords_blacklist: ["内部员工通道", "保证一定退款成功"]   # 过度承诺一票否决
  keywords_required_if:                # 白名单条件触发：提到退款就必须披露时效
    when_output_contains: "退款"
    must_contain: ["1-3个工作日"]

  # —— 执行指标（腾讯：调用次数 / token 阈值）——
  budget: {max_tool_calls: 6, max_total_latency_ms: 8000}

  # —— 基线对比（腾讯：基线快照机制）——
  baseline:
    session_ref: "sess_2026-07-12_refund-001"   # 指向人工确认过的基线会话
    compare: [call_sequence_normalized, artifact_exists, token_ratio<=1.5]
```

各检查字段的适用场景速查：

| DSL 字段 | 适用场景 | 不适用 / 注意 |
|---|---|---|
| must_call / must_not_call | 安全与正确性强依赖某次调用（先鉴权后操作、禁跳过校验） | 不要枚举全部调用强制顺序，会惩罚合法替代路径 |
| partial_order | 有明确前置依赖但路径可变的流程 | 只表达"必须先 A 后 B"，不表达步数 |
| params 约束 | 金额、ID、枚举等可值域化的参数 | 语义等价参数（同义改写）判不了，交给 judge |
| output_schema / length | 一切结构化产物 | 格式之外的内容质量判不了 |
| keywords 黑白名单 | 合规红线、必备披露、禁用话术 | 变体绕过（同义替换）防不全，是必要非充分手段 |
| budget | 防死循环、防成本失控、效率回归 | 阈值需从基线统计得出，不能拍脑袋 |
| baseline compare | 回归评测、"过程/结果/效率是否退化" | 基线需随被测系统变更而重录（见 2.7） |

lab03 的样本集正是按这份 DSL 的字段逐项构造正负样本的（黑名单命中"内部员工通道"、白名单缺失"1-3个工作日"、调用 9 次超上限 6、总耗时 11500ms 超预算 8000ms、amount=300 超值域 [0,150]），每类失败都被对应的评分器拦下并给出正确问题分类。

### 2.5 评分输出规范：绝不止 pass/fail

阿里的评分输出规范是本章最重要的设计点之一：**评分输出不止 pass/fail，还要有问题分类（现象层：事实性错误 / 答非所问 / 过度承诺）、问题现象、置信度、判定依据——为 RCA 提供"现象入口"；且现象分类 ≠ 最终根因**。

一条失败样本如果只告诉你 "fail"，下游什么都做不了：不知道坏在哪个环节（无法聚类）、不知道判定有多可靠（无法决定要不要人工复核）、不知道为什么失败（无法回放调试）。因此评分器应统一返回一个五元组（lab03 的 `ScoreResult` 即此结构）：

| 字段 | 类型 | 下游用途 |
|---|---|---|
| score | 连续分 [0,1] | 灰度阈值、漂移观察（二值门禁用 passed，趋势观察用 score） |
| passed | bool | 门禁硬判定 |
| issue（问题分类） | 枚举常量 | badcase 聚类、RCA 映射表的键、报告分布统计 |
| confidence | [0,1] | 自动采信 vs 升级人工复核的路由信号 |
| evidence（判定依据） | 人可读文本 | 回放核对、误报申诉、人审快速定位 |

一条真实失败样本的评分输出长这样（lab03 中"退款金额超值域"样本的等价物）：

```json
{
  "case_id": "refund-001",
  "scorer": "check_tool_params",
  "score": 0.0,
  "passed": false,
  "issue": "tool_param_error",
  "confidence": 1.0,
  "evidence": "refund.amount=300.0 超出合法范围 [0, 150]（订单实付 150）",
  "prompt_version": "v1.8",
  "model": "candidate-a"
}
```

`issue` 供聚类与 RCA 映射，`evidence` 供人审复核，`prompt_version`/`model` 绑定让同一 issue 能按版本聚成问题簇。

三条落地纪律：

1. **问题分类必须是可枚举的常量，不是自由文本**。lab03 定义了 13 个 issue 常量（empty_output / too_short / too_long / invalid_json / missing_field / type_error / blacklist_hit / whitelist_missing / tool_not_called / tool_param_error / too_many_calls / time_budget_exceeded / none）。可枚举才能可统计，才能被下游"问题现象 × 功能模块"映射表直接消费（详见第 E11 章 · Badcase 根因分析与优化闭环）。
2. **现象 ≠ 根因，必须分层**。"关键工具未调用"是现象；根因可能是 prompt 没写清触发条件、工具描述缺失、或上下文被覆盖。阿里 RCA 五步的第二步"范围收敛"正是拿现象去查映射表缩小候选模块——程序化评分输出的 issue 就是这条流水线的入口。阿里 RCA 中"规则定位硬错误"的清单——**工具未调用 / 顺序违反 SOP / 参数缺失 / 报错未重试 / DB 状态未变 / 引用来源不存在**——几乎每一项都是程序化评分器能直接给出的确定性信号。
3. **判定依据让每条失败可申诉**。evidence 字段（如 "refund.amount=300.0 超出合法范围 [0, 150]"）让人审和开发者不用重跑就能复核结论；没有 evidence 的 fail 在评审会上等于没有结论。

聚类的价值用阿里的实例最直观：报告不是列 100 条 badcase，而是产出"**退款已发货场景中，Agent 23 次跳过订单状态校验，主要集中在 v1.8 Prompt**"——这句话的"23 次"来自 issue=tool_not_called 的可统计聚合，"v1.8 Prompt"来自评分记录上绑定的 prompt 版本。没有结构化的评分输出，就不可能有这样的聚类。

### 2.6 分层筛查流水线：粗筛 → 精判 → 人工复核

当样本量大、评分手段贵贱悬殊时，不能让每条样本都走全套检查。阿里的分层筛查流水线：

```
待评样本（离线评测集 / 线上抽样 / badcase 回流）
   │
   ▼
┌─────────────────────────────────────────────┐
│ 粗筛层：规则 Scorer + 轻量 Judge               │
│ 空输出 / 长度 / JSON 解析 / 关键词（只看输出文本） │
└──────┬──────────────────────┬────────────────┘
       │ 明确失败              │ 通过或存疑
       ▼                      ▼
  直接定案                 ┌──────────────────────────────┐
  （给出问题分类，          │ 精判层：完整规则 + Judge        │
   绝不进精判）             │ 工具断言 / 参数值域 / LCS 对齐 /  │
                           │ LLM 语义判定（需要 trace 与模型） │
                           └──────┬─────────────┬──────────┘
                                  │ 结论可信      │ 高风险 / 低置信 / 冲突
                                  ▼              ▼
                             入库 + RCA      ┌────────────────┐
                                             │ 人工复核层（E06）│
                                             │ 终判并回收口径   │
                                             └────────────────┘
```

各层职责与输出：

| 层 | 手段 | 职责 | 输出 |
|---|---|---|---|
| **粗筛层** | 规则 Scorer + 轻量 Judge | 快速分流：明显通过 / 明显失败 / 存疑 | 明显失败的直接定案并给问题分类 |
| **精判层** | 完整规则 + Judge | 确认 badcase，处理边界样本 | 初始问题分类 / 现象 / 置信度 / 判定依据 |
| **人工复核层** | 专家 | 高风险 / 低置信 / 冲突 / 口径未固化的样本 | 终判结论，回收口径反哺前两层 |

关键纪律：**粗筛已明确失败的样本绝不进精判**。否则昂贵的判定能力（trace 解析、LLM 往返）被垃圾样本稀释，评测成本随样本量线性恶化。

**分层的依据不是"哪个评分器写得早"，而是"评分器依赖的信息范围"**：

- 只看输出文本本身的规则最便宜（空输出、长度、JSON 解析、关键词）→ 粗筛；
- 需要完整 trace / 工具调用记录 / 环境状态的判定较贵（工具断言、参数值域、LCS 对齐）→ 精判前段；
- 需要 LLM 语义判断的最贵（语气、groundedness、策略合理性）→ 精判后段；
- 需要政策口径与价值判断的 → 人工层。

**成本账要用数字说话**。lab03 的实测结果（固定种子、可复现）：19 条样本中粗筛拦截 8 条明显失败（空输出 / JSON 损坏 / 异常长度 / 缺字段 / 类型错误 / 黑名单 / 白名单缺失），11 条进入精判层；LLM Judge 仅被调用 10 次；按相对成本单元计，**实际开销 490 单元 vs 全量走精判的 baseline 874 单元，节省 43.9%**（实验断言阈值 ≥35%）。样本越脏、judge 越贵，分层节省越大——这正是阿里把分层筛查写进平台架构的原因。

人工复核层的路由条件（高风险 / 低置信 / 规则与 Judge 冲突 / 新模型新 Prompt 上线抽样等）展开见第 E06 章 · 人工评估与评分路由。

### 2.7 评分工程实践：扣分制、基线快照、轨迹对齐与稳定性阈值

这一节集中讲腾讯（含 TPerf 实战案例）沉淀下来的四套工程机制，都是"程序化评分如何长期运营"的答案。

**（1）扣分制与达标线。** 腾讯的评分规则：初始 100 分负分制，每处不符扣对应分至 0，**达标线 80 分**（推荐值，按 Agent 类型与业务风险调整）。扣分项（原文数字）：

| 扣分项 | 分值 |
|---|---|
| 任务结果不符预期 | −100（直接归零） |
| 步骤遵循性，每步 | −10 |
| 步骤输出结果，每步 | −10 |
| 工具/知识库调用，每项 | −10 |
| 分析耗时（基准 5 分钟），每超 1 分钟 | −10 |
| 一致性 | N 次（建议 N=5）全达标取均值 |

每次评分输出 **JSON 扣分明细 + 原因**，渲染 HTML 报告归档；报告头部带用例总数 / 通过率 / 平均分 / 模型版本与费用 / 总 token / 平均费用每 Trial。扣分制的好处是**分数可归因**：80 分与 60 分的差距能逐项拆出来，而不是一个黑盒总分。

**（2）基线快照机制。** 基线 = **单用例执行 1 次后经人工确认的预期过程与预期结果快照**——回答"正确的执行应该长什么样"。预期过程含 CoT、工具调用序列（入参返回）、中间产物、完整 Trace；预期结果含最终响应、输出文件、输出报告。流程：用例设计只定义 prompt 与检查规则 → 执行 1 次 → 人工审核 → 不可接受则修后重跑 → OK 则该次快照成为基线。后续每次执行与基线对比，分三个方面：

- **过程对比**：调用序列一致 / 关键步骤缺失 / 顺序偏离 → 判"过程退化"（确定性评分器程序化判定）；思维链合理性、步骤最优交给 Rubric 以基线为参考答案对比语义差异；
- **结果对比**：产物存在 / 关键内容缺失 / 产物不一致 → 判"结果退化"；结论准确性、表述完整性交给 Rubric；
- **效率对比**：token / 步骤数超基线比例，如 **>50% → 效率退化**。

基线更新时机是常考点：**Agent/Skill 逻辑变更、模型版本升级、用例本身修改（prompt 或检查规则变了）**——三者任一发生，重新执行 1 次并人工确认。TPerf 的基线配置随代码仓库 Git 版本化；用例不硬编码预期输出，而是用基线会话标识指向人工确认正确的记录、评测时动态获取——这样基线更新有据可查、可回滚。

**（3）轨迹序列对齐：LCS + 归一化（TPerf 实战）。** 程序化判定"工具调用序列是否一致"最忌讳 exact match（时间戳不同、查询参数不同都会误判）。腾讯 TPerf 的做法：**LCS（最长公共子序列）对齐基线与 Trial 步骤，先做归一化再对齐**，归一化规则五条（原文）：时间戳占位 / 搜索工具忽略查询参数 / 写入操作只留路径 / 终端命令提取脚本名 / 连续读文件组内不校验顺序。对齐后：**不一致 / 多余 / 缺少 / 顺序错各扣 2 分，上限 −10**。这套机制在 lab06 有完整实现，运行：`cd evals-special/labs && python3 eval_lab06_trajectory_eval.py`（轨迹三层评估详见第 E07 章）。

TPerf 的效率评分同样是程序化的：耗时基准 300s，每超 10% 扣 1；token 以基线为基准每超 10% 扣 1，上限 −10。模型评分维度（关键判定不一致直接 −80、章节内容每项 −5 上限 −80）则交给 CodeBuddy CLI 逐项对比——确定性与模型评分各管一段，最后合成。

**（4）一致性标准与得分公式。** 基线对比不能要求逐字一致，腾讯给出三档标准：**数值型**整数精确、小数相对误差 ≤1%；**结论型**异常等级与关键发现一致；**建议型**核心排查方向一致即可。得分公式（TPerf）：`trial_score = max(0, 100 + 各项扣分)`；`trial_pass = score ≥ 80`；`case_score = 全 pass 取均值，任一 trial 不达标则该用例 0 分`——最后一条正是 pass^k 思想在评分规则里的落地（详见第 E02 章 · 评估指标体系与第 E09 章 · 统计学基础）。

**（5）稳定性容忍阈值分级。** N 次执行（建议 N=5），只要 1 次不通过即存在稳定性风险，但容忍度按使用类型分级（腾讯原文）：**关键决策类（问题定位/故障诊断）0%——N/N 全过，任何一次失败都可能误判；辅助分析类（性能分析/报告生成）≤10%；创意生成类（代码建议/文案）≤40%**。N=5 的结果解读：全过 = 稳定；1/5 失败 = 存在幻觉，按类型判断；2/5 = 高幻觉率，深入排查；5/5 失败 = 稳定失败，**先查任务定义或基线**。腾讯特别提示：**0% 的 pass^N 通常说明任务定义有问题，不是能力不行**——这条经验在诊断"评分器自己坏了"时极其有用（人工评分的六个必要场景之一就是"诊断通过率异常：0% 或 100% 通常是任务/评分器坏了，不是模型弱"）。

TPerf 的零容忍决策是个好案例：TPerf 虽属辅助分析类，但结论直接影响优化决策与发布判断，一次错误结论可能导致性能问题漏检上线——因此采用关键决策类标准（任一 Trial 不达标该用例 0 分）。**容忍阈值不是由任务类型机械决定的，而是由错误的业务代价决定的**。

**（6）用例集构成与执行画像（TPerf 实测数字）。** TPerf 的用例集按场景分组共 9 大类、30+ 用例，每个用例对应一条真实且不可变的压测记录（可复现）：

| 场景分组 | 用例数 | 场景分组 | 用例数 |
|---|---|---|---|
| CPU 瓶颈 | 6 | TCP 队列 | 3 |
| 网卡 | 5 | Nginx | 1 |
| 磁盘 | 4 | 配置问题 | 1 |
| 磁盘 IO | 2 | 正常场景 | 5 |
| 内存 | 1 | — | — |

执行侧的工程数字：支持 7 模型对比（每用例 × 每模型参数化测试）；Trial 并发 + 评分并行 + 三评分器并行；限流自动重试（≤5 次）；单用例约 3000s；全量 30+ 用例 × 7 模型约 3–5 小时；用 pytest 实现、TCase 平台管理用例；trace 取自 Knot AG-UI 协议事件流（工具调用事件/文本消息事件/token 消耗），由事件流解析器构建调用步骤列表。另有两条值得抄的设计：**基线配置随代码仓库 Git 版本化、执行结果每次重新生成并归档**；**支持重新评分**——评分逻辑调整后无需重新触发 Agent，历史 trace 直接重算分。这把"评分器升级"与"被测系统重跑"解耦了，是评测平台降本的关键机制。

最后补两条门禁口径（腾讯引用 Anthropic 推荐）：**确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%**；能力测评起步通过率 20–50%（目标山峰，主动拓展），回归测评接近 100%（防御漂移，只增不减，CI 每次运行），通过率稳定 100% 后用例"毕业"进回归集。

### 2.8 规则的边界：哪些东西规则永远判不了

程序化评分的边界与它的优点同源：**只能判"能写成规则的已知硬条件"**。阿里给出的分工口径：规则看硬条件（工具、状态、字段、禁用动作），**LLM 看"语义/策略合理性"**。三类东西规则永远判不了：

| 判不了的 | 例子 | 该交给谁 |
|---|---|---|
| 语义正确性 | 回复引用的退款政策是否真实存在、事实是否准确 | LLM Judge（groundedness 检查，见第 E05 章） |
| 语气与体验 | 是否像"热情专业的旅行顾问"、是否有同理心、是否啰嗦 | LLM Judge rubric（见第 E05 章） |
| 策略合理性 | 该先澄清还是先操作、补偿口径是否符合内部政策 | 人工定口径 + Judge 辅助（见第 E06 章） |

还有两个与边界相关的常考问题：

1. **假阳性（结果对、路径错）**：回复看似正确，但执行路径已偏离或带风险——阿里对此的处方是**加过程型与风险型检查**（工具断言、禁用动作、SOP 顺序），腾讯则在 Rubric 评分输出中专门设了 `is_false_positive` 布尔字段（结果对但过程错的虚假成功）。程序化评分能抓住其中可规则化的部分（跳过校验工具、越权调用），抓不住的部分要靠轨迹级评估与 judge（详见第 E07 章 · 轨迹与 Agent 级评估）。
2. **规则会不会被钻空**：关键词黑名单会被同义改写绕过、单点断言会被"表面达标"满足。对策是黑白名单只做必要非充分的第一道防线，关键检查用状态级多点校验，并给评分器本身配对抗样本（见本章易错点 9 与第 E10 章）。

拿到一个新检查需求时，用这个顺序决定它该落在哪一层：

```
这条判定能写成代码断言吗？
├── 能，且只看输出/trace 就有确定答案 ──→ 程序化评分（本章）
├── 写不成代码，但可以写成"人/模型能对照的判断标准" ──→ LLM Judge + rubric（第 E05 章）
│       └── judge 与人工一致率校准到 ~85% 才进自动化（阿里/腾讯口径）
└── 依赖内部政策口径 / 价值判断 / 高风险兜底 ──→ 人工（第 E06 章）
```

**本章收束**：程序化评分 = 确定性优先的八类检查 + 结构化输出前提 + DSL 规格 + 五元组输出 + 分层流水线 + 扣分制/基线/对齐工程。它判不了的语义、语气与策略合理性，正是下一层的领地——详见第 E05 章 · LLM-as-Judge 深入。

## 四、经典面试题与参考答案

#### 题 1（基础）：什么是程序化评分？常见的检查项有哪些？

**答题思路**：先给定义与四个特性（快/稳/免费/可单测），再报菜名式过八类清单，最后点一句它在三层中的位置。

**参考答案：** 程序化评分是把评测中的"硬条件"写成代码断言，由脚本（断言/Lint/AST/解析器）确定性执行。特点：毫秒级、零费用、稳定性 100%（同一输入永远同一结论）、可单测可版本化，是三层评分（确定性 > Rubric > 人工）的第一层，承担硬门禁角色。常见检查项八类：① schema/格式校验；② 空输出与异常长度；③ 关键词/正则黑白名单；④ 分类任务的 P/R/F1；⑤ 有参考答案时的语义相似度；⑥ 工具调用断言（是否调用/参数正确/禁用工具）；⑦ 执行指标（调用次数/token 阈值/耗时预算）；⑧ 基线对比（与人工确认的基线快照逐项比）。Airbnb 对前两项的评价是"永远有用"，并强调程序化检查"确定性、最先跑"。

#### 题 2（基础）：为什么说"能用代码判断的绝不用模型"？三类评分器怎么选？

**答题思路**：四个理由（成本/稳定性/可审计/零偏差）逐条给数字，再给选择顺序与门禁分工，最后补"分层防御不是三选一"。

**参考答案：** 四个理由：① 成本——规则毫秒级免费，Judge 秒级加 API 费，人工分钟到小时级；② 稳定性——代码断言 100% 稳定，Judge 有抖动需降噪，人工取决于标注员水平；③ 可审计——规则在代码里可单测、可 review、可 git 版本化，prompt 里的规则做不到；④ 零偏差——不存在 judge 的位置/冗长/自我偏好问题。腾讯的选择优先级是确定性 > Rubric > 人工，门禁角色也分层：确定性做硬门禁，Rubric 做分级门禁（error 硬/warning 软），人工不进门禁只做采样审查与校准。但注意三层是分层防御不是三选一：规则只能判"已知硬指标"，语义/语气/策略合理性必须交给 Judge 与人工，阿里口径是"规则主判、Judge 辅助、人工兜底"。

#### 题 3（进阶）：为什么说结构化输出是程序化评分的前提？如果模型只能输出自由文本会怎样？

**答题思路**：对照两种做法的失败模式，落到三件工程事（生成侧约束/解析兜底/格式失败计数），用 DoorDash 迁移案例收尾。

**参考答案：** 程序化评分依赖稳定可解析的结构。Airbnb 明确建议用 JSON schema 严格类型化的结构化输出，不要只靠 prompt 措辞产出结构，否则下游管道会坏。对照来看：强类型约束下格式由解码层保证，直接 `json.loads` 即可断言字段与类型；靠 prompt 措辞则无保证，模型偶发多说话、漏引号、markdown 包裹，解析要靠脆弱正则打补丁，失败还常常静默。工程上三件事：生成侧尽量用 API 的结构化输出约束；解析失败本身作为评分信号（判 fail 并给问题分类 invalid_json），绝不让评分器抛异常中断批跑；把格式失败率单列统计。一个反哺生产的例子：DoorDash 模型迁移时发现新模型工具参数形状不符，修复手段是确定性的输入防护——错误形状强制转换回预期形状而非丢弃调用，最终迁移延迟降 35%、质量无损。

#### 题 4（进阶）：评分输出应该包含哪些字段？只报 pass/fail 会失去什么？

**答题思路**：报五元组字段，把每个字段挂到一个下游能力上（聚类/RCA 路由/人工路由/申诉），结尾强调现象 ≠ 根因。

**参考答案：** 阿里的规范：评分输出不止 pass/fail，还要有问题分类（现象层）、问题现象、置信度、判定依据。对应五元组实现：score（连续分，供趋势观察）/ passed（门禁硬判定）/ issue（可枚举的问题分类常量）/ confidence（把握度）/ evidence（判定依据）。只报 pass/fail 会失去四个下游能力：① 聚类——issue 可枚举才能统计出"退款已发货场景 23 次跳过订单状态校验，集中在 v1.8 Prompt"这样的问题簇；② RCA 路由——issue 是"问题现象 × 功能模块"映射表的键，是 RCA 的现象入口；③ 人工复核路由——低置信样本才升级人工；④ 申诉与回放——没有 evidence 的 fail 无法复核。最后强调现象 ≠ 根因：现象进 RCA 流水线，根因由后续分模块诊断产出，二者不能混。

#### 题 5（进阶）：给一个电商退款客服 Agent 设计程序化评分规格（expected behavior）。

**答题思路**：按 DSL 五方面现场写规格（工具断言/输出断言/预算/基线/风险分级），并说明检查项来源是 badcase 观察而非拍脑袋。

**参考答案：** 按 DSL 五个方面写：① 工具断言——must_call 含 query_order（退款前必查订单），must_not_call 含绕过校验的直接退款工具，partial_order 约束先鉴权后执行，参数约束 execute_refund.amount ∈ [0, 订单实付]；② 输出断言——schema 必填 action/reason，长度上下限（过短装不下最小结构、过长疑似失控），黑名单（"保证一定退款成功"等过度承诺话术）与条件白名单（提到退款必须披露"1-3个工作日"时效）；③ 执行指标——调用次数上限、总耗时预算，防死循环与成本失控；④ 基线对比——与人工确认的基线会话做归一化后的序列对齐与效率比（token/步骤超基线 >50% 判效率退化）；⑤ 风险分级——P0 用例失败即门禁拦截，并按风险等级决定是否追加人工复核。设计依据不是拍脑袋，而是从 badcase 回流中观察到的失败模式反推（Airbnb 做法：跑 100 条样本人工精读再建测试）。

#### 题 6（进阶）：如何程序化判定"工具调用序列是否正确"？exact match、无序集合、偏序约束、LCS 对齐各在什么时候用？

**答题思路**：四种粒度由严到松排开，各配一个适用场景，引用 TPerf 的归一化规则与扣分数字作为实战锚点。

**参考答案：** 四种粒度由严到松：① exact match——只适合完全确定性的流水线，真实 Agent 路径多样，用它会把合法替代路径判错；② 无序关键调用集合——只查 must_call/must-not-call 是否满足，适合安全护栏；③ 偏序约束——只约束关键先后（先鉴权后操作），保留路径自由度，适合流程合规；④ LCS 对齐 + 归一化——允许局部插入/缺失/乱序，按差异扣分而非一票否决，适合"过程是否退化"的回归判定。腾讯 TPerf 用第四种：先把步骤归一化（时间戳占位 / 搜索工具忽略查询参数 / 写入只留路径 / 终端命令提取脚本名 / 连续读文件组内不校验顺序），再 LCS 对齐，不一致/多余/缺少/顺序错各扣 2 分、上限 −10。核心取舍：断言守关键调用（安全），对齐量化退化程度（回归），永不要求全序列逐字一致。动手可跑 `cd evals-special/labs && python3 eval_lab06_trajectory_eval.py`。

#### 题 7（进阶）：解释粗筛 → 精判 → 人工复核的分层筛查流水线，并算一笔成本账。

**答题思路**：三层职责 + 一条路由纪律 + 分层依据（依赖信息范围），最后用 lab03 的成本单元数字定量收尾。

**参考答案：** 阿里的三层设计：粗筛层用规则 Scorer + 轻量 Judge 快速分成明显通过/明显失败/存疑；精判层用完整规则 + Judge 确认 badcase 并产出初始问题分类/现象/置信度/判定依据；人工复核层处理高风险/低置信/冲突/口径未固化样本。路由纪律：粗筛已明确失败的样本绝不进精判，否则昂贵判定被垃圾样本稀释，成本随样本量线性恶化。分层依据是评分器依赖的信息范围：只看输出文本的最便宜（空输出/长度/JSON/关键词），需要完整 trace 的次之（工具断言/参数值域/LCS），需要 LLM 语义判断的最贵。成本账（lab03 实测，固定种子可复现）：19 条样本粗筛拦截 8 条，11 条进精判，LLM Judge 仅调用 10 次，实际开销 490 成本单元 vs 全量精判 baseline 874 单元，节省 43.9%（实验断言 ≥35%）。样本越脏、judge 越贵，节省越大。

#### 题 8（系统设计）：为公司的 Agent 评测平台设计完整的程序化评分子系统。

**答题思路**：按"接口契约 → 用例规格 → 流水线 → 门禁报告 → RCA 衔接 → 评分器自身 QA"六组件讲，每个组件给一个关键设计决策。

**参考答案：** 六个组件：① **评分器接口契约**——所有评分器（规则或 Judge 包装）统一返回五元组 {score, passed, issue, confidence, evidence} 加评分器署名，issue 从可枚举常量表取，接口即 lab03 的 ScoreResult；② **用例规格**——prompt + expected_behavior DSL（must_call/参数约束/预算/黑白名单/基线引用），基线用会话标识指向人工确认快照而非硬编码预期输出，随代码仓库版本化；③ **分层流水线**——粗筛（文本级便宜规则）→ 精判（trace 级规则 + Judge）→ 人工复核路由（低置信/高风险/冲突），粗筛定案的失败不进精判，全程记录各层拦截数与成本单元；④ **门禁与报告**——扣分制（初始 100、达标线 80、扣分明细 JSON），P0 用例一票否决，输出按问题分类聚合的分布报告，版本对比带统计口径（详见第 E09 章）；⑤ **与 RCA 衔接**——issue 作为"现象入口"进 RCA 映射表，评分记录绑定 prompt/模型版本支持问题簇聚类；⑥ **评分器自身 QA**——配 golden 正负样本（含"看起来对其实错"的对抗样本）防误杀与漏放，评分器变更走回归，通过率 0%/100% 触发异常诊断（通常是评分器坏了不是模型弱），线上抽检与评分器结论的一致率持续监控。

#### 题 9（进阶）：回归集通过率从 92% 突然变成 100%，你的第一反应是什么？怎么排查？

**答题思路**：展示"先怀疑测量系统再谈模型能力"的资深反应，按评分器 → 基线 → 用例 → 交叉验证的顺序排查。

**参考答案：** 第一反应不是庆祝，而是怀疑测量系统。腾讯的经验：通过率 0% 或 100% 通常是任务或评分器坏了，不是模型弱。排查顺序：① 查评分器——最近有没有改过断言、正则、基线或聚合逻辑？用留存的 golden 正负样本（尤其"看起来对其实错"的对抗样本）重跑评分器，验证它还能抓住坏样本；② 查基线——基线是否被意外重录成了当前版本的输出（基线与被测同源会互相"背书"）；③ 查用例——回归集是否被悄悄删掉了失败用例，或数据文件路径失效导致断言空转；④ 查被测——是否真发生了能力跃升，用另一套未动过的评测集交叉验证，并抽查 20~50 条"通过"样本人工确认。结论要能区分"真的变好了"与"尺子变松了"。同样的逻辑适用于分数突变 0%：先查任务定义与基线，再怀疑能力。

## 五、易错点 · 反直觉点

1. **把规则能判的交给 Judge**：格式、字段、工具调用这类硬条件让 LLM 判，等于花钱买抖动——judge 会偶发误判且结论不可复现，门禁随之不稳。→ 真相：确定性 > Rubric > 人工是选择优先级，规则判不了的才升级。→ 记忆锚点：**能写断言的绝不写 prompt**。
2. **评分输出只有 pass/fail**：失败的样本没法聚类、没法路由、没法归因，评测平台退化成"出分工具"。→ 真相：必须有问题分类/置信度/判定依据，它们是 RCA 的现象入口与人工复核的路由信号。→ 记忆锚点：**fail 必须带着"为什么 fail"出门**。
3. **把现象分类当根因**："工具未调用"写进根因报告，修复动作只能是无力的"加强 prompt"。→ 真相：现象 ≠ 根因，现象进映射表缩圈，根因靠分模块诊断产出，要指向 owner 与处理动作。→ 记忆锚点：**现象是门牌号，根因是住户**。
4. **工具序列 exact match**：时间戳不同、查询参数不同、合法路径顺序不同，全被判错；评测集退化成背答案。→ 真相：先归一化（时间戳占位/忽略查询参数/写入只留路径），再 LCS 对齐按差异扣分，关键调用用 must-call 断言守。→ 记忆锚点：**断言守关键，对齐量退化**。
5. **靠解析自由文本做程序化检查**：模型一句"好的，结果如下："就能让你的正则全线失效。→ 真相：结构化输出（JSON schema 强类型）是前提，解析失败本身也要计为问题分类，而不是抛异常。→ 记忆锚点：**结构不强制，规则全白写**。
6. **所有样本走全套检查**：明显 JSON 损坏的样本也去调 LLM judge，昂贵判定被垃圾稀释。→ 真相：粗筛定案的失败绝不进精判；分层依据是评分器依赖的信息范围。→ 记忆锚点：**便宜的筛子先过，贵的判官只审疑案**。
7. **通过率 100% 当好消息直接汇报**：可能是评分器坏了、基线被同源污染、或失败用例被悄悄移除。→ 真相：0% 和 100% 都是异常信号，先查任务定义与评分器，再谈模型能力。→ 记忆锚点：**满分先怀疑尺子**。
8. **基线快照一劳永逸（或动不动重录）**：被测系统升级后不重录，基线测的是旧世界；每次跑完都重录，基线永远在给现状背书。→ 真相：只有三个重录时机——Agent/Skill 逻辑变更、模型版本升级、用例本身修改，且重录必须再过一次人工确认。→ 记忆锚点：**基线只在世界变了时变**。
9. **把关键词黑名单当安全的全部**：同义改写、拆字、隐喻都能绕过正则。→ 真相：黑白名单只是必要非充分的第一道防线，语义层的过度承诺/注入回声要靠 Judge，高风险场景保留人工复核。→ 记忆锚点：**正则判存在，Judge 判语义，人判口径**。

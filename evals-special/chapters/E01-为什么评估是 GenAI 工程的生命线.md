# 第 E01 章 · 为什么评估是 GenAI 工程的生命线

> 一句话导读：传统软件"上线前跑一遍测试、之后靠断言保平安"的范式，在 GenAI 系统上全面失效。本章回答一个根本问题——**为什么评估（evals）不是交付前的检查点，而是贯穿 GenAI 全生命周期的生命线**。学完本章，你能讲清三大根本难题、Airbnb 三大陷阱、"跑几条 case 感觉还行"的四个具体失效场景、评估的四重身份，并会用评估经济学框架向老板论证评测投入——这些也正是面试开场最高频的"为什么"类问题。

## 二、核心概念精讲

### 2.1 三大根本难题：GenAI 系统为什么"天生难测"

阿里与腾讯的评测方法论不约而同地把 GenAI 工程的门槛概括为三件事（阿里称之为"三大门槛"）：**非确定性、黑盒化、错误级联放大**。这三点不是工程瑕疵，而是这类系统的内禀属性。

| 难题 | 本质 | 直接工程后果 | 传统测试为何失灵 |
|---|---|---|---|
| 非确定性 | 同一输入不一定有同一输出（采样、上下文组装、工具时变） | 单次运行结果只是分布中的一个样本；"复现"要重新定义为统计意义上的 | 断言 `assert output == expected` 天然不成立 |
| 黑盒化 | 模型内部决策不透明：为什么选这个工具、为什么这样改写 query，看不见 | 失败无法定位到"哪一步、因为什么"；只能靠结构化 trace 反推 | 传统软件可以断点调试、读源码，GenAI 只能读 trace |
| 错误级联放大 | 多步链路中，前一步的小偏差会被后续步骤放大成错误结论 | 步级 95% 正确率 × 20 步 ≈ 36% 端到端成功率；错误在终点才暴露，根因却在起点 | 单元测试"每个模块都对"推不出"系统对" |

Airbnb 对同一问题的表述是：GenAI 与传统软件的差异在于**输出不可预测、"正确"依赖判断、用 AI 评 AI 又引入新风险**；一次请求可能同时包含搜索 / 推理 / 外部动作 / 文本生成，**每个环节都可能独立失败**。腾讯则补充了黑盒化带来的一个微妙痛点：答案碰巧对但推理路径错时，你**分不清"正确调用工具后回答"与"训练数据碰巧答对"**——前者可信赖，后者是定时炸弹。

**级联放大值得用一个具体的多步 agent 展开**。设想一个退款客服 agent 处理"这个东西我要退，怎么寄回？"：

| 步骤 | 正常行为 | 本次实际行为 | 偏差大小 |
|---|---|---|---|
| 1. 意图识别 | 识别为「退货退款」 | 误判为「取消订单」 | 只差一个意图标签 |
| 2. 订单查询 | 查到目标订单 | 查到目标订单 | 无 |
| 3. 政策校验 | 退货政策：需先校验物流签收状态 | 取消政策：无需校验，直接放行 | 关键校验被跳过 |
| 4. 执行动作 | 生成退货寄回单 | 直接取消订单、作废优惠券 | 不可逆副作用 |
| 5. 回复用户 | 给出寄回指引 | "已为您取消订单" | 用户目标彻底落空 |

第 1 步一个标签的偏差，到第 4 步已经变成**不可逆的资损与投诉**。这就是阿里强调"多步链路前一个小偏差会被放大成错误结论"的含义。量化版本是同一个乘法：**若每步可靠性为 p，n 步任务的端到端成功率上界约为 pⁿ**——p=0.95、n=20 时只剩约 36%。τ-bench（Sierra AI，arXiv 2406.12045，2024）提供了实证：GPT-4o 在 retail 域单次通过率 pass^1 ≈60%（官方榜单 60.4%；摘要口径为不足 50%），而要求 8 次独立试验全部通过的 pass^8 ≈25%（摘要 <25%）；airline 域 pass^1 ≈42%、pass^8 跌至约 16%。"能做对一次"与"稳定做对"之间的鸿沟，比直觉大得多——**这道鸿沟只能靠评估体系量化，靠 demo 永远看不见**。

三大难题不是抽象抱怨，它们各自对评测体系提出了硬性设计要求：

| 难题 | 对评测体系的硬性要求 | 出处 |
|---|---|---|
| 非确定性 | 多 trial 重复 + 统计口径报数（pass^k、置信区间）；评测执行环境隔离，避免多用例共享状态导致分数不可复现 | 阿里：评测执行环境隔离是平台基本要求；腾讯：N 次执行的容忍阈值分级 |
| 黑盒化 | 结构化 trace 是**被测系统的标准能力而非事后补救**：稳定记录工具名、入参、返回值、时间戳、耗时、错误，复杂 agent 还要记录计划、检索、护栏决策 | 阿里/腾讯共识（详见第 E7 章） |
| 错误级联 | 评估不能只看终点输出：Airbnb 分 step / trajectory / session 三层，阿里分 Turn / Session / Trace / Outcome 四层 | 两家独立得出同构结论（详见第 E7 章） |

**非确定性的来源至少有三层**，理解这一点才能理解"为什么固定种子也不够"：① 模型层——采样本身的随机性（temperature / top-p）；② 环境层——工具返回与外部数据随时间变化，同一条用例今天跑和下周跑看到的"世界"可能不同；③ 组装层——上下文组装、并发与重试逻辑带来的差异。这也是为什么阿里把"评测执行环境隔离、避免多用例共享状态"列为平台级要求，为什么 DoorDash 要用 fixtures 冻结外部状态（详见第 E8 章）——**控制变异来源，是分数有意义的前提**。

换句话说：**三大难题各自消灭了传统测试的一根支柱**——非确定性消灭了"断言"，黑盒化消灭了"断点调试"，级联放大消灭了"单元测试通过即系统通过"。评估体系就是把这三根支柱换成新支柱（统计判定、trace 归因、分层评估）的工程。

### 2.2 三大陷阱：没有评估的产品会掉进哪里（Airbnb）

Airbnb 在点评摘要、客服、房东/房客消息、内部洞察等多个 GenAI 场景的实践中总结出：**没有早期评测计划的产品，通常掉进三个坑**。这是本章最该背下来的框架之一：

| 陷阱 | 表现 | 机理 | 典型症状 |
|---|---|---|---|
| 虚假信心（false confidence） | 用一个浅层 helpfulness 分数自我安慰："模型评分 4.5/5，挺好" | 泛化的"有没有帮助"抓不住真实失败模式：幻觉、过度承诺、答非所问都被礼貌的通顺回答糊过去 | 分数很漂亮，投诉照样涨 |
| 未被发现的回归（undetected regression） | 改了一版 prompt，新场景变好了，旧场景悄悄变差，无人知晓 | 没有回归集，就没有"改动前 vs 改动后"的可比较基线 | 质量曲线其实下行，团队感觉在进步 |
| 指标与产品目标脱节（wasted effort） | 评测指标涨分，产品结果不动 | 指标测的不是真实产品失败，而是"模型说话的姿势" | 赢了指标，输了体验（Goodhart 定律的标准现场） |

Airbnb 十条要点中的第 ② 条就是针对第一坑的解药：**避免泛化 helpfulness，瞄准真实产品失败**。

腾讯的痛点表从另一个视角刻画了"没有评估"的日常，与 Airbnb 三坑一一对应且更细：

| 腾讯痛点 | 对应 Airbnb 陷阱 |
|---|---|
| 主观性强，靠"感觉变好了" | 虚假信心 |
| 悄悄退化：改 prompt / 升级依赖后旧场景变差无人知晓 | 未被发现的回归 |
| 人工验证成本高：Skill 越多、模型越快，人肉回归指数增长，只能选择性验证留盲区 | （回归问题的成本侧） |
| 模型不敢升级：无对比数据支撑切换决策 | 指标缺位 → 决策瘫痪 |
| 缺少效率基线：变贵变慢无法归因到版本 | 同上 |
| 过程易忽略：答案碰巧对但推理路径错 | （假阳性的温床，见 2.4） |

每个陷阱都有对应的解药，这也是后续章节的索引方式：

| 陷阱 | 解药 | 详见 |
|---|---|---|
| 虚假信心 | 指标从观察到的真实失败推导（Airbnb EDD 原则之二）；拒绝万能 helpfulness，按维度拆分评分 | 第 E2 / E5 章 |
| 未被发现的回归 | 回归集只增不减 + 变更触发 CI 回归 + 版本对比带统计口径 | 第 E10 / E9 章 |
| 指标与产品目标脱节 | 离线指标与线上信号（转人工率、投诉率、任务完成率）联动校准，离线涨线上降即回滚 | 第 E12 章 |

一句话总结：**没有评估的 GenAI 团队不是在迭代，而是在抽签**——每次改 prompt 都不知道这次是改进还是退化，只能靠线上用户的投诉来"开奖"。

### 2.3 评估 vs 传统软件测试：四项本质差异

面试高频问法："评估和软件测试到底有什么不一样？"下面这张对照表是标准答案骨架：

| 维度 | 传统软件测试 | GenAI 评估 |
|---|---|---|
| 输入空间 | 有限、可枚举：参数有类型、有边界，等价类划分后可穷尽 | 开放自然语言 + 多轮上下文 + 工具返回的组合爆炸；用户会说出你想不出的话 |
| 判定方式 | 确定性断言：期望输出唯一，`assert actual == expected` | "正确"依赖判断：一个目标有多种可接受结果（DoorDash 称之为"开放式目标"），需要 rubric / 程序化检查 / judge / 人工的分层判定 |
| 回归语义 | 回归 = 功能明确坏掉：同输入必同输出，坏了就是断了 | 回归 = 统计分布上的悄悄漂移：输出仍"看起来像样"，但错误率升了、路径变了、语气飘了；不跑回归集根本发现不了 |
| 通过标准 | 100% 通过是默认要求（确定性系统，失败即 bug） | 分级设定：Anthropic 推荐口径（腾讯评测方案引用）——**确定性任务用例集整体通过率 100%，非确定性任务 ≥95%**；高风险场景进一步用 pass^k 做发布线 |
| 失败复现 | 改到哪个断点就能复现 | 需要固定 seed / temperature / 环境快照做"统计可复现"，且要区分"能力不足"与"稳定性不足" |
| 测试与生产的关系 | 测试通过 ≈ 可以上线 | 离线分数只是必要条件：还要影子 / 灰度 / 线上监控（offline-online gap 见 2.5） |

注意最后一行：传统测试里"测试通过"几乎是上线的充分条件；GenAI 里**评估通过只是拿到了一张入场券**，线上还有第二场考试。这个认知差异是许多从传统 QA 转过来的团队最容易栽跟头的地方。

**但也不是全盘推翻**——从测试到评估，有些东西必须换，有些东西原样保留，分清楚这两堆才能说服传统 QA 背景的同事：

| 保留（测试工程的遗产） | 替换（GenAI 的新规则） |
|---|---|
| 质量左移：问题越早发现修复成本越低 | 断言 → 分层判定（程序化规则 / judge / 人工，详见第 E4–E6 章） |
| 回归集 + 变更触发回归 | "100% 通过" → 统计通过标准 + 置信区间 + 显著性（详见第 E9 章） |
| 门禁与发布流程挂钩 | 测试报告 → 评测报告 + 失败归因（分数必须能稳定转成行动项，阿里） |
| 测试资产版本化管理 | 期望输出唯一 → 一个目标多种可接受结果（rubric 描述"成功长什么样"而非指定唯一答案） |
| CI 自动化执行 | 测试一次即结束 → 持续评测：离线 + 线上双环境（EDDOps） |

腾讯把这个转变浓缩成一句目标陈述：**可重复、可量化、可持续演进的评估闭环——每次变更都能快速跑出可比较的分数，用数据代替直觉，用全量代替抽查**。

### 2.4 "跑几条 case 感觉还行"为什么不够：四个具体失效场景

阿里评测方法论里有一节标题极其直白：**为什么"跑几条 case 感觉还行"不够**。它给出的四个场景，每一个都值得配一个例子：

**场景 1：同一 prompt 跑通一次 ≠ 稳定可用。**
非确定性系统里，一次成功只是从行为分布里抽到的一个样本。客服 agent 在你手测的那一次恰好走对了流程，不代表它 100 次里有 100 次走对——腾讯的稳定性判读经验：N=5 次执行中 1 次失败就"存在稳定性风险"，而容忍阈值按场景分级：**关键决策类（问题定位 / 故障诊断）容忍 0%，辅助分析类 ≤10%，创意生成类 ≤40%**。用户不会接受"多试几次总有一次成功"（阿里一致性双指标的原话）——至少一次成功率（能力上限）与连续成功率（生产要求）必须分开报，生产级场景看后者。

**场景 2：改 prompt / 换模型 / 调工具参数，可能改坏原有场景，且不易第一时间发现。**
这是"未被发现的回归"的日常形态。DoorDash 的仿真评测博客里有个诚实的细节：其 11 轮迭代中**第 3 轮曾出现回落**——没有回归集的团队甚至不会知道哪一轮回落了。解法是把每次手工检查沉淀为可复跑的用例，变更触发回归（详见第 E10 章）。

**场景 3：多步链路里，前一个小偏差会被放大成错误结论。**
即 2.1 的退款案例。手测几条 case 时你只看到终点输出"像那么回事"，看不到第 1 步的意图偏差正在被第 3 步的政策跳过放大。没有轨迹级评估（详见第 E7 章），级联放大永远发生在你的视线之外。

**场景 4（最隐蔽）：有些样本最终答案看似对，但执行路径已偏离或带风险——这类假阳性在生产迟早暴露。**
Airbnb 明确指出：**只看最终答案不够，推理路径、工具参数、工作流可能在结果看似正确时已经失败**。腾讯痛点表里的对应表述：分不清"正确调用工具后回答"与"训练数据碰巧答对"。一个跳过身份校验却恰好没造成损失的退款操作、一个靠猜碰对了答案的查询，都是"这次结果对、下次事故见"的假阳性。阿里对假阳性的工程回应是：**加过程型与风险型检查**（详见第 E11 章 RCA 体系）。

四个场景各自对应一种评测机制，这张映射表可以作为"为什么需要完整评测体系"的速答版：

| 失效场景 | 对应的评测机制 | 本特辑出处 |
|---|---|---|
| 一次跑通 ≠ 稳定 | 多 trial 重复 + pass^k / 连续成功率 + 按场景分级的容忍阈值 | 第 E2 章、`eval_lab01` |
| 新改动改坏旧场景 | 回归集（只增不减）+ PR 合入前自动回归 | 第 E10 章、`eval_lab10` |
| 前步偏差被级联放大 | 结构化 trace + step / trajectory / session 分层评估 | 第 E7 章、`eval_lab06` |
| 结果对但路径错的假阳性 | 过程型 / 风险型检查、must-call / must-not-call 断言 | 第 E7 / E11 章、`eval_lab06` |

> 动手：构造"完全正确 / 结果对但路径错 / 路径对但结果错 / 全错"四类 agent 运行，验证只看结果的评分会放过假阳性——
> `cd evals-special/labs && python3 eval_lab06_trajectory_eval.py`

**结论**：评测体系必须**嵌入研发流程**而不是挂在上线前当关卡。用阿里的原话收束本节："评测平台不只是'出分工具'，核心价值是把问题稳定转化为可执行修复、形成持续迭代闭环。"

### 2.5 评估的四重身份：度量、门禁、指南针、飞轮

把评估只理解成"测试"，会低估它至少三倍的价值。成熟体系里，评估同时扮演四个角色：

| 身份 | 回答的问题 | 失效时的后果 | 工业实践证据 |
|---|---|---|---|
| 质量度量（尺子） | 现在到底有多好？ | 靠感觉决策，团队对"好没好"永远达不成共识 | DoorDash：eval harness 把质量信号从"平均每天 1 条员工反馈"升级为**每天 2,000 个自动评分会话**；全国上线前 agent 质量分 **+8 分**、错误率**近乎减半** |
| 发布门禁（闸门） | 这个变更能不能上线？ | 每次发布靠胆量；坏版本流入生产 | DoorDash 仿真评测飞轮：**任何变更必须通过全部 50+ 个 eval 才能上线**；阿里把 P0 指标设为上线门禁（不达标不发）；学术侧已有"评测结果即发布证据"的证据驱动发布管理研究（arXiv 2603.15676，2026） |
| 迭代指南针（罗盘） | 下一步该改什么？改了真的变好了吗？ | 优化靠轶事：最近一次、最惊人的失败主导修复方向 | Airbnb 核心习惯 **"When in doubt, look at your data"**：跑约 100 个样本，人工读输出和 trace，归类错误，围绕它们建测试——其旅行客服案例中，100 个 prompt 读出了 15 个 groundedness 失败、8 个正确但啰嗦、5 个不当拒答、3 个 JSON 失败，修复优先级由此而来；GEPA（arXiv 2507.19457）更是直接把 eval 分数当作 prompt 优化的目标函数 |
| 数据飞轮入口（齿轮） | 线上失败如何变成资产？ | 失败修完即弃，同类问题反复发生 | Discord AITL（EMNLP 2025 工业赛道）：人工标注持续回流驱动再训练，把再训练周期从**月级压缩到周级**，美国试点 recall@75 **+11.7%**、precision@8 **+14.8%**、有用性 **+8.4%**、采用率 **+4.5%** |

四重身份之间有递进关系，逐层展开：

1. **度量**是第一层：没有可信的分数，一切无从谈起。但注意度量的有效性前提是"尺子本身经过校准"——judge 与人工一致率达标（Airbnb 目标 high 80s~90s%，阿里参考值约 85% 后进自动化，腾讯口径 ≥85% 可用）才谈得上度量（详见第 E5 章）。
2. **门禁**把度量接入发布流程：离线门禁 + 线上灰度联动。阿里的口径是三类信号一起看——离线质量信号（核心场景通过率、P0 风险数、关键工具参数正确率）、线上体验信号（转人工率、重复追问率、投诉率、满意度）、业务结果信号（任务完成率、工单闭环率、退款成功率）——**离线提升但线上关键信号恶化，触发回滚或降级**。
3. **指南针**把度量接入开发循环：这是评估从"防守"转向"进攻"的一步。Airbnb 的迭代纪律（一次只改一个变量：固定模型变 prompt → 固定 prompt 变模型 → 都固定变 serving 配置）保证了分数变化可归因（详见第 E10 章）。
4. **飞轮**把度量接入数据资产：badcase → 评测用例 → 训练数据 → 模型更新 → 新的线上信号回流（详见第 E12 章）。走到这一步，评估才真正成为"生命线"——它不再消耗资源，而是持续生产资产。通用循环长这样（DoorDash、Discord AITL、EDDOps 控制环的共同骨架）：

```text
生产失败 / 真实 trace
      │ 编码为测试用例（带出处与切片标签，进回归集）
      ▼
自动流水线（生成场景 / 模拟对话 / 分层打分）
      │ 定位失败簇，选对改动
      ▼
修 prompt / 架构 → 重跑达标（门禁）→ 发布
      │ 线上信号（judge 分、转人工率、投诉）
      └──────────────回流──────────────┘
```

**别把离线分数当终点**。即便四重身份都立起来，仍要记住：客服对话基准研究（arXiv 2510.22143，2025）明确指出，由于真实部署环境的分布漂移与交互复杂性，**强 offline 基准成绩只是部署可靠性的弱指标**。当前共识是"离线是必要不充分"——离线门禁之后还有影子 / 灰度 / A/B 的最后一公里。

DoorDash 把这个问题表述为"双环境"挑战：**开发与生产的质量可能背离**。他们的解法是同一条 rubric + 同一个校准过的 judge 同时跑在真实会话与模拟会话上——离线结论才能带到线上，线上失败才能离线复现（详见第 E12 章）。DoorDash 报告其离线模拟提升与线上真实流量表现一致（其飞轮 5 分钟内可跑 200+ 场模拟对话、模拟环境幻觉率下降约 90%），但这是持续验证出来的结论，不是默认前提。

### 2.6 评估经济学：eval 成本 vs 线上失败成本的粗算框架

"评测很贵，值得吗？"——这是向管理层要资源时的必答题。回答它需要一个两边都摆上桌的粗算框架。

**（1）eval 成本侧（可预算、可工程化压缩）：**

| 成本项 | 估算方式 | 工业参照 |
|---|---|---|
| 用例建设（一次性） | 用例数 × 单例专家工时 | 阿里经验：先做 **50–200 条**高质量 golden set 覆盖核心路径与高风险边界；Anthropic 官方建议起步只需 **20–50 个**真实用例 |
| 每次运行的推理成本 | 用例数 × trials × 单条 token × 单价 | DoorDash 全量 sweep = **50 场景 × 8 trials = 400 次对话** |
| 判定成本 | 规则检查近乎免费；judge 按 token 计费；人工最贵 | 分层筛查（规则粗筛 → judge 精判 → 人工兜底）就是为压这项成本设计的（详见第 E4/E6 章） |
| 人工校准（一次性 + 持续） | 校准集大小 × 标注工时 | Airbnb：从 20–100 个专家标注样本起步；gold set 50–100 条必须含坏样本 |
| 基础设施 | harness / trace 存储 / 平台人力 | Anthropic 博客提及 Bolt 约 **3 个月**建成 eval 体系——这是"从零到能用"的量级参照 |

**（2）线上失败成本侧（不可预算、随流量放大）：**

| 成本项 | 内容 | 为什么贵 |
|---|---|---|
| 直接修复 | 排查、回滚、hotfix 的工程工时 | 线上 debug 没有 trace 时是盲查；阿里 RCA 五步的存在就是为了把它变成结构化流程 |
| 资损与补偿 | 错误退款、过度承诺、越权操作造成的真金白银损失 | 不可逆：错退的款收不回来，承诺出去的补偿必须兑现 |
| 用户流失与口碑 | 投诉、差评、卸载 | 滞后且难归因，等看见时已经成规模 |
| 合规与安全风险 | 隐私泄露、违规内容、金融合规事故 | 单次事故可能超过整个评测体系多年的成本 |

**（3）收益侧：评估省下的钱有据可查（均以公司原文数字为准）：**

- DoorDash：全量回归从人工 **6+ 小时压到约 20 分钟**（50 场景 × 8 trials 的 sweep，人工本地聊约 1 分钟/次）；支撑底座模型从 Claude Sonnet 4.6 迁移到 Gemini 3.5 Flash，**延迟降 35%、质量无损**——没有 harness，这种迁移"不敢做"，延迟收益就拿不到。
- 腾讯反向论证：没有评估时"模型不敢升级（无对比数据支撑切换决策）""缺少效率基线（变贵变慢无法归因版本）"——评估缺位本身就是持续的成本。

**（4）粗算模板（面试可现场列）：**

```text
eval 年化成本 ≈ 用例建设(一次性) + 运行频次 × 单次推理成本 + judge 成本 + 校准人力
线上失败年化成本 ≈ 日会话量 × 失败率 × 单次失败成本(修复工时 + 资损期望 + 流失期望)
决策规则：只要 eval 能把失败率压低 Δ，且 Δ × 线上失败年化成本 > eval 年化成本，就值得投
```

代入量级感受一下（**以下业务数字为示意，仅演示框架用法**，实际必须换成自家真实数据）：

| 项目 | 示意取值 | 年化量级 |
|---|---|---|
| 日会话量 | 10,000 | — |
| 线上失败率（无评测基线） | 1% → 100 次失败/天 | — |
| 单次失败综合成本（修复工时 + 资损期望 + 流失期望） | 200 元 | 线上失败 ≈ 73 万元/年 |
| 评测介入后的失败率压低 Δ | 0.5 个百分点（保守取值；DoorDash 实证错误率"近乎减半"，此处再打对折） | 挽回 ≈ 36 万元/年 |
| 评测流水线成本 | 每日全量 400 条对话（DoorDash sweep 规模）× 分层 judge + 每周人工校准 | 数万元/年量级 |

ROI ≥ 5 倍，且这还没算评测带来的"敢做"收益——DoorDash 若没有 harness，就拿不到模型迁移那 35% 的延迟下降。**一个数量级的差距，就是"生命线"三个字的经济学含义。**

**（5）向业务方汇报时的口径转换**：算完账还要会"翻译"。向非技术决策者汇报时，用产品语言而不是模型语言——说"三连全对率只有 42%"而不是"单次通过率 75%"，说"每天 2,000 个会话被自动质检"而不是"我们建了个 eval harness"。评测的价值必须落在对方关心的坐标系里（发布风险、资损、人力节省），这也是第 E2 章"把指标写进发布门禁"的前置技能。

### 2.7 业界的答案：EDD（评测驱动开发）速览

三大难题 + 三大陷阱 + 四重身份，把行业推向了一个共同的方法论终点：**Evaluation-Driven Development（EDD，评测驱动开发）**——把评测从"上线前的一次性检查点"变成贯穿全生命周期的"持续治理机制"：先定义期望行为（eval 即规约），在开发、发布、运行各阶段持续产生评测证据，用证据驱动最小化修复与受控迭代。

三股力量在 2024–2026 年把 EDD 从口号变成了工程学科：

| 力量 | 证据 |
|---|---|
| 学术成型 | EDD/EDDOps 过程模型与三层参考架构（arXiv 2411.13768，2024-11 首发，2025-11 v3）：Plan → Build → Run(offline+online) → Analyze & Improve 四阶段闭环 |
| 官方采纳 | Anthropic《Demystifying evals for AI agents》（2026-01）主张先定义期望行为再开发、eval 进 CI/CD；OpenAI evaluation best practices 建议从一开始就反复评测、每次变更都跑 continuous evaluation |
| 工业验证 | Airbnb 的 EDD 五原则与迭代纪律、DoorDash 的评测 harness（"迭代控制面"）、腾讯的能力测评→回归测评毕业机制（详见第 E10、E15 章） |

EDDOps 论文对 134 篇学术文献 + 27 份工业灰色文献的统计，揭示了供需错配：**学术界 93.28% 的评测研究只做部署前（pre-deployment），仅 2.24% 覆盖部署后，4.48% 是持续评测；而工业灰色文献中 40.74% 已是持续评测、81.48% 已用评测驱动适配**。换句话说：最前沿的工程实践已经跑到了学术研究前面——这也是本特辑以工业实践为骨架、以论文为佐证的原因。

EDD 成熟度的两条证据（Anthropic 官方博客，2026-01）：SWE-bench Verified 成绩一年内从 40% 涨到 80%+，评测驱动的快速迭代是幕后推手；CORE-Bench 上 Opus 4.5 在**修复任务与评分器之后**从 42% 跳到 95%——后一个数字同时揭示了一个反直觉事实：**评测系统自己也会出 bug**。DoorDash 的四条 Lessons Learned 里有一条与之呼应：被标记的失败中有真实一部分其实是 harness 自身故障（judge 误报、trace 缺口），必须并行修复才可信。所以评测基础设施本身也要被评估、被版本管理（详见第 E10 章）。

EDD 的核心心智模型可以用一句话概括（Airbnb 定义，详见第 E10 章）：**不是预测所有失败，而是发现 → 捕获 → 反复检查失败模式**。这与 TDD 的精神同构：你无法在写代码前穷举所有 bug，但你可以保证每个发现过的 bug 都有一条永不消失的测试。

**本章与后续章节的路线图**：本章论证了"为什么"，其余 15 章逐一回答"怎么做"——

| 问题 | 章节 | 一句话预告 |
|---|---|---|

| | 第 E6 章 · 人工评估与评分路由 | 专家时间 60%+ 花在校准与诊断 |

（主手册第 8 章 · Agent 评估与可观测性 提供了这套体系的浓缩版，本特辑是其深挖版。）

**面试 30 秒版**（当被问"为什么 GenAI 必须做评估"时，可以直接背这段开场）：

> 传统软件有确定性断言，GenAI 有三大根本难题——非确定性、黑盒化、错误级联放大，
> 传统测试的三根支柱（断言、断点调试、单元测试推断）因此逐一失效。
> 不做评估，产品会掉进三大陷阱：虚假信心、未被发现的回归、指标与产品目标脱节（Airbnb 总结）。
> 所以评估必须承担四重身份：质量度量、发布门禁、迭代指南针、数据飞轮入口。
> 投入多少由评估经济学决定：eval 成本可预算，线上失败成本不可预算且随流量放大。
> 业界的答案是 EDD——发现失败、捕获失败、反复检查失败。

**本章小结**：三大难题（非确定性、黑盒化、级联放大）摧毁了传统测试的三根支柱；不做评估会掉进三大陷阱（虚假信心、未发现回归、指标脱节）；因此评估必须承担四重身份（度量、门禁、指南针、飞轮）；投多少由评估经济学决定，答案是"杠杆投入"；方法论终点是 EDD。把这五句话讲顺，本章的面试题就都有了骨架。

| 10 | 评估经济学：eval 成本 vs 线上失败成本 | ⭐⭐ | 向管理层要资源的实战题，要能列出两边的成本项并给出决策规则 |
| 11 | 离线分数是必要不充分条件（offline-online gap） | ⭐⭐ | 考"离线门禁之后还有什么"：影子 / 灰度 / A/B / 线上监控 |
| 12 | EDD 的定义与心智模型 | ⭐ | 考方法论视野：发现→捕获→反复检查失败模式，eval 即规约 |
| 13 | 学术与工业的评测供需错配（EDDOps 统计） | ⭐ | 加分谈资：学术 93% 停留在部署前，工业 40%+ 已是持续评测 |

## 四、经典面试题与参考答案

#### 题 1（基础）：为什么说评估是 GenAI 工程的"生命线"，而不是可选项？

**参考答案：**
因为 GenAI 有三个内禀属性让"先上线再修"变得不可承受：① **非确定性**——同一输入不一定同一输出，单次运行只是分布中的一个样本，不评估就不知道分布长什么样；② **黑盒化**——内部决策不透明，没有评估产生的 trace 与分数，失败连归因都无从谈起；③ **错误级联放大**——多步链路里单步 95% 正确率 × 20 步只剩约 36% 端到端成功率，小偏差会被放大成错误结论。叠加后果是：不做评估会掉进虚假信心、未被发现的回归、指标与产品目标脱节三大陷阱（Airbnb 总结）。而评估在成熟体系里同时是质量度量、发布门禁、迭代指南针和数据飞轮入口——它不是交付前的关卡，而是贯穿全生命周期的基础设施，所以叫"生命线"。

#### 题 2（基础）：Airbnb 总结的"没有早期评测计划"的三大陷阱是什么？各举一个例子。

**参考答案：**
① **虚假信心**：用浅层 helpfulness 分数自我安慰——模型回答礼貌通顺，泛化的"有没有帮助"打高分，但幻觉、过度承诺、答非所问全被糊过去，分数漂亮、投诉照涨。② **未被发现的回归**：改一版 prompt 让新场景变好，旧场景悄悄变差；没有回归集就没有前后对比基线，质量下行而团队感觉在进步。③ **指标与产品目标脱节**：评测指标测的是"模型说话的姿势"而非真实产品失败，指标涨分、产品不动，力气白花（Goodhart 定律现场）。解药是 Airbnb 十条要点之一：避免泛化 helpfulness，瞄准真实产品失败，把指标从观察到的错误中推导出来。

#### 题 3（基础）：GenAI 评估和传统软件测试的本质区别是什么？

**参考答案：**
四项本质差异：① **输入空间**——测试的参数有限可枚举，自然语言输入 + 多轮上下文 + 工具返回组合爆炸，用户会说出你想不出的话；② **判定方式**——测试是确定性断言、期望输出唯一，GenAI 一个目标有多种可接受结果，"正确"依赖判断，需要规则 / judge / 人工分层判定；③ **回归语义**——测试的回归是功能明确坏掉，GenAI 的回归是统计分布上的悄悄漂移，不跑回归集发现不了；④ **通过标准**——测试默认 100% 通过，GenAI 要分级设定（Anthropic 推荐口径：确定性任务用例集 100%、非确定性任务 ≥95%，高风险场景用 pass^k 做发布线）。还有一层：测试通过≈可上线，而离线评估通过只是必要条件，后面还有灰度与线上监控。

#### 题 4（进阶）：有人说"我跑了十几条 case 都通了，效果不错"。请指出这个结论的所有漏洞。

**参考答案：**
四个具体漏洞（阿里评测方法论的四个失效场景）：① **一次跑通 ≠ 稳定**：非确定性系统里一次成功只是一个样本；要报 N 次重复的成功率分布，腾讯口径 N=5 里 1 次失败就算有稳定性风险，关键决策类容忍 0%。② **改坏旧场景看不见**：这十几条 case 没有沉淀为回归集，下次改 prompt / 换模型时旧场景退化无人知晓（未被发现的回归）。③ **级联放大测不出**：手测只看终点输出，多步链路前段的小偏差会被后段放大，十几条 case 也覆盖不了分支组合。④ **假阳性漏检**：可能存在"最终答案看似对、执行路径已偏离或带风险"的样本——跳过校验恰好没出事、训练数据碰巧答对，这类样本迟早在线上引爆。正确姿势：把 case 沉淀为可复跑用例，多 trial 报 pass^k，加过程型与风险型检查，扩到覆盖核心路径与高风险边界的 golden set（阿里经验 50–200 条起步）。

#### 题 5（进阶）：一个 agent 单次任务成功率 75%，要上"用户不会重试"的客服场景。这个数够用吗？该用什么指标定发布线？

**参考答案：**
不够。75% 的单次成功率意味着每次服务 4 个用户就有 1 个失败；而在不可重试、无人值守的场景，用户不接受"多试几次总有一次成功"（阿里一致性双指标的原话）。该用 **pass^k**（k 次独立试验全部成功）定发布线：按 Anthropic 文档的示例算法，p=0.75、k=3 时 pass^3 = 0.75³ ≈ 42%——一个"看起来 75% 不错"的 agent，三连全对只有四成把握。τ-bench 的实证同向：GPT-4o 在 retail 域 pass^1 ≈60%（官方榜单 60.4%），pass^8 ≈25%。工程结论：① 发布门槛用低 k 的 pass^k（如 k=3~8）而非 pass@1；② 同时报至少一次成功率作为能力上限参照，两者的 gap 就是稳定性债；③ 客服/退款/支付等不可逆场景按关键决策类对待，稳定性容忍阈值取最严（腾讯分级：关键决策类 0%）。

#### 题 6（进阶）：评估在 GenAI 开发流程中扮演哪几重角色？分别用什么工业实践佐证？

**参考答案：**
四重身份，层层递进：① **质量度量**——把"感觉变好了"变成可比较的数字：DoorDash 的 harness 把质量信号从平均每天 1 条员工反馈升级为每天 2,000 个自动评分会话，全国上线前质量分 +8、错误率近乎减半。② **发布门禁**——变更能不能上线由证据决定：DoorDash 任何变更必须通过全部 50+ 个 eval；阿里 P0 指标不达标不发布。③ **迭代指南针**——告诉团队下一步改什么：Airbnb "When in doubt, look at your data"，100 个 prompt 人工精读读出 15 个 groundedness 失败、5 个不当拒答，修复优先级由此而来。④ **数据飞轮入口**——线上失败变资产：Discord AITL 用标注回流把再训练周期从月级压到周级，试点有用性 +8.4%。只把评估当"测试"，就只拿到了第一重。

#### 题 7（进阶）：老板问"评测这么贵，值得投吗？"你怎么用评估经济学回答？

**参考答案：**
把两边成本摆上桌。eval 成本侧可预算：用例建设（一次性，阿里经验 50–200 条 golden set 起步）、每次运行推理成本（用例 × trials × token × 单价）、judge 判定成本（分层筛查可压一个量级）、人工校准（Airbnb 从 20–100 个专家样本起步）。线上失败成本侧不可预算且随流量放大：修复工时、资损补偿（错退款收不回）、用户流失、合规事故。决策规则：eval 能把失败率压低 Δ，且 Δ×线上失败年化成本 > eval 年化成本，就值得。量级参照（DoorDash 原文数字）：全量回归从人工 6+ 小时压到约 20 分钟；harness 支撑底座模型迁移拿到延迟降 35% 且质量无损——没有评测，这种收益根本不敢拿。腾讯的反向证据：无评估时"模型不敢升级、变贵变慢无法归因"。结论：评测是杠杆投入，不是成本中心。

#### 题 8（系统设计）：团队的退款客服 agent 一个月后要上线，目前没有任何评测体系。设计一个最小可行评测体系与落地路径。

**参考答案：**
按"先止血、再立柱、后闭环"三步：
**第一周（止血）**：从真实失败出发——收集已有的线上投诉与人工验证记录，手挑 20–50 条高风险 case（Anthropic 起步口径），人工精读输出与 trace（Airbnb 100 样本法的小规模版），归类错误模式。
**第二、三周（立柱）**：① 建 50–200 条 golden set（阿里经验），覆盖核心退款路径 + 高风险边界（已发货退款、运费险、大额退款），含坏样本；② 打分分层：确定性优先——订单状态、工具调用断言、金额精确性用代码判，语义与话术交给 judge（详见第 E4/E5 章）；③ 校准 judge：与人工标注一致率达到 ≥85%（阿里/腾讯参考线）才允许自动放量；④ 定门禁：确定性用例 100%、非确定性 ≥95%（Anthropic 口径），P0 风险样本零容忍，pass^k 报稳定性。
**第四周起（闭环）**：eval 进 CI，PR 触发回归；上线配灰度，跟踪转人工率、投诉率等线上信号；badcase 回流进用例集（只增不减）。
组织上指定一名最终人类决策者裁决"好 vs 坏"争议（Airbnb EDD 五原则之一）。若预算允许，用 Bolt 的量级做心理锚点：从零到可用约 3 个月（Anthropic 博客引用）——一个月上线的是最小版本，体系本身要持续生长。

## 五、易错点 · 反直觉点

1. **误区：同一个 prompt 跑通了一次，说明这个能力是稳定的。**
   真相：非确定性系统里一次成功只是分布中的一个样本。腾讯口径：N=5 次执行只要 1 次不通过即存在稳定性风险；τ-bench 上 GPT-4o retail pass^1 ≈60%（官方榜单 60.4%）而 pass^8 ≈25%（摘要 <25%）。
   记忆锚点：**单次运行是样本，不是结论。**

2. **误区：改完 prompt 没出事，就是没 regression。**
   真相：GenAI 的回归是统计分布上的悄悄漂移，不会自己报警；没有"变更前 vs 变更后"的可比较回归集，退化根本不可见——这正是 Airbnb 三大陷阱中的"未被发现的回归"。
   记忆锚点：**回归不会敲门，只有回归集能开门。**

3. **误区：最终答案对了就行，过程不重要。**
   真相：假阳性是 GenAI 最隐蔽的失败——跳过身份校验恰好没造成损失、训练数据碰巧答对，"这次结果对、下次事故见"。Airbnb 明确：推理路径、工具参数、工作流可能在结果看似正确时已经失败。
   记忆锚点：**结果对是一次，路径错是每次。**

4. **误区：helpfulness / 平均分高，就是质量好。**
   真相：泛化分数天然平滑掉真实失败模式（幻觉、过度承诺、答非所问都被礼貌的通顺糊过去），这就是 Airbnb 的"虚假信心"陷阱；指标一旦与产品目标脱节，涨分只是自我安慰（Goodhart）。
   记忆锚点：**指标不指向真实产品失败，就指向自欺。**

5. **误区：自动评测不放心，那就加人肉验证。**
   真相：腾讯痛点表指出，Skill 越多、模型越快，人肉回归指数增长，最终只能选择性验证、留下盲区——人工不是更可靠的路线，而是更贵的路线。专家时间应花在刀刃上（校准 judge、诊断异常，60%+ 占比，腾讯经验法则）。
   记忆锚点：**人肉回归是指数成本，评测自动化是唯一线性解。**

6. **误区：评估是上线前的一道抽查，过了就结束。**
   真相：评估有四重身份（度量 / 门禁 / 指南针 / 飞轮）且贯穿开发—发布—运行全程；离线分数还只是必要条件，后面有灰度、线上监控、badcase 回流。EDDOps 统计显示工业界 40.74% 的评测已是持续评测。
   记忆锚点：**评估是逗号，不是句号。**

7. **误区：新模型在 eval 上分数大跌，说明新模型弱。**
   真相：DoorDash 从 Claude Sonnet 4.6 迁移到 Gemini 3.5 Flash 时 harness 分数大跌，最终查明**不是能力差距，是兼容性差距**——工具签名要 plain string 而 Flash 传了 JSON 对象、system prompt 是围绕旧模型惯例隐式调优的。"低分反映的是为旧模型适配的系统，不是更弱的模型。"
   记忆锚点：**低分先怀疑环境，再怀疑模型。**

8. **误区：只看平均分 / 总体通过率就够了。**
   真相：平均分天然掩盖切片退化——某类高风险场景全线崩坏，可以被大量简单场景的分数稀释掉。GEPA（arXiv 2507.19457）的 Pareto 前沿选择隐含的原则正是"按切片看指标，防止平均分掩盖退化"。
   记忆锚点：**平均会说谎，切片不会。**

9. **误区：评测体系是纯成本中心，是"质量保险"式的必要之恶。**
   真相：评估经济学算的是杠杆账——DoorDash 用 harness 拿到回归提速（6+ 小时 → 20 分钟）与模型迁移收益（延迟 -35%、质量无损）；评估还持续生产资产（用例库、根因标签库、校准集）。阿里原话："质量资产越厚，Agent 迭代越不靠个人经验和临时救火。"
   记忆锚点：**评测买的不是保险，是杠杆。**

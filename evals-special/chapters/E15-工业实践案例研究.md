## 二、核心概念精讲

### 2.1 Airbnb：EDD 方法论与迭代纪律

**背景与三大坑。** Airbnb 的 GenAI 应用包括点评摘要、客服、房东/房客消息、内部洞察；产品团队自定评测标准，基础设施组提供共享工具与跨团队指南——注意这是**实践（practice）而非强制令（mandate）**，这一组织形态本身就是考点。Airbnb 总结，项目早期没有评测计划会掉进三个坑：

| 坑 | 表现 | 后果 |
|---|---|---|
| 虚假信心 | 用一个浅层 helpfulness 分看着挺高 | 上线后真实场景翻车，分数没预测任何东西 |
| 未被发现的回归 | 改 prompt 后质量悄悄变差 | 没有回归集，没人知道旧场景坏了 |
| 浪费精力 | 指标与产品结果脱节 | 团队优化了半天，产品体验纹丝不动 |

**核心习惯："When in doubt, look at your data."** 具体动作是**100 样本人工精读法**：跑约 100 个样本（真实或合成），人工读输出和 trace，找错误、归类，再围绕这些错误建测试。这是全特辑最便宜也最高杠杆的动作——不需要任何基础设施，只需要一个下午和一双眼睛（详见第 E10 章 · 评测驱动开发（EDD））。

**EDD 五原则**（面试必答）：

1. **尽早设定目标与上线门槛（launch gates）**，即便它们是在数据评审中才逐渐清晰的；
2. **从观察到的错误中推导指标**，与跨职能伙伴共同制定（不是拍脑袋定 helpfulness）；
3. **用少而精的 judge**：3–5 个经校准的评估器好过一堆嘈杂的评估器；
4. **指定一个最终人类决策者**，裁决"好 vs 坏"的争议；
5. **让产品伙伴持续参与**对比与错误诊断。

**三层评估框架**（Airbnb 版三层评分）：

| 层 | 内容 | 关键点 |
|---|---|---|
| 程序化检查（确定性，最先跑） | 格式/schema 校验、空/异常长度、关键词正则、P/R/F1、语义相似度 | 前两项"永远有用"；结构化输出要用 JSON schema 强类型化，**不要只靠 prompt 措辞产出结构**，否则下游管道会坏 |
| LLM-as-a-Judge | 强模型按 rubric 评另一模型输出（语气/连贯/有据性/相关性） | 五条规则：每个质量维度一个 judge；judge 模型尽量与生成模型不同源；带 few-shot；强制输出 schema；清晰打分说明 |
| 人工评估 | 建 ground truth、安全高风险决策、细微差别与创意、裁决自动评估器冲突 | 从 **20–100 个专家标注样本**起步；rubric 稳定且需要规模时才扩大标注队伍；**专家有分歧就先停下解决分歧再谈自动化** |

一句被反复引用的话："**如果人都无法一致地应用 rubric，模型也不可能。**"

**Judge 校准五步法**（全特辑通用流程，第 E5 章展开）：① 建 50–100 条 gold set（**必须含坏样本**）；② 用 judge 跑该集合；③ 目标一致率 **high 80s ~ 90s%**，分歧可用 Cohen's kappa / Krippendorff's alpha 度量；④ 检查分歧 → 改 rubric/示例 → 重复；⑤ 失败模式变化时重新校准。核心警告：**未校准的 judge 会制造误导性信心。**

**完整案例演练：旅行平台客服政策问答助手**（面试复述率极高的一段）：

| 阶段 | 动作 | 数字与发现 |
|---|---|---|
| 探索 | 跑 100 个 prompt 人工读输出 | 发现 **15 个 groundedness 失败、8 个正确但啰嗦、5 个不当拒答、3 个 JSON 失败** |
| 建测试 | JSON 与长度检查；groundedness / conciseness 各一个 judge；PM/SME 标注 gold | **60 条 gold**（含失败样本） |
| 校准 | judge 跑 gold 集 | 初始一致率 **78%（过低）**——根因是 judge **误罚了正确的改述**；修 rubric 与示例后达 **88%**；检索改进减少 groundedness 失败 |
| 规模化与监控 | 扩容 + 上线后持续运行 | 扩到 **5,000 样本**；每日抽样 **5% 去标识化生产流量**；跑检查与 judge；标记样本送人工；**每周 PM 评审**，新增测试与修复 |

**迭代纪律：一次只改一个变量。** 顺序是：先固定模型变 prompt → 再固定 prompt 变模型 → 再都固定变 serving 配置。Judge 筛候选，顶尖候选反哺 judge 改进，直到双方稳定。这条纪律回答了一个高频追问："你们同时改了 prompt 和模型，怎么知道是谁的功劳？"——答案是：不允许同时改。

**Agentic 评估三层**（详见第 E7 章 · 轨迹与 Agent 级评估）：只看最终答案不够——推理路径、工具参数、工作流可能在结果看似正确时已经失败。Airbnb 分 **step-level**（单工具调用/推理步）/ **trajectory-level**（整体路径是否合理高效）/ **session-level**（整个交互是否达成用户目标）；agent 通常在 root 下发 trace 和 span，可通过树遍历重建 trace，校验 subagent 调用与工具使用。

**隐私注记**：生产抽样用隐私保护方法——人工评审前去标识化、用途限定于安全与质量。

**Airbnb 十条要点**（原文收束，面试可直接引用）：① 建复杂工具前先人工看输出与 trace；② 避免泛化 helpfulness，瞄准真实产品失败；③ 从小标注集起步快速迭代；④ 不要万能 judge，按维度拆分；⑤ judge 校准到高一致率后再信任；⑥ 代码检查 + 模型 judge + 人工评审结合；⑦ gold set 必须含坏样本；⑧ 评整个系统（检索/工具/agent 路径）；⑨ 上线前测试要在线上持续运行；⑩ 评测是跨职能产品活动。

> 动手：`labs/eval_lab05_judge_calibration.py` 用纯标准库复现了"78% → 88%"这个校准循环（v1 judge 误罚正确改述 → 分析分歧 → 修 rubric → v2 达标）。运行：`cd evals-special/labs && python3 eval_lab05_judge_calibration.py`；EDD 全闭环（门禁/回归/一次一变量）见 `labs/eval_lab10_edd_loop.py`。

### 2.2 DoorDash：Eval Harness 的工程架构

DoorDash 的 Ask DoorDash 是四家案例中**工程细节最完整**的一篇。先看成果数字（全部为原文数字）：

| 指标 | 数字 |
|---|---|
| 质量信号规模 | 从平均 **1 条/天**的员工反馈 → **2,000 个/天自动评分会话** |
| 上线前质量 | 全国上线前 agent 质量分 **+8 分**，错误率**近乎减半**，达到生产发布标准 |
| 回归效率 | 全量回归：手工 **6+ 小时 → 自动约 20 分钟** |
| 模型迁移 | 支撑底座模型迁移（Claude Sonnet 4.6 → Gemini 3.5 Flash）：**延迟降 35%**、质量无损 |

**五大挑战 → 五大设计要求**（原文表格，系统设计题的标准答题骨架）：

| 挑战 | 设计要求 |
|---|---|
| 开放式目标（一个用户目标有多种可接受结果） | 每个目标表达成 rubric：**具体到每次能同样判，宽泛到容纳所有合法路径** |
| 执行不可见（judge 需要看到对话之下的工具调用；不同标准需要执行记录的不同部分） | trace 会话并重建为"按标准定制的视图"，**judge 只看该标准需要的证据**，隔绝无关 trace 噪声 |
| 无法安全彩排（不能拿真用户试变更，历史会话不能对改过的 agent 重放） | **按需生成会话**：模拟用户驱动 agent 跑场景，外围数据固定（fixtures），同场景每次一致 |
| 规模化判断（是否帮到用户需要人类级判断，但人工不可扩展） | **校准过的 LLM judge 顶替人类评审** |
| 双环境（开发与生产质量可能背离） | 真实会话与模拟会话用**同一 rubric + 同一 judge**：离线结论带到线上，线上失败离线复现 |

**评测镜像运行时架构。** Ask DoorDash 是多智能体架构：用户消息 → Orchestrator → 路由到领域 Agent（如 Restaurant Discovery Agent）；领域 Agent 直接处理或交还 Orchestrator。评测与之同形：**路由在 Orchestrator 评；护栏贯穿全流程评；任务能力在每个领域 Agent 评**。这是"评什么"与"架构长什么样"一一对应的范本。

**组件一：Rubric 体系。** 每条标准是一个 **binary check**，汇总为会话级总分。三类评测实例：

- **Guardrail（全体 agent 适用）**：如"沟通质量：回复简洁、不向用户叙述思维过程"；"信任与诚实：不呈现可证伪虚假信息"；
- **Capability · 餐厅发现**："约束满足：推荐满足配送时间/预算/饮食限制"；"结果多样性：真实差异而非近似重复"；
- **Capability · 杂货购物**："购物执行：用户的明确修改请求被执行"；"商品相关性"。

两个独创设计：① **Eligibility 适用性前置**——judge 先判该标准是否适用本会话，不适用则跳过（例如食谱流程不因缺少复购步骤被扣分）；② **离线 checklist 式 rubric**——场景级清单，例："两人份 ≤$60 素食 taco 购物清单"，验证每件商品都是素食 taco 原料、小计 ≤$60。这类标准**比宽泛通用标准方差更低，小样本更有用，支撑更快迭代**。每条标准都写成"从会话本身可验证"——同一 rubric 既供人工校准又供 judge 规模化。

**组件二：Transcript Builder（证据切片）。** 基础设施：每会话用 **OpenTelemetry** 打点，trace 存内部 **ClickHouse**；span 记录用户输入、模型输出、工具调用与返回、展示给用户的 widgets。问题是原始 trace 完整但难判：工具返回可能巨大、schema 脚手架与无信号字段多、证据散落多个 span/turn。Transcript Builder 是一组 Python 脚本：**重组分散 span、删无质量信号 token、裁超大载荷**，产出紧凑视图。最关键的设计：**每条标准声明自己依赖的证据，builder 只给 judge 那一片**——grounding 检查拿 agent 论断 + 背后工具输出；多样性检查拿推荐 + 原始请求；叙述检查拿 agent 工作时流式输出的文本。**聚焦证据让判断更一致。**

**组件三：Conversation Simulator + Fixtures。** LLM 扮演购物者；scenario 定义开场请求、用户目标、对提问/结果的反应方式（详见第 E8 章 · 对话 Agent 与仿真评测）。依赖外部状态时用 **fixtures**：录制工具返回替代实时调用。原文实例：复购场景开场 "Reorder my usuals"，`get_reorder_items` 固定返回录制的 `reorder_history_v1`（Albertsons 订单：Meadow Gold 全脂牛奶 ×2、Oroweat 全麦面包、牛油果、Ben & Jerry's 冰淇淋……）。每次运行看到相同订单 → 预期结果可预测，judge 可对照同一商品集评分。**成本账**：全量 sweep = **50 场景 × 8 trials = 400 次对话**；人工本地聊约 1 分钟/次 → **6+ 小时**；模拟器约 **20 分钟**。

**组件四：LLM-as-a-Judge（GEPA 校准）。** 定位是"带紧反馈环的测量问题"——样本够多（每天估计生产质量）+ 出分够快（不成为发布瓶颈）。人工用在杠杆最大处：**定 rubric、标注校准集、审计 judge 行为**；打分主力是 judge。原文立场鲜明："LLM Judge only useful if it agrees with human reviewers." 校准方法用 **GEPA（反射式 prompt 优化）**打磨 judge 判定边界：迭代提出 judge prompt 修订，**只保留在留出集上提升与人工标注一致率的版本**。校准持续进行：rubric 演进（新增能力）时收新标注、重新校准。judge 逐条标准独立评分：输入 = 标准 + 该标准依赖的证据；输出 = verdict + 简短 rationale。

**平台化：Eval Service。** trace 存储、实时评测执行、UI 化 judge 开发、标注工作流。组织路径值得抄：起步用**嵌入式平台团队**与 harness 并行共建，再沉淀为共享评测服务（paved path）供其他团队采用。

**反馈闭环（四步）**：① **失败聚类成主题**——逐条看失败会"轶事驱动"（最近/最惊奇的失败主导修复），而 rubric 标准天然是问题簇：grounding 失败 / 缺替代品 / 糟糕叙述分开调查，失败列表变成**按影响排序的主题列表**；② **从发现到解决**——从失败簇出发，coding agent 检查失败 trace、相关代码路径、近期变更、历史调查；修复明确时直接起草 PR，prompt/上下文学习改动则产出诊断 + 建议供人审；③ **Agent Skills 化**——把 eval-driven 工作流（聚类失败、调查失败模式）打包成 Agent Skills，可重复、可复用、可改进；skill 分错簇或写弱修复 → **更新 skill 而非打补丁一次性运行**；④ 总结论——harness 不只是记分板，是**迭代的控制面（control plane for iteration）**：生产监控 + 失败聚类 + agent 辅助调查 + 发布前验证连成一环。

**实战案例 1：Reasoning leakage。** 日常线上评分发现泄漏激增：任务完成但叙述中冒出系统语言（"reorder skill"、工具名、"fetch"、"in parallel"）——"像编码 agent 而非购物助手"。诊断指向 prompt 设计：合并沟通规则，分离内部 skill 指令与面向用户语言。离线用生产中**最易触发的场景**验证：**泄漏率降 11%**；hero 场景全量扫描无回归；上线后监控确认阶跃改善。

**实战案例 2：底座模型迁移（兼容性差距 ≠ 能力差距）。** agent 跑在 Claude Sonnet 4.6；5 月中 Gemini 3.5 Flash 发布，benchmark 显示可降延迟。离线 harness 一跑：**分数大跌**。但 eval 给出具体失败模式，AI coding agent 做假设与实验后得出结论：**不是能力差距，是兼容性差距**——Flash 部分工具参数格式不同（工具签名要 plain string，Flash 传 `{"dishes": [...]}` JSON 对象）；系统 prompt 围绕 Sonnet 惯例隐式调优。原文金句："低分反映的是为 Sonnet 适配的系统，不是更弱的模型。"修复小而准：工具输入确定性防护（错误形状**强制转换**回预期形状而非丢弃调用）；prompt 显式写出 Sonnet 原本自行推断的内容（用数据中精确店名、不超出工具结果渲染）。"不是改模型，是修正模型周围的环境。"重跑 eval：Flash 与 Sonnet 质量持平（harness 噪声范围内）→ 迁移生产 → **延迟降 35%、质量无损**。

**DoorDash 四条 Lessons Learned**：① Judge 需要"为问题塑形"的 transcript 视图——删无关、只留标准依赖的证据；② 环境必须受控，否则分数测量的是噪声——fixtures 冻结上游世界；③ 离线结果只有能带到线上才有意义——同一 rubric + 同一校准 judge 两边跑，**各自调 judge 分数会难调和地背离**；④ 评测系统自己也产生 bug 报告——被标记失败中有真实一部分是 harness 自身故障（judge 误报、trace 缺口），并行修复才可信。

### 2.3 阿里：评测平台的治理体系

阿里技术《Agent 评测：方法论与体系设计》共十章，是四家中**治理视角最完整**的一篇。总命题：**Agent 评测是把「不稳定的智能行为」持续收敛成「可发布的工程质量」，不是上线前抽查。** 三大门槛：非确定性（同输入不一定同输出）、黑盒化（内部决策不透明）、错误级联放大（前步小错后续放大）。

**为什么"跑几条 case 感觉还行"不够**（四个失效场景，第 E1 章展开）：同一 prompt 跑通一次 ≠ 稳定可用；每次改模型/prompt/工具参数都可能改坏原有场景且不易第一时间发现；多步链路前一个小偏差会被放大成错误结论；更隐蔽的是**假阳性**——有些样本最终答案看似对，但执行路径已偏离或带风险，在生产迟早暴露。结论：评测体系必须嵌入研发流程；**评测平台不只是"出分工具"，核心价值是把问题稳定转化为可执行修复、形成持续迭代闭环**。

**指标体系（P0/P1/P2 分层）**：五大类指标按用途分层——**P0 上线门禁（不达标不发）、P1 版本比较与工程优化、P2 体验改善与长期观察**（详见第 E2 章 · 评估指标体系）。两个关键口径：

- **一致性双指标**：任务重复运行 N 次——**至少一次成功率**（能力上限）vs **连续成功率**（每次都要成功，客服/支付/退款/合规等生产级场景看这个）。用户不会接受"多试几次总有一次成功"。
- **统计口径门禁**：版本对比要配套统计检验——关键指标置信区间 + 与基线的显著性判断 + **最小可感知变化阈值**（提前定义提升多少才值得发布）。"门禁不只看差了多少，还要看差异是否超过统计噪声。"

**评测数据集**：评测集不是线上随机抽样——线上样本有**幸存者偏差**：正常流程占多数，易错边缘场景占比低，随机采样报告"看起来不错"但关键问题漏掉。Golden Set 默认作为基线评测集（相对稳定、长期复用的核心样本），用于版本对比与发布门禁。四类来源：**专家设计用例**（定标准）、**扩展用例**（先用规则确定场景类型/订单状态/用户诉求/期望动作等结构字段，再用 LLM 生成接近真实用户的自然语言表达）、**线上真实数据**、**badcase 回流**（如"Agent 直接承诺一定退款成功"）。规模路径：**先做 50–200 条高质量 golden set** 覆盖核心业务路径与高风险边界，成熟后扩展分类采样集、长尾集、对抗集、线上回流集。

**评分原则：规则主判，Judge 辅助，人工兜底。** 规则看"硬条件"（工具、状态、字段、禁用动作），LLM 看"语义/策略合理性"；能写成代码的由规则主判；高风险/抽检/低置信/变更观察期追加 LLM Judge；能自动稳定判断的不长期依赖人工。阿里口径的 judge 工程要点：每分档有可执行标准；输出 reason（定位 + badcase 聚类）；few-shot 含边界样本与判定 CoT；**周期性校准，与人工复核一致率约 85%（参考值）后进日常自动化**；偏差治理——judge 与生成模型同源会偏爱自己风格 → 多 LLM 对抗打分。

**人工评分路由**（阿里独创，详见第 E6 章）：不由分数阈值单独决定——自动评分不确定（边界分/低置信/reason 含糊/多 judge 分歧）进人工；新模型/新 Prompt/新工具 Schema/新活动上线抽样进人工；规则与 Judge 冲突进人工终判并回收口径。**分层筛查**：粗筛层（规则 Scorer + 轻量 Judge，快速分明显通过/明显失败/存疑）→ 精判层（完整规则 + Judge，确认 badcase 并产出初始问题分类/现象/置信度/判定依据）→ 人工复核层（高风险/低置信/冲突/口径未固化）。评分输出**不止 pass/fail**：还要问题分类（现象层：事实性错误/答非所问/过度承诺）、问题现象、置信度、判定依据——为 RCA 提供"现象入口"，且**现象分类 ≠ 最终根因**。

**Judge 持续运营**：维护 Judge 金标校准集；每次 Judge prompt/模型升级固定产出三类统计——与人工标注一致性（一致率或多模型对抗 Kappa）、高风险样本漏判率（合规/资损/隐私）、边界样本稳定性（重复评测波动）。

**Badcase RCA 五步**（本章重点，详见第 E11 章 · Badcase 根因分析与优化闭环）。入口两条通路：离线评测集 + 线上（会话/人工质检/投诉工单/低满意度/版本回归失败/监控告警）→ 汇入同一 badcase 任务表与同一 RCA Pipeline：

| 步骤 | 动作 | 关键机制 |
|---|---|---|
| ① 证据汇总 | 按 sessionId/chatId/traceId/评测运行 ID 找链路日志 | 汇总用户输入、Agent 回复、模块 IO、prompt、工具调用、异常、耗时、中间产物；状态以持久化任务记录为准 |
| ② 范围收敛 | 维护"**问题现象 × 功能模块**"映射 | 答非所问 → 优先看意图识别/Query 改写/知识筛选；过度承诺 → 优先看风险拦截/回复生成；命中走确定性路径，未命中 LLM 兜底缩圈；**映射表只缩小候选，不直接定责** |
| ③ 分模块诊断 | 候选模块逐个读 input/output/prompt/工具返回/异常日志 | 输出 PASS/SOFT_PASS/FAIL + 问题摘要、关键证据、改进建议。实例：现象"事实性错误" → 先看 FAQ 检索是否召回正确政策 → 知识检索是否保留关键片段 → 回复生成是否忠实使用证据；前两段通过而回复仍错 → 回复生成 FAIL |
| ④ 责任判定 | 消费"现象 + 分模块诊断 + 根因知识库" | 三层策略：严重模块结论直接定责 → 规则引擎匹配确定性模式 → LLM 汇总复杂链路责任传递；输出责任模块/问题大类（语义理解/知识召回/工具执行/风险防控）/问题枚举/修复建议 |
| ⑤ 结构化落盘 | 写入任务记录 | 问题分类/现象/枚举/责任层/责任模块/置信度/详细报告/修复建议，看板渐进展示 |

工程实现：单次 badcase 分析建模为**异步 Multi-Agent Workflow**，同样遵循"确定性优先、模型辅助、人审兜底"：规则定位硬错误（工具未调用/顺序违反 SOP/参数缺失/报错未重试/DB 状态未变/引用来源不存在）→ Trace Scorer 定位过程偏差 → 映射表缩圈 → LLM 辅助语义归类聚类 → 高风险/低置信/冲突进人工复核，人工结论反校准规则/Judge Prompt/根因标签。

**根因标签体系**：标签要稳定、可统计、**指向 owner 与处理动作**，可绑定解决角色：运营可配置/算法需优化/工程需修复/业务需定口径。实例："已发货退款未查订单状态" → 归"工具覆盖与执行"、枚举"关键工具未调用"、责任模块 = 退款 Skill/退款流程执行模块。支持聚类：同根因/同场景/同工具/同知识点的失败自动聚成问题簇——报告不只列 100 条 badcase，而是产出"**退款已发货场景中，Agent 23 次跳过订单状态校验，主要集中在 v1.8 Prompt**"。

**自动优化建议（第 8 章）**：建议项不能停留在"优化 Prompt/加强训练/提升准确率"——要明确**失败范围、证据、具体动作、owner、验收方式、优先级**；产出结构化行动项，能被工单系统/看板/配置平台/研发流水线直接消费（"建议是质量工程里的标准任务对象"）。每个建议可展开证据链。

**全链路闭环（第 9 章）**：完整评测平台含九个能力模块；终点不是报告，而是把线上失败持续转化为可复用研发资产。发布阶段离线门禁与线上灰度联动，跟踪三类信号：

| 信号类 | 指标 |
|---|---|
| 离线质量信号 | 核心场景通过率、P0 风险数、关键工具参数正确率 |
| 线上体验信号 | 转人工率、重复追问率、投诉率、满意度变化 |
| 业务结果信号 | 任务完成率、工单闭环率、退款/赔付成功率 |

红线：**离线提升但线上关键信号恶化 → 触发回滚或降级！** 另外两条工程约束：Trace 输出是被测 Agent 的**标准能力而非事后补救**（稳定记录工具名、入参、返回值、时间戳、耗时、错误；复杂 Agent 还记录计划、检索、Guardrail）；评测执行环境隔离，避免多用例共享状态导致分数不可复现。

**反馈生产与质量资产库**：一条 Badcase 至少生产 3 类反馈，平台分三条生产线（评测集/训练数据/知识修订，详见第 E12 章）。入库标准五条：失败可复现（或至少有稳定 Trace + 人工确认）、期望行为明确、根因标签清楚、样本有代表性（覆盖一类问题而非一次性环境抖动）、已脱敏合规。样本治理：同簇保留代表例；P0/P1 风险长期保留；稳定多版本通过且低风险者降级为抽样集；新分布出现时主动学习优先抽取低置信/高影响/新意图/新工具/新知识点样本进人工确认。最终沉淀**质量资产库**：用例库、Trace 库、根因标签库、修复建议库、Judge 校准集、回归集。"质量资产越厚，Agent 迭代越不靠个人经验和临时救火。"

**第 10 章收束**：评测体系的成败取决于它能否在跨团队协作中**长期、稳定地产生可执行行动项**；低分必须稳定转成行动项，否则再精细的分数也只是报表。

### 2.4 腾讯：测评模板与阈值体系

腾讯技术工程这篇是四家中**最像"可直接抄的模板"**的一篇。总公式：

```
Eval = Agent 输入 → 执行 → 捕获执行过程（Trace + 产物） → 一组检查规则 → 可对比的分数
```

目标：可重复、可量化、可持续演进的评估闭环；每次变更都能快速跑出可比较的分数；**用数据代替直觉，用全量代替抽查**。

**痛点表**（立项依据模板）：主观性强（靠"感觉变好了"）；悄悄退化（改 prompt/升级依赖旧场景变差无人知晓）；人工验证成本高（Skill 越多模型越快，人肉回归指数增长，只能选择性验证留盲区）；模型不敢升级（无对比数据支撑切换决策）；缺少效率基线（变贵变慢无法归因版本）；过程易忽略（答案碰巧对但推理路径错，分不清"正确调用工具后回答"与"训练数据碰巧答对"）。

**三类评分器**（选择优先级：**确定性 > Rubric > 人工**）：

| 维度 | 确定性评分器 | Rubric 评分器 | 人工评分器 |
|---|---|---|---|
| 谁来评 | 脚本（Bash/Python/断言/Lint/AST） | 大模型（固定版本） | 领域专家 |
| 规则写在哪 | 代码里 | Prompt + JSON Schema | 人脑 + 标注指南 |
| 成本 | 毫秒级/免费 | 秒级/API 费用 | 分钟-小时级/人力 |
| 稳定性 | 100% | 有抖动（需降噪） | 取决于标注员水平 |
| 覆盖 | 已知硬指标 | 未知软指标 | 主观 + 边缘场景 |
| 典型用例 | 文件存在、构建/测试通过 | 代码风格、意图贴合、解释清晰度 | 校准 LLM、诊断 0%/100% 异常、红队 |
| 门禁角色 | 硬门禁 | 分级门禁（error 硬/warning 软） | 不进门禁，做采样审查 |

确定性评分器类型：工具调用检查（是否调用指定工具、参数是否正确）、产物检查（文件存在、内容符合预期）、关键词匹配、执行指标（调用次数/token 阈值）、基线对比（与基线快照逐项对比）。Rubric 规则示例：`observation_points`（回答是否基于项目规范而非通用知识/推理是否清晰连贯/有无幻觉编造）；`scoring`：`process_score` 0-100、`result_score` 0-100、`is_false_positive` bool（结果对但过程错的虚假成功）。

**人工评分六个必要场景**：① 校准 LLM 评委（最核心；抽样 100–200 条对齐，**一致率 ≥85% 才可用**）② 主观任务打分 ③ 诊断通过率异常（**0% 或 100% 通常是任务/评分器坏了，不是模型弱**）④ 建 Ground Truth（新套件前 20–50 个参考解）⑤ Trace 采样审查（每周固定抽样读轨迹找隐藏失败模式）⑥ 高风险兜底（医疗/金融/安全 100% 人工复核）。经验法则：能自动化的坚决不找专家；**专家时间 60%+ 花在"校准 LLM 评委"与"诊断异常"**。

**五大评测维度**（详见第 E2 章）：

| 维度 | 级别 | 评分方式 | 要点 |
|---|---|---|---|
| 功能正确性 | P0 | 代码判 | pass@1/pass^k、任务完成度、指令遵循（JSON Schema/正则）、工具调用正确性；必须自动化全覆盖 |
| 过程质量 | P1 | Rubric + 人工 | 推理合理性、步骤最优性（实际步数 vs 参考解法）、信息完整性、上下文利用率、自我纠错；最能体现"智能"，自动化最难 |
| 效率与成本 | P1 | 代码判 | Token avg/p95、工具调用次数、延迟 p50/p95/p99、失败重试率、¥/task；"**pass@1 高但 token 花 10 倍的方案生产上不可接受**" |
| 鲁棒性与安全 | P0 | 代码 + 人工 | 一致性（pass^k，k=5/10）、异常恢复（故障注入）、抗注入红队、幻觉率、越权断言、合规、误拒%/漏拒%；金融/医疗/企业数据 Agent 必须前置 |
| 体验与对齐 | P2 | Rubric + 人工 | 语气、清晰度、主动澄清、同理心、可解释性、CSAT/NPS；P2 但决定产品生死 |

术语口径：**pass^k = k 次每次都通过（稳定性）；pass@k = k 次至少 1 次通过（峰值能力）**。落地顺序：P0 先落地，P2 按需补。不同 Agent 类型侧重不同（知识库问答 → 准确性/幻觉/溯源；代码编写 → 产物可运行性；功能工具 → 过程合规性；问题定位 → 过程 + 结果双重验证），差异在"用什么评分器、检查什么"，流程不变。

**用例集设计四场景**（详见第 E3 章 · 黄金数据集与用例设计）：① 触发（该触发吗？正向：各种合法表述都触发；负向：相似但不相关 prompt 不误触发）→ ② 核心逻辑（过程对吗？工具调用序列/参数/顺序）→ ③ 产物质量（产物好吗？准确/完整/格式）→ ④ 异常容错（出错扛得住？优雅降级 vs 崩溃/死循环/静默失败/泄露）。**负向触发用例为什么必不可少**："只测正例，Agent 可能学会什么都触发——**过度触发比不触发更难发现**。"经验法则：**核心逻辑用例量通常是其他三类之和的 2–3 倍**；N 条分支至少 N 个正向 + 关键分支负向。

**评分规则（扣分制）**：初始 100 分负分制，每处不符扣对应分至 0；**达标线 80 分**（推荐值，按 Agent 类型与业务风险调整）。扣分维度：任务结果不符预期 −100；步骤遵循性每步 −10；步骤输出结果每步 −10；工具/知识库调用每项 −10；分析耗时基准 5 分钟每超 1 分钟 −10；一致性 N 次（建议 N=5）全达标取均值。每次评分输出 JSON 扣分明细 + 原因，渲染 HTML 报告归档。

**用例基线机制**（腾讯独创）：基线 = 单用例执行 1 次后经人工确认的预期过程与预期结果快照（"正确的执行应该长什么样"）。预期过程含 CoT、工具调用序列（入参返回）、中间产物、完整 Trace；预期结果含最终响应、输出文件、输出报告。流程：用例设计只定义 prompt 与检查规则 → 执行 1 次 → 人工审核过程与结果 → 不可接受则修后重跑 → OK 则该次快照成为基线。后续每次执行与基线对比：过程对比（关键步骤缺失/顺序偏离 → 过程退化）、结果对比（关键内容缺失/产物不一致 → 结果退化）、效率对比（token/步骤数超基线比例，如 **>50% → 效率退化**）。基线更新时机：Agent/Skill 逻辑变更、模型版本升级、用例本身修改 → 重新执行 1 次并人工确认。

**稳定性评估与容忍阈值分级**：N 次执行，只要 1 次不通过即存在稳定性风险。容忍阈值按使用类型分级：

| 使用类型 | 例子 | 失败容忍阈值 |
|---|---|---|
| 关键决策类 | 问题定位/故障诊断 | **0%**（N/N 全过，任何一次失败都可能误判） |
| 辅助分析类 | 性能分析/报告生成 | **≤10%** |
| 创意生成类 | 代码建议/文案 | **≤40%** |

N=5 的解读：全过 = 稳定；1/5 失败 = 存在幻觉，按类型判断；2/5 = 高幻觉率深入排查；5/5 失败 = 稳定失败，先查任务定义或基线。调试技巧：**0% pass^N 通常说明任务定义有问题，不是能力不行**。

**能力测评 vs 回归测评**：能力测评回答"Agent 能把什么做好"（起步通过率 20–50%，目标山峰，主动拓展频繁迭代）；回归测评回答"原有能力是否还在"（接近 100%，防御漂移，**只增不减**，CI 每次运行）。通过率稳定 100% 后用例"毕业"进回归集。引用 Anthropic 推荐：**确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%**。Bad case 处理流：复现记录完整轨迹 → 分析根因定预期行为 → 修复 → 纳入用例集防回归 → 进能力集，稳定后毕业到回归集。

**工程落地细节**：Trace 前置三要求——结构化（JSONL/JSON）、内容完整（每步工具名/入参/返回/时间戳，理想含思维链与决策依据）、格式跨版本稳定；不支持时优先推动被测系统增加 Trace 输出，"设计阶段就把结构化 Trace 作为标准能力，而非事后补救"。环境隔离：clone 仓库到临时目录；每用例前重置（`git checkout . && git clean -fd`）；产物统一归档。触发时机：提示词变更（CI 自动，PR 合入前回归）、模型版本升级（手动验证兼容性）、定期巡检（定时全量回归）。

**TPerf 实战案例**（把上面所有模板跑了一遍的真实项目）：TPerf AI 分析 Agent 属功能工具类型，部署在 Knot 智能体平台，MCP 调用 TPerf-API 取性能数据 + 知识库检索，决策树判断资源瓶颈与压测有效性，输出结构化性能分析报告。测评侧重：操作步骤合规性 + 执行效率 + 输出报告质量。

| 评分维度 | 机制 | 扣分 |
|---|---|---|
| 操作步骤（确定性） | **LCS 最长公共子序列**对齐基线与 Trial 步骤，归一化：时间戳占位/搜索工具忽略查询参数/写入只留路径/终端命令提取脚本名/连续读文件组内不校验顺序 | 不一致/多余/缺少/顺序错各 −2，上限 −10 |
| 效率（确定性） | 耗时基准 300s 每超 10% 扣 1；token 以基线为基准每超 10% 扣 1 | 各上限 −10 |
| 关键判定（模型评分） | 压测有效性/性能结果与基线不一致 | 直接 −80 |
| 章节内容（模型评分） | CPU/内存/网络/磁盘 IO/业务指标/根因定位/优化建议/完整性/准确性，调用 CodeBuddy CLI 逐项对比 | 每项 −5，上限 −80 |

一致性标准三档：数值型（整数精确/小数相对误差 ≤1%）、结论型（异常等级与关键发现一致）、建议型（核心排查方向一致即可）。**稳定性 0 容忍说明**：TPerf 虽属辅助分析类，但结论直接影响优化决策与发布判断，一次错误结论可能导致性能问题漏检上线 → 采用关键决策类标准（任一 Trial 不达标该用例 0 分）。计分公式：`trial_score = max(0, 100 + 各项扣分)`；`trial_pass = score ≥ 80`；`case_score = 全 pass 取均值，任一不达标为 0`。

用例集与执行数字：**9 大场景分组 30+ 用例**（CPU 瓶颈 6/网卡 5/磁盘 4/磁盘 IO 2/内存 1/TCP 队列 3/Nginx 1/配置问题 1/正常场景 5），每个用例对应真实 TPerf 压测记录（不可变、可复现）；支持 **7 模型对比**（每用例 × 每模型参数化测试）。用例不硬编码预期输出，通过基线会话标识（session_id + message_id）指向人工确认正确的分析记录，评测时从 Knot API 动态获取。执行：Trial 并发 + 评分并行 + 三评分器并行；限流自动重试（≤5 次）；单用例约 **3000s**；全量 30+ × 7 模型约 **3–5 小时**；pytest 实现，TCase 平台管理用例。关键设计：基线配置随代码仓库 Git 版本化；执行结果每次重新生成并归档；支持重新评分（评分逻辑调整后无需重新触发 Agent）。

> 动手：`labs/eval_lab01_metric_system.py` 复现 pass@k/pass^k 与"容忍阈值分级"判定；`labs/eval_lab06_trajectory_eval.py` 复现 LCS 轨迹对齐扣分与假阳性捕获。运行：`cd evals-special/labs && python3 eval_lab01_metric_system.py` / `python3 eval_lab06_trajectory_eval.py`

### 2.5 四家横向对比：共识与独创贡献

把四家放在一起看，会发现**独立演化的实践收敛到了几乎相同的骨架**——这正是"评测体系的客观规律"的證據，也是面试中最高密度的得分点。

**共识表**（素材汇总）：

| 共识点 | Airbnb | DoorDash | 阿里 | 腾讯 |
|---|---|---|---|---|
| 三大难题 | 非确定性/判断依赖/AI 评 AI | 开放目标/执行不可见/无法安全彩排/规模化判断/双环境 | 非确定性/黑盒化/错误级联 | 非确定性/黑盒化/错误级联 |
| 三层评分 | 程序化 → Judge → 人工 | binary rubric + judge + 人工定标准/标注/审计 | 规则主判 → Judge 辅助 → 人工兜底 + 路由 | 确定性 > Rubric > 人工（优先级） |
| Judge 校准线 | high 80s ~ 90s 一致率 | 与人工标注一致（GEPA 优化） | ~85% 后进自动化 | ≥85% 可用 |
| 起步标注规模 | 50–100 gold set（含坏样本） | rubric + 校准集 + 20–50 参考解 | 50–200 golden set | 前 20–50 参考解 |
| 过程评估 | step/trajectory/session 三层 | transcript builder + 按标准定制视图 | Turn/Session/Trace/Outcome 四层；假阳性 | 过程质量维度 + LCS 基线对齐 |
| 闭环 | 每周 PM 评审新增测试 | 失败聚类 → coding agent → Agent Skills | RCA 五步 → 行动项 → 反馈生产 → 质量资产库 | badcase → 能力集 → 毕业回归集 |

六条可以直接背诵的共识：

1. **难题同源**：非确定性、不可见、错误放大/级联——四家的全部机制都是对这三件事的响应；
2. **三层评分**：确定性优先，模型 judge 居中，人工兜底且只花在高杠杆处——没有一家让模型 judge 未经校准直接进门禁，也没有一家让专家做日常全量打分；
3. **~85% 校准线**：judge 与人工一致率约 85%（high 80s ~ 90s）是四家不约而同的"可用线"；
4. **golden set 从小起步**：20–50 参考解 / 50–100 / 50–200，都强调含坏样本、含边界，都走"先小后扩"；
5. **过程评估不可省**：只看最终答案会放过假阳性——四家各自给出了 step/trajectory/session、transcript 视图、Turn/Session/Trace/Outcome、LCS 基线对齐四种实现；
6. **闭环是终点**：评测的价值不在出分，而在"失败 → 用例/修复/资产"的持续转化。

**独创贡献表**（各家"别人没有的那一手"）：

| 公司 | 独创贡献 | 解决的具体问题 |
|---|---|---|
| Airbnb | 迭代纪律（一次只改一个变量）、judge 少而精（3–5 个）、100 样本人工精读法、"专家分歧先停下" | 归因混乱、评估器噪声、拍脑袋指标 |
| DoorDash | Transcript Builder（证据切片）、fixtures、GEPA 校准、eligibility 前置、checklist 式 rubric、评测镜像运行时架构、Agent Skills 化闭环 | judge 被无关 trace 噪声干扰、环境漂移、rubric 误伤不适用场景 |
| 阿里 | RCA 五步归因体系、统计口径门禁、结构化行动项、反馈生产线（一 badcase ≥3 类产出）、质量资产库、人工评分路由 | 低分无法转化为修复、责任不清、口径漂移 |
| 腾讯 | 基线快照机制、扣分制（80 分线）、稳定性容忍阈值分级、能力/回归"毕业"机制、LCS 轨迹对齐 + 归一化 | 无参照系、无阈值、用例集无序膨胀 |

**一个元观察**：四家恰好覆盖评测体系建设的四个层面——**Airbnb 教你纪律（怎么迭代），DoorDash 教你工程（怎么搭 harness），阿里 教你治理（怎么让组织消费评测结果），腾讯 教你模板（第一周就能跑起来的最小集）**。面试回答"你怎么搭评测体系"时，按这四层组织答案比堆砌工具名高级得多。

### 2.6 从零落地路线图：30 天 / 90 天

综合四家实践（每一步都标注出处），给一份可以直接拿去答辩的路线图。

**里程碑一：30 天 —— 可用的评测最小集**（目标：一条命令跑出可比较的分数）

| 周 | 动作 | 出处与要点 |
|---|---|---|
| W1 | 结构化 Trace 前置 | 阿里/腾讯：Trace 是被测 Agent 的标准能力而非事后补救；JSONL 结构化、每步工具名/入参/返回/时间戳、跨版本格式稳定。同时做 Agent 类型分类定评测侧重（"类型不分，评测结果基本不可用"） |
| W1–W2 | 100 样本人工精读 | Airbnb：跑 ~100 个真实/合成样本，人工读输出与 trace，归类错误（参照旅行客服案例的 15/8/5/3 分类法），错误类型即测试清单 |
| W2–W3 | 建 50–200 条 golden set | 阿里：覆盖核心业务路径 + 高风险边界；四类来源（专家设计/结构字段先行 LLM 扩展/线上真实数据/badcase 回流）；**必须含坏样本**（Airbnb）；每条用例有明确期望行为 |
| W3–W4 | 程序化评分第一批 | 腾讯：确定性优先——schema 校验、空/异常长度、关键词、工具调用断言、执行指标（调用次数/token 阈值）；阿里分层筛查的粗筛层 |
| W4 | 基线快照 + 首条 CI | 腾讯：每用例执行 1 次 → 人工确认 → 快照为基线；提示词变更触发 PR 合入前回归 |

30 天验收标准（四家口径合成）：能跑全量 golden set 并输出分层报告；任何一次 prompt 变更能在合入前看到"改坏了哪些旧场景"；团队不再用"感觉变好了"描述版本差异。

**里程碑二：90 天 —— 体系闭环**（目标：低分稳定转化为行动项）

| 模块 | 动作 | 出处与要点 |
|---|---|---|
| Judge 上线 | 3–5 个按维度拆分的 judge | Airbnb 少而精；每维一个、与生成模型不同源、few-shot、强制输出 schema |
| Judge 校准 | 50–100 条校准集（含坏样本）→ 一致率目标 ≥85% | 四家共识线；分析分歧改 rubric 重复（Airbnb 78→88 路径）；分歧用 Cohen's kappa 度量；可用 GEPA 式反射优化只保留留出集一致率提升的版本（DoorDash） |
| 环境受控 | fixtures 冻结外部状态 + 会话模拟器 | DoorDash：同场景每次一致；成本参照 50 场景 × 8 trials = 400 对话，人工 6h+ → 模拟器 20min |
| 门禁与统计 | P0 门禁 + 置信区间 + 显著性 + 最小可感知变化 | 阿里："门禁不只看差了多少，还要看差异是否超过统计噪声"；一致性双指标（至少一次 vs 连续成功率） |
| 用例治理 | 能力集（20–50% 起步）+ 回归集（只增不减）+ 毕业机制 | 腾讯：稳定 100% 毕业进回归；Anthropic 口径确定性 100%/非确定性 ≥95% |
| RCA 闭环 | 现象 × 模块映射表 + 根因标签绑定 owner + 结构化行动项 | 阿里 RCA 五步；行动项带失败范围/证据/动作/owner/验收方式/优先级 |
| 在线联动 | 每日抽样去标识化流量（Airbnb 5%）；离线线上同一 rubric + 同一 judge（DoorDash）；三类信号联动，离线升线上降 → 回滚（阿里） | 详见第 E12 章 · 在线评估与数据飞轮 |
| 组织机制 | 指定人类终判者 + 每周 PM 评审 | Airbnb 原则四、五；专家时间 60%+ 花在校准与诊断（腾讯） |

90 天验收标准：阿里第 10 章口径——评测体系能否在跨团队协作中长期、稳定地产生可执行行动项。对照 DoorDash 的成绩单设定自己的预期：质量信号从人工 1 条/天到自动评分 2,000 个/天、全量回归从 6+ 小时到约 20 分钟，都是在一个季度量级的持续建设后取得的。

|---|---|---|---|

| 6 | Transcript Builder 证据切片 | ⭐⭐⭐ | judge 只看该标准依赖的证据，聚焦让判断更一致——深水区细节 |
| 7 | Fixtures 与环境受控 | ⭐⭐ | 环境不受控时分数测量的是噪声；50×8=400 对话 6h+→20min 的成本账 |
| 8 | 离线-线上同一 rubric + 同一 judge | ⭐⭐⭐ | 各自调 judge 分数会难调和地背离；离线结论必须能带到线上 |
| 9 | 阿里 RCA 五步与根因标签绑定 owner | ⭐⭐⭐ | 评测平台的治理价值：现象 × 模块映射、三层定责、标签可统计可指派 |
| 10 | 结构化行动项 vs "优化 Prompt" | ⭐⭐ | 建议必须带失败范围/证据/动作/owner/验收方式/优先级，否则只是报表 |
| 11 | 腾讯三类评分器优先级（确定性 > Rubric > 人工） | ⭐⭐ | 成本/稳定性/覆盖的取舍逻辑；专家时间 60%+ 在校准与诊断 |
| 12 | 扣分制 + 基线快照 + 容忍阈值分级 | ⭐⭐ | 模板落地能力：80 分线、快照即参照系、关键决策类 0% 容忍 |
| 13 | 能力测评 vs 回归测评与"毕业"机制 | ⭐⭐⭐ | 用例集治理：20–50% 爬山峰 vs 接近 100% 防漂移，只增不减 |
| 14 | 兼容性差距 vs 能力差距（模型迁移） | ⭐⭐⭐ | DoorDash 案例：低分反映的是为旧模型适配的系统；先修环境再谈换模型 |

## 四、经典面试题与参考答案

#### 题 1（基础）：什么是 Eval-Driven Development？请复述 Airbnb 的五原则。

**参考答案：**
EDD 是 Airbnb 提出的 GenAI 开发方法论：不追求预先穷举所有失败，而是**发现错误 → 捕获为测试 → 反复检查**的持续循环，评测驱动开发全程。五原则：① 尽早设定目标与上线门槛（launch gates），即便它们在数据评审中才逐渐清晰；② 从观察到的错误中推导指标，与跨职能伙伴共同制定；③ 用少而精的 judge——3–5 个经校准的评估器好过一堆嘈杂的评估器；④ 指定一个最终人类决策者裁决"好 vs 坏"争议；⑤ 让产品伙伴持续参与对比与错误诊断。配套的核心习惯是 "When in doubt, look at your data"：拿约 100 个样本人工精读输出与 trace，归类错误再建测试。EDD 还包含两条纪律：judge 未校准到 high 80s~90s 一致率不信任；迭代一次只改一个变量。

#### 题 2（基础）：项目早期不做评测计划会掉进哪些坑？Airbnb 怎么描述的？

**参考答案：**
Airbnb 总结三大坑：① **虚假信心**——用浅层 helpfulness 分看着不错，但分数没有预测真实产品质量；② **未被发现的回归**——改 prompt 后旧场景质量悄悄变差，没有回归集就无人知晓；③ **浪费精力**——指标与产品结果脱节，团队优化的方向不产生业务价值。对策都在 EDD 里：指标从观察到的真实错误推导（而非拍脑袋 helpfulness）、回归测试只增不减并每周 PM 评审新增、产品伙伴持续参与错误诊断保证指标对齐产品目标。旅行客服案例是完整示范：100 个 prompt 精读发现 15 个 groundedness 失败/8 个啰嗦/5 个不当拒答/3 个 JSON 失败——每条都是"浅层 helpfulness 分抓不到"的真实失败模式。

#### 题 3（进阶）：LLM judge 怎么校准？请结合 Airbnb 旅行客服案例讲一遍完整流程，并给出四家共识的量化标准。

**参考答案：**
流程五步（Airbnb）：① 建 50–100 条 gold set，**必须含坏样本**；② 用 judge 跑该集合；③ 看一致率，目标 high 80s ~ 90s%，分歧用 Cohen's kappa 或 Krippendorff's alpha 度量；④ 逐条检查分歧 → 改 rubric/示例 → 重复；⑤ 失败模式变化时重新校准。案例：旅行客服助手，PM/SME 标注 60 条 gold（含失败样本），judge 初始一致率 **78%**——根因不是模型弱，而是 rubric 有缺陷：judge 把"正确的改述"误罚为 groundedness 失败；修订 rubric 与示例后达到 **88%**。四家量化口径高度收敛：Airbnb high 80s~90s、阿里 ~85% 后进日常自动化、腾讯 ≥85% 才可用（抽样 100–200 条对齐）、DoorDash 用 GEPA 迭代 judge prompt 且只保留留出集一致率提升的版本。关键警告：未校准 judge 制造的是**误导性信心**；且 judge 与生成模型同源会偏爱自己风格，需不同源或多模型对抗打分。

#### 题 4（进阶）：DoorDash 的 eval harness 面对哪五大挑战？各自的设计要求是什么？Transcript Builder 解决什么问题？

**参考答案：**
五大挑战 → 五大设计要求：① 开放式目标（一个目标多种可接受结果）→ 每个目标表达成 rubric，具体到每次能同样判、宽泛到容纳所有合法路径；② 执行不可见 → 把 trace 重建为"按标准定制的视图"，judge 只看该标准需要的证据；③ 无法安全彩排 → 模拟用户按需生成会话 + fixtures 固定外围数据；④ 规模化判断 → 校准过的 LLM judge 顶替人类评审；⑤ 双环境背离 → 真实与模拟会话用同一 rubric + 同一 judge。Transcript Builder 是挑战②的实现：原始 trace 完整但难判（工具返回巨大、脚手架字段多、证据散落多 span），它用一组 Python 脚本重组分散 span、删无信号 token、裁超大载荷；最关键的是**每条标准声明依赖的证据，builder 只给 judge 那一片**——grounding 检查拿论断 + 工具输出，多样性检查拿推荐 + 原始请求。聚焦证据让判断更一致，这是"judge 为什么稳"的工程答案。

#### 题 5（进阶）：为什么评测需要 fixtures？DoorDash 的全量回归成本账怎么算？

**参考答案：**
fixtures 用录制的工具返回替代实时调用，冻结外部状态：目录会变、门店库存会变、测试账号会漂移，不受控的环境让同一用例每次测的其实是不同的题——DoorDash 的教训是"环境必须受控，否则分数测量的是噪声"。实例：复购场景 "Reorder my usuals"，`get_reorder_items` 固定返回录制的 `reorder_history_v1`（Albertsons 订单：Meadow Gold 全脂牛奶 ×2、Oroweat 全麦面包、牛油果、Ben & Jerry's 冰淇淋），每次运行看到相同订单，预期结果可预测，judge 可对照同一商品集评分；fixtures 还能构造欺诈、大额退款等真实里难遇到的难例。成本账：全量 sweep = 50 场景 × 8 trials = 400 次对话，人工本地聊约 1 分钟/次即 6+ 小时，模拟器约 20 分钟——两个数量级的差距，这是"回归只增不减"在经济上成立的前提。成果：全国上线前质量分 +8 分、错误率近乎减半，质量信号从人工 1 条/天到自动评分 2,000 个/天。

#### 题 6（进阶）：换模型后离线评测分数大跌，你怎么判断是新模型不行还是系统不适配？请举 DoorDash 的实例。

**参考答案：**
先看 eval 给出的**具体失败模式**而不是总分。DoorDash 实例：agent 跑在 Claude Sonnet 4.6，迁到 Gemini 3.5 Flash 后离线 harness 分数大跌；coding agent 分析失败 trace 后判定**不是能力差距，是兼容性差距**——Flash 部分工具参数格式不同（工具签名要 plain string，Flash 传 `{"dishes": [...]}` JSON 对象），且系统 prompt 围绕 Sonnet 惯例隐式调优。"低分反映的是为 Sonnet 适配的系统，不是更弱的模型。"修复小而准：① 工具输入确定性防护——错误形状强制转换回预期形状而非丢弃调用；② prompt 显式写出 Sonnet 原本自行推断的内容（用数据中精确店名、不超出工具结果渲染）。"不是改模型，是修正模型周围的环境。"重跑 eval 质量持平（harness 噪声范围内）后迁移生产，延迟降 35%、质量无损。答题要点：有 eval 才有资格谈迁移——没有失败模式分解，"benchmark 说它行"不能支撑决策。

#### 题 7（进阶）：阿里怎么做 badcase 根因分析？请完整讲五步，并说明根因标签为什么要"绑定 owner"。

**参考答案：**
入口两条通路（离线评测集 + 线上会话/质检/工单/低满意度/回归失败/告警）汇入同一任务表，然后五步：① **证据汇总**——按 sessionId/traceId 聚合用户输入、回复、模块 IO、prompt、工具调用、异常、耗时；② **范围收敛**——查"问题现象 × 功能模块"映射表（答非所问 → 意图识别/Query 改写/知识筛选；过度承诺 → 风险拦截/回复生成），命中走确定性路径，未命中 LLM 兜底缩圈，映射表只缩小候选不直接定责；③ **分模块诊断**——候选模块逐个读 IO，输出 PASS/SOFT_PASS/FAIL（实例：事实性错误 → FAQ 检索 PASS → 知识检索 PASS → 回复生成 FAIL）；④ **责任判定**——三层策略：严重模块直接定责 → 规则引擎匹配 → LLM 汇总责任传递；⑤ **结构化落盘**——问题分类/现象/枚举/责任层/责任模块/置信度/修复建议写入任务记录。根因标签必须稳定、可统计、**指向 owner**（运营可配置/算法需优化/工程需修复/业务需定口径），否则标签只是分类学不是管理工具；聚簇后报告变成"退款已发货场景中 Agent 23 次跳过订单状态校验，集中在 v1.8 Prompt"——直接可派单。

#### 题 8（进阶）：腾讯的三类评分器怎么选？为什么人工评分器"不进门禁"？

**参考答案：**
选择优先级**确定性 > Rubric > 人工**。确定性评分器（脚本/断言/Lint/AST）毫秒级、免费、100% 稳定，覆盖已知硬指标，做硬门禁；Rubric 评分器（固定版本大模型 + Prompt + JSON Schema）秒级、有 API 费用、有抖动需降噪，覆盖未知软指标，做分级门禁（error 硬/warning 软）；人工评分器分钟-小时级、成本最高、一致性取决于标注员，覆盖主观与边缘场景，**不进门禁，做采样审查**。人工不进门禁的原因：人力无法随版本频率扩展，且标注员间一致性本身是噪声源；但人工有六个不可替代的场景——校准 LLM 评委（最核心，抽样 100–200 条，一致率 ≥85% 才可用）、主观任务打分、诊断 0%/100% 通过率异常、建 Ground Truth（前 20–50 参考解）、Trace 采样审查、高风险 100% 复核。经验法则：专家时间 60%+ 花在"校准评委"与"诊断异常"，坚决不做日常全量打分。

#### 题 9（系统设计）：你加入一个还没有评测体系的 Agent 团队，给出 30 天与 90 天两个里程碑的落地计划，每一步说明依据哪家的实践。

**参考答案：**
**30 天（可用最小集）**：W1 结构化 Trace 前置——Trace 是被测 Agent 的标准能力而非事后补救（阿里/腾讯：JSONL、每步工具名/入参/返回/时间戳、跨版本格式稳定），并按 Agent 类型定评测侧重；W1–W2 跑 ~100 样本人工精读，归类错误（Airbnb 100 样本法，错误类型即测试清单）；W2–W3 建 50–200 条 golden set，覆盖核心路径 + 高风险边界，四类来源：专家设计/结构字段先行的 LLM 扩展/线上真实数据/badcase 回流，必须含坏样本（阿里/Airbnb）；W3–W4 程序化评分第一批（schema/空输出/关键词/工具调用断言/执行指标，腾讯确定性优先）；W4 基线快照——每用例执行 1 次人工确认后快照为基线（腾讯），接 CI 做 PR 前回归。**90 天（体系闭环）**：3–5 个按维度拆分的 judge 并校准到 ≥85% 一致率（四家共识线；Airbnb 78→88 路径，DoorDash GEPA）；fixtures + 会话模拟器冻结环境（DoorDash：400 对话 6h+→20min）；P0 门禁带统计口径——置信区间 + 显著性 + 最小可感知变化，一致性看连续成功率（阿里）；能力集/回归集分治 + 毕业机制（腾讯）；RCA 五步 + 根因标签绑定 owner + 结构化行动项（阿里）；每日抽样去标识化流量、离线线上同一 rubric 同一 judge、离线升线上降即回滚（Airbnb/DoorDash/阿里）；组织上指定人类终判者 + 每周 PM 评审（Airbnb）。验收用阿里第 10 章口径：低分能否稳定转成行动项。

#### 题 10（系统设计）：四家公司的评测体系有哪些共识？如果只能保留五条写进你团队的评测宪章，保留哪五条？

**参考答案：**
共识清单：难题同源（非确定性/黑盒/错误级联）、三层评分（确定性 → judge → 人工）、judge 校准线约 85%、golden set 从小起步（20–200 条，含坏样本）、过程评估不可省（防假阳性）、闭环是终点（失败 → 用例/修复/资产）。我的五条宪章：① **确定性优先**——能用代码判断的绝不用模型，三层评分按成本/稳定性/覆盖路由（腾讯优先级 + 阿里分层筛查）；② **judge 未校准不进门禁**——一致率 ≥85% 是可用线，gold 集必须含坏样本，升级必重校准（四家共识 + Airbnb 78→88）；③ **评测环境受控**——fixtures 冻结外部状态，同用例同条件，否则分数测量的是噪声（DoorDash）；④ **离线-线上一把尺子**——同一 rubric + 同一校准 judge，离线升线上降触发回滚（DoorDash 原则三 + 阿里三类信号）；⑤ **低分必须变成行动项**——带失败范围/证据/owner/验收方式，评测资产只增不减（阿里第 10 章 + 腾讯回归集毕业机制）。五条背后的共同逻辑：评测不是出分工具，而是把不确定性收敛为可发布质量的治理系统。

## 五、易错点 · 反直觉点

1. **误区：judge 一致率低就换更强的模型。** 真相：Airbnb 案例中 78% 的根因是 rubric 缺陷——judge 误罚了正确的改述，修 rubric 与示例后到 88%，不是换模型。**记忆锚点：校准从看分歧样本开始，不是从换模型开始。**
2. **误区：换模型后离线分数大跌 = 新模型不行。** 真相：DoorDash 迁移 Gemini 3.5 Flash 时分数大跌，实为兼容性差距（工具参数形状、围绕 Sonnet 惯例调优的 prompt），修正环境后质量持平、延迟降 35%。**记忆锚点：低分测的是"为旧模型适配的系统"，先修环境再评模型。**
3. **误区：线上随机抽样就能当评测集。** 真相：线上样本有幸存者偏差——正常流程占多数、易错边缘占比低，随机采样报告"看起来不错"但关键问题漏掉（阿里）。**记忆锚点：随机抽样的评测报告是虚假信心。**
4. **误区：pass@1 高就能上线。** 真相：生产级场景（客服/支付/退款/合规）看连续成功率（pass^k），用户不会接受"多试几次总有一次成功"（阿里一致性双指标；腾讯关键决策类 0% 容忍）。**记忆锚点：能力上限看至少一次，生产可靠看连续成功。**
5. **误区：逐条看失败、修一条是一条。** 真相：逐条修会"轶事驱动"——最近、最惊奇的失败主导修复优先级；rubric 标准天然是问题簇，先聚类再按影响排序（DoorDash）。**记忆锚点：先修簇，再修例。**
6. **误区：离线一套 judge，线上另一套 judge，各自调到最好。** 真相：DoorDash 教训三——各自调 judge，两边分数会以难调和的方式背离；离线结论只有能带到线上才有意义。**记忆锚点：同一 rubric、同一 judge，一把尺子量两边。**
7. **误区：用例只测正向触发就够了。** 真相：只测正例，Agent 可能学会什么都触发——过度触发比不触发更难发现（腾讯）；负向触发用例必不可少。**记忆锚点：负向用例测的是触发的边界。**
8. **误区：通过率 0% 或 100% 是模型能力的两极。** 真相：0%/100% 通常是任务定义或评分器坏了，不是模型弱/强（腾讯人工评分六场景之三；0% pass^N 先查任务定义与基线）。**记忆锚点：两个极端先怀疑尺子。**
9. **误区：回归集和能力集一样维护，都追求覆盖新场景。** 真相：两者目标相反——能力集起步 20–50%，爬山峰、主动拓展；回归集接近 100%、防漂移、只增不减、CI 每次运行；稳定 100% 的用例才"毕业"进回归集（腾讯；Anthropic 口径确定性 100%/非确定性 ≥95%）。**记忆锚点：能力集爬山峰，回归集守底线。**
10. **误区：评测平台的价值是把分数算准。** 真相：阿里第 10 章——成败取决于能否在跨团队协作中长期、稳定地产生可执行行动项；低分不能稳定转成行动项，再精细的分数也只是报表。**记忆锚点：评测的终点是行动项，不是报告。**

2. **DoorDash《Building Ask DoorDash (Part 3): Evaluation》**（Steven Xu, Fabio Flores, Twisha Jain, 2026-06-30）——五大挑战表、Transcript Builder、fixtures、GEPA 校准、reasoning leakage 与模型迁移两个实战案例。工程层必读，细节密度最高。
3. **阿里技术《Agent 评测：方法论与体系设计》（2026 年第 28 篇）**——P0/P1/P2 指标、评分路由、RCA 五步、结构化行动项、反馈生产与质量资产库，共十章。治理层必读。
4. **腾讯技术工程《AI Agent & Skill 测评方案及落地实践》**（martinskxu，TEG 云架构平台部网关测试团队）——三类评分器、五维度、四场景用例、扣分制、基线快照、容忍阈值分级、TPerf 实战。模板层必读，可直接抄。

**特辑内交叉引用**：

- 方法论展开：第 E1 章 · 为什么评估是 GenAI 工程的生命线（三大坑与四个失效场景）、第 E10 章 · 评测驱动开发（EDD）（Airbnb 案例演练与 DoorDash 反馈闭环）
- 指标与数据：第 E2 章 · 评估指标体系（P0/P1/P2 与五维度）、第 E3 章 · 黄金数据集与用例设计（四来源与四场景）、第 E9 章 · 评估的统计学基础（门禁统计口径）
- 评分三层：第 E4 章 · 程序化评分、第 E5 章 · LLM-as-Judge 深入（校准与 GEPA）、第 E6 章 · 人工评估与评分路由
- 过程与仿真：第 E7 章 · 轨迹与 Agent 级评估（三层模型与 Transcript Builder）、第 E8 章 · 对话 Agent 与仿真评测（模拟器与 fixtures）
- 闭环与在线：第 E11 章 · Badcase 根因分析与优化闭环（RCA 五步全展开）、第 E12 章 · 在线评估与数据飞轮（三类信号与发布联动）
- 主手册浓缩版：主手册第 8 章 · Agent 评估与可观测性（本章是其在工业实践维度的深挖）

# 第 E11 章 · Badcase 根因分析与优化闭环

> 评分只回答"有多差"，RCA（Root Cause Analysis，根因分析）才回答"为什么差、谁来修、修完怎么证明"。
> 本章以阿里的 RCA 五步法为骨架，拆解 badcase 从发现到修复验收的全链路工程：双通路入口、
> 范围收敛、三态诊断、三层定责、问题簇聚类、结构化行动项与反馈生产线。学完你应该能独立设计
> 一条"badcase 进、行动项出"的质量闭环，并在面试中讲清每一步的成本、置信度与 owner。

## 二、核心概念精讲

### 2.1 为什么 badcase 治理是评测体系的分水岭

阿里对评测平台的总命题是：**评测平台不只是"出分工具"，核心价值是把问题稳定转化为可执行修复、
形成持续迭代闭环**；成熟体系要回答三类问题——评什么 / 怎么判 / **怎么用**。第三问恰恰是大多数
团队的断点：分数跑出来了，然后呢？其第 10 章的结论更直接：**评测体系的成败取决于它能否在
跨团队协作中长期、稳定地产生可执行行动项；低分必须稳定转成行动项，否则再精细的分数也只是报表。**

badcase 治理难在三个结构性事实（与第 E1 章的三大门槛一脉相承）：

| 难题 | 对 RCA 的直接后果 |
|---|---|
| 非确定性 | 同一输入不一定同输出，badcase 可能难以复现，必须先固化 Trace 再谈分析 |
| 黑盒化 | 内部决策不透明，不读模块 IO 就只能猜 |
| 错误级联放大 | 多步链路前一个小偏差被放大成错误结论——**最终答案错的地方，往往不是根因所在** |

第三条是 RCA 存在意义的核心：多模块流水线里，错误会沿链路向下传播。意图识别判错，后面 Query
改写、知识筛选、回复生成全部跟着错；只看最后一眼"回复不对"就去改生成层 prompt，等于给下游
背锅侠加药量，真正的病灶纹丝不动。

**第一个必须内化的区分：现象 ≠ 根因。** 评分层（第 E4 章的程序化评分与第 E5 章的 Judge）产出
的是**现象分类**：事实性错误 / 答非所问 / 过度承诺……阿里明确要求评分输出不止 pass/fail，还要
带**问题分类（现象层）/ 问题现象 / 置信度 / 判定依据**——这四样东西构成 RCA 的"现象入口"。
现象是症状，根因是病灶；同一种症状可能对应完全不同的病灶（同样是"事实性错误"，可能是检索召回
了过期文档，也可能是生成层没忠实使用证据），同一种病灶也可能表现为多种症状。RCA 的全部工作，
就是把现象翻译到根因：**哪个模块、什么失败类型、谁是 owner、怎么验收**。

### 2.2 Badcase 双通路入口与同一任务表

badcase 有两条入口通路，阿里要求它们**汇入同一 badcase 任务表与同一 RCA Pipeline**：

| 入口 | 具体来源 | 特点 |
|---|---|---|
| 离线评测集 | 回归失败、发布门禁不达标、能力集低分样本、Judge 低分 | 有完整评测运行 ID、可复现、期望行为已定义 |
| 线上 | 会话抽检、人工质检、投诉工单、低满意度反馈、版本回归失败、监控告警 | 真实分布、带业务后果，但证据散、需脱敏 |

"同一张表"不是管理洁癖，而是工程必需：

1. **口径统一**：离线与线上用同一套根因标签体系，才能回答"线上这类问题在离线集里有没有覆盖"——
   这正是第 E12 章 DoorDash"离线-线上同一 rubric + 同一校准 judge"原则在 badcase 侧的镜像。
2. **去重与聚类面向全量**：聚类永远面向任务表全量（历史 + 新增），只看今天这一批会低估问题簇
   的规模。lab09 的自检断言即如此：4 条新诊断 + 8 条历史记录合并聚成 4 个簇、合计 12 条。
3. **状态以持久化任务记录为准**：分析到哪一步、定责结论是什么、谁认领了修复，都以任务表字段为
   准，不依赖人的记忆和群聊记录。

任务表的落盘 schema（对应 lab09 `build_rca_record` 的输出字段）：

| 字段 | 含义 | 示例 |
|---|---|---|
| case_id / session_id | 案例与链路标识 | bc-004 / sess-bc004 |
| scenario / source | 业务场景 / 入口通路 | 退货退款 / 线上投诉工单 |
| issue_class | 问题分类（报告大类） | 工具执行 |
| symptom | 现象（评分层产出） | 跳过校验 |
| enumeration | 问题枚举（更细失败类型，即根因标签） | 关键工具未调用 |
| root_module / confidence / method | 责任模块 / 置信度 / 定责路径 | 回复生成 / 0.72 / llm_fallback |
| evidence / rationale | 逐模块证据枚举 / 定责理由 | 各模块 verdict + reason |
| prompt_version | 出事时的 Prompt 版本 | prompt_v2 |
| fix_suggestion | 结构化修复建议（含 owner） | 补回硬约束并全量回归，owner：算法需优化 |

两条纪律：

- **入库先脱敏**。线上会话含用户隐私，入库标准里"已脱敏合规"是硬条件（阿里）；Airbnb 的生产
  抽样同样要求人工评审前去标识化、用途限定于安全与质量（详见第 E3 章）。
- **入口本身要留痕**。`source` 字段决定了后续分析的一个关键问题：这个簇是"离线集早就该拦住"
  还是"线上才暴露的新分布"——前者问责评测集覆盖度，后者触发新用例补充。

### 2.3 RCA 五步总览：证据汇总与范围收敛

阿里 RCA 五步（本章主体）：

| 步骤 | 输入 | 输出 | 方法基调 |
|---|---|---|---|
| ① 证据汇总 | sessionId / chatId / traceId / 评测运行 ID | 该会话的完整模块 IO 链 | 纯工程：日志聚合、按 ts 重建 |
| ② 范围收敛 | 现象分类 + 场景 | 候选模块列表（2~3 个） | 映射表命中走确定性；未命中 LLM 兜底缩圈 |
| ③ 分模块诊断 | 候选模块的 input/output/prompt/工具返回/异常 | 每模块 verdict + 证据 + 摘要 | 规则检查为主，逐模块本地判定 |
| ④ 责任判定 | 现象 + 分模块诊断 + 根因知识库 | 责任模块 / 问题分类 / 枚举 / 修复建议 | 三层漏斗：严重 FAIL → 规则 → LLM |
| ⑤ 结构化落盘 | 以上全部 | 任务记录 + 看板渐进展示 | 结构化写入，供工单/看板消费 |

**第一步：证据汇总。** 按 sessionId/chatId/traceId/评测运行 ID 找链路日志，汇总用户输入、Agent
回复、模块 IO、prompt、工具调用、异常、耗时、中间产物。线上日志是多会话交错、乱序到达、混着
心跳与指标噪声的，聚合纪律是**只信时间戳、不信到达顺序**，噪声日志丢弃但计数。这一步成立的前
提是被测 Agent 有结构化 Trace——阿里与腾讯都强调 **Trace 输出是被测 Agent 的标准能力而非事后
补救**：稳定记录工具名、入参、返回值、时间戳、耗时、错误；结构化 trace 要求可解析、内容完整、
跨版本格式稳定（详见第 E7 章）。没有 trace 的 badcase，RCA 只能退化为"看最终回复猜"。

**第二步：范围收敛。** 为什么不直接对全模块做无差别分析？两个原因：**成本高**（每个模块都要
读 IO、跑检查、可能调 LLM）、**噪声大**（无关模块的 SOFT_PASS 会干扰判断）。阿里的做法是维护
一张"**问题现象 × 功能模块**"映射表：

| 问题现象 | 优先候选模块 |
|---|---|
| 答非所问 | 意图识别 / Query 改写 / 知识筛选 |
| 事实性错误 | FAQ 检索 / 知识检索 / 回复生成 |
| 过度承诺 | 风险拦截 / 回复生成 |
| 订单未澄清 | 槽位抽取 / 上下文判断 |
| 跳过校验 | 订单状态查询 / 回复生成（lab09 补充条目） |

三条使用纪律：

1. **命中走确定性路径，未命中 LLM 兜底缩圈**——映射表是经验沉淀，LLM 只处理表外的新现象；
2. **映射表只缩小候选，不直接定责**——定责永远发生在诊断之后，跳过诊断直接定责等于把"经验"
   当"证据"；
3. **候选要并入场景必需步骤**——lab09 的 `narrow_scope` 会把该场景的 REQUIRED_STEPS（如退款
   场景必须先查订单状态）并入候选，防止映射表漏掉关键工具。

### 2.4 分模块诊断：三态判定与责任传递

**诊断动作**：对候选模块逐个读 input / output / prompt / 工具返回 / 异常日志，每个检查器只回答
一个问题——"这个模块拿到它的输入后，尽到自己的职责了吗？"输出包括：问题摘要、关键证据、改进
建议、结构化归因字段。

**为什么是三态而不是二态？** 这是责任传递分析的基础：

| verdict | 含义 | 典型成因 |
|---|---|---|
| PASS | 本模块 IO 均正常 | 无 |
| SOFT_PASS | 基本通过但轻微瑕疵 | **模块自身逻辑没错，输出却有问题——通常是上游错误沿流水线传播** |
| FAIL | 本模块自身处理违反职责 | 本地错误（error）或必需步骤缺失（missing） |

若只有 PASS/FAIL，"上游错、下游跟着错"的链条上每个下游模块都会被判 FAIL，定责时只能和稀泥
"人人有份"；显式建模 SOFT_PASS，才能把"真凶"和"被牵连者"分开。lab09 的实现机制：按流水线
顺序检查，维护 `upstream_bad` 标记——一旦某模块 FAIL/SOFT_PASS，其后本应 PASS 的模块自动降级
为 SOFT_PASS 并注明"上游已出错，错误可能沿流水线向下传播"。

**案例演练：现象"事实性错误"**（阿里原文实例 + lab09 bc-002 的具体化）：

> 用户问"这款手机的电池容量是多少？"，Agent 答"3000mAh"，正确答案是 5000mAh。

诊断顺序是沿信息流逐段排查：

| 模块 | 检查问题 | 结果 |
|---|---|---|
| FAQ 检索 | 是否召回正确政策/参数 | SOFT_PASS（无命中或低分，回退知识检索，非本模块之错） |
| 知识检索 | 是否保留关键片段 | **FAIL：命中 K-1024 v1 过期文档（最新版为 v2，旧版写着 3000mAh）** |
| 回复生成 | 是否忠实使用证据 | SOFT_PASS：草稿忠实引用了召回片段——忠实本身没错，错在证据是脏的 |

前两段通过而回复仍错 → 回复生成 FAIL、前两模块 PASS/SOFT_PASS（原文口径）；lab09 进一步把
"忠实引用脏证据"判为 SOFT_PASS，责任归到链条最上游的知识检索。注意两个检查器设计细节：

- **本地检查只读本模块 IO**：知识筛选模块只要"筛选结果与自己拿到的意图自洽"即无本地错误——
  意图本身就是上游给的脏输入时，锅不在筛选；
- **启发式无法证伪时不下结论**：意图识别用主题关键词反推，命中唯一主题才敢判错，命中 0 个或
  多个主题宁可放过——诊断器误报会污染整条 RCA 的可信度。lab09 专门放了一条健康对照会话，
  断言"健康会话不允许出现 FAIL"。

另有一个运营信号值得注意（腾讯口径，同样适用于诊断器自身）：**通过率 0% 或 100% 通常是任务或
评分器坏了，不是模型弱**——诊断器长期全 PASS 或全 FAIL 时先怀疑诊断器（详见第 E6 章人工评估
的"诊断异常"场景）。

### 2.5 责任判定：三层漏斗与缺失型错误陷阱

责任判定层消费"**现象 + 分模块诊断 + 根因知识库**"，产出四个字段：**责任模块 / 问题分类
（报告大类）/ 问题枚举（更细失败类型）/ 修复建议**。报告大类按阿里的口径分为四类：
**语义理解 / 知识召回 / 工具执行 / 风险防控**。

核心是**三层策略**，设计逻辑是"越确定的方法越靠前"——它同时是一个成本漏斗：

| 层 | 策略 | 适用 | 置信度（lab09 口径） |
|---|---|---|---|
| 1 | **严重模块结论直接定责**（一票否决） | 关键防线模块 FAIL，后果不可逆（资损/合规） | 0.95 |
| 2 | **规则引擎匹配确定性模式** | 沿因果链归因到"最上游的非缺失型 FAIL" | 0.90 |
| 3 | **LLM 汇总复杂链路责任传递** | 缺失型错误、跨模块推理难题 | ≤0.72 |

**第 1 层**：风险拦截这类关键防线一旦 FAIL（检出过度承诺却放行），无需再分析——后果不可逆的
模块拥有一票否决权。**第 2 层**：按流水线顺序排序所有 FAIL，取**最靠前的非缺失型 FAIL** 为
责任模块，其后异常视为传播后果。**第 3 层**：剩下的 FAIL 全是缺失型（模块根本没执行），规则
无法处理，才交给 LLM。

阿里给出的确定性定位清单（第 1、2 层能覆盖的硬错误与过程偏差）：

| 手段 | 能定位的问题 |
|---|---|
| 规则定位硬错误 | 工具未调用 / 顺序违反 SOP / 参数缺失 / 报错未重试 / DB 状态未变 / 引用来源不存在 |
| Trace Scorer 定位过程偏差 | 计划与目标不一致 / 证据不足 / 工具返回被误读 / 上下文被覆盖 |
| 映射表缩圈 | 现象 → 候选模块（第 ② 步的延续） |
| LLM 辅助语义归类聚类 | "解释不完整 / 口径理解错 / 意图澄清不足"映射到既有分类，**避免同类拆散** |

**缺失型错误的归因陷阱（高频考点）**：工具没被调用，锅不在工具本身——模块根本没执行，定责给
它没有意义；要追问的是"**谁本应触发它却没有触发**"：是 Prompt 忘了写约束？是意图识别没给出
触发条件？还是编排层路由错了？阿里经典案例"已发货退款未查订单状态"的完整归因是：归"**工具
覆盖与执行**"大类、枚举"**关键工具未调用**"、责任模块 = 退款 Skill / 退款流程执行模块。lab09
的简化模块划分里，工具调用决策由 Prompt 驱动的回复生成层负责，于是第 3 层 LLM 兜底给出的结论
是：`prompt_v2` 移除了"退款前必须先查订单状态"的硬约束，属**提示词回归**，置信度 0.72
（低于规则层的 0.90——LLM 结论天然要打折扣）。

**漏斗的两条自检指标**（lab09 断言）：置信度必须随层级递减（0.95 > 0.90 > 0.72）；LLM 兜底
调用次数应远小于 badcase 总数（lab 中 4 条 case 只触发 1 次）。如果 LLM 兜底占比居高不下，
说明规则库没在沉淀——每次人审复核的新模式都应该回流成规则。

**LLM 兜底的输出纪律**：证据不足时给低置信结论并转人工，而不是硬猜（lab09 MockLLM 的兜底
输出 confidence=0.3 + "建议人工复核并补充根因知识库"）。这条纪律与第 E6 章的人工评分路由
完全一致：低置信进人工，人工结论再反哺机器。

### 2.6 结构化落盘：根因标签体系与问题簇

**第五步落盘**：把问题分类 / 现象 / 枚举 / 责任层 / 责任模块 / 置信度 / 详细报告 / 修复建议写入
任务记录，看板渐进展示（诊断中 → 已定责 → 已认领 → 修复中 → 待验收 → 已闭环）。落盘记录必须
可被工单系统 / 看板 / 配置平台 / 研发流水线**直接消费**——JSON 可往返、字段枚举化、无自由文本。

**根因标签体系是聚类与统计的齿轮**，阿里给出三条设计原则：

1. **稳定**：标签是枚举不是作文；同类问题永远落同一个标签，避免"解释不完整"和"回复不够
   详细"各算一类；
2. **可统计**：能按标签聚合出趋势（"知识召回类本月占比 38%，环比 +9pct"）；
3. **指向 owner 与处理动作**：标签可绑定解决角色，四类角色分工：

| owner 角色 | 含义 | 动作示例 |
|---|---|---|
| 运营可配置 | 改配置/知识库即可，不动代码 | 下线知识库过期版本文档、增补 FAQ |
| 算法需优化 | Prompt / 检索策略 / few-shot | 补回"先查订单状态"硬约束（prompt_v2 → v3） |
| 工程需修复 | 代码缺陷 / 防线缺失 | 将"确定性赔付承诺"加入拦截规则库、赔付转人工审批 |
| 业务需定口径 | 流程规范本身没定义 | "订单已发货 + 用户拒收 + 运费险 + 特殊类目"该走哪条流程 |

第四类最容易被忽视：有些 badcase 的根因不在系统，而在**业务规则从未被定义**——此时修复动作是
"业务先定口径"，再谈落地（第 E6 章人工评分的"定口径"场景同源）。

**问题簇：报告的最终形态不是 badcase 列表，而是少数几个主题。** 同根因 / 同场景 / 同工具 /
同知识点的失败自动聚成簇，阿里给出的标杆产出是：

> "退款已发货场景中，Agent **23 次**跳过订单状态校验，主要集中在 **v1.8 Prompt**。"

一句话同时回答了：什么场景、什么问题、多大规模、嫌疑版本。修复才能一次覆盖一批，而不是一条
一条打补丁。聚类键的选择有讲究：用 **(场景, 责任模块)** 而不是"用户问题文本相似度"——文本
相似的两条 case 完全可能是不同根因（都问退款，一条是工具没调、一条是知识库过期），反之亦然；
而根因标签恰好满足"稳定、可统计、指向 owner"。簇内还应统计**主导 Prompt 版本**（lab09 输出：
退货簇 5 次跳过校验，集中在 prompt_v2，4/5）——这是把"嫌疑版本"量化出来的关键一步。

DoorDash 从 rubric 侧给出了互为印证的实践：**rubric 标准天然是问题簇**——grounding 失败 /
缺替代品 / 糟糕叙述分开调查，失败列表就变成了按影响排序的主题列表；逐条看失败会"轶事驱动"
（最近、最惊奇的失败主导修复决策），必须靠聚类对抗这种注意力偏差。

### 2.7 RCA 的工程实现：异步 Multi-Agent Workflow 与人审兜底

阿里把**单次 badcase 分析建模为一个异步 Multi-Agent Workflow**：证据汇总、范围收敛、分模块
诊断、责任判定各是一个节点，任务状态持久化在任务表里，失败可重试、可中断续跑。选异步的原因
很实在：线上 badcase 是持续流入的（每天若干条到上百条），同步阻塞既无必要也扛不住峰值。

Workflow 内部同样遵循"**确定性优先、模型辅助、人审兜底**"的总原则（与第 E4 章评分三层、
第 E5 章 Judge 治理一脉相承）：

```
规则定位硬错误（毫秒级，置信度最高）
   └─► Trace Scorer 定位过程偏差（秒级）
          └─► 映射表缩圈 + LLM 语义归类（API 成本，有抖动）
                 └─► 高风险 / 低置信 / 结论冲突 → 人工复核（分钟级，终判）
```

**人审兜底的三个触发条件**：高风险场景（资损/合规/隐私，即使自动定责置信度高也要复核）、
低置信结论（LLM 兜底输出 confidence 低于阈值）、规则与 LLM 结论冲突。**人工结论不是用完即弃，
而是三类反校准的原料**：反校准规则库（新模式沉淀为新规则）、反校准 Judge Prompt（定责提示词
迭代）、反校准根因标签（发现标签缺口或标签漂移）。这样 LLM 兜底占比会随时间下降，系统越用
越便宜、越用越确定。

**RCA 系统自己也会出错**，需要像对待被测系统一样对待它：

| 失效模式 | 治理手段 |
|---|---|
| LLM 兜底"胡说" | 低置信强制转人工；兜底输出必须给 rationale 供复核 |
| 映射表过时（新现象命中旧映射） | 未命中走 LLM 缩圈；定期用人工复核样本回测映射表命中率 |
| 诊断器误报 | 健康对照会话断言"不允许出现 FAIL"；0%/100% 异常先怀疑诊断器 |
| badcase 其实是评测系统误报 | 定责层保留"未发现任何 FAIL，可能不是系统错误"分支（lab09 layer 0） |

最后一条尤其重要：DoorDash 的 Lesson Learned 第 4 条明确，**被标记失败中有真实一部分是 harness
自身故障（judge 误报、trace 缺口），要并行修复才可信**。所以根因标签库里应当有"评测/质检误报"
这一类——RCA 不只给被测系统看病，也给评测系统看病。

工程上建议额外跟踪四个 RCA 自身的质量指标（本章归纳）：定责一致率（与人工复核抽样对齐，
参照第 E5 章 ~85% 的 judge 校准线）、LLM 兜底占比（应单调下降）、簇平均规模（越大说明修复
杠杆越高）、行动项转化率（badcase 变成已验收修复的比例——第 2.1 节"低分必须稳定转成行动项"
的直接度量）。

### 2.8 从原因到动作：结构化行动项与全链路闭环

**阿里的第 8 章（自动优化建议）给修复建议定了红线**：不能停留在"优化 Prompt / 加强训练 /
提升准确率"这类泛化建议——要明确**失败范围、证据、具体动作、owner、验收方式、优先级**；产出
**结构化行动项**，能被工单系统 / 看板 / 配置平台 / 研发流水线直接消费（原文口径："建议是质量
工程里的标准任务对象"）。每个建议要能**展开证据链**；不同根因对应不同优化手段，原文提出可分
四个等级（未展开细节，工程落地常与 2.6 的 owner 四分类对齐）。

以 lab09 的退款案例为例，一条合格的行动项长这样：

| 字段 | 内容 |
|---|---|
| 失败范围 | 退货退款场景"已发货"分支；线上投诉工单 + 离线回归共 5 例（任务表全量） |
| 证据链 | ① 回复草稿直接承诺退款 → ② trace 中无订单状态查询 span（kind=missing）→ ③ 知识库 K-2019 v3 明文要求"退款前必须先确认订单状态" → ④ prompt_v2 相比 v1 丢失该硬约束 |
| 具体动作 | 回复生成 Prompt 补回硬约束：退款请求必须先调用订单状态查询（prompt_v2 → prompt_v3） |
| owner | 算法需优化 |
| 验收方式 | 该场景全量回归通过；"跳过校验"簇清零；退款回归集无新增失败 |
| 优先级 | P0（资损风险，已发货直接退款会造成货损） |

优先级判定可借用 EDDOps（arXiv 2411.13768）的"**最小有效变更优先**"原则：先改 prompt / 路由 /
护栏，再动架构 / 工具契约 / 模型——变更面越小，回归验证越便宜，责任也越清晰。

**行动项的验收不是"改完了"，而是三层证明**：

1. **离线证明**：新增用例（这条 badcase 本身转化而来）通过 + 既有回归集不回归。腾讯的标准路径：
   复现记录完整轨迹 → 分析根因定预期行为 → 修复 → 纳入用例集防回归 → 进能力集，稳定后毕业到
   回归集；Anthropic 的口径（腾讯转引）：确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%
   （详见第 E10 章）。
2. **线上证明**：修复上线后观察三类信号——离线质量信号、线上体验信号（转人工率、重复追问率、
   投诉率、满意度）、业务结果信号（任务完成率、工单闭环率、退款成功率）；DoorDash 的 reasoning
   leakage 案例是范本：线上评分发现泄漏 → 修 prompt → 用生产中**最易触发的场景**离线验证
   （泄漏率降 11%）→ hero 场景全量扫描无回归 → 上线后监控确认阶跃改善（详见第 E12 章）。
3. **簇级证明**：该问题簇的规模归零或降到噪声水平——单条 case 通过不代表簇被消灭。

**反馈生产：一条 badcase 至少生产 3 类反馈。** 阿里的第 9 章把闭环拆成三条生产线：

| 生产线 | 产出 | 去向 |
|---|---|---|
| 评测集线 | 新用例（badcase 本体 + 同簇变体） | 能力集 → 毕业后回归集（只增不减） |
| 训练数据线 | 修复前后轨迹构成的偏好对 / 正确示范 | SFT / 偏好优化（详见第 E12 章数据飞轮） |
| 知识修订线 | 过期文档下线、知识点增补、口径澄清 | 知识库 / 配置平台（owner：运营可配置） |

入库标准五条（阿里）：**失败可复现**（或至少有稳定 Trace + 人工确认）；**期望行为明确**
（可写成规则 / Judge 标准 / 人工验收标准）；**根因标签清楚**（归到具体能力域或业务流程）；
**样本有代表性**（覆盖一类问题而非一次性环境抖动）；**已脱敏合规**。配套样本治理：同簇保留
代表例（防止簇膨胀淹没重点）；P0/P1 风险长期保留；稳定多版本通过且低风险者降级为抽样集；
新分布出现时主动学习优先抽取低置信 / 高影响 / 新意图 / 新工具 / 新知识点样本进人工确认。

**终局是质量资产库**：用例库、Trace 库、根因标签库、修复建议库、Judge 校准集、回归集。
阿里的原话是："**质量资产越厚，Agent 迭代越不靠个人经验和临时救火。**"

最后看一个"闭环 agent 化"的前沿样本——DoorDash 的反馈闭环：失败按 rubric 标准聚类成主题 →
**coding agent 检查失败 trace、相关代码路径、近期变更、历史调查** → 修复明确时**直接起草 PR**，
prompt/上下文学习类改动则产出诊断 + 建议供人审 → 整套 eval-driven 工作流（聚类失败、调查失败
模式）打包成 **Agent Skills**，可重复、可复用、可改进；skill 分错簇或写出弱修复时，**更新 skill
而非打补丁一次性运行**。DoorDash 对此的定位值得背诵：harness 不只是记分板，是**迭代的控制面
（control plane for iteration）**——生产监控 + 失败聚类 + agent 辅助调查 + 发布前验证连成一环。

## 四、经典面试题与参考答案

#### 题 1（基础）：评分层把一条 case 标成"事实性错误"，这是根因吗？评分输出除了 pass/fail 还应提供什么？

**参考答案：** 不是。"事实性错误"是**现象分类**（症状），不是根因（病灶）——同为事实性错误，
可能是知识检索召回了过期文档，也可能是回复生成没有忠实使用证据，修复动作完全不同。阿里明确
要求评分输出不止 pass/fail，还要带四样东西：**问题分类（现象层）、问题现象、置信度、判定依据**，
它们构成 RCA 的"现象入口"。现象分类 ≠ 最终根因，RCA 的任务就是把现象翻译到根因：哪个模块、
什么失败类型、谁是 owner。

#### 题 2（基础）：请复述 Badcase RCA 的五步流程，每步的输入、输出与一条关键纪律。

**参考答案：** 阿里口径：① **证据汇总**：按 sessionId/chatId/traceId/评测运行 ID 聚合链路日志
（用户输入、Agent 回复、模块 IO、prompt、工具调用、异常、耗时、中间产物）；纪律：状态以持久化
任务记录为准，只信时间戳不信到达顺序。② **范围收敛**：用"问题现象 × 功能模块"映射表缩到
2~3 个候选模块（答非所问→意图识别/Query 改写/知识筛选等）；纪律：**映射表只缩小候选，不直接
定责**，命中走确定性路径、未命中 LLM 兜底缩圈。③ **分模块诊断**：逐模块读 IO/prompt/工具返回，
输出 PASS/SOFT_PASS/FAIL 与证据；纪律：本地检查只读本模块 IO，上游错误显式传播为 SOFT_PASS。
④ **责任判定**：消费"现象 + 诊断 + 根因知识库"，三层漏斗定责并输出问题分类/枚举/修复建议。
⑤ **结构化落盘**：写入任务记录（分类/现象/枚举/责任层/责任模块/置信度/报告/建议），看板渐进
展示，供工单系统直接消费。

#### 题 3（进阶）：为什么要做"范围收敛"？映射表命中后能直接定责吗？

**参考答案：** 不能。全模块无差别分析有两个代价：**成本高**（每模块都要读 IO 跑检查，LLM 诊断
还有 API 费用）与**噪声大**（无关模块的 SOFT_PASS 会干扰判断，把定责带偏）。映射表把候选缩到
2~3 个模块，但**它只缩小候选、不直接定责**，原因有三：① 映射是经验先验，不是证据——同一现象
在不同 case 里根因可能完全不同；② 跳过诊断直接定责，就失去了"证据链"，修复无法验收、人审
无法复核；③ 映射表会过时，新现象可能命中旧映射。正确流程：映射表缩圈 → 候选模块逐个诊断 →
诊断之后才定责；未命中映射表时退化为 LLM 兜底缩圈。另外工程上建议把场景必需步骤（如退款必查
订单状态）并入候选，防止映射表漏掉关键工具。

#### 题 4（进阶）：为什么分模块诊断要用 PASS/SOFT_PASS/FAIL 三态而不是二态？举个"责任传递"的例子。

**参考答案：** 二态无法区分"本地错误"与"上游传播"。多模块流水线里错误会向下传播：意图识别
把退货问题误判成物流查询，Query 改写、知识筛选、FAQ 检索会一路跟着错——若只有 PASS/FAIL，
四个模块全 FAIL，定责只能"人人有份"，修复变成四处打补丁。三态下：意图识别 FAIL（真凶），
后续模块本地逻辑没错但输出受污染 → SOFT_PASS（被牵连者），定责沿因果链归到最上游的
非缺失型 FAIL。再如知识检索召回过期文档（FAIL），回复生成忠实引用了脏证据——忠实本身没错，
判 SOFT_PASS，责任归知识检索而非生成层。SOFT_PASS 是"责任传递"分析的基础，也是修复只改一处
就能覆盖一批 badcase 的依据。

#### 题 5（进阶）：退款场景 SOP 要求先查订单状态，但 trace 里这个工具从未被调用。锅该算谁头上？RCA 系统如何保证不背错锅？

**参考答案：** 这是**缺失型错误**：模块根本没执行，定责给未执行的模块本身没有意义——要追问
"**谁本应触发它却没有触发**"。候选解释：Prompt 忘了写硬约束（提示词回归）、意图识别没给出
触发条件、编排层路由错误、或工具本身不可用。区分它们要补证据：对比 prompt 版本 diff（lab09
案例中 prompt_v2 移除了"退款前必须先查订单状态"约束 → 提示词回归）、检查意图输出是否正确、
查工具注册与健康状态。阿里该案例的归因：大类"工具覆盖与执行"、枚举"关键工具未调用"、
责任模块 = 退款 Skill/退款流程执行模块。在三层定责漏斗中，缺失型错误规则层处理不了（没有
"最上游非缺失型 FAIL"可归），落在第 3 层由 LLM 做跨模块推理，置信度低于规则层（lab09：
0.72 < 0.90），低置信转人工复核。

#### 题 6（进阶）：如何设计一套根因标签体系？问题簇的聚类键为什么选 (场景, 责任模块) 而不是用户问题文本相似度？

**参考答案：** 标签三原则（阿里）：**稳定**（枚举不是自由文本，同类问题永远落同一标签，靠 LLM
归类时要把"解释不完整/口径理解错"映射到既有分类，避免同类拆散）；**可统计**（能聚合成趋势
看占比与环比）；**指向 owner 与处理动作**（绑定四类解决角色：运营可配置/算法需优化/工程需
修复/业务需定口径）。聚类键选 (场景, 责任模块) 的原因：文本相似的两条 case 完全可能根因不同
（都问退款，一条是工具没调、一条是知识库过期），文本不同的也可能同根因——文本相似度度量的是
"表面像不像"，根因标签度量的才是"修起来是不是同一件事"。簇内再统计主导 Prompt 版本，产出
"退款已发货场景 23 次跳过订单状态校验，集中在 v1.8 Prompt"这类可直接驱动修复决策的结论。

#### 题 7（进阶）：为什么"优化 Prompt、提升准确率"这种修复建议不可接受？给出你的行动项结构。

**参考答案：** 它不可执行、不可验收、无 owner：改哪个 prompt 的哪一句？改完怎么证明？谁来改？
阿里第 8 章的红线：建议必须明确**失败范围、证据、具体动作、owner、验收方式、优先级**，产出
结构化行动项，能被工单系统/看板/配置平台/研发流水线直接消费——"建议是质量工程里的标准任务
对象"。示例（退款案例）：失败范围 = 退货退款"已发货"分支、全量 5 例；证据链 = 草稿直接承诺
退款 → trace 无订单状态查询 span → 知识库明文要求先查状态 → prompt_v2 丢失该约束；动作 =
v2→v3 补回硬约束；owner = 算法需优化；验收 = 该场景全量回归通过且簇清零、回归集无新增失败；
优先级 = P0（资损）。每个建议可展开证据链，优先级按"最小有效变更优先"（EDDOps：先 prompt/
路由/护栏，再架构/模型）。

#### 题 8（进阶）：RCA 系统自己也会出错——LLM 兜底胡说、映射表过时、甚至 badcase 本来就是评测误报。你怎么保证 RCA 结论可信？

**参考答案：** 四道防线：① **确定性优先的漏斗结构**——能用规则定的绝不用 LLM；LLM 兜底占比
应随规则沉淀单调下降，占比不降说明人审结论没回流。② **置信度显式分层 + 低置信强制人审**——
严重 FAIL 0.95、规则 0.90、LLM ≤0.72（lab09 口径）；高风险场景（资损/合规）即使高置信也复核；
LLM 证据不足时输出低置信转人工，不硬猜。③ **人审结论三类反校准**——反校准规则库（新模式变新
规则）、反校准定责 Prompt、反校准根因标签（补标签缺口）；并像校准 judge 一样定期抽样对齐定责
一致率（参照 ~85% 校准线）。④ **给评测系统留出口**——定责层保留"未发现任何 FAIL，可能不是
系统错误"分支，根因库里设"评测/质检误报"类：DoorDash 明确被标记失败中有真实一部分是 harness
自身故障（judge 误报、trace 缺口），并行修复才可信。另外用健康对照会话断言诊断器不误报。

#### 题 9（系统设计）：为一个日均万级会话的客服 Agent 设计 badcase RCA 与优化闭环平台。

**参考答案：** 分六层：
**① 入口层**：离线（回归失败/门禁不达标/Judge 低分）+ 线上（会话抽检/人工质检/投诉工单/低
满意度/监控告警）双通路汇入同一任务表；入库五标准过滤（可复现/期望明确/根因标签清楚/有
代表性/已脱敏）。
**② 证据层**：全量结构化 Trace（工具名/入参/返回/时间戳/耗时/错误 + prompt 版本），按
sessionId 聚合、按 ts 重建，噪声计数。
**③ 分析层**：每条 badcase 一个异步 Multi-Agent Workflow 跑五步——映射表缩圈（命中走确定性、
未命中 LLM 兜底）→ 候选模块三态诊断 → 三层漏斗定责（严重 FAIL 一票否决/规则因果链/LLM 缺失型
归因）。
**④ 聚类层**：全量任务表按 (场景, 责任模块) 聚簇，输出主导版本与规模，按影响排序——报告只讲
主题不讲轶事。
**⑤ 行动层**：每簇生成结构化行动项（范围/证据链/动作/owner 四分类/验收/优先级），工单系统消费；
人审兜底低置信与高风险，结论反校准规则库与标签库。
**⑥ 闭环层**：反馈生产三条线——评测集线（badcase 转用例，能力集毕业进回归集，只增不减）、
训练数据线（修复前后轨迹做偏好对）、知识修订线（过期文档下线）；验收三层证明（离线回归 +
线上三类信号 + 簇级清零）；沉淀用例库/Trace 库/根因标签库/修复建议库/Judge 校准集/回归集。
度量 RCA 自身：定责一致率、LLM 兜底占比、行动项转化率。

## 五、易错点 · 反直觉点

1. **把现象当根因**：看到"答非所问"就去改生成层 prompt。→ 真相：现象是症状，"答非所问"
   的根因常在意图识别/Query 改写/知识筛选，改生成层是给被牵连者加药量。→ **记忆锚点：先翻译，
   再开药。**
2. **全模块无差别分析**：每条 badcase 把八个模块全查一遍。→ 真相：成本高且噪声大，无关模块的
   SOFT_PASS 会干扰定责；映射表缩到 2~3 个候选是标准做法。→ **记忆锚点：先缩圈，再尸检。**
3. **映射表命中直接定责**：跳过诊断直接写结论。→ 真相：映射是先验不是证据，只缩小候选；定责
   永远发生在诊断之后，否则修复没有证据链、无法验收。→ **记忆锚点：映射表是导航，不是法官。**
4. **缺失型错误甩锅给缺失的模块**："订单状态查询没执行 → 订单状态查询模块的锅"。→ 真相：模块
   没执行就定责给它没有意义，要问"谁本应触发它却没有触发"（Prompt/编排/意图）。→ **记忆锚点：
   没上场的人不背锅。**
5. **多模块同时 FAIL 就"人人有份"**：二态判定下四处打补丁。→ 真相：缺了 SOFT_PASS 就无法区分
   真凶与被牵连者；沿因果链归因到最上游的非缺失型 FAIL，一处修复覆盖整条传播链。→ **记忆锚点：
   上游一个因，下游一片果。**
6. **按用户问题文本相似度聚类**：以为问法相似就是同一类问题。→ 真相：文本相似根因可以完全不同；
   聚类键用 (场景, 责任模块) 才能对齐"修起来是不是同一件事"。→ **记忆锚点：按病灶聚类，不按口音
   聚类。**
7. **修复建议停在"优化 Prompt"**：无范围、无证据、无 owner、无验收。→ 真相：这种建议不可执行也
   不可验收，等于没分析；行动项必须是能被工单系统消费的标准任务对象。→ **记忆锚点：没有验收方式
   的建议只是感想。**
8. **RCA 全程交给 LLM**：每条 case 直接丢给大模型写归因报告。→ 真相：成本爆炸、置信度无分层、
   结论不可复核；正确结构是确定性优先、模型辅助、人审兜底，LLM 只处理规则搞不定的长尾且占比应
   持续下降。→ **记忆锚点：规则在前，模型在后，人工兜底。**
9. **修完就完，不回流**：badcase 修好就关闭工单。→ 真相：不回评测集，同类问题换个表述还会再来；
   一条 badcase 至少要生产三类资产（评测集/训练数据/知识修订），并进回归集只增不减。→ **记忆锚点：
   不回流不闭环。**
10. **根因标签自由发挥**：每次定责写一句话感想。→ 真相：自由文本不可统计、不可聚类、指不了
    owner；标签必须枚举化、稳定、绑定解决角色（运营/算法/工程/业务）。→ **记忆锚点：标签是枚举，
    不是作文。**

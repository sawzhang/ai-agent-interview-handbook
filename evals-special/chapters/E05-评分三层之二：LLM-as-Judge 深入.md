# 第 E05 章 · 评分三层之二：LLM-as-Judge 深入

> 一句话导读：规则判不了的（语气、有据性、策略合理性），交给 LLM Judge；但**裁判本身是一台未经校验就会漂移的测量仪器**。本章讲透：judge 的解剖结构（rubric + 证据切片 + verdict + rationale）、rubric 工程（二元检查 / eligibility 前置 / "描述成功长什么样"）、四大偏差的机理-量化-缓解全表、Airbnb 式五步校准闭环（78%→88% 实战）、阿里"三统计"持续运营、JudgeBench 揭示的"高一致≠正确"、以及 2024-2026 可训练 judge 与 judge 攻防前沿。学完本章，你能独立搭建、校准、运营一个可进门禁的 judge 子系统，并在面试中回答"裁判可信吗"这个 evals 最核心的问题。

## 二、核心概念精讲

### 2.1 定位：Judge 是「测量仪器」，不是「打分捷径」

**为什么需要这一层。** 阿里对评分分工的总纲是：**规则看"硬条件"（工具、状态、字段、禁用动作），LLM 看"语义/策略合理性"**。第 E04 章已经说明规则永远判不了语义正确性、语气、策略合理性——这些"未知软指标"正是腾讯三类评分器对照表中 Rubric 评分器的覆盖区：大模型（固定版本）按写在 Prompt + JSON Schema 里的规则打分，秒级出结果、付 API 费用、稳定性"有抖动（需降噪）"、做分级门禁（error 硬 / warning 软）。

**Judge 解决的是规模化判断问题。** DoorDash 在构建 Ask DoorDash 评测体系时，把"规模化判断"列为五大挑战之一：**"是否帮到用户需要人类级判断，但人工不可扩展"**，解法就是"校准过的 LLM judge 顶替人类评审"。他们给出的量级对比（原文数字）：员工反馈平均只有 **1 条/天**，而评测体系做到 **2,000 个/天自动评分会话**；全国上线前 agent 质量分 **+8 分**、错误率**近乎减半**；全量回归从手工 **6+ 小时**压到自动**约 20 分钟**。没有 judge，这个反馈密度根本不可能存在。

**但 judge 的定位必须摆正：它是一个带紧反馈环的测量问题。** DoorDash 的原话是两条：

1. "LLM Judge only useful if it agrees with human reviewers."（judge 只有与人工评审一致时才有用）
2. 人工用在杠杆最大处：**定 rubric、标注校准集、审计 judge 行为**；打分主力才是 judge。

换个说法：**judge 是评测管线里最核心的"测量仪器"，仪器本身需要校准（元评估）、需要防作弊（鲁棒性测试）、需要版本管理（prompt + 模型 + 参数）——否则整个评测体系建立在一个未被校验的传感器上**（_research/01-llm-judge.md 调研结论）。Airbnb 对未校准 judge 的判词只有八个字：**"未校准 judge 会制造误导性信心"**——分数看起来很精确，量出来的却是 rubric 的缺陷。

**引入 judge 之前，先回答三个问题（决策表）：**

| 问题 | 是 | 否 |
|---|---|---|
| 这条检查能写成代码断言吗（schema/关键词/工具调用/预算）？ | 写成规则，不用 judge（第 E04 章） | 继续问下一行 |
| 人能否对这条标准给出一致的判断？ | 写 rubric，进 judge 校准流程 | 先停下：人都判不一致，说明标准未定义清楚（找业务定口径，第 E06 章） |
| 该判断是否依赖内部政策口径（赔付规则、合规红线）？ | 人工定口径 → 能规则化就规则化，不能则 judge + 人工复核双轨 | judge 独立承担，按本章流程校准与运营 |

**一笔经济学账。** DoorDash 全量回归 sweep = **50 场景 × 8 trials = 400 次对话**：人工本地聊约 1 分钟/次 → **6+ 小时**；模拟器 + judge 约 **20 分钟**。按每次变更都跑一遍、每周数次变更计算，judge 化评测把迭代周期从"天"压到"小时"——这正是"评测是迭代指南针"（第 E01 章）能成立的前提。反过来说：**如果你的 judge 未经校准，你只是用 20 分钟拿到了一份错误的报告，然后更快地把事情做坏。**

这一节的结论：**引入 judge 的门槛很低（写个 prompt 就行），但让 judge 可信的门槛很高（校准 + 运营 + 元评估）**。本章剩下七节全部在讲后半句。

### 2.2 Judge 的解剖：rubric + 证据切片 + verdict + rationale

一个生产级 judge 的调用接口由四部分组成。Airbnb 给出的五条纪律与 DoorDash 的接口设计互相印证：

**Airbnb 的 judge 使用规则（原文）：**

| # | 规则 | 工程含义 |
|---|---|---|
| 1 | **每个质量维度一个 judge** | 不要万能 judge；groundedness、语气、简洁性各配一个，互不污染。配套原则：judge 要少而精——**3-5 个经校准的评估器好过一堆嘈杂的评估器**（EDD 五原则之三） |
| 2 | **judge 模型尽量与生成模型不同** | 防自我偏好（实证见 2.4；GPT-4 对自己输出的识别率约 72%，2404.13076） |
| 3 | **带 few-shot** | 示例中必须含边界样本（阿里补充：few-shot 含边界样本与判定 CoT） |
| 4 | **强制输出 schema** | JSON 结构化输出，verdict 与 rationale 分字段，下游可解析、可统计 |
| 5 | **清晰打分说明** | 每分档有可执行标准（阿里），不允许"凭感觉给分" |

**DoorDash 的 judge 接口（逐条标准独立评分）：**

- **输入 = 标准 + 该标准依赖的证据**。注意不是"整条 trace 扔给 judge"：每条标准声明自己依赖哪片证据，Transcript Builder 只把那一片交给 judge（详见第 E07 章 · 轨迹与 Agent 级评估）。例如 grounding 检查只拿"agent 的论断 + 背后工具输出"；多样性检查只拿"推荐结果 + 原始请求"；叙述检查只拿 agent 工作时流式输出的文本。**聚焦证据让判断更一致**，也避免无关 trace 噪声干扰判决。
- **输出 = verdict + 简短 rationale**。

把两边合成一个可直接照抄的 judge prompt 骨架：

```text
[system]
你是严格的评估器。只评判下面这【一条】标准，不要顺带评价任何其他质量。
先判断该标准是否适用于本会话（eligibility）；不适用则 applicable=false 并结束。

[user]
## 标准（rubric，单条）
{criterion_text}
## 判 1 分当且仅当
{positive_desc}          # 描述"成功长什么样"
## 判 0 分当且仅当
{negative_desc}          # 枚举典型失败现象
## Few-shot（含边界样本与判定思路）
{examples}
## 证据（仅该标准依赖的 trace 切片）
{evidence_slice}
## 输出（严格 JSON，禁止其他文本）
{"applicable": bool, "verdict": 0|1, "confidence": 0.0~1.0,
 "rationale": "引用证据中的原文说明判定依据，≤80 字"}
```

**输出侧的规范**与第 E04 章程序化评分的五元组同构：rationale 不止是"解释"，它承担三个职能——① 定位（错在哪一片证据上）；② badcase 聚类（阿里：输出 reason 用于定位与聚类）；③ 审计（人工复核 judge 行为时读的就是 rationale）。阿里进一步要求：**每分档有可执行标准；输出 reason；高风险/抽检/低置信场景的 judge 结论要带置信度**，置信度低的进人工路由（详见第 E06 章 · 人工评估与评分路由）。腾讯的 rubric 评分器输出则是典型的结构化样例：`observation_points`（回答是否基于项目规范而非通用知识 / 推理是否清晰连贯 / 有无幻觉编造）+ `scoring`（process_score 0-100、result_score 0-100、is_false_positive bool）。

**为什么要 rationale 先行、分数随后？** 这与 GenRM（2408.15240，2024）揭示的规律一致：把评分做成"先写判据、再给结论"的生成任务，比裸打分更稳健、更可审计，还能继承模型的推理能力。工程上记住一条：**没有 rationale 的分数不可 debug，也不可被人工审计**。

一次完整调用的样例（DoorDash guardrail 风格）——注意 judge 只拿到该标准声明的那片证据：

```text
输入：
  标准：沟通质量——回复简洁，不向用户叙述思维过程。
  证据切片：agent 面向用户的全部回复文本（不含内部工具调用）。
判定：
  {"applicable": true, "verdict": 0, "confidence": 0.92,
   "rationale": "第 2 轮回复中出现『我先去查一下 reorder skill 的返回』，
                 向用户叙述了内部执行过程，命中判 0 条件。",
   "问题分类": "叙述泄漏", "置信度": 0.92}
```

其中 `问题分类`/`置信度` 与第 E04 章程序化评分的输出规范同构——三层评分共用一套输出契约，下游的 RCA 流水线（第 E11 章）才能无差别消费。上例的"叙述泄漏"正是 DoorDash 实战案例 1（reasoning leakage）中被日常线上评分捕获的失败模式。

### 2.3 Rubric 工程：描述「成功长什么样」

Rubric 是 judge 的"法律条文"，其质量决定 judge 的上限。四个关键设计决策：

**（1）二元检查 vs 分级打分**

| 维度 | 二元检查（binary check） | 分级打分（1-5 / 0-100） |
|---|---|---|
| 输出 | 0/1 + rationale | 分档分数 + rationale |
| 方差 | 低，判定边界清晰 | 高，"3 分还是 4 分"人都会摇摆 |
| 汇总 | 逐条 binary 汇总为会话级总分（DoorDash） | 加权平均，权重本身是争议源 |
| 迭代 | 每条标准独立可改、可单独校准 | 改一档描述牵动全量表 |
| 适用 | 行为合规、约束满足、事实核对 | 创意质量、体验类细粒度观察 |

DoorDash 的选择很明确：**每条标准是 binary check，汇总为会话级总分**。其 guardrail 与 capability 标准实例（原文）：

- Guardrail（全体 agent 适用）："沟通质量：回复简洁、不向用户叙述思维过程"；"信任与诚实：不呈现可证伪虚假信息"。
- Capability·餐厅发现："约束满足：推荐满足配送时间/预算/饮食限制"；"结果多样性：真实差异而非近似重复"。
- Capability·杂货购物："购物执行：用户的明确修改请求被执行"；"商品相关性"。

**（2）checklist 式场景 rubric：低方差信号。** DoorDash 的离线评测进一步把标准写成场景级清单。例："两人份 ≤$60 素食 taco 购物清单"——验证**每件商品都是素食 taco 原料、小计 ≤$60**。这种 checklist 比宽泛通用标准**方差更低，小样本更有用，支撑更快迭代**（详见第 E08 章 · 对话 Agent 与仿真评测）。

**（3）eligibility 适用性前置。** DoorDash 的独创设计：**judge 先判该标准是否适用本会话，不适用则跳过**——例如"复购流程"标准不会因为一个食谱会话缺少复购步骤而被扣分。这就是 2.2 骨架中 `applicable` 字段的来源。不做 eligibility 的后果：总分被一堆"不适用但判了 0"的标准拖低，且拖低幅度随会话类型漂移，分数彻底失去可比性。

**（4）描述成功，而非指定唯一答案。** DoorDash 对开放式目标的 rubric 要求（原文）：**"具体到每次能同样判，宽泛到容纳所有合法路径"**。rubric 写"推荐满足配送时间/预算/饮食限制"，而不是"必须推荐那三家店"——前者判的是约束，后者背的是答案（对照第 E04 章"不要强制固定调用序列"的同一思想）。

**一条铁律。** Airbnb 的原话值得裱起来：**"如果人都无法一致地应用 rubric，模型也不可能。"** rubric 写得含糊（"回答要好"），人标不一致，此时不是 judge 不行，是标准不行——先停下修 rubric，再谈校准（人工分歧处理详见第 E06 章）。

**完整 rubric 实例（Airbnb 房源 listing 解释可读性，判 0/1）：**

```text
标准：listing 解释文本的可读性与语气
判 1 分：输出读起来像一位「热情专业的旅行顾问」——
        语气友好、信息以旅客视角组织、措辞自然。
判 0 分（命中任一即 0）：
  - 语气错误（冷淡、机械、公文腔）
  - 出现内部术语（系统字段名、业务黑话）
  - 格式差（整块无排版、乱用符号）
  - 语法问题
  - 措辞过繁（堆砌形容词、信息密度低）
输出：reason（引用原文指出命中项）+ 0/1
```

注意这个实例同时示范了三件事：**正向描述"成功长什么样"（热情专业的旅行顾问）+ 负向枚举可观察的失败现象 + 强制输出 reason**。阿里对 rubric 的补充要求是"**每分档有可执行标准**"——即每个分数档都要像上面"判 0 分"列表一样落到可观察、可引用的现象，而不是形容词。

**Rubric 好坏对照（评审 rubric 时逐行过一遍）：**

| 维度 | 坏 rubric | 好 rubric | 原因 |
|---|---|---|---|
| 可观察现象 | "回答要专业" | "不出现内部术语、不出现系统字段名" | 前者两人打不出同一个分；后者命中与否可引用原文 |
| 容纳合法路径 | "必须推荐宫保鸡丁" | "推荐满足预算 ≤¥100 且不含用户忌口食材" | 前者背答案、惩罚合法变体；后者判约束不判路径（DoorDash："具体到每次能同样判，宽泛到容纳所有合法路径"） |
| 适用边界 | 所有会话一律评"复购引导" | eligibility 前置：不适用则跳过 | 否则不适用场景被系统性扣分，总分随会话类型漂移 |
| 分档锚定 | 1-5 分但只写"5=最好" | 每分档列可执行标准与示例（Airbnb 0/1 实例的写法） | 无锚定的分级打分方差大到人都会摇摆 |
| 证据声明 | 把整条 trace 扔给 judge | 标准声明依赖的证据，只交那一片 | 无关噪声降低判决一致性（DoorDash Transcript Builder） |

### 2.4 Judge 偏差全景：四大偏差的机理、量化与缓解

Judge 是模型，模型就有偏好。2023-2026 的研究把偏差从" anecdote"变成了可量化的测量学问题。四大偏差总表（全部数字来自 _research/01-llm-judge.md）：

| 偏差 | 机理 | 量化方式 | 缓解手段 | 关键论文（arxiv，年份） |
|---|---|---|---|---|
| **位置偏差** | 成对评判中偏好出现在特定位置（常为第一个）的候选 | **swap consistency**：交换 A/B 位置前后判决的一致率；等质量对照组的胜率偏离 50% 的幅度 | 双向交换取平均（成本 ×2）；句级对齐 Split and Merge：拆句→语义对齐→逐单元比较 | 2305.17926（2023）首次系统证明 LLM 不是公平评估器；2310.01432（2023） |
| **冗长偏差** | 把"更长"当成"更好"，模型可通过写更长刷分 | 把长度作为协变量回归 `logit(P(win)) = α·质量 + β·长度`，看长度项系数 β | **LC win rate**：回归掉长度项后重估胜率；排行榜同时发布原始与 LC 两指标 | 2404.04475（2024，TMLR）：AlpacaEval 与 Chatbot Arena 人类排名相关性从 **0.937 提升到 0.982** |
| **自我偏好** | judge 识别并偏好自己生成的文本 | 自我识别率（judge 能否二分类出自己的输出）+ 自我胜率相对 50% 的偏移 | judge 与生成模型不同家族；异构评审团；基于自我识别检测的统计校准 | 2404.13076（2024）：GPT-4、Claude-2、Llama-2、Mistral 均显著偏好自己输出，**GPT-4 对自身输出识别率约 72%**，开源模型自我偏好更强 |
| **风格偏差** | markdown/列表/自信语气等表面特征主导判决，压倒事实性与安全性 | 风格扰动 A/B：同一内容两种排版看判决翻转；跨模型效应量 | 风格受控对照；组合去偏（见下） | 2409.15268（2024）：judge 偏好与安全性/世界知识/指令跟随等对齐指标几乎不相关，却强烈偏好风格特征；2604.23178（2026）：风格偏差效应量 **0.10–0.76**，是**最主要的残余偏差** |

三个必须展开的要点：

**（1）偏差必须被测量，而不是被假设。** 量化偏差的"零刻度"是**等质量对照组**：两组答案真实质量完全相同时，任何一方的胜率显著偏离 50%，只能来自裁判偏差。动手验证：`labs/eval_lab04_judge_bias.py` 用 MockJudge（真实质量信号 + 可注入的位置/冗长/自我偏好偏差）完整演示了"注入偏差→量化→缓解→断言缓解有效"的闭环，运行：`cd evals-special/labs && python3 eval_lab04_judge_bias.py`。

**（2）评审团（jury）优于单 judge，但有前提。** PoLL（2404.18796，2024，COLM）用三个不同家族的中等规模模型（Command-R、Llama-3-70B、Mistral-Large）组成评审团多数投票，替代单一 GPT-4 judge，三大发现：**与人类判断的相关性高于单一大 judge；成本降到几分之一；跨家族组合显著缓解自我偏好**（评委与选手不同源）。但集成的增益依赖**评委误差独立**：同代模型共享大量训练语料与对齐配方，风格偏好这类偏差是**共模**的——评审团对自我偏好有效，对共模的风格/格式偏差几乎无效。工程建议：评委来自 ≥2 个模型家族 + ≥2 种规模档。阿里实践中的对应做法是**多 LLM 对抗打分**治理"judge 与生成模型同源会偏爱自己风格"的偏差。

**（3）不要迷信单点银弹，组合去偏 + 中端模型才是最优性价比。** 2026 年的系统复盘论文 Judging the Judges（2604.23178，2026）对"去偏方法本身"做了大规模评测：**9 种去偏策略 × 5 个 judge 模型（Google/Anthropic/OpenAI/Meta 四家族）× 3 个基准（MT-Bench n=400、LLMBar n=200、自建 n=375）× 4 类偏差**。核心结论：

- 单点去偏策略（swap / calibration / CoT 等）多数**收益有限且跨模型不稳定**；
- **风格偏差是最主要的残余偏差**（偏向 markdown/结构化输出）；
- **"中端模型 + 组合去偏"能胜过前沿 judge 且便宜约 15 倍**：Gemini 2.5 Flash + 组合策略达到全场最高一致率 **71.0%（κ=0.549）**，约 **$0.001/次评测**；而最佳前沿配置 Claude Sonnet 4 仅 **69.5%**，约 **$0.015/次评测**。

这三条对工程决策的直接含义：去偏要像做 eval 一样**在自己的领域数据上验证迁移性**，而不是照搬论文结论；预算有限时，优先把钱花在组合策略上而不是最贵的模型上。

**判决协议的选择：**

| 协议 | 形式 | 优点 | 注意事项 |
|---|---|---|---|
| 单点绝对打分（pointwise） | 一条输出 + rubric → 0/1 或分档 | 可独立评分、可跨批次比较；DoorDash/阿里生产主流 | 必须 rubric 锚定，否则分数漂移；分档间定义要互斥 |
| 成对比较（pairwise） | 两条输出 → 谁更好 | 版本对比时信号最强 | 位置偏差重灾区，必须交换聚合；胜率先验 50% 使小样本即可看出方向 |
| 参考对比（reference-based） | 输出 + 参考答案 → 判一致性 | 有金标时最省 judge 推理 | 参考答案本身要维护；警惕字面匹配误罚正确改述（Airbnb 78% 案例） |

**默认判决协议（综合上述证据的推荐配置）：** 双向位置交换取平均（或随机化位置）+ 判据先行（先写理由再打分）+ 温度 0 / 低采样；成对比较优于绝对打分（绝对打分必须配 rubric 锚定）。

### 2.5 Judge 校准完整流程：从 78% 到 88%

校准是 judge 从"能用"到"可信"的唯一通道。Airbnb 的**五步法**（原文流程）：

```
① 建 50-100 条 gold set（必须含坏样本）
② 用 judge 跑该集合
③ 目标一致率 high-80s~90s%；分歧可用 Cohen's kappa / Krippendorff's alpha 度量
④ 检查分歧样本 → 改 rubric / few-shot 示例 → 回到 ②
⑤ 失败模式变化时重新校准（rubric 演进、被测系统改版、新能力上线）
```

**实战案例（Airbnb 旅行平台客服政策问答助手，校准段）：** PM/SME 标注 **60 条 gold（含失败样本）**；judge 初始一致率 **78%（过低）**——分歧分析发现 **judge 误罚了"正确的改述"**（答案正确但与参考措辞不同，字面重叠式 rubric 把它判错）；修订 rubric（放宽改述惩罚、增加事实核对项）与 few-shot 后一致率达到 **88%**；同期检索改进减少了 groundedness 失败。`labs/eval_lab05_judge_calibration.py` 完整复刻了这个案例（60 条 gold、"正确的改述"与"流畅的错误"两类陷阱样本、v1 一致率 ~80% → v2 ≥85%），运行：`cd evals-special/labs && python3 eval_lab05_judge_calibration.py`。

**gold set 的两条硬性要求：**

1. **必须含坏样本**（Airbnb 十条要点之⑦）。只有好样本的 gold set 校准不出 judge 的"漏判"能力——judge 全判 pass 也能刷高一致率。
2. **必须含两类陷阱样本**：正确的改述（考验 judge 是否死抠字眼）与流畅的错误（读起来通顺、实则事实错误，考验 judge 能否核对事实）。前者对应上面 78% 的根因，后者对应"风格压倒实质"的偏差（2409.15268）。

**一致率与 Cohen's kappa：为什么必须看两个数。** 一致率（agreement）直观但有陷阱：若 gold set 中 90% 是 good 样本，judge 无脑全判 good 也有 90% 一致率。Cohen's kappa 扣除随机一致：

```
κ = (p_o − p_e) / (1 − p_e)
p_o = 观测一致率；p_e = 按双方边际分布算出的期望随机一致率
常用解读：<0.2 差 / 0.2-0.4 弱 / 0.4-0.6 中等 / 0.6-0.8 良好 / >0.8 几乎完全一致
```

样本类别不平衡越严重，κ 与一致率的差距越大——这正是"门禁要带统计口径"（第 E02 章、第 E09 章）在 judge 校准上的体现。多于两个标注者或有序类别时，用 Krippendorff's alpha。

**分歧诊断决策表（第 ④ 步怎么"检查分歧"）：** 把不一致样本按"样本类别 × 分歧方向"拆开后，按表索骥：

| 分歧模式 | 典型根因 | 处方 |
|---|---|---|
| FN 集中在"正确的改述" | rubric 死抠字面（字面重叠式判据） | 放宽改述惩罚，把"与参考一致"改为"事实核对"（Airbnb 78%→88% 的修法） |
| FP 集中在"流畅的错误" | judge 只看通顺度，不核对证据 | 在 rubric 中加"必须引用证据原文"要求 + 负向 few-shot |
| 人机在同类样本上也不一致 | rubric 本身含糊（人都用不一致） | 先停下修标准/找业务定口径（第 E06 章），再重标 gold |
| 边界样本反复摇摆 | 判决抖动：温度过高 / 判据未锐化 | 温度降到 0；把"基本/大致"类措辞换成可观察判据 |
| 分歧均匀散布、无模式 | judge 模型能力不足或任务超出 judge 边界 | 换更强/异构 judge；或该维度降级为人工评分 |

关键纪律：**分歧分析必须按"样本类别 × 方向"拆开看，整体一致率会掩盖局部失效**——这也是阿里要求 judge 输出 reason、DoorDash 把"审计 judge 行为"列为人工三大杠杆之一的原因。

**四家公司的校准口径对照（全部为素材原文数字）：**

| 公司 | 口径 | 细节 |
|---|---|---|
| Airbnb | 目标一致率 **high-80s~90s** | 50-100 gold set 含坏样本；分歧用 Cohen's κ / Krippendorff's α 度量；失败模式变化时重新校准 |
| 阿里 | 与人工复核一致率约 **85%（参考值）后进日常自动化** | 周期性校准；一致性统计用一致率或多模型对抗 Kappa |
| 腾讯 | 一致率 **≥85% 才可用** | 抽样 **100-200 条**对齐人工与 judge；"校准 LLM 评委"是人工六个必要场景中**最核心**的一个 |
| DoorDash | 只保留在留出集上**提升与人工标注一致率**的 judge prompt 修订版本 | 用 **GEPA prompt optimization** 打磨 judge 判定边界；rubric 演进（新增能力）时收新标注、重新校准 |

**GEPA：把 judge 调优从炼丹变成自动化搜索。** GEPA（2507.19457，2025）是反射式 prompt 进化优化器：对含 LLM prompt 的系统采样轨迹→用自然语言反思失败原因→提出并测试 prompt 更新→在帕累托前沿上合并互补经验。论文数字：在多个任务上**超过 GRPO 最高约 10%、超过最强 DSPy 基线最高约 13.5%，且 rollout 消耗少最高约 35 倍**。DoorDash 把它用在 judge 校准上（上表第四行）：迭代提出 judge prompt 修订，只保留在留出集上提升一致率的版本。其工程意义：当人工校准标签只有几十到几百条（典型情况）时，GEPA 式反射优化比 RL 微调现实得多；优化对象就是 rubric 措辞、评分流程、few-shot 示例，优化目标是"与人工标签的一致率"。**注意防过拟合：必须保留 held-out 校准集**——优化目标本身会被 gaming。

把五步法压成一段可执行的循环（`labs/eval_lab05_judge_calibration.py` 的完整实现即此结构）：

```text
gold   = 加载校准集()            # 50-100 条人工判定；必含坏样本 +
                                 # 「正确的改述」「流畅的错误」两类陷阱
while True:
    pred   = judge.run(gold)                    # ② 跑 judge
    report = 一致性报告(pred, gold)              # 一致率 / κ / 混淆矩阵
    if report.一致率 >= 0.85 and report.kappa >= 0.6:
        break                                   # 达标：阿里/腾讯口径
    分歧 = report.按(样本类别, 方向).分组()       # ④ 分歧诊断（见上表）
    rubric = 修订(rubric, 分歧)                  # 修判据 / 加 few-shot
    judge  = judge.换(rubric)                    # 回到 ②
# ⑤ 上线后：失败模式变化（新能力/被测系统改版/rubric 演进）→ 回到 ①
```

**校准不是一次性动作。** 第 ⑤ 步常被忽视：被测系统的能力边界变了、新的失败模式出现了、rubric 新增标准了，judge 的判定边界就过期了。DoorDash 明确写道：校准持续——rubric 演进时收新标注、重新校准。

### 2.6 Judge 的持续运营：校准集、升级三统计、版本化

Judge 通过校准只是开始，生产运营要解决三个问题：**怎么知道它漂移了？升级时怎么验证？分数跨版本怎么比？**

**上线前速查表（judge 计量自检，任何一条为"否"都先补课）：**

| # | 检查项 | 对应小节 |
|---|---|---|
| 1 | rubric 每条标准都能让人一致地判定？ | 2.3 |
| 2 | 校准集 50-100 条，含坏样本与两类陷阱？ | 2.5 |
| 3 | 一致率 ≥85% 且 κ ≥0.6？ | 2.5 |
| 4 | 高风险样本漏判率单独测过？ | 2.6 |
| 5 | judge 与生成模型不同源（或有统计修正）？ | 2.4 |
| 6 | 版本四元组（模型/prompt/参数/协议）已登记？ | 2.6 |
| 7 | 离线与线上是同一 rubric + 同一 judge？ | 2.6 |
| 8 | 安全场景过了鲁棒性探针（风格扰动/注入）？ | 2.7/2.8 |

**（1）维护 Judge 金标校准集，定期复测。** 像校准传感器一样管理 judge：为每个领域维护 50-500 条人工/客观真值的校准集，定期测一致率与正确率漂移（JudgeBench 式客观真值优先于人类一致率，见 2.7）。阿里把这件事写成制度：**每次 Judge prompt/模型升级，固定产出三类统计**：

| # | 统计项 | 测什么 | 失守后果 |
|---|---|---|---|
| 1 | **与人工标注一致性**（一致率或多模型对抗 Kappa） | judge 的判定口径有没有漂移 | 分数系统性偏松/偏紧，门禁形同虚设 |
| 2 | **高风险样本漏判率**（合规/资损/隐私） | 最坏的那类错误 judge 放过了多少 | 一次漏判可能就是事故；这是"校准集里必须含坏样本"的运营版 |
| 3 | **边界样本稳定性**（重复评测波动） | 同一边界样本多次评测的判决抖动 | 分数噪声淹没真实版本差异，A/B 结论不可信 |

**（2）Judge 必须版本化。** judge 的"版本"是四元组：**judge 模型（固定版本）+ judge prompt（含 rubric 与 few-shot）+ 生成参数（温度等）+ 判决协议（单评/成对、是否交换位置）**。任一变更都产生新版本的分数，与旧版本分数不可直接比较。腾讯三类评分器表中 Rubric 评分器一栏写的就是"大模型（**固定版本**）"。实操上给每个 judge 建一份"计量档案"：记录模型、prompt 版本、温度、判决协议、校准集上的历史一致率曲线——回归评测分数异动时，第一步就是查 judge 的计量档案有没有变（对照第 E10 章"一次只改一个变量"的迭代纪律）。

**（3）离线与线上必须同一套 judge。** DoorDash 的三条 lessons 之一：**真实会话与模拟会话用同一 rubric + 同一校准 judge，两边分数才可对齐；各自调 judge，分数会以难调和的方式背离**。离线门禁说"变好了"、线上体验说"变差了"时，如果两边 judge 不同源，你连"哪边在说谎"都无法判断（离线-线上联动详见第 E12 章 · 在线评估与数据飞轮）。

**（4）接受"评测系统自己也产生 bug 报告"。** DoorDash 的第四条 lesson：**被标记失败中有真实一部分是 harness 自身故障（judge 误报、trace 缺口）**，要与产品缺陷并行修复。这解释了为什么 judge 的 rationale 与置信度字段如此重要——它们是区分"模型错了"与"judge 错了"的唯二线索。

### 2.7 Judge 元评估：高一致 ≠ 正确

前两节讲"judge 与人工对齐"，本节讲一个更尖锐的问题：**如果人工本身不是 ground truth 呢？如果 judge 们集体犯错呢？** 2024 年起，"judge 的元评估"成为独立赛道，核心结论一致：**前沿 judge 在客观困难任务上准确率只有 ~57% 量级，与人类评审仍有明显差距，且 judge 间一致性高但可能"集体犯错"。**

**元评估基准速览（全部来自 _research/01-llm-judge.md）：**

| 基准 | arxiv（年份） | 方法 | 关键数字与发现 |
|---|---|---|---|
| **JudgeBench** | 2410.12784（2024，ICLR 2025） | 350 个困难问题，偏好标签由代码执行/单元测试等**客观真值**产生，覆盖知识/推理/数学/编码 | 最强 LLM judge 准确率仅约 **57%**（GPT-4o 量级），人类评审约 **78%**；judge 间互相一致率很高（**>75%**），但"一致性"与"正确性"相关性很弱——**judge 们会一起犯错**；推理型模型（o1 系）在部分客观评判任务上并不占优 |
| **RewardBench** | 2403.13787（2024，NeurIPS D&B） | ~3,000 偏好对，四维度（Chat/Chat-Hard/Safety/Reasoning），测 reward model / judge 的成对判别准确率 | 未经专门 RM 训练的通用 prompted judge 已可与专用 reward model 竞争甚至更好；成为 HF 上 RM 事实排行榜 |
| **CriticBench** | 2402.14809（2024，ACL Findings） | 批判-纠错能力：找错、定位错误步骤、修正，8 类任务 | LLM 批判能力显著弱于生成能力；**自纠不对称**——评别人明显好于评自己；解释了 self-refine 收益有限 |
| **MM-Eval** | 2410.17578（2024） | 18 种语言的人类偏好标注，同时测 LLM judge 与 reward model | judge 可靠性在非英语语言上**显著下降**，不同语言呈现不同偏差模式 |
| **Know Thy Judge** | 2503.04474（2025） | 安全 judge 的**鲁棒性元评估**：wild 分布漂移 + 针对性对抗攻击 | 仅改变模型输出的**风格**（同一数据集），假阴性率跳变最高达 **0.24**；对抗攻击可让部分安全 judge 把 **100%** 的有害生成判为安全 |

**元评估指标工具箱**（建 judge 校准报表时照抄）：

1. **与人类一致率 + Cohen's κ**（校正随机一致）——基础款，但受人工标注噪声限制；
2. **客观真值正确率**（JudgeBench 路线）——用单元测试/答案验证器产生金标偏好，比"与人类一致"更干净的测量，**优先**；
3. **相关性**：Kendall τ / Spearman / Pearson——排行榜层面与人类偏好排名的相关（LC-AlpacaEval 的 0.937→0.982 即此类）；
4. **鲁棒性元评估**（Know Thy Judge 路线）：风格扰动、提示敏感性、对抗攻击下的假阴性率变化；
5. **Bradley-Terry / Elo**（竞技场聚合）：P(A>B)=exp(θ_A)/(exp(θ_A)+exp(θ_B))，Arena-Hard（2406.11939，2024）用该框架把 arena 人类数据蒸馏为自动基准，与 Arena 相关性 **~0.98**（动手实现见 `labs/eval_lab11_arena_bradley_terry.py`）。

**对评测体系的直接含义：**

- **judge 间一致性不能当验收指标。** MT-Bench（2306.05685，2023，NeurIPS 2023）确立范式时以"GPT-4 judge 与人类一致性约 80%+，与人类间一致性相当"作为合法性论证；JudgeBench 之后，这个论证不够了——验收 judge 要看**客观真值正确率**与**鲁棒性**，一致性只是必要不充分条件。学界分歧至今未消：一致性足够用于"相对排名"（排行榜场景），但绝对能力测量必须回到客观真值或人类评审。
- **多语言产品不能只校准英语 judge**（MM-Eval）；跨模态 judge 泛化更差（MM-JudgeBench，2604.19405，2026）。
- **安全 judge 上线前必须过鲁棒性元评估**：风格扰动测试、对抗后缀、prompt injection——judge 是攻击面，不是旁观者（见 2.8）。
- **judge 选型：RewardBench 初筛，领域校准集终裁。** RewardBench 只测"成对判别"，不测打分校准、多轮对话、鲁棒性——公开榜单上的名次不能替代自己校准集上的验证。任何"换 judge 模型"的决策，最终以本领域校准集的三统计（2.6）为准。

### 2.8 前沿路线：可训练 judge、prompt 进化与 judge 攻防

2024-2026 年，judge 从"提示词工程"走向"模型工程"，再走向"攻防对抗"。演进主线分四段（_research/01-llm-judge.md 调研结论）：

| 阶段 | 主题 | 代表工作 |
|---|---|---|
| 2023-2024 上半年 | 偏差的实证 catalog：四大偏差相继被量化，第一批缓解方法出现 | 2305.17926、2404.04475、2404.13076、2310.01432、2404.18796 |
| 2024 下半年 | judge 的"元评估"成为独立赛道：以客观真值校准 judge | JudgeBench 2410.12784、CriticBench 2402.14809、RewardBench 2403.13787、MM-Eval 2410.17578 |
| 2024-2025 | 可训练的 judge：从提示词工程走向模型工程 | Prometheus/Prometheus 2、Self-Taught Evaluators 2408.02666、GenRM 2408.15240、RM-R1 2505.02387 |
| 2025-2026 | judge 的优化与攻防：prompt/rubric 成为可优化对象，可攻击性被正面研究 | GEPA 2507.19457、Know Thy Judge 2503.04474、PoisonedRAG 2402.07867、2604.23178 |

三条主线：

**主线一：可训练的 judge（judge 专用模型）。**

| 范式 | 代表工作（arxiv，年份） | 核心思想 | 关键数字 |
|---|---|---|---|
| Rubric 监督微调 | Prometheus（2310.08491，2023）；Prometheus 2（2405.01535，2024，EMNLP） | 开源评测专用模型；rubric + 细粒度反馈作为输入/输出格式；Prometheus 2 首次同时支持直接评估（1-5 分 + rubric）与成对排序 | 7B/8x7B 两规模；直接评估协议上与人类偏好相关性达 0.3-0.4 量级并超过 GPT-4 judge |

开源 judge 模型的三大工程红利（Prometheus 2 路线）：**本地部署（数据不出域）、成本低、可针对领域 rubric 微调**；rubric-as-input 的接口设计已成事实标准。JudgeLM（2310.17631，2023）则更早证明了"微调大模型做 judge"的可扩展性。

**主线二：judge 调优的路线选择。** 综合素材的工程建议：

| 你手上有什么 | 推荐路线 | 理由 |
|---|---|---|
| 人工标签 < 几百条（典型情况） | **GEPA 式 prompt/rubric 进化** | 样本效率比 RL 高一个数量级以上；DoorDash 生产验证 |
| 标签数千条+ | **Prometheus 式监督微调** | 数据够才值得动权重；换来本地部署与低成本 |
| 判据可验证（代码/数学/格式约束） | **RM-R1 式 RL** | 偏好方向本身就是规则奖励，无需人工标注 |
| 任何自训练 judge | **必须保留独立于训练分布的冻结校准集** | 防"judge 回声室"：合成数据会放大种子 judge 的偏差，后续工作记录了迭代坍缩风险 |

**主线三：judge 攻防。** 这是与 reward hacking、安全评测的直接交界：

- **judge 可被直接攻击。** Know Thy Judge（2503.04474，2025）：对抗攻击可让部分安全 judge 把 **100%** 的有害生成判为安全；仅改变输出风格即可让假阴性率跳变最高 **0.24**。安全评测管线必须包含"judge 红队"环节：风格扰动测试、对抗后缀、prompt injection 测试；judge 验收不能只看干净集准确率，还要报告鲁棒性元评估结果。
- **消费外部内容的 judge 可被投毒。** RAG/agent 场景中，judge 会读检索结果、网页、工具返回——间接 prompt injection 与检索投毒（PoisonedRAG，2402.07867，2024）可以直接操纵这些 judge。对策：judge 输入的证据切片做注入检测；关键安全判决用"judge + 规则 + 人工"三重冗余。
- **judge 分数作训练奖励时的纪律。** SOS-Bench（2409.15268，2024）证明 judge 偏好与安全性、世界知识、指令跟随等具体对齐指标**几乎不相关**，以 judge 胜率为优化目标的偏好优化（DPO 等）可能只是在"优化风格"；AlpacaEval 的长度 gaming 是"训练钻评测空子"的早期案例。工业主流做法：judge 分数可作辅助奖励，但必须配规则验证器与人工抽检闭环，并监控训练过程中 judge 分数与独立基准的背离（Goodhart 预警）。
- **agentic 场景的 rubric 验证仍是开放问题**：Can LLM-as-a-Judge Reliably Verify Rubrics in Agentic Scenarios?（2606.29920，2026）正面追问 judge 在多步 agent 场景下验证 rubric 的可靠性；FairJudge（2602.06625，2026）尝试自适应、去偏、一致的 judge 框架。趋势判断：**judge 校准正在成为一等公民，judge 鲁棒性测试将进入上线 checklist**。

## 四、经典面试题与参考答案

#### 题 1（基础）：什么是 LLM-as-a-Judge？它在三层评分体系中的位置是什么？能判什么、不能判什么？

**参考答案：** LLM-as-a-Judge 指用一个（通常更强的）LLM 按 rubric 评判另一个模型的输出，自 MT-Bench（2306.05685，2023）确立以来成为开放式生成评测的事实标准，因为它便宜、快速、可扩展——DoorDash 用它把评测规模从员工反馈平均 1 条/天做到 2,000 个/天自动评分会话。三层评分中：规则判"硬条件"（schema、工具调用、预算），judge 判"语义/策略合理性"（语气、有据性、策略是否合理），人工定口径并校准 judge。Judge 能判的：规则写不出、但人能一致判断的软指标；不能判的：一是代码能判的（用了浪费且引入抖动，"能用代码判断的绝不用模型"）；二是依赖内部政策口径的问题（阿里：judge 能判礼貌/清晰，但判不了"叠加优惠差价是否应补偿"这类要业务先定口径的问题）；三是它自身未被校准前，什么都"判不准"——未校准 judge 制造误导性信心。

#### 题 2（基础）：请描述一个生产级 judge 的解剖结构：输入由什么组成、输出应包含什么、有哪些工程纪律？

**参考答案：** 输入 = 单条标准（rubric）+ 该标准依赖的证据切片。DoorDash 的做法是每条标准声明依赖的证据，Transcript Builder 只把那一片给 judge（grounding 检查拿论断 + 工具输出；多样性检查拿推荐 + 原始请求），聚焦证据让判断更一致。输出 = verdict + rationale（+ 置信度、问题分类），rationale 要引用证据原文，供定位、badcase 聚类与人工审计。工程纪律按 Airbnb 五条：① 每个质量维度一个 judge（3-5 个经校准的评估器好过一堆嘈杂的）；② judge 模型尽量与生成模型不同源（防自我偏好）；③ 带 few-shot，含边界样本；④ 强制输出 JSON schema；⑤ 清晰打分说明，每分档有可执行标准。外加两条运营纪律：judge 前可加 eligibility 判断（不适用则跳过），judge 本身要版本化管理。

#### 题 3（进阶）：设计 rubric 时，二元检查与分级打分（1-5 分）怎么选？为什么 DoorDash 推荐二元？

**参考答案：** 选 binary 的理由有四：① 方差低——"0 还是 1"的判定边界清晰，"3 分还是 4 分"连人都会摇摆，judge 抖动更大；② 汇总干净——逐条 binary 汇总为会话级总分，不需要为加权平均的权重吵架；③ 可独立迭代——每条标准单独可改、可单独校准，改一档描述则牵动全量表；④ 校准目标明确——一致率、漏判率都好算。DoorDash 的 guardrail/capability 标准全是 binary（如"不呈现可证伪虚假信息"）。分级打分适合创意质量、体验观察等确实存在连续谱的维度，但要求每分档有可执行标准（阿里）且锚定示例。折中实践：分级维度先拆成若干 binary 子检查，再映射回分档；以及 checklist 式场景 rubric（"两人份 ≤$60 素食 taco 清单"）——比宽泛标准方差更低，小样本即可迭代。无论哪种，铁律是"人都无法一致应用的 rubric，模型也不可能"。

#### 题 4（进阶）：LLM Judge 有哪些常见偏差？分别如何量化、如何缓解？

**参考答案：** 四大偏差。① 位置偏差（2305.17926，2023）：成对评判偏好特定位置；量化用 swap consistency（交换 A/B 前后判决一致率）与等质量对照组胜率偏离 50% 的幅度；缓解是双向交换取平均或句级对齐 Split and Merge（2310.01432，2023）。② 冗长偏差：把更长当更好；量化用长度作为协变量回归看系数；缓解是 LC win rate（2404.04475，2024），把 AlpacaEval 与 Arena 人类排名相关性从 0.937 提到 0.982。③ 自我偏好（2404.13076，2024）：judge 偏好自己的输出，GPT-4 自我识别率约 72%；量化用自我识别率 + 自我胜率偏移；缓解是异构 judge、PoLL 评审团（2404.18796，2024）。④ 风格偏差（2409.15268，2024）：markdown/格式/自信语气压倒实质；量化用同内容双排版 A/B；2604.23178（2026）系统复盘 9 种去偏策略发现单点策略收益有限，风格偏差是最主要残余偏差（效应量 0.10-0.76），"中端模型 + 组合去偏"胜过前沿 judge 且便宜约 15 倍（71.0% κ=0.549 @ $0.001/次 vs Claude Sonnet 4 69.5% @ $0.015/次）。默认协议：交换聚合 + 判据先行 + 温度 0。

#### 题 5（进阶）：请完整描述校准一个 LLM Judge 的流程，并给出量化标准。如果一致率长期卡在 80% 左右，你怎么诊断？

**参考答案：** 按 Airbnb 五步法：① 建 50-100 条 gold set，必须含坏样本与两类陷阱（正确的改述、流畅的错误）；② 用 judge 跑该集合；③ 看一致率，目标 high-80s~90s，分歧用 Cohen's κ / Krippendorff's α 度量（注意 base rate 陷阱）；④ 逐条检查分歧样本，归因是 rubric 含糊、few-shot 缺失还是 judge 能力不足，修 rubric/示例后重跑；⑤ 失败模式变化时重新校准。工业口径：阿里 ~85% 后进日常自动化，腾讯 ≥85% 可用，DoorDash 用 GEPA 自动迭代 judge prompt、只保留留出集一致率提升的版本。Airbnb 实战：judge 初始 78%，根因是字面重叠式 rubric 误罚正确的改述，修 rubric 后 88%。卡在 80% 的诊断路径：先按"样本类别 × 分歧方向"分解混淆矩阵（FN 误罚好答案 / FP 放过坏答案各在哪类样本）；若是改述被误罚→rubric 从字面匹配转向事实核对；若是流畅错误漏判→给 judge 证据核对步骤与负向 few-shot；若人机之间对同一批样本也不一致→先修 rubric 定义（人都用不一致，模型不可能一致）；最后才考虑换更强的 judge 模型。

#### 题 6（进阶）：为什么只看一致率不够？请用例子说明 Cohen's kappa 的价值。

**参考答案：** 一致率不扣除"随机一致"，在类别不平衡时会严重虚高。例：gold set 100 条中 90 条 good、10 条 bad，judge 无脑全判 good，一致率也有 90%——看起来达标，实际上它对坏样本的漏判率是 100%。Cohen's kappa 用 κ=(p_o−p_e)/(1−p_e) 扣除按边际分布算出的期望随机一致 p_e：上例中 p_e=0.9×0.9+0.1×0.1=0.82，κ=(0.9−0.82)/0.18≈0.44，只是"中等"，真相现形。两点延伸：① 解读参考 <0.2 差 / 0.2-0.4 弱 / 0.4-0.6 中等 / 0.6-0.8 良好 / >0.8 几乎完全一致；② 校准集要故意保持足够的坏样本比例（Airbnb：gold set 必须含坏样本），否则一致率与 κ 同时失真。工程上还应把一致率拆成误罚率（FN，惩罚正确改述）与漏判率（FP，放过流畅错误）分别看——阿里对高风险样本的漏判率是 judge 升级的三统计之一，因为合规/资损场景的漏判代价远高于误罚。

#### 题 7（进阶）：为什么 judge 要与被评模型不同源？如果成本所限只能用同一个模型，怎么降低风险？

**参考答案：** 实证依据是自我偏好偏差（2404.13076，2024）：GPT-4、Claude-2、Llama-2、Mistral 都能以显著高于随机的概率识别自己生成的文本，并在成对评判中系统性偏好自己的输出；GPT-4 对自身输出识别率约 72%，且自我偏好强度与自我识别能力正相关，开源模型更甚。同源自评相当于"裁判和选手是同一个模型"，回归对比中模型会系统性高估自己的新版本。缓解首选：judge 与被评模型分属不同模型家族；关键评测用 PoLL 评审团（2404.18796，2024）——三个跨家族中端模型（Command-R、Llama-3-70B、Mistral-Large）多数投票，与人类相关性高于单一 GPT-4 judge、成本降到几分之一、显著缓解自我偏好。成本所限必须同源时的降级方案：① 统计校准——按自我识别检测修正胜率估计（原论文提出的方法）；② 绝对打分 + rubric 锚定替代成对比较（自评的成对比较是自我偏好重灾区）；③ 用客观真值校准集持续测该同源 judge 的正确率（JudgeBench 路线），一旦漂移立即降级处理；④ 高风险维度坚持换异构 judge 或人工。注意 PoLL 的边界：评审团只对独立误差有效，风格偏好是共模偏差，跨家族集成也治不了。

#### 题 8（进阶）：JudgeBench 显示最强 judge 的客观准确率只有 ~57%，而 judge 之间互相一致率超过 75%。这对我们构建评测体系意味着什么？

**参考答案：** 三个含义。① "judge 间高一致"不能作为验收指标——一致只说明它们共享同样的偏见（共模错误），不说明正确；MT-Bench 时代"与人类一致率 ~80%"的合法性论证在客观真值面前不够了（JudgeBench，2410.12784，2024，ICLR 2025：350 个由单元测试等客观验证产生偏好标签的困难问题，最强 judge ~57%，人类 ~78%）。② 元评估要优先用客观真值：凡是判据可程序验证的领域（代码、数学、格式约束），用单元测试/答案验证器造 judge 校准集，比"与人类一致"更干净；人类一致率留给无法客观验证的主观维度，并配 κ。③ 对 judge 的能力边界保持谦卑：judge 适合做"低成本筛查与排序"，不适合做"最终裁决"——所以三层评分里人工才是校准源与高风险终判者（第 E06 章），所以阿里要求高风险/低置信/冲突样本进人工复核，所以推理模型也不一定更好（JudgeBench 报告 o1 系在客观评判上不占优，"会推理"≠"会评判"）。答题加分点：补充 CriticBench（2402.14809，2024）的"批判能力弱于生成能力、自评弱于评他"，说明 57% 并非意外。

#### 题 9（系统设计）：为公司的 Agent 评测平台设计一个「Judge 服务」：解剖、校准、版本化、路由、监控，给出完整方案。

**参考答案：** 分五层设计。① 接口层：judge 按"单条标准 + 证据切片"调用（DoorDash 接口），输出 {applicable, verdict, confidence, rationale, 问题分类}；每个业务维度一个 judge，控制在 3-5 个（Airbnb）；证据由 Transcript Builder 按标准声明切片供给（第 E07 章）。② 校准层：每 judge 配 50-100 条 gold 校准集（含坏样本、正确的改述、流畅的错误、高风险样本）；按五步法迭代到一致率 ≥85%（腾讯口径）且 κ≥0.6；rubric 措辞优化可用 GEPA 自动进化，留出集防过拟合。③ 版本层：judge 版本 = 模型 + prompt + 温度 + 协议四元组，任一变化即新版本；每个版本建计量档案（校准集历史曲线）；新旧版本过渡期双跑对比。④ 路由层（衔接第 E06 章）：judge 结论不是终点——边界分/低置信/rationale 含糊/多 judge 分歧/规则与 judge 冲突 → 人工终判并回收口径；高风险场景自动通过也定期人工复核。⑤ 监控层：阿里三统计随每次升级固定产出（与人工一致性、高风险漏判率、边界样本稳定性）；日常抽样人工审计 judge 行为（DoorDash：审计 judge 是人工三大杠杆之一）；离线与线上强制同一 rubric + 同一 judge；把 harness 自身故障（judge 误报）单列缺陷池并行修复。成本策略：中端模型 + 组合去偏优先（2604.23178：71.0% 一致率 @ $0.001/次，比前沿配置便宜约 15 倍），关键门禁维度再上评审团。

#### 题 10（系统设计）：你准备把 judge 分数作为 RL 训练的奖励信号。请评估风险并设计治理方案。

**参考答案：** 风险有四类。① 风格 gaming：SOS-Bench（2409.15268，2024）证明 judge 偏好与安全性/知识/指令跟随等真实对齐指标几乎不相关，却强烈偏好格式、长度、拒绝话术——以 judge 胜率为目标做 DPO/RL 可能只是在优化风格；AlpacaEval 长度 gaming 是早期案例（LC-AlpacaEval，2404.04475，2024 因此而生）。② 直接攻击：训练循环里的策略模型会主动探索 judge 的漏洞，本质是自动化、持续化的对抗攻击——Know Thy Judge（2503.04474，2025）显示对抗攻击可让安全 judge 100% 放行有害输出，风格扰动即可让假阴性率跳变 0.24。③ 回声室：若用 judge 生成偏好数据再训模型（Self-Taught Evaluators，2408.02666，2024 式循环），种子 judge 的偏差会被放大，存在迭代坍缩风险。④ Goodhart：judge 分数上升但真实能力不涨，且越优化背离越大。治理方案：a) judge 分数只做辅助奖励，与规则验证器（可验证判据优先，参考 RM-R1，2505.02387，2025 的思路）和人工抽检组合；b) 训练前做 gaming 探针（长度/格式扰动测试），确认分数不可被低成本刷取；c) 保留独立于训练分布的冻结校准集，定期测 judge 客观正确率（JudgeBench 路线）；d) 监控训练过程中 judge 分数与独立基准（线上信号、客观测试）的背离，背离超阈值即停训复盘；e) judge 与被训模型不同源，防自我偏好混入奖励。

## 五、易错点 · 反直觉点

1. **误区：写一个"万能 judge"对所有维度统一打分。** 真相：Airbnb 明确要求每个质量维度一个 judge，且 judge 要少而精——3-5 个经校准的评估器好过一堆嘈杂的；万能 judge 会把语气问题与事实问题混在一个分数里，无法归因、无法单独校准。记忆锚点：**judge 按维度拆，宁少勿杂**。
2. **误区：judge 写个 prompt 就能进门禁。** 真相：未校准 judge 制造"误导性信心"——分数精确，量的却是 rubric 的缺陷；必须校准到 high-80s~90s（Airbnb）/ ≥85%（阿里、腾讯口径）之后才谈自动化。记忆锚点：**先校准，再门禁**。
3. **误区：judge 用和被评模型同一个模型，省钱又省心。** 真相：自我偏好有硬实证——GPT-4 对自己输出的识别率约 72%，四个主流模型都系统性偏好自己的生成（2404.13076，2024）；同源自评会系统性高估自己的新版本。记忆锚点：**裁判与选手不同源**。
4. **误区：judge 之间一致率 >90%，说明 judge 可靠。** 真相：JudgeBench（2410.12784，2024）显示 judge 间互相一致率 >75%，但最强 judge 客观准确率只有 ~57%（人类 ~78%），且一致性与正确性相关性很弱——它们会一起犯错。记忆锚点：**高一致 ≠ 正确，可能是共谋**。
5. **误区：校准集全放好样本，因为"坏样本看起来不吉利"。** 真相：全好样本的校准集测不出漏判能力——judge 无脑全判 pass 也能刷出高一致率；gold set 必须含坏样本（Airbnb 十条要点之⑦），且要含"正确的改述"与"流畅的错误"两类陷阱。记忆锚点：**没有坏样本的校准集是假的**。
6. **误区：一致率 90% 已经很好，不必看 kappa。** 真相：若 90% 样本是 good，全判 good 的傻 judge 一致率也是 90%（κ≈0.44，仅中等）。类别越不平衡，一致率越会撒谎。记忆锚点：**看 κ，别只看一致率**。
7. **误区：找到一篇去偏论文就照搬（swap / CoT / 校准各挑一个"银弹"）。** 真相：2604.23178（2026）对 9 种策略 × 5 模型 × 3 基准的系统复盘显示：单点策略多数收益有限且跨模型不稳定；风格偏差是最主要的残余偏差；组合策略 + 中端模型才是性价比之王（便宜约 15 倍且一致率更高）。记忆锚点：**去偏靠组合，银弹不存在**。
8. **误区：judge prompt 随手改，反正"改得更好了"。** 真相：judge 版本 = 模型 + prompt + 参数 + 协议，任一变更都让新旧分数不可比；回归异动时查不到是模型变了还是 judge 变了。阿里的三统计（一致性/高风险漏判率/边界稳定性）必须随每次升级产出。记忆锚点：**judge 即资产，改动即发版**。
9. **误区：推理模型（o1/R1 系）一定更会当 judge。** 真相：JudgeBench 报告推理型模型在部分客观评判任务上并不占优；Critique 研究显示 CoT judge 会"推理出错误的自信"。"会推理"≠"会评判"，评判能力要单独元评估。记忆锚点：**推理强 ≠ 评判强**。
10. **误区：judge 不执行代码、不碰外部世界，所以没有安全问题。** 真相：judge 是攻击面——对抗攻击可让安全 judge 把 100% 的有害输出判为安全（2503.04474，2025）；消费检索内容/工具返回的 judge 可被 PoisonedRAG（2402.07867，2024）式投毒操纵；judge 分数进训练循环还会被 reward hacking。记忆锚点：**judge 也要红队**。

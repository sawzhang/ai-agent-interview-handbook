# 第 E08 章 · 对话 Agent 与仿真评测

> 一句话导读：对话 Agent 的质量无法用"一问一答"的静态数据集衡量——用户会追问、改主意、发脾气、等你引导他操作。
> 本章解决"没有真实用户参与时，如何端到端、可复现、低成本地评测多轮对话 Agent"：
> Conversation Simulator（LLM 扮演用户）+ Fixtures（冻结外部世界）+ checklist 式 rubric + 全量 sweep 的成本工程。
> 学完你能得到：对话评测五大难点与四层判分框架、DoorDash 会话模拟器与 fixtures 的完整设计细节、
> τ-bench/τ²-bench 学术范式与 pass^k 可靠性数字、模拟器保真度的验证方法，以及仿真评测的边界与 offline-online gap 治理。

## 二、核心概念精讲

### 2.1 对话评测的五个特殊难点：为什么不能"每轮打分取平均"

单轮问答评测的范式是"输入 → 输出 → 对照参考答案"。对话 Agent 把这个范式打碎了——
**阿里技术在《Agent 评测：方法论与体系设计》中把对话 Agent 的特殊难点归纳为五类**，
并给出一条总纲式判据：**不要只平均每轮分数——每轮都"答得还行"但最终没解决问题，仍是失败。**

| # | 难点 | 典型表现 | 对评测的要求 |
|---|---|---|---|
| 1 | **上下文累积** | 关键信息散落在第 2、5、9 轮；agent 后文覆盖前文（"上下文被覆盖"是阿里 RCA 中的常见根因） | 必须会话级评测；单轮 judge 看不到跨轮信息是否被正确继承 |
| 2 | **目标切换** | 用户中途改主意："先不退了，帮我换成换货"；一个会话包含多个子目标 | 场景库要含目标切换用例；按最终达成的目标判分，而非第一个目标 |
| 3 | **情绪回应** | 用户愤怒、焦虑时，"答案正确但语气冰冷"会直接升级为投诉 | 体验维度（同理心、语气）单独成 rubric，属 P2 但决定产品生死（腾讯五维之一） |
| 4 | **人工接管** | 该转人工时不转（硬扛）、不该转时乱转（甩锅）；转接时上下文丢失 | 升级决策本身是评测对象：转接时机、转接时的信息交接质量 |
| 5 | **多轮引导** | agent 需要指挥用户完成动作（点链接、查设置、拍照上传），而不只是自己执行 | τ²-bench 证明"引导用户操作比直接操作难得多"（见 2.4） |

**四层判分框架（阿里）**：对话 Agent 要同时看四个层面，任何一层单独成立都不够：

| 层 | 评什么 | 典型检查 |
|---|---|---|
| **Turn**（单轮） | 单条回复的质量 | 语气、格式、不泄露、不编造 |
| **Session**（整段会话） | 整个交互是否连贯推进 | 是否绕圈、是否重复追问、上下文是否一致 |
| **Trace**（执行轨迹） | 对话之下的工具调用与推理 | 工具选对了吗、参数对吗、跳过校验了吗（详见第 E7 章） |
| **Outcome**（最终结果） | 用户的问题到底解决没有 | 退款是否真的发起、订单是否真的改成功 |

四层的关系是：**Outcome 是最终裁决，Turn/Session/Trace 是归因与护栏**。
一个会话可以每轮 Turn 分都很高（礼貌、流畅、格式正确），但 Outcome 是失败的——
用户绕了八轮还是没退成款。反过来，Outcome 成功也可能掩盖 Trace 层的风险
（跳过了订单状态校验恰好没出事，即"假阳性"，详见第 E7 章）。
**工程口径：门禁判 Outcome 与关键 Trace 断言，Turn/Session 分用于诊断与体验迭代，绝不互相替代。**

这套四层与 Airbnb 的 step/trajectory/session 三层（第 E7 章）、
腾讯的"触发→核心逻辑→产物质量→异常容错"四场景用例组织（第 E3 章）互为表里：
对话评测的特殊性在于，**Session 层的"推进质量"无法静态判分，必须让一个会动态反应的用户把会话跑完**——
这就引出了本章的主体：仿真评测。

### 2.2 Conversation Simulator：让 LLM 扮演用户

**（1）为什么必须"按需生成会话"。** DoorDash 在 Ask DoorDash 评测 harness 的五大挑战中，
把对话评测的困境表述得最尖锐：

| 挑战 | 设计要求（DoorDash 原文表） |
|---|---|
| 开放式目标（一个用户目标有多种可接受结果） | 每个目标表达成 rubric：具体到每次能同样判，宽泛到容纳所有合法路径 |
| 执行不可见（judge 需要看到对话之下的工具调用） | 把 trace 重建为"按标准定制的视图"，judge 只看该标准需要的证据 |
| **无法安全彩排**（不能拿真用户试变更；历史会话不能对改过的 agent 重放） | **按需生成会话：模拟用户驱动 agent 跑场景，外围数据固定（fixtures），同场景每次一致** |
| 规模化判断（是否帮到用户需要人类级判断，但人工不可扩展） | 校准过的 LLM judge 顶替人类评审 |
| 双环境（开发与生产质量可能背离） | 真实会话与模拟会话用同一 rubric + 同一 judge |

注意第三条里的关键洞察：**历史会话不能对改过的 agent 重放**——agent 变了，面对同一句话的回应就变了，
对话路径随之完全不同，"重放"测的已不是同一个交互。所以正确姿势不是回放录像，而是
**让一个 LLM 扮演用户，按场景设定与 agent 现场对戏**，每次生成一条新会话。

**（2）模拟器的解剖：scenario 三要素。** DoorDash 的 Conversation Simulator 让 LLM 扮演购物者，
一个 **scenario（场景）定义三件事**：开场请求、用户目标、对提问/结果的反应方式。
场景是数据而不是代码——sweep 要跑几十上百个场景，场景必须可序列化、可版本管理、可由非工程师编写。
一个结构化完整的场景配置实例（字段组织参照 DoorDash 公开描述与本特辑 lab 约定）：

```yaml
evalId: grocery-reorder-001
sessionInput:                      # 会话的环境输入（渠道、用户档案等）
  channel: chat
  userLocale: en-US
conversationScenario:
  opening: "Reorder my usuals"     # 开场请求：模拟器的第一句话
  userGoal: >
    完成常购清单复购；确认配送时间；不接受用含花生商品替换
  persona:                         # 从真实工单抽取：脾气 + 情境叙事 + 期望结果
    temper: "耐心有限，但讲道理"
    contextStory: "每周日晚固定复购的常客，这周赶时间"
    expectedOutcome: "订单确认 + 明确配送窗口"
  reactionPolicy:                  # 反应策略：模拟器行为的"性格"
    whenAskedClarification: "挤牙膏式补充：一次只说一条自己知道的信息"
    whenNoProgressTwice: "要求升级/投诉——像真人一样给过机会才发火"
    whenResultWrong: "反驳并给出自己的依据，不轻易接受"
fixtures:                          # 冻结外部状态（见 2.3）
  get_reorder_items: reorder_history_v1
rubric: [reorder-checklist-v2, guardrail-communication, trust-honesty]
trials: 8                          # 每场景重复运行次数（支撑 pass^k，见 2.6）
```

**（3）persona 从哪来：四条进料线。**

| 来源 | 做法 | 出处 |
|---|---|---|
| 真实工单抽取 | persona 携带**脾气、情境叙事、期望结果**，会反驳、补充细节、逐步升级而非一上来就转人工 | DoorDash 仿真评测飞轮 |
| 隐式画像挖掘 | 从真实人机交互记录反推未明说的特征（性格、表达习惯、目标倾向），驱动的模拟器在个性化、真实性、多轮一致性上优于直接 prompt | arxiv 2502.18968（2025） |
| 真实日志语料 | WildChat（100 万条 ChatGPT 交互，arxiv 2405.01470，2024）、LMSYS-Chat-1M（arxiv 2309.11998，2023）提供真实用户表达分布 | 构建模拟器/评测集的原料 |
| 规模化合成 | 以 persona 网格批量合成（腾讯参与的 10 亿 persona 工作，arxiv 2406.20094，2024）；PersonaBOT 用 RAG 增强 persona 的准确性（arxiv 2505.17156，2025） | 扩大场景覆盖 |

注意方向上的呼应：**真实日志 → 隐式画像 → 模拟器 → 回归测试**，这本身就是一条数据飞轮
（详见第 E12 章）——模拟器的 persona 不必全靠手写模板，可以从生产对话中"挖掘"。

**（4）行为真实性：模拟器要做动态判断，而不是念台词。** 一个合格的模拟用户在会话中持续回答四个问题：
**是否已解决？是否有进展？是否需要更多信息？是否在绕圈？** 并据此决定配合、追问还是升级。
DoorDash 的要求是**升级行为像真人**：给过几次机会、agent 反复答得差才投诉，
会反驳、会补充细节、会逐步升级，而不是一上来就转人工。
本特辑 `labs/eval_lab07_simulator_fixtures.py` 用一个最小状态机实现了这种"真人耐心"：
未解决但有进展 → 继续配合；被反问 → 补充信息；连续 2 次无进展 → 升级投诉
（`cd evals-special/labs && python3 eval_lab07_simulator_fixtures.py`）。

**（5）合作型模拟的系统性高估与非合作模拟。** 如果模拟用户总是礼貌、信息完备、轻易满意，
它会把 agent 的能力系统性高估。ChatChecker（arxiv 2507.16792，2025）把"找茬式测试"工程化：
persona 驱动的**非合作**用户模拟器——用户会不耐烦、跑题、表达模糊、中途改主意——
配 **Breakdown Detector**（检测对话崩坏点，定位失败轮次，服务回归归因）与
**Dialogue Rater**（对系统质量打分）三件套。
工程推论：**场景库必须包含"难缠用户"切片**（易怒、模糊、改主意、多目标），
否则你在一个礼貌的假用户身上测出了一个礼貌的假高分。
同理，lab07 的 checklist 还验证了一件反直觉的事：**编造商品的 agent 可以让"用户"满意收尾**——
模拟用户的满意不等于任务正确，结果判定必须独立于对话氛围（见 2.5）。

### 2.3 Fixtures：冻结外部世界，否则分数测量的是噪声

**（1）问题：实时外部状态让评测不可复现。** 对话 Agent 的背后是一圈活着的外部系统：
商品目录每天在变、门店库存实时波动、测试账号状态漂移。如果评测时真的调用这些接口，
**同一条用例每次测的其实是不同的题**——今天通过明天失败的差异，可能全部来自环境而不是 agent。
DoorDash 的 Lesson Learned 第二条原话是：**"环境必须受控，否则分数测量的是噪声。"**

**（2）解法：录制工具返回，回放替代实时调用。** fixtures 的做法是：
把工具的真实返回录制成固定 payload，评测运行时拦截工具调用、原样回放。
DoorDash 复购场景的实例：开场请求 "Reorder my usuals"，工具 `get_reorder_items`
固定返回录制的 **`reorder_history_v1`**——一份 Albertsons 的历史订单
（Meadow Gold 全脂牛奶 ×2、Oroweat 全麦面包、牛油果、Ben & Jerry's 冰淇淋……）。
于是**每次运行 agent 都看到同一份订单 → 预期结果可预测 → judge 可以对照同一商品集评分**。
把这份 fixture 展开成结构化 JSON 大致如下（商品清单忠实于原文，字段结构为示意）：

```json
{
  "fixture_id": "reorder_history_v1",
  "recorded_from": "生产会话录制并脱敏",
  "merchant": "Albertsons",
  "items": [
    {"name": "Meadow Gold Whole Milk", "qty": 2},
    {"name": "Oroweat Whole Wheat Bread", "qty": 1},
    {"name": "Avocado", "qty": 3},
    {"name": "Ben & Jerry's Ice Cream", "qty": 1}
  ]
}
```

**（3）fixtures 的三重价值与对照。**

| 方案 | 可复现性 | 能测什么 | 风险 |
|---|---|---|---|
| 实时调用生产/测试 API | ❌ 数据随时间漂移 | 当下真实分布 | 分数方差混入环境噪声；可能产生真实副作用 |
| 重放历史会话 | ⚠️ 只有一侧可控 | 旧 agent 的行为 | agent 变更后对话路径完全不同，重放失效（2.2） |
| **fixture + 模拟器按需生成** | ✅ 外部状态冻结 | 任意场景含罕见难例 | 保真度需要持续校验（2.7） |

第三重价值常被忽略：**fixture 让"真实里很难遇到的场景"变成可批量测试的用例**——
DoorDash 用 mock 后端模拟订单/退款/时间戳来复现**欺诈、大额退款**等边角案例。
这类场景在真实流量里占比极低（正是第 E3 章说的幸存者偏差），却恰恰是资损与合规的高风险区。

**（4）fixture 的治理。** fixtures 不是写完就完：

1. **版本化**：`reorder_history_v1` 的命名暗示了版本演进；场景配置与 fixture 一起进仓库、带 provenance（EDDOps 对评测资产的通用要求，见第 E10 章）。
2. **防 mock 漂移**：录制的返回要与生产 API 定期对账——上游 schema 变了、字段语义变了而 fixture 没更新，评测全绿、上线即炸（主手册第 8 章 · Agent 评估与可观测性）。
3. **环境隔离**：评测执行环境要隔离，避免多用例共享状态导致分数不可复现（阿里）；每条用例从干净状态启动。
4. **脱敏合规**：fixture 源自真实数据时必须去标识化、用途限定（Airbnb 隐私注记，见第 E3 章）。

> 动手：`labs/eval_lab07_simulator_fixtures.py` 专门设置了对照组——同一 agent、同样采样随机性下，
> fixture 组 N 次评分一致，而"漂移的伪实时数据"组方差显著膨胀，亲眼验证
> "环境不受控时分数测量的是噪声"。运行：`cd evals-special/labs && python3 eval_lab07_simulator_fixtures.py`

### 2.4 标准范式：从 τ-bench 到 DoorDash 全流水线

**（1）τ-bench：对话 Agent 仿真评测的模板。** 学术侧的范式源头是 Sierra 的
**τ-bench**（arxiv 2406.12045，2024）：LLM 用户模拟器与 agent 多轮对话，
agent 需遵守领域政策（retail/airline 域的企业规则）并调用 API 工具，
最终以**数据库终态哈希**做可验证判定（而非只看对话文本），并用 **pass^k**
刻画"单次通过率在多次独立试验下的一致性"。这套"模拟器 + 可验证终态 + 重试验可靠性"设计
成为后续几乎所有对话 Agent 仿真评测的模板，也被 DoorDash 等工业实践直接借用。

τ-bench 最具冲击力的数字（论文摘要转述，量级可信、精确值以原文为准）：

| 指标 | retail 域 | airline 域 | 含义 |
|---|---|---|---|
| pass^1（单次成功率） | ~61% | ~35% | "能做对一次" |
| pass^8（8 次全对） | ~25% | ~16% | "稳定做对" |

GPT-4o 从 pass^1 到 pass^8 腰斩再腰斩，说明**"能做对一次"与"稳定做对"之间差距巨大**——
对话每多一轮、任务每多一步，误差都在复合。这也是为什么生产级对话 Agent 的发布门槛
应当使用 pass^k（低 k）而非 pass@1（指标定义与无偏估计见第 E2 章，统计口径见第 E9 章）。

**（2）τ²-bench：双控与"多轮引导"难点。** τ²-bench（arxiv 2506.07982，2025）把范式升级为
**dual-control（双控）**：模拟用户不再只是说话，也能自己执行工具动作（点击邮件链接、改路由器设置），
agent 必须通过对话**引导用户完成动作**，并处理联合行动中的信息不对称；新增 telecom 域，
任务涉及跨系统排障、指导非专家用户。评测显示：**即使最强模型，在双控设定下的成功率也远低于
τ-bench 单控设定——引导用户操作比直接操作难得多。**
这为 2.1 的第五个难点（多轮引导）提供了定量注脚：客服/支持类 agent 的真实瓶颈是"指挥用户"，
仿真评测若让用户侧没有行为能力，会系统性高估 agent。

**（3）DoorDash 的全流水线：评测镜像运行时架构。** DoorDash 是多 agent 架构：
用户消息 → Orchestrator → 路由到领域 Agent（如 Restaurant Discovery Agent）→ 领域 Agent
直接处理或交还 Orchestrator。评测与之同形：**路由在 Orchestrator 评；护栏贯穿全流程评；
任务能力在每个领域 Agent 评**（组织方式详见第 E7 章）。对话仿真评测在这条流水线上的位置：

```text
场景库（scenario + persona + fixture）
  → Conversation Simulator 生成模拟用户消息
  → 被测 agent 全流程运行（工具调用被 fixture 拦截回放）
  → OpenTelemetry trace 落 ClickHouse → Transcript Builder 按标准切证据片
  → 校准过的 LLM judge 逐条标准二元判定（verdict + rationale）
  → 汇总为会话级分数 → 全量 sweep 报告（按场景 × trial）
```

两个贯穿性约定：① **离线与线上用同一 rubric + 同一校准 judge**——这是 DoorDash Lesson Learned 第三条：
离线结果只有能带到线上才有意义；若离线线上各自调 judge，两边分数会以难调和的方式背离
（详见第 E12 章）。② **judge 校准用 GEPA**（arxiv 2507.19457，2025）：
迭代提出 judge prompt 修订，只保留在留出集上提升与人工标注一致率的版本
（GEPA 机制与"eval 作为优化目标"见第 E10 章；judge 校准全流程见第 E5 章）。

**（4）generator-verifier gap：为什么 judge 模式可行。** DoorDash 仿真评测飞轮依赖一个经验事实：
**判定比生成容易**——LLM 裁判读全对话 + 工具调用 + 政策后给二元判定 + 理由，
比让模型从零生成完美服务要可靠得多；裁判再用人工标注样本校准到与专家一致后才上量。
这正是"LLM-as-a-Judge"在对话场景成立的前提（judge 的偏差与校准见第 E5 章）。

### 2.5 场景级 checklist rubric：低方差信号

仿真评测把"跑会话"变成了自动化，但"判会话"仍然是方差的主要来源。
DoorDash 的答案是把开放式目标翻译成**场景级 checklist 式 rubric**。

**（1）实例：素食 taco 购物清单。** DoorDash 杂货购物场景的 rubric 例子：
**"两人份 ≤$60 素食 taco 购物清单"**——judge 逐项验证：每件商品都是素食 taco 原料；
小计 ≤$60。对比两条路线：

| 维度 | 宽泛通用标准（"购物清单是否合理"） | checklist 式场景标准 |
|---|---|---|
| 判定一致性 | 低——"合理"人各有解 | 高——每项非真即假、可附证据 |
| 方差 | 高，需要大样本才看得出差异 | **低，小样本也有用，支撑更快迭代** |
| 可归因性 | 只知道"不好" | 知道是哪一项坏了（超预算？混入荤食？编造商品？） |
| 适用面 | 任何会话 | 绑定具体场景，场景库要自己长出来 |

这与第 E5 章的通用结论一致：**judge 做二值判断比打连续分可靠**；
DoorDash 的每条标准都是 binary check，汇总为会话级总分。

**（2）eligibility 适用性前置。** checklist 有一个隐蔽杀手：不适用的标准误伤会话。
DoorDash 的设计是 judge **先判该标准是否适用本会话，不适用则跳过**——
例如食谱流程不因缺少复购步骤被扣分。适用性判断与标准判定分开，
避免"标准越多、误伤越多"，也让 rubric 可以跨场景复用。

**（3）与四层判分的对应。** checklist 主要落在 **Outcome/Session 层**；
Guardrail 类标准（如"回复简洁、不向用户叙述思维过程""不呈现可证伪虚假信息"）
面向全体 agent 贯穿全流程。lab07 的极简 checklist——目标商品在清单里 / 总价≤预算 /
无编造商品——足以抓住超预算与编造商品两类失败，**即使"用户"在对话里表示满意**。

### 2.6 全量 sweep 的成本账与实验设计

**（1）一笔明账（DoorDash 原文数字）。** 仿真评测的经济性是它成为 CI 门禁的前提：

| 项目 | 数字 |
|---|---|
| 全量 sweep 规模 | **50 场景 × 8 trials = 400 次对话** |
| 人工本地聊 | 约 1 分钟/次 → **6+ 小时** |
| 模拟器并行跑 | **约 20 分钟** |
| 飞轮吞吐 | **5 分钟内跑 200+ 场模拟对话** |
| 门禁纪律 | 一次触发跑完全流程，**任何变更必须通过全部 50+ 个 eval 才能上线** |

两个数量级的时间差，正是"回归集只增不减"（第 E10 章）在经济上成立的前提。
DoorDash 报告的整套成果数字：质量信号从平均 **1 条/天**员工反馈 → **2,000 个/天**自动评分会话；
全国上线前 agent 质量分 **+8 分**、错误率**近乎减半**，达到生产发布标准；
11 轮迭代中第 3 轮曾回落——回归是常态，门禁的价值正是抓住它；
**模拟环境幻觉率下降约 90%**；离线提升与线上真实流量表现一致。
这套 harness 还支撑了底座模型迁移（Claude Sonnet 4.6 → Gemini 3.5 Flash）：
先被离线评测拦下（分数大跌），定位为兼容性差距而非能力差距，小修后
**延迟降 35%、质量无损**（案例全程见第 E15 章）。

**（2）为什么是 8 trials。** 每场景重复 N 次不是浪费，而是可靠性测量本身：
N 次独立运行支撑 pass^k 估计（τ-bench 口径报 pass^1 与 pass^8），
并吸收模型采样与模拟器行为的方差。实验设计要点：

- **固定模拟器与 seed**：模拟用户的模型版本、温度固定，随机种子受控——模拟器是非确定性来源之一，其变异要么固定、要么用多 trial 吸收（统计处理见第 E9 章）；
- **trial 间环境重置**：fixture 保证外部状态一致，每条 trial 从干净状态启动；
- **报告统计口径**：通过率带置信区间（Wilson/bootstrap），版本对比用配对检验——
  400 次对话的样本量下，多大的分差才算"真变好"是统计问题而非感觉问题（第 E9 章）。

**（3）分层预算。** E2E 对话仿真位于评测金字塔顶层（单元 grader → 轨迹/结构测试 → E2E 模拟，
arxiv 2601.18827，2026），是最贵的一层。落地节奏通常是：PR 触发 smoke 场景子集（少量场景 × 少 trial）
+ 每日/每次模型变更跑全量 sweep + 高风险切片（欺诈、退款、人工接管）常设。
OpenAI 托管 Evals 平台的下线（2026 宣布）也提示：**评测资产（场景 + fixture + rubric）
要用开放格式托管在自家仓库，与运行平台解耦**（第 E10 章）。

### 2.7 模拟器的保真度与仿真评测的边界

仿真评测最大的风险不是技术故障，而是**在假用户身上测出假结论**。三个层次的清醒：

**（1）模拟器 ≠ 真实用户。** 模拟器与被测 agent 常用同族模型（同源偏差），可能互相"太好懂"；
合作型模拟高估、非合作型又可能过于刁钻；学界尚无公认的"模拟器保真度"标准指标。
DAUS（arxiv 2402.13374，2024，Amazon）直面了这个问题：**未经微调的通用 LLM 当用户模拟器
不可靠——会偏离用户目标、幻觉出不存在的对话事实**；DAUS 用领域数据微调 + 受控解码，
显著提升目标一致性（goal compliance）并抑制幻觉行为，使模拟对话更接近真实分布。
工程结论：**用户模拟器本身需要被"评测与校准"——模拟器质量直接决定下游 agent 评测效度；
领域微调/对齐模拟器是工业级仿真评测流水线的常见投资。**

**（2）保真度抽检的常规动作。** 没有单一指标能裁决保真度，工业界的务实做法是一组抽检：

| 动作 | 检查什么 | 失效信号 |
|---|---|---|
| 真实对话小样本对照 | 模拟会话与真实会话在轮次分布、升级率、失败模式上是否同构 | 模拟器"太乖"或"太刁" |
| 换模拟器模型敏感性分析 | 换另一个模型当用户，版本对比结论是否翻转 | 结论翻转 → 测的是"应付某模拟器的技巧" |
| persona 来自真实日志 | 隐式画像（2502.18968）/真实工单抽取是否持续更新 | 校准集过时，分布漂移 |
| offline-online 相关性回测 | 离线模拟涨幅是否在线上兑现 | 系统性不兑现 → 重建场景库 |

**（3）offline-online gap：离线是必要不充分。** 学术侧的实证很直接：
真实客服对话基准研究（arxiv 2510.22143，2025）明确指出，由于部署环境的分布漂移与交互复杂性，
**强 offline 基准成绩只是部署可靠性的弱指标**。另一侧，Discord 的 AITL 数据飞轮
（EMNLP'25 工业赛道，ACL Anthology 2025.emnlp-industry.135）把
offline 与 online 评测设置之间的一致性当作专门对象来量化。
DoorDash 能报告"离线提升与线上一致"，前提是同一 rubric + 同一校准 judge 两边跑。
完整治理链路：**离线门禁 → shadow → canary → A/B → 线上抽样评测**，
阿里给了最硬的联动规则：**离线提升但线上关键信号（转人工率、重复追问率、投诉率、满意度、
任务完成率、工单闭环率）恶化 → 触发回滚或降级**（发布联动详见第 E12 章）。

**（4）仿真评测系统自己也会坏。** DoorDash Lesson Learned 第四条：
**评测系统自己也产生 bug 报告**——被标记的失败中有真实一部分是 harness 自身故障
（judge 误报、trace 缺口），需要与业务 bug 并行修复。
所以成熟的仿真流水线都保留一条"harness 健康度"指标：A/A 噪声基线、
judge 与人工抽检的一致率漂移、fixture 失效率。评测系统本身也要被评测（主手册第 8 章同此观点）。

## 四、经典面试题与参考答案

#### 题 1（基础）：评测对话 Agent 和评测单轮问答有什么本质区别？为什么不能把每轮分数取平均当会话成功率？

**参考答案：**
单轮评测是"输入→输出→对照参考"，对话评测面对五个特殊难点（阿里归纳）：
① 上下文累积——关键信息跨轮分布、可能被后文覆盖；② 目标切换——用户中途改主意，一个会话多个子目标；
③ 情绪回应——答案对但语气差会升级为投诉；④ 人工接管——转接时机与交接质量本身要评；
⑤ 多轮引导——指挥用户操作比自己执行更难（τ²-bench 定量证明）。
不能平均的原因：每轮都"答得还行"但最终没解决问题仍是失败——Turn 层的礼貌流畅无法推出
Outcome 层的任务达成，用户绕八轮没退成款，平均每轮 4 分没有任何意义。
正确做法是四层分开看：Outcome 做最终裁决与门禁，Turn/Session/Trace 做归因与体验迭代，互不替代。

#### 题 2（基础）：什么是 fixtures？为什么仿真评测环境必须冻结外部状态？

**参考答案：**
fixtures 是把工具的真实返回录制成固定 payload，评测运行时拦截调用、原样回放。
原因：对话 Agent 背后的目录、库存、账号状态都在实时漂移，若评测时实时调用，
同一条用例每次测的是不同的题——分差可能全部来自环境而非 agent。
DoorDash 的教训原话是"环境必须受控，否则分数测量的是噪声"。
实例：复购场景开场 "Reorder my usuals"，`get_reorder_items` 固定返回录制的
`reorder_history_v1`（Albertsons 订单：Meadow Gold 全脂牛奶 ×2、Oroweat 全麦面包、
牛油果、Ben & Jerry's 冰淇淋），每次运行看到相同订单，预期结果可预测，judge 可对照同一商品集评分。
附带收益：fixtures 还能构造欺诈、大额退款等真实流量里罕见的难例，对冲幸存者偏差。
治理三件事：fixture 版本化、定期与生产 API 对账防 mock 漂移、用例间环境隔离。

#### 题 3（进阶）：请设计一个用户模拟器的 scenario 结构。怎样让模拟用户的行为"像真人"而不是"念台词"？

**参考答案：**
scenario 三要素（DoorDash 定义）：**开场请求**（模拟器的第一句话）、**用户目标**（含期望结果）、
**反应策略**（对提问/结果的反应方式）。persona 建议携带脾气、情境叙事、期望结果，
从真实工单抽取，或用隐式画像方法从真实日志反推（arxiv 2502.18968）。
行为真实性靠动态判断而非脚本：模拟器每轮回答四个问题——是否已解决、是否有进展、
是否需要更多信息、是否在绕圈——据此选择配合、补充、追问或升级。
升级行为要像真人：给过几次机会、反复答差才投诉，会反驳、逐步升级而非一上来就转人工（DoorDash）。
还要刻意包含非合作切片：用户不耐烦、跑题、表达模糊、中途改主意（ChatChecker，arxiv 2507.16792），
因为合作型模拟会系统性高估 agent。配置应是数据不是代码——可序列化、可版本管理、非工程师可写。

#### 题 4（进阶）：τ-bench 的评测范式由哪些组件构成？它的 pass^k 数字说明了什么？

**参考答案：**
四个组件：① LLM 用户模拟器与 agent 多轮对话；② agent 需遵守领域政策（retail/airline 业务规则）
并调用 API 工具；③ 以**数据库终态哈希**做可验证判定，而非只看对话文本——抗话术干扰；
④ 用 pass^k 刻画可靠性：单次通过率在多次独立试验下的一致性。
数字（论文摘要转述）：GPT-4o retail 域 pass^1 ≈60%（官方榜单 60.4%）、airline 域 ≈42%，
而 pass^8 跌至约 25% / 16%——"能做对一次"与"稳定做对"差距巨大，
因为对话每多一轮、误差复合一次。工程推论：生产级对话 Agent 应以 pass^k（低 k）作发布门槛，
pass@1 只作能力上限参照；τ²-bench（arxiv 2506.07982）进一步把用户侧升级为能动手的"双控"，
最强模型双控成功率也远低于单控——引导用户操作比直接操作难得多。

#### 题 5（进阶）：为什么 checklist 式 rubric 比宽泛标准更适合仿真评测？请举一个设计实例，并说明 eligibility 前置的作用。

**参考答案：**
宽泛标准（"购物清单是否合理"）人各有解，judge 判定方差高，需要大样本才看得出差异；
checklist 把开放式目标拆成非真即假、可附证据的检查项，判定一致性高、方差低，
**小样本也有用，支撑更快迭代**，且失败时能定位到具体坏项。
实例（DoorDash 杂货场景）："两人份 ≤$60 素食 taco 购物清单"——逐项验证每件商品都是素食 taco 原料、
小计 ≤$60。每条标准都是 binary check，汇总为会话级总分。
eligibility 前置：judge 先判该标准是否适用本会话，不适用则跳过——食谱流程不因缺复购步骤被扣分。
没有这一步，标准越多误伤越多；有了它，rubric 才能跨场景复用。
延伸：判定要独立于对话氛围——编造商品的 agent 可能让模拟用户满意收尾，
所以结果检查必须查事实（商品真实性、价格），不能只问"用户是否满意"。

#### 题 6（进阶）：用户模拟器本身也是 LLM。你如何验证它的可靠性，防止"在假用户身上测出假结论"？

**参考答案：**
先承认已知缺陷：DAUS（arxiv 2402.13374，Amazon）证明未经微调的通用 LLM 模拟器会偏离用户目标、
幻觉出不存在的对话事实；模拟器与被测 agent 同族时存在同源偏差，互相"太好懂"；
学界尚无公认的保真度标准指标。验证手段分四层：
① 模拟器自身指标：目标一致性（是否守住 persona 目标）、幻觉率（是否编造不存在的事实），
必要时领域微调 + 受控解码（DAUS 路线）；
② 真实对话对照抽检：模拟会话与真实会话在轮次分布、升级率、失败模式上是否同构；
③ 敏感性分析：换一个模拟器模型重跑，若版本对比结论翻转，说明测的是"应付特定模拟器的技巧"；
④ offline-online 相关性回测：离线模拟涨幅是否在线上兑现，系统性不兑现就重建场景库。
组织上把模拟器当资产管理：persona 从真实日志持续挖掘更新（隐式画像/数据飞轮），
合作/非合作/模糊/易怒等切片齐全，定期保真度抽检。

#### 题 7（系统设计）：为一个外卖/零售客服对话 Agent 设计端到端仿真评测体系。

**参考答案：**
按"场景库—演员—舞台—判官—门禁—回流"六层设计：
**① 场景库**：scenario = 开场请求 + 用户目标 + 反应策略，persona 从真实工单抽取
（脾气、情境叙事、期望结果），覆盖复购、退款、投诉、目标切换、难缠用户等切片；
每条场景带 provenance 与 slice 标签，场景即数据、可版本管理。
**② 模拟器**：LLM 扮演用户，动态判断解决/进展/缺信息/绕圈，升级像真人（给过机会才投诉）；
含非合作切片；固定模型版本与 seed。
**③ fixtures**：录制工具返回冻结目录/库存/订单状态；专门构造欺诈、大额退款难例；
fixture 版本化并定期与生产对账；用例间环境隔离。
**④ 判分**：场景级 checklist rubric（binary check + eligibility 前置）+ 终态校验（订单/退款状态）；
judge 逐条标准独立评分、输入为 transcript 证据切片 + 工具调用 + 政策，输出 verdict + rationale；
judge 用人工标注校准（GEPA 打磨，一致率达标才进门禁）；评测镜像运行时架构——路由、护栏、领域能力分开评。
**⑤ 门禁与实验设计**：全量 sweep = 场景 × 8 trials（支撑 pass^k 与方差吸收），
PR 跑 smoke 子集、每日与模型变更跑全量；通过率带置信区间，版本对比用配对检验。
**⑥ 回流**：线上失败与 harness 自身故障（judge 误报、trace 缺口）分两条线修复；
同一 rubric + 同一 judge 跑线上抽样，离线升线上降触发回滚；失败场景回流为新 scenario。
成本锚点（DoorDash）：50 场景 × 8 trials = 400 对话，人工 6h+ → 模拟器约 20min；
上线前质量分 +8、错误率近乎减半、2,000 会话/天自动评分。

#### 题 8（系统设计/开放）：你的对话 Agent 仿真评测全绿，但上线后转人工率与投诉率没降。给出你的排查框架与治理方案。

**参考答案：**
先定位差距来源，五个候选：
① **模拟器失真**：合作型用户过多、persona 过时、模拟器与被测模型同源互相迎合——
做真实对话对照抽检与换模拟器敏感性分析；
② **rubric 与真实痛点错位**：仿真测的是任务完成，投诉来自语气、等待、解释缺失、
结果对了但没告知（把线上投诉做归因分类，反查评测盲区）；
③ **环境保真度不足**：fixture 与生产漂移、线上才有的真实数据形态（超长订单、多语言）没覆盖——
fixture 对账 + 用线上真实会话补场景；
④ **offline-online 口径分裂**：离线线上两套 judge 或两套 rubric——统一为同一 rubric + 同一校准 judge
（DoorDash 原则三：各自调 judge 分数会难调和地背离）；
⑤ **分布漂移**：评测集停留在旧分布——对比线上抽样与场景库分布做覆盖度审计。
理论锚点：arxiv 2510.22143 明确强 offline 成绩只是部署可靠性的弱指标；
阿里联动规则最硬：离线提升但线上关键信号恶化 → 回滚或降级。
治理上把仿真定位成"必要不充分"：离线门禁之外保留 shadow/canary 第二道闸，
线上抽样用同一 rubric 持续评分，offline-online 相关性定期回测，不兑现即重建场景库。

## 五、易错点 · 反直觉点

1. **把每轮分数平均当会话成功率**：每轮都礼貌流畅，用户绕八轮没解决问题仍是失败。
   → 真相：Outcome 层才是最终裁决，Turn 分只做诊断。→ 记忆锚点：**平均分会奖励"礼貌地不作为"。**
2. **用历史会话重放测新版本**：以为录像回放最真实，实际 agent 一变更，对话路径完全不同，重放测的不是同一个交互。
   → 真相：DoorDash 的结论是"按需生成会话"，模拟器驱动 agent 现场跑场景。→ 记忆锚点：**重放测的是旧 agent 的过去，不是新 agent 的未来。**
3. **评测时实时调用外部 API**：目录在变、库存在变、账号在漂移，同一条用例每次测的是不同的题。
   → 真相：fixtures 冻结外部状态，分数差异才能归因于 agent。→ 记忆锚点：**环境不受控时，分数测量的是噪声。**
4. **模拟用户太合作**：礼貌、信息完备、轻易满意的模拟器，把 agent 测出礼貌的假高分。
   → 真相：合作型模拟系统性高估；场景库必须有不耐烦、跑题、改主意的非合作切片（ChatChecker）。→ 记忆锚点：**假用户不会投诉，假分数不会说谎——只会骗你。**
5. **模拟器与被测 agent 同源**：同族模型互相"太好懂"，评测变成自家人对暗号。
   → 真相：同源偏差需靠换模拟器敏感性分析与真实对话抽检对冲；模拟器质量直接决定评测效度（DAUS）。→ 记忆锚点：**裁判、模拟器、被测者，三角关系越独立越可信。**
6. **fixture 写完不维护**：上游 schema 变了、字段语义变了，fixture 还停在旧世界，评测全绿、上线即炸。
   → 真相：fixture 要版本化、定期与生产 API 对账（mock drift 治理）。→ 记忆锚点：**冻结的是状态，不是维护责任。**
7. **只报 pass@1 不报 trial 设计**：单次成功率 61% 听起来不错，τ-bench 里 GPT-4o 的 pass^8 只有约 25%。
   → 真相：对话/客服类生产场景必须报 pass^k 与试验次数，能力上限与可靠性分开报告。→ 记忆锚点：**能做对一次 ≠ 稳定做对。**
8. **只看"用户是否满意"判成功**：编造商品的 agent 可以让模拟用户满意收尾。
   → 真相：结果判定要独立于对话氛围——查事实（商品真实性、价格、终态），满意度只是 P2 观察项。→ 记忆锚点：**满意可以被话术制造，终态不会撒谎。**
9. **把仿真当终点**：离线模拟全绿就直接全量上线。
   → 真相：强 offline 成绩只是部署可靠性的弱指标（arxiv 2510.22143）；仿真之后还有 shadow/canary 与线上同 rubric 抽检，离线升线上降要敢回滚。→ 记忆锚点：**仿真是排练场，不是公演。**
10. **忽略 harness 自身故障**：失败列表里全是"agent 的错"。
    → 真相：被标记失败中有真实一部分是评测系统自己的 bug（judge 误报、trace 缺口），要并行修复（DoorDash Lesson 4）。→ 记忆锚点：**秤不准时，先修秤再称象。**

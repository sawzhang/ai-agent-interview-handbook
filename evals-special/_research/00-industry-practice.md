## 一、Airbnb：Eval-Driven Development（EDD）方法论

### 背景与三大坑
- GenAI 与传统软件差异：输出不可预测、"正确"依赖判断、用 AI 评 AI 引入新风险；一次请求可能同时含搜索/推理/外部动作/文本生成，每环节可独立失败。
- 应用场景：点评摘要、客服、房东/房客消息、内部洞察。产品团队自定标准，基础设施组供共享工具与跨团队指南（是实践不是强制令）。
- 无早期评测计划的三个常见坑：**虚假信心**（浅层 helpfulness 分）、**未被发现的回归**（改 prompt 后质量悄悄变差）、**浪费精力**（指标与产品结果脱节）。
- 核心习惯："When in doubt, look at your data."——跑约 100 个样本（真实或合成），人工读输出和 trace，找错误、归类，再围绕它们建测试。

### EDD 五原则
1. 尽早设定目标与上线门槛（launch gates），即便它们在数据评审中才逐渐清晰。
2. 从观察到的错误中推导指标，与跨职能伙伴共同制定。
3. 用少而精的 judge：3–5 个经校准的评估器好过一堆嘈杂的评估器。
4. 指定一个最终人类决策者，裁决"好 vs 坏"争议。
5. 让产品伙伴持续参与对比与错误诊断。

### 三层评估框架
1. **程序化检查**（确定性、最先跑）：格式/schema 校验（永远有用）、空/异常长度（永远有用）、关键词正则（安全合规）、P/R/F1（分类任务）、语义相似度（有参考答案时）。建议用结构化输出（JSON schema 严格类型化），不要只靠 prompt 措辞产出结构，否则下游管道会坏。
2. **LLM-as-a-Judge**：强模型按 rubric 评另一模型输出（语气/连贯/有据性/相关性），成本低于全量人工。规则：每个质量维度一个 judge；judge 模型尽量与生成模型不同；带 few-shot；强制输出 schema；清晰打分说明。"如果人都无法一致地应用 rubric，模型也不可能。"
   - Rubric 实例（房源 listing 解释可读性）：好输出像"热情专业的旅行顾问"记 1 分；语气错误/内部术语/格式差/语法问题/措辞过繁记 0 分；judge 返回 reason + 0/1。
3. **人工评估**：建 ground truth、安全高风险决策、细微差别与创意、解决自动评估器间冲突。从 20–100 个专家标注样本起步；rubric 稳定且需要规模时才扩大标注队伍；专家有分歧就先停下解决分歧再自动化。

### Judge 校准五步
1. 建 50–100 条 gold set（必须含坏样本）；2. 用 judge 跑该集合；3. 目标一致率 high 80s~90s%，分歧可用 Cohen's kappa / Krippendorff's alpha 度量；4. 检查分歧→改 rubric/示例→重复；5. 失败模式变化时重新校准。未校准 judge 会制造误导性信心。

### 开发阶段映射
评测方法按 开发期/发布前/生产 三阶段映射，强调分层防御与持续监控，而非一次性测试。

### Agentic 评估三层
- 只看最终答案不够：推理路径、工具参数、工作流可能在结果看似正确时已经失败。
- **Step-level**（单工具调用/推理步）/ **Trajectory-level**（整体路径是否合理高效）/ **Session-level**（整个交互是否达成用户目标）。
- Agent 通常在 root 下发 trace 和 span；可通过树遍历重建 trace，校验 subagent 调用与工具使用。

### 实战演练：旅行平台客服政策问答助手
1. 探索：跑 100 个 prompt 读输出 → 发现 15 个 groundedness 失败、8 个正确但啰嗦、5 个不当拒答、3 个 JSON 失败。
2. 建测试：JSON 与长度检查；groundedness/conciseness 各一个 judge；PM/SME 标注 60 条 gold（含失败样本）。
3. 校准：judge 初始一致率 78%（过低）——judge 误罚了正确的改述；修 rubric 与示例后达 88%；检索改进减少 groundedness 失败。
4. 规模化与监控：扩到 5,000 样本；每日抽样 5% 去标识化生产流量；跑检查与 judge；标记样本送人工；每周 PM 评审，新增测试与修复。

### 迭代纪律
一次只改一个变量：先固定模型变 prompt → 再固定 prompt 变模型 → 再都固定变 serving 配置。Judge 筛候选，顶尖候选反哺 judge 改进，直到双方稳定。

### 隐私
生产抽样用隐私保护方法：人工评审前去标识化、用途限定于安全与质量。

### 十条要点
① 建复杂工具前先人工看输出与 trace；② 避免泛化 helpfulness，瞄准真实产品失败；③ 从小标注集起步快速迭代；④ 不要万能 judge，按维度拆分；⑤ judge 校准到高一致率后再信任；⑥ 代码检查+模型 judge+人工评审结合；⑦ gold set 必须含坏样本；⑧ 评整个系统（检索/工具/agent 路径）；⑨ 上线前测试要在线上持续运行；⑩ 评测是跨职能产品活动。

## 二、DoorDash：Ask DoorDash 评测 Harness（原文全文精读）

### 成果数字
- 质量信号：平均 1 条/天员工反馈 → **2,000 个/天自动评分会话**。
- 全国上线前 agent 质量分 **+8 分**，错误率**近乎减半**，达到生产发布标准。
- 全量回归：手工 **6+ 小时 → 自动约 20 分钟**。
- 支撑底座模型迁移（Claude Sonnet 4.6 → Gemini 3.5 Flash）：**延迟降 35%**、质量无损。

### 五大挑战 → 五大设计要求（原文表格）
| 挑战 | 设计要求 |
|---|---|
| 开放式目标（一个用户目标有多种可接受结果） | 每个目标表达成 rubric：具体到每次能同样判，宽泛到容纳所有合法路径 |
| 执行不可见（judge 需要看到对话之下的工具调用；不同标准需要执行记录的不同部分） | trace 会话并重建为"按标准定制的视图"，judge 只看该标准需要的证据，隔绝无关 trace 噪声 |
| 无法安全彩排（不能拿真用户试变更，历史会话不能对改过的 agent 重放） | 按需生成会话：模拟用户驱动 agent 跑场景，外围数据固定（fixtures），同场景每次一致 |
| 规模化判断（是否帮到用户需要人类级判断，但人工不可扩展） | 校准过的 LLM judge 顶替人类评审 |
| 双环境（开发与生产质量可能背离） | 真实会话与模拟会话用同一 rubric + 同一 judge：离线结论带到线上，线上失败离线复现 |

### 评测镜像运行时架构
多智能体架构：用户消息 → Orchestrator → 路由到领域 Agent（如 Restaurant Discovery Agent）；领域 Agent 直接处理或交还 Orchestrator。评测同形：**路由在 Orchestrator 评；护栏贯穿全流程评；任务能力在每个领域 Agent 评**。

### Rubric
- 每条标准是 binary check，汇总为会话级总分。
- 三类评测实例：Guardrail（全体 agent，如"沟通质量：回复简洁、不向用户叙述思维过程"；"信任与诚实：不呈现可证伪虚假信息"）；Capability·餐厅发现（"约束满足：推荐满足配送时间/预算/饮食限制"；"结果多样性：真实差异而非近似重复"）；Capability·杂货购物（"购物执行：用户的明确修改请求被执行"；"商品相关性"）。
- **Eligibility 适用性前置**：judge 先判该标准是否适用本会话，不适用则跳过（食谱流程不因缺复购步骤被扣分）。
- **离线 checklist 式 rubric**：场景级清单。例："两人份 ≤$60 素食 taco 购物清单"——验证每件商品都是素食 taco 原料、小计 ≤$60。比宽泛通用标准方差更低，小样本更有用，支撑更快迭代。
- 每条标准写成"从会话本身可验证"——同一 rubric 既供人工校准又供 judge 规模化。

### Transcript Builder
- 每会话用 **OpenTelemetry** 打点；trace 存内部 **ClickHouse**；span 记录用户输入、模型输出、工具调用与返回、展示给用户的 widgets。
- 原始 trace 完整但难判：工具返回可能巨大；schema 脚手架与无信号字段多；证据散落多 span/turn。
- Transcript Builder = 一组 Python 脚本：重组分散 span、删无质量信号 token、裁超大载荷 → 紧凑视图。
- **每条标准声明依赖的证据，builder 只给 judge 那一片**：grounding 检查拿 agent 论断+背后工具输出；多样性检查拿推荐+原始请求；叙述检查拿 agent 工作时流式输出的文本。聚焦证据让判断更一致。

### Conversation Simulator
- LLM 扮演购物者；scenario 定义开场请求、用户目标、对提问/结果的反应方式。
- 依赖外部状态时用 **fixtures**：录制工具返回替代实时调用。例：复购场景开场 "Reorder my usuals"，`get_reorder_items` 固定返回录制的 `reorder_history_v1`（Albertsons 订单：Meadow Gold 全脂牛奶 ×2、Oroweat 全麦面包、牛油果、Ben & Jerry's 冰淇淋…）。每次运行看到相同订单 → 预期结果可预测，judge 可对照同一商品集评分。
- 成本账：全量 sweep = **50 场景 × 8 trials = 400 次对话**；人工本地聊约 1 分钟/次 → 6+ 小时；模拟器约 20 分钟。

### LLM-as-a-Judge
- 定位：带紧反馈环的测量问题——样本够多（每天估计生产质量）+ 出分够快（不成为发布瓶颈）。
- 人工用在杠杆最大处：**定 rubric、标注校准集、审计 judge 行为**；打分主力是 judge。
- "LLM Judge only useful if it agrees with human reviewers."
- 校准方法：用 **GEPA prompt optimization** 打磨 judge 判定边界——迭代提出 judge prompt 修订，只保留在留出集上提升与人工标注一致率的版本。校准持续：rubric 演进（新增能力）时收新标注、重新校准。
- judge 逐条标准独立评分：输入=标准+该标准依赖的证据；输出=verdict+简短 rationale。

### Eval Service（平台化）
trace 存储、实时评测执行、UI 化 judge 开发、标注工作流。起步用嵌入式平台团队与 harness 并行共建；正沉淀为共享评测服务（paved path）供其他团队采用。

### 反馈闭环
1. **失败聚类成主题**：逐条看失败会"轶事驱动"（最近/最惊奇失败主导修复）。**rubric 标准天然是问题簇**——grounding 失败/缺替代品/糟糕叙述分开调查 → 失败列表变按影响排序的主题列表。
2. **从发现到解决**：瓶颈转移到"选对改动并验证影响"。从失败簇出发，**coding agent 检查失败 trace、相关代码路径、近期变更、历史调查**；修复明确时直接起草 PR；prompt/上下文学习改动则产出诊断+建议供人审。
3. **Agent Skills 化**：把 eval-driven 工作流（聚类失败、调查失败模式）打包成 Agent Skills——可重复、可复用、可改进。skill 分错簇或写弱修复 → 更新 skill 而非打补丁一次性运行。
4. harness 不只是记分板，是**迭代的控制面（control plane for iteration）**：生产监控+失败聚类+agent 辅助调查+发布前验证连成一环。

### 案例 1：Reasoning leakage
- 日常线上评分发现泄漏激增：任务完成但叙述冒出系统语言（"reorder skill"、工具名、"fetch"、"in parallel"）——"像编码 agent 而非购物助手"。
- 诊断指向 prompt 设计：合并沟通规则，分离内部 skill 指令与面向用户语言。
- 离线用生产中最易触发的场景验证：**泄漏率降 11%**；hero 场景全量扫描无回归；上线后监控确认阶跃改善。

### 案例 2：底座模型迁移
- agent 跑在 Claude Sonnet 4.6；5 月中 Gemini 3.5 Flash 发布，benchmark 显示可降延迟。
- 离线 harness：**分数大跌**。eval 给出具体失败模式，AI coding agent 做假设与实验。
- 结论：**不是能力差距，是兼容性差距**——Flash 部分工具参数格式不同（工具签名要 plain string，Flash 传 `{"dishes": [...]}` JSON 对象）；系统 prompt 围绕 Sonnet 惯例隐式调优。"低分反映为 Sonnet 适配的系统，不是更弱的模型。"
- 修复小而准：工具输入确定性防护（错误形状**强制转换**回预期形状而非丢弃调用）；prompt 显式写出 Sonnet 原本自行推断的内容（用数据中精确店名、不超出工具结果渲染）。"不是改模型，是修正模型周围的环境。"
- 重跑 eval：Flash 与 Sonnet 质量持平（harness 噪声范围内）→ 迁移生产 → 延迟降 35%、质量无损。

### 四条 Lessons Learned
1. Judge 需要"为问题塑形"的 transcript 视图——删无关、只留标准依赖的证据。
2. 环境必须受控，否则分数测量的是噪声——fixtures 冻结上游世界，固定场景稳定任务条件。
3. 离线结果只有能带到线上才有意义——同一 rubric+同一校准 judge 两边跑；各自调 judge 分数会难调和地背离。
4. 评测系统自己也产生 bug 报告——被标记失败中有真实一部分是 harness 自身故障（judge 误报、trace 缺口），并行修复才可信。

## 三、阿里技术：Agent 评测方法论与体系设计（十章精读）

> 总命题：Agent 评测是把「不稳定的智能行为」持续收敛成「可发布的工程质量」，不是上线前抽查。
> 三大门槛：非确定性（同输入不一定同输出）、黑盒化（内部决策不透明）、错误级联放大（前步小错后续放大）。

### 为什么"跑几条 case 感觉还行"不够
同一 prompt 跑通一次≠稳定可用；每次改模型/prompt/工具参数都可能改坏原有场景且不易第一时间发现；多步链路前一个小偏差会被放大成错误结论；更隐蔽：有些样本最终答案看似对，但执行路径已偏离或带风险——这类假阳性在生产迟早暴露。
评测体系必须嵌入研发流程；评测平台不只是"出分工具"，核心价值是把问题稳定转化为可执行修复、形成持续迭代闭环。成熟体系要回答三类问题（评什么/怎么判/怎么用）。

### Agent 类型与评测侧重
先分类型再定指标，"类型不分，评测结果基本不可用"。评测骨架可复用（执行用例→采集 Trace→Scorer 评分→报告→根因归类），按业务定制的是"评什么、怎么判"。Skill 本身也需测评：是否该触发、触发后流程对不对、工具参数对不对、产物是否可用、异常能否降级。

### 对话 Agent 五个特殊难点与四层评判
上下文、目标切换、情绪回应、人工接管等。不要只平均每轮分数：每轮都"答得还行"但最终没解决问题仍是失败。同时看 **Turn（单轮）/ Session（整段会话）/ Trace（执行轨迹）/ Outcome（最终结果）**四层。

### 指标体系（P0/P1/P2）
五大类指标，**P0 上线门禁（不达标不发）、P1 版本比较与工程优化、P2 体验改善与长期观察**。
一致性双指标：任务重复运行 N 次——**至少一次成功率**（能力上限）vs **连续成功率**（每次都要成功，客服/支付/退款/合规等生产级场景）。用户不会接受"多试几次总有一次成功"。
版本对比要配套统计检验：**关键指标置信区间 + 与基线的显著性判断 + 最小可感知变化阈值**（提前定义提升多少才值得发布）。"门禁不只看差了多少，还要看差异是否超过统计噪声。"

### 评测数据集建设
- 评测集不是线上随机抽样——线上样本有**幸存者偏差**：正常流程占多数，易错边缘场景占比低；随机采样报告"看起来不错"但关键问题漏掉。
- Golden Set 默认作为基线评测集（相对稳定、长期复用的核心样本），用于版本对比与发布门禁。
- 四类来源：**专家设计用例**（定标准）；**扩展用例**（先用规则确定场景类型/订单状态/用户诉求/期望动作等结构字段，再用 LLM 生成接近真实用户的自然语言表达）；**线上真实数据**（真实客服会话/工单）；**badcase 回流**（如"Agent 直接承诺一定退款成功"）。
- 规模路径：**先做 50–200 条高质量 golden set** 覆盖核心业务路径与高风险边界；成熟后扩展分类采样集、长尾集、对抗集、线上回流集。
- Skill 用例沿"触发→核心逻辑→产物质量→异常容错"组织：先确认该不该触发→过程对不对→产物好不好→异常/工具失败/边界下稳不稳。核心逻辑用例最多，覆盖主要分支与高风险分支。

### 评分：规则主判，Judge 辅助，人工兜底
- 规则看"硬条件"（工具、状态、字段、禁用动作），LLM 看"语义/策略合理性"；能写成代码的由规则主判；高风险/抽检/低置信/变更观察期追加 LLM Judge；能自动稳定判断的不长期依赖人工。
- 好的 LLM Judge：每分档有可执行标准；输出 reason（定位+badcase 聚类）；few-shot 含边界样本与判定 CoT；**周期性校准，与人工复核一致率约 85%（参考值）后进日常自动化**；偏差治理（judge 与生成模型同源会偏爱自己风格 → 多 LLM 对抗打分）。
- 人工评分适用环节：新建评测集定口径（如"订单已发货+用户拒收+运费险+特殊类目"该走哪条流程需业务先定）；校准 Judge（抽一批人工先判——judge 能判礼貌/清晰，但判不了"叠加优惠差价是否应补偿"这类依赖内部政策的问题）；处理争议样本；抽查高风险场景（赔付/隐私/合规/投诉升级，自动通过也要定期人工复核）。
- **人工评分路由**：不由分数阈值单独决定——自动评分不确定（边界分/低置信/reason 含糊/多 judge 分歧）进人工；新模型/新 Prompt/新工具 Schema/新活动上线抽样进人工；规则与 Judge 冲突进人工终判并回收口径。
- **分层筛查**：粗筛层（规则 Scorer+轻量 Judge，快速分明显通过/明显失败/存疑）→ 精判层（完整规则+Judge，确认 badcase 并产出初始问题分类/现象/置信度/判定依据）→ 人工复核层（高风险/低置信/冲突/口径未固化）。
- 评分输出不止 pass/fail：还要**问题分类（现象层：事实性错误/答非所问/过度承诺）/问题现象/置信度/判定依据**——为 RCA 提供"现象入口"。现象分类≠最终根因。
- 假阳性 case（回复看似正确但路径/风险检查不过）→ 加过程型与风险型检查。
- Judge 持续运营：维护 Judge 金标校准集；每次 Judge prompt/模型升级固定产出三类统计：**与人工标注一致性（一致率或多模型对抗 Kappa）、高风险样本漏判率（合规/资损/隐私）、边界样本稳定性（重复评测波动）**。

### Badcase RCA 五步（第 7 章）
入口两条通路：离线评测集 + 线上（会话/人工质检/投诉工单/低满意度/版本回归失败/监控告警）→ 汇入同一 badcase 任务表与同一 RCA Pipeline。
1. **证据汇总**：按 sessionId/chatId/traceId/评测运行 ID 找链路日志，汇总用户输入、Agent 回复、模块 IO、prompt、工具调用、异常、耗时、中间产物。状态以持久化任务记录为准。
2. **范围收敛**：不对全模块无差别分析（成本高噪声大）。维护"**问题现象 × 功能模块**"映射：答非所问→优先看意图识别/Query 改写/知识筛选；过度承诺→优先看风险拦截/回复生成；订单未澄清→槽位抽取/上下文判断。命中走确定性路径，未命中 LLM 兜底缩圈。映射表只缩小候选，不直接定责。
3. **分模块诊断**：候选模块逐个读 input/output/prompt/工具返回/异常日志，输出问题摘要、关键证据、改进建议、结构化归因字段。实例：现象"事实性错误"→先看 FAQ 检索是否召回正确政策→知识检索是否保留关键片段→回复生成是否忠实使用证据；前两段通过而回复仍错 → 回复生成 FAIL，前两模块 PASS/SOFT_PASS（基本通过但轻微瑕疵）。
4. **责任判定**：消费"现象+分模块诊断+根因知识库"，输出责任模块/问题分类（报告大类：语义理解/知识召回/工具执行/风险防控）/问题枚举（更细失败类型）/修复建议。三层策略：严重模块结论直接定责→规则引擎匹配确定性模式→LLM 汇总复杂链路责任传递。
5. **结构化落盘**：写入任务记录（问题分类/现象/枚举/责任层/责任模块/置信度/详细报告/修复建议），看板渐进展示。
- 工程实现：单次 badcase 分析建模为异步 Multi-Agent Workflow。RCA 也按"确定性优先、模型辅助、人审兜底"：规则定位硬错误（工具未调用/顺序违反 SOP/参数缺失/报错未重试/DB 状态未变/引用来源不存在）→ Trace Scorer 定位过程偏差（计划与目标不一致/证据不足/工具返回被误读/上下文被覆盖）→ 映射表缩圈 → LLM 辅助语义归类聚类（"解释不完整/口径理解错/意图澄清不足"映射到既有分类，避免同类拆散）→ 高风险/低置信/冲突进人工复核，人工结论反校准规则/Judge Prompt/根因标签。
- 根因标签要稳定、可统计、指向 owner 与处理动作；可绑定解决角色：运营可配置/算法需优化/工程需修复/业务需定口径。实例："已发货退款未查订单状态"→归"工具覆盖与执行"、枚举"关键工具未调用"、责任模块=退款 Skill/退款流程执行模块。
- 支持聚类：同根因/同场景/同工具/同知识点的失败自动聚成问题簇——报告不只列 100 条 badcase，而是产出"退款已发货场景中，Agent 23 次跳过订单状态校验，主要集中在 v1.8 Prompt"。

### 自动优化建议（第 8 章）
建议项不能停留在"优化 Prompt/加强训练/提升准确率"——要明确失败范围、证据、具体动作、owner、验收方式、优先级；产出结构化行动项，能被工单系统/看板/配置平台/研发流水线直接消费（"建议是质量工程里的标准任务对象"）。每个建议展开证据链。不同根因对应不同优化手段，可分四个等级。

### 全链路闭环（第 9 章）
- 完整评测平台九个能力模块；终点不是报告，而是把线上失败持续转化为可复用研发资产。
- 发布阶段离线门禁与线上灰度联动，跟踪三类信号：**离线质量信号**（核心场景通过率、P0 风险数、关键工具参数正确率）；**线上体验信号**（转人工率、重复追问率、投诉率、满意度变化）；**业务结果信号**（任务完成率、工单闭环率、退款/赔付成功率）。**离线提升但线上关键信号恶化 → 触发回滚或降级！**
- Trace 输出是被测 Agent 的标准能力而非事后补救：稳定记录工具名、入参、返回值、时间戳、耗时、错误；复杂 Agent 还记录计划、检索、Guardrail。评测执行环境隔离，避免多用例共享状态导致分数不可复现。
- **反馈生产**：一条 Badcase 至少生产 3 类反馈；平台可分三条生产线。**入库标准**：失败可复现（或至少有稳定 Trace+人工确认）；期望行为明确（可写成规则/Judge 标准/人工验收标准）；根因标签清楚（归到具体能力域或业务流程）；样本有代表性（覆盖一类问题而非一次性环境抖动）；已脱敏合规。
- 样本治理：同簇保留代表例；P0/P1 风险长期保留；稳定多版本通过且低风险者降级为抽样集；新分布出现时主动学习优先抽取低置信/高影响/新意图/新工具/新知识点样本进人工确认。
- 沉淀质量资产库：用例库、Trace 库、根因标签库、修复建议库、Judge 校准集、回归集。"质量资产越厚，Agent 迭代越不靠个人经验和临时救火。"

### 第 10 章
评测体系的成败取决于它能否在跨团队协作中长期、稳定地产生可执行行动项；低分必须稳定转成行动项，否则再精细的分数也只是报表。

## 四、腾讯技术工程：AI Agent & Skill 测评方案及落地实践

> 公式：Eval = Agent 输入 → 执行 → 捕获执行过程（Trace + 产物） → 一组检查规则 → 可对比的分数。
> 目标：可重复、可量化、可持续演进的评估闭环；每次变更都能快速跑出可比较的分数；用数据代替直觉，用全量代替抽查。

### 痛点表
主观性强（靠"感觉变好了"）；悄悄退化（改 prompt/升级依赖旧场景变差无人知晓）；人工验证成本高（Skill 越多模型越快，人肉回归指数增长，只能选择性验证留盲区）；模型不敢升级（无对比数据支撑切换决策）；缺少效率基线（变贵变慢无法归因版本）；过程易忽略（答案碰巧对但推理路径错，分不清"正确调用工具后回答"与"训练数据碰巧答对"）。

### 三类评委（选择优先级：确定性 > Rubric > 人工）
| 维度 | 确定性评分器 | Rubric 评分器 | 人工评分器 |
|---|---|---|---|
| 谁来评 | 脚本（Bash/Python/断言/Lint/AST） | 大模型（固定版本） | 领域专家 |
| 规则写在哪 | 代码里 | Prompt + JSON Schema | 人脑+标注指南 |
| 成本 | 毫秒级/免费 | 秒级/API 费用 | 分钟-小时级/人力 |
| 稳定性 | 100% | 有抖动（需降噪） | 取决于标注员水平 |
| 覆盖 | 已知硬指标 | 未知软指标 | 主观+边缘场景 |
| 典型用例 | 文件存在、构建/测试通过 | 代码风格、意图贴合、解释清晰度 | 校准 LLM、诊断 0%/100% 异常、红队 |
| 门禁角色 | 硬门禁 | 分级门禁（error 硬/warning 软） | 不进门禁，做采样审查 |

确定性评分器类型：工具调用检查（是否调用指定工具、参数是否正确）、产物检查（文件存在、内容符合预期）、关键词匹配、执行指标（调用次数/token 阈值）、基线对比（与基线快照逐项对比）。
Rubric 规则示例：observation_points（回答是否基于项目规范而非通用知识/推理是否清晰连贯/有无幻觉编造）；scoring：process_score 0-100、result_score 0-100、is_false_positive bool（结果对但过程错的虚假成功）。
人工评分六个必要场景：① 校准 LLM 评委（最核心；抽样 100–200 条对齐，**一致率 ≥85% 才可用**）② 主观任务打分 ③ 诊断通过率异常（0% 或 100% 通常是任务/评分器坏了，不是模型弱）④ 建 Ground Truth（新套件前 20–50 个参考解）⑤ Trace 采样审查（每周固定抽样读轨迹找隐藏失败模式）⑥ 高风险兜底（医疗/金融/安全 100% 人工复核）。
经验法则：能自动化的坚决不找专家；专家时间 60%+ 花在"校准 LLM 评委"与"诊断异常"。

### 五大评测维度
1. **功能正确性（P0，代码判）**：结果正确性（pass@1/pass^k）、任务完成度（子目标打点）、指令遵循（JSON Schema/正则/字段检查）、工具调用正确性（调用日志断言）。必须自动化全覆盖。
2. **过程质量（P1，Rubric+人工）**：推理合理性（1-5 分）、步骤最优性（实际步数 vs 参考解法）、信息完整性（要点覆盖率）、上下文利用率、自我纠错能力（Trace 分析）。最能体现"智能"，自动化最难，Rubric 主战场。
3. **效率与成本（P1，代码判）**：Token avg/p95、工具调用次数 avg/p95、延迟 p50/p95/p99、失败重试率、单次任务成本 ¥/task。"pass@1 高但 token 花 10 倍的方案生产上不可接受"，每个任务带成本画像。
4. **鲁棒性与安全（P0，代码+人工）**：一致性（pass^k，k=5/10）、异常恢复（故障注入）、抗对抗/抗注入（红队用例集）、幻觉率、越权风险（权限断言）、合规（PII 正则+人工抽查）、拒绝合理性（误拒%/漏拒%）。金融/医疗/企业数据 Agent 必须前置。
5. **体验与对齐（P2，Rubric+人工）**：语气风格、回复清晰度、主动澄清（模糊需求主动提问而非瞎猜）、同理心、可解释性、用户满意度（👍/👎、CSAT/NPS）。P2 但决定产品生死；早期 Rubric+人工抽样，成熟后 A/B+用户反馈闭环。
术语：pass^k = k 次每次都通过（稳定性）；pass@k = k 次至少 1 次通过（峰值能力）。P0 先落地 P2 按需补。

### 不同类型 Agent 测评侧重
知识库问答→准确性/幻觉检测/引用溯源（依赖 Rubric）；代码编写→产物正确性/可运行性（依赖确定性：编译/测试）；功能工具→过程合规性/工具调用正确性（过程对比基线）；问题定位→推理链路/根因准确性（过程+结果双重验证）。差异在"用什么评分器、检查什么"，流程不变。

### 用例集设计四场景
① 触发（该触发吗？正向：各种合法表述都触发；负向：相似但不相关 prompt 不误触发）→ ② 核心逻辑（过程对吗？工具调用序列/参数/顺序；负向：缺步骤/错工具/错参数）→ ③ 产物质量（产物好吗？准确/完整/格式；负向：缺失/格式错/幻觉）→ ④ 异常容错（出错扛得住？正向：优雅降级明确提示；负向：崩溃/死循环/静默失败/泄露）。
负向触发用例为什么必要："只测正例，Agent 可能学会什么都触发——过度触发比不触发更难发现。"
核心逻辑用例三步法：梳理分支流程图→每条分支至少 1 用例→补组合与边界（分支间组合/阈值边缘/跨分支冲突）。经验法则：核心逻辑用例量通常是其他三类之和的 2–3 倍；N 条分支至少 N 个正向+关键分支负向；分支过多先覆盖高频与易错。
异常容错子类：异常输入（不存在的 ID→告知不存在不编造；非法格式→提示错误；缺 ID→主动追问而非瞎猜）、边界条件（数据量极大不超时；数据为空告知无数据）、环境故障（mock_tool_failure→优雅降级不无限重试）。

### 评分规则（扣分制）
初始 100 分负分制，每处不符扣对应分至 0；**达标线 80 分**（推荐值，按 Agent 类型与业务风险调整）。维度：任务结果不符预期 -100；步骤遵循性每步 -10；步骤输出结果每步 -10；工具/知识库调用每项 -10；分析耗时基准 5 分钟每超 1 分钟 -10；一致性 N 次（建议 N=5）全达标取均值。每次评分输出 JSON 扣分明细+原因，渲染 HTML 报告归档。

### 用例基线机制
基线 = 单用例执行 1 次后经人工确认的预期过程与预期结果快照（"正确的执行应该长什么样"）。预期过程：CoT、工具调用序列（入参返回）、中间产物、完整 Trace；预期结果：最终响应、输出文件、输出报告。
流程：用例设计只定义 prompt 与检查规则 → 执行 1 次 → 人工审核过程与结果 → 不可接受则修后重跑 → OK 则该次快照成为基线。后续每次执行与基线对比：确定性评分器做程序化判定（调用序列一致/产物存在/token 超标）；Rubric 以基线为参考答案对比语义差异。过程对比（关键步骤缺失/顺序偏离→过程退化 vs 思维链合理性/步骤最优）、结果对比（关键内容缺失/产物不一致→结果退化 vs 结论准确性/表述完整性/建议质量）、效率对比（token/步骤数超基线比例，如 >50% →效率退化）。
基线更新时机：Agent/Skill 逻辑变更、模型版本升级、用例本身修改（prompt 或检查规则变了）→ 重新执行 1 次并人工确认。

### 执行与维护
触发时机：提示词变更（CI 自动，PR 合入前回归）、模型版本升级（手动，验证兼容性）、定期巡检（定时全量回归）。
**能力测评 vs 回归测评**：能力测评"Agent 能把什么做好"（起步 20–50%，目标山峰，主动拓展频繁迭代）；回归测评"原有能力是否还在"（接近 100%，防御漂移，只增不减 CI 每次运行）。通过率稳定 100% 后用例"毕业"进回归集。引用 Anthropic 推荐：确定性任务用例集整体通过率需 100%，非确定性任务 ≥95%。
Bad Case 处理：复现记录完整轨迹→分析根因定预期行为→修复→纳入用例集防回归→进能力集，稳定后毕业到回归集。

### 工程落地
Trace 前置依赖：结构化（JSONL/JSON）、内容完整（每步工具名/入参/返回/时间戳，理想含思维链与决策依据）、格式跨版本稳定。不支持时：有日志无结构→写解析器（成本高易碎）；仅最终输出→只能结果评测；可改造→推动增加 Trace 输出（推荐）。"设计阶段就把结构化 Trace 作为标准能力，而非事后补救"。
环境隔离：clone 仓库到临时目录；每用例前重置（git checkout . && git clean -fd）；产物统一归档。
稳定性评估：N 次执行，只要 1 次不通过即存在稳定性风险。容忍阈值按使用类型：**关键决策类（问题定位/故障诊断）0%（N/N 全过，任何一次失败都可能误判）；辅助分析类（性能分析/报告生成）≤10%；创意生成类（代码建议/文案）≤40%**。N=5 解读：全过=稳定；1/5 失败=存在幻觉，按类型判断；2/5=高幻觉率深入排查；5/5 失败=稳定失败，先查任务定义或基线。调试技巧：0% pass^N 通常说明任务定义有问题，不是能力不行。
测评报告：头部（用例总数/通过率/平均分/模型版本与费用/总 token/平均费用每 Trial）、用例列表（分组/均分/直方图）、单用例详情（基线耗时/token/费用/步骤数、prompt、多 Trial 聚合、逐 Trial 明细：分数/耗时/token/费用/步骤扣分/效率扣分/结果扣分）。

### TPerf 实战案例
TPerf AI 分析 Agent：功能工具类型，部署在 Knot 智能体平台，MCP 调用 TPerf-API 取性能数据+知识库检索，决策树判断资源瓶颈与压测有效性，输出结构化性能分析报告。测评侧重：操作步骤合规性+执行效率+输出报告质量。
评分（满分 100 扣分制）：确定性维度——操作步骤（**LCS 最长公共子序列**对齐基线与 Trial 步骤，归一化：时间戳占位/搜索工具忽略查询参数/写入只留路径/终端命令提取脚本名/连续读文件组内不校验顺序；不一致/多余/缺少/顺序错各扣 2，上限 -10）；效率（耗时基准 300s 每超 10% 扣 1；token 以基线为基准每超 10% 扣 1，上限 -10）。模型评分维度——关键判定（压测有效性/性能结果与基线不一致直接 -80）；章节内容（CPU/内存/网络/磁盘IO/业务指标/根因定位/优化建议/完整性/准确性每项 -5，上限 -80；调用 CodeBuddy CLI 逐项对比）。一致性标准：数值型整数精确/小数相对误差 ≤1%；结论型异常等级与关键发现一致；建议型核心排查方向一致即可。
稳定性 0 容忍说明：TPerf 虽属辅助分析类，但结论直接影响优化决策与发布判断，一次错误结论可能导致性能问题漏检上线 → 采用关键决策类标准（任一 Trial 不达标该用例 0 分）。
公式：trial_score = max(0, 100+各项扣分)；trial_pass = score ≥ 80；case_score = 全 pass 取均值，任一不达标为 0。
用例集：9 大场景分组 30+ 用例（CPU 瓶颈 6/网卡 5/磁盘 4/磁盘 IO 2/内存 1/TCP 队列 3/Nginx 1/配置问题 1/正常场景 5），每个用例对应真实 TPerf 压测记录（不可变，可复现）；支持 7 模型对比（每用例 × 每模型参数化测试）。用例不硬编码预期输出，通过基线会话标识（session_id+message_id）指向人工确认正确的分析记录，评测时从 Knot API 动态获取。
执行：Trial 并发+评分并行+三评分器并行；限流自动重试（≤5 次）；单用例约 3000s；全量 30+×7 模型约 3–5 小时；pytest 实现，TCase 平台管理用例。Trace 获取：Knot AG-UI 协议事件流（工具调用事件/文本消息事件/时间 token 消耗），事件流解析器构建调用步骤列表，参数简化处理。
关键设计：基线配置随代码仓库 Git 版本化；执行结果每次重新生成并归档；支持重新评分（评分逻辑调整后无需重新触发 Agent）。
